# Add Basics — Incrementally Build Your Environment

<Callout type="tip" title="What you'll learn">
In this tutorial, you'll learn how to use `evnx add` to:
- Add the variables of a service (PostgreSQL) and a framework (Django)
- Check a whole stack before adding it, with `--dry-run`
- Add your own variables, as arguments or at a prompt
- Run it again safely: names already there are skipped
</Callout>

## What is `add` and why use it?

`evnx init` sets a project up. `evnx add` brings in what the project needs next
(a database, a payment provider, a variable of your own) without retyping names
from someone's README. It writes the same section headings `init` does, into
`.env.example` (the template you commit) and `.env` (your values), and it never
writes a name twice.

---

## Step 1: start from a blank project

```console
$ evnx init --yes
✓ Created .env from template
✓ Created .gitignore with .env*, !.env.example, !.env.sample, !.env.template
✓ Created .env.example (no variables yet)
  ✓ created .evnx.toml with an empty [vars]: evnx add records new variables there
```

`init` also creates `.evnx.toml` (**v0.10.16+**), the project's variable contract. From
here on, every `add` records the variables it introduces under `[vars]` in that file,
and the commands that read it print `config    .evnx.toml` first.

## Step 2: add a service

Without `--yes`, `add` shows what it will write and asks first:

```console
$ evnx add service postgresql
  config    .evnx.toml

  Add Service  Adding variables for 'postgresql'

Preview:
6 variables
  • service ×6
  Categories: Database
Add these 6 variables to .env.example and .env? [Y/n] yes
  ✓ added 6 variable(s) to [vars] in .evnx.toml
✓ Added 6 variables for PostgreSQL
```

`.env.example` now has:

```env
# ── Database ──
# Full connection string (overrides individual DB_* vars)
DATABASE_URL=postgresql://user:password@localhost:5432/dbname
DB_HOST=localhost
# (required)
DB_NAME=your_db_name_value
# Database password (use strong value in production)
DB_PASSWORD=your_db_password_value
DB_PORT=5432
# (required)
DB_USER=your_db_user_value

# Added by evnx add on 2026-10-25 07:30
```

`.env` gets the same names. Replace the placeholders there with your values;
leave `.env.example` as the template your team shares.

<Callout type="tip" title="Which ids are there?">
`evnx add --list` prints every id: services, infrastructure, frameworks and
blueprints. Aliases work too: `evnx add service postgres`. In a terminal you
can also leave the id out (`evnx add service`) and pick from a list.
</Callout>

## Step 3: add a framework

`--language` is optional: framework ids are unique.

```console
$ evnx add framework django --yes
  config    .evnx.toml
  ✓ added 4 variable(s) to [vars] in .evnx.toml
! 1 variable with a different value in .env.example: kept as it is
  • DATABASE_URL (existing: "postgresql://user:password@localhost:5432/dbname", new: "sqlite:///db.sqlite3")
✓ Added 4 variables for Django, skipped 1 already present
```

Django also declares `DATABASE_URL`, defaulting to SQLite, Django's own
out-of-the-box database. `add` kept the PostgreSQL line you already had, said
so, and added the other four.

## Step 4: check a whole stack before adding it

`--dry-run` shows what would happen and writes nothing:

```console
$ evnx add blueprint django_enterprise --dry-run
  config    .evnx.toml
Dry run (from blueprint 'Django Secure (Django + Postgres + Celery)'): nothing was written.
  .env.example: would add 15 variables: AWS_ACCESS_KEY_ID, AWS_REGION, AWS_SECRET_ACCESS_KEY, RABBITMQ_DEFAULT_PASS, RABBITMQ_DEFAULT_USER, RABBITMQ_URL, REDIS_DB, REDIS_HOST, REDIS_PASSWORD, REDIS_PORT, REDIS_URL, SENTRY_AUTH_TOKEN, SENTRY_DSN, SENTRY_ORG, SENTRY_PROJECT
  already there, would skip: ALLOWED_HOSTS, DATABASE_URL, DB_HOST, DB_NAME, DB_PASSWORD, DB_PORT, DB_USER, DEBUG, DJANGO_SETTINGS_MODULE, SECRET_KEY
  .env: would add 15 variables: AWS_ACCESS_KEY_ID, AWS_REGION, AWS_SECRET_ACCESS_KEY, RABBITMQ_DEFAULT_PASS, RABBITMQ_DEFAULT_USER, RABBITMQ_URL, REDIS_DB, REDIS_HOST, REDIS_PASSWORD, REDIS_PORT, REDIS_URL, SENTRY_AUTH_TOKEN, SENTRY_DSN, SENTRY_ORG, SENTRY_PROJECT
```

The blueprint includes PostgreSQL, so its `DATABASE_URL` is the PostgreSQL URL
you already have, and it is simply skipped. Run it again without `--dry-run`
(and with `--yes`, or answer the question) to add the rest.

## Step 5: add your own variables

As arguments, one or several at once:

```bash
evnx add custom API_URL=https://api.example.com DEBUG=false --yes
```

```console
  config    .evnx.toml
  ✓ added 1 variable(s) to [vars] in .evnx.toml
! 1 variable with a different value in .env.example: kept as it is
  • DEBUG (existing: "True", new: "true")
✓ Added 1 custom variable, skipped 1 already present
```

Django already declared `DEBUG=True` in step 3, so `add` keeps it and says so, as it
did for `DATABASE_URL`. A name you add is never allowed to change one that is there.

Or at the prompt: a name, a value, and `More options?` for a description, a
category and whether it is required. An empty name finishes.

```text
Variable name (or Enter to finish): STRIPE_WEBHOOK_SECRET
Value for STRIPE_WEBHOOK_SECRET (hidden; .env only; Enter for YOUR_KEY_HERE): [hidden]
More options? (description, category, required) yes
Description (Enter for none): Stripe webhook signing secret
Category: Application
Is this variable required? yes
Variable name (or Enter to finish):

Preview:
  • 1 variable to add
Append these variables to .env.example and .env? yes
  ✓ added 1 variable(s) to [vars] in .evnx.toml
✓ Added 1 custom variable
```

```env
# ── Custom Variables ──

# [Application] Stripe webhook signing secret (required)
STRIPE_WEBHOOK_SECRET=YOUR_KEY_HERE
```

That is `.env.example`, the file you commit. The value you typed (`whsec_test_123`
here, not shown on screen because the name looks like a secret, **v0.10.4+**) went
into `.env` only (**v0.10.3+**; it used to go into both).

<Callout type="warning" title="Real secrets">
A value typed as an argument lands in your shell history. For a real secret,
give the name alone (`evnx add custom STRIPE_WEBHOOK_SECRET`): in a terminal,
`add` asks for the value without echoing it. Or keep the placeholder and fill
in `.env`.
</Callout>

## Step 6: run it again

```console
$ evnx add service postgresql --yes
  config    .evnx.toml
· Nothing to add: 6 variables for PostgreSQL already in .env.example
```

Nothing is written twice, and a value you set in `.env` is never replaced.

## In scripts and CI

`add` asks only when there is a terminal and no `--yes`. In CI there is no
terminal, so give `--yes`, or `--dry-run` to check first. `--json` prints the
result as one document for a script to read. Without either, `add` stops with
exit code 2 and prints the command to run:

```console
$ evnx add service twilio
Error: there is no terminal to confirm with.

Add --yes to write without asking:
  evnx add service twilio --yes

No verdict: evnx did not finish. This is not a clean result.
```

---

## Common pitfalls to avoid

### Real values in `.env.example`

`.env.example` is committed. Keep placeholders there; real values go in `.env`,
which `init` and `add` keep out of git (`add` warns if it could be committed:
`.env is not covered by .gitignore`).

### Expecting `add` to change a value

`add` adds names. It never changes a value that is already there, in either
file. To change one, edit the file.
