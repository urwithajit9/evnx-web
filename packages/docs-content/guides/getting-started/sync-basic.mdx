## What is sync and why use it?

When working on a project with a team, everyone needs the same environment variables, but not the same values.

- **`.env`**: your local file with real credentials (never commit this!)
- **`.env.example`**: the team template with placeholder values (commit this!)

`evnx sync` keeps the two consistent by variable **name**. It only adds: it never removes a
variable or changes a value already there.

<Callout type="danger" title="Security first">
Never commit `.env` to version control. Use placeholders in `.env.example`; sync writes
them for you.
</Callout>

## Forward vs reverse sync

### Forward sync (`.env` → `.env.example`)

**Use when:** you added a new variable to your local `.env` and want to share it with the team.

```bash
# You added NEW_API_KEY and FEATURE_BETA to .env
evnx sync
```

At a terminal, sync asks how to add them:

```text
┌─ Variables to Add ───────────────────────────────────────────────────────────┐
│ Found 2 variables in .env missing from .env.example:                         │
│   • NEW_API_KEY                                                              │
│   • FEATURE_BETA                                                             │
└──────────────────────────────────────────────────────────────────────────────┘

Add these to .env.example?:
> Yes, add with placeholder values (recommended)
  Yes, add with actual values ! SECURITY RISK
  Let me choose individually
  No, skip
```

Press Enter for placeholders, and answer `n` to the optional comment:

```text
✓ Updated .env.example (+2 variables)
```

**Result:**

```text
APP_NAME=YOUR_VALUE_HERE

# Synced from .env
NEW_API_KEY=YOUR_KEY_HERE
FEATURE_BETA=YOUR_VALUE_HERE
```

### Reverse sync (`.env.example` → `.env`)

**Use when:** your team added variables to `.env.example` and you need them locally.

```bash
# The team added FEATURE_FLAG and ANALYTICS_KEY to .env.example
evnx sync --direction reverse
```

```text
Add to .env?:
> Yes, with the template's values (placeholders where it has none)
  Yes, prompt me for real values
  Let me choose individually
  No, skip
```

The first answer copies the template's values. The second asks for each one, with the
template's value as the default:

```text
Add to .env?: Yes, prompt me for real values
Value for FEATURE_FLAG [true]: false
Value for ANALYTICS_KEY [YOUR_KEY_HERE]: ak_live_123
✓ Added 2 variables to .env
```

**Result:**

```text
APP_NAME=shop

# Added by evnx sync
FEATURE_FLAG=false
ANALYTICS_KEY=ak_live_123
```

<Callout type="tip" title="Quick decision guide">
- Added variables to your `.env`? → `evnx sync` (forward)
- Pulled team changes? → `evnx sync --direction reverse`
- Not sure? → `evnx sync --check` tells you which side is behind; `evnx sync --dry-run` shows what forward sync would write
</Callout>

## Your first sync: step by step

### You have a .env and no template yet

```bash
evnx sync
```

```text
· .env.example not found, creating from .env
Create .env.example with:
> Placeholder values (recommended — safe to commit)
  Actual values copied from .env  ! SECURITY RISK
```

Press Enter:

```text
✓ Created .env.example

Next steps:
  1. Review .env.example to ensure the placeholders are appropriate
  2. Commit .env.example to Git (never commit .env)
```

The template keeps your variable names and replaces every value:

```text
# Generated from .env
# Replace all placeholder values with real credentials

APP_NAME=YOUR_VALUE_HERE
DATABASE_URL=postgres://user:password@localhost:5432/dbname
STRIPE_SECRET_KEY=YOUR_KEY_HERE
DEBUG=false
```

A database URL keeps its scheme, with `user:password@localhost` in place of the real
credentials and host, and a `DEBUG` switch keeps its value. The
[placeholder rules](/guides/commands/sync#placeholder-rules) list them all. Commit
`.env.example`:

```bash
git add .env.example
git commit -m "Add .env.example"
```

### A teammate builds their .env from the template

**Step 1: create .env**

```bash
evnx sync --direction reverse
```

```text
· .env not found, creating from .env.example
✓ Created .env
! Replace placeholder values with real credentials!
```

The new `.env` holds the template's values and is readable by you only (`0600`).

**Step 2: see what still needs a real value**

```bash
evnx validate
```

```text
  ✗  APP_NAME looks like a placeholder
     .env

  ✗  STRIPE_SECRET_KEY looks like a placeholder
     .env
     →  Get from Stripe Dashboard

  2 errors
```

**Step 3: edit .env with real values**

```bash
nano .env
```

**Step 4: validate again**

```bash
evnx validate
```

```text
✓ All required variables present
✓ All checks passed
```

✅ **You're done!** Your project is ready.

<Callout type="info" title="Adding a brand-new variable">
`evnx add custom` asks for a name and a value and writes both files at once: the value
to `.env`, a placeholder to `.env.example`. Sync is for bringing two files that already
exist back into step.
</Callout>

## Preview before applying changes

Use `--dry-run` to see what would change:

```bash
evnx sync --dry-run
```

```text
Preview:
Target: .env.example (action: Add)

  · NEW_API_KEY = YOUR_KEY_HERE
  · FEATURE_BETA = YOUR_VALUE_HERE

(dry-run: no files were modified)
```

`·` marks a placeholder sync generated. In a reverse preview, `!` marks a value copied
as it is from the template.

To ask "are the files in step?" use `--check`, which exits `1` when they are not:

```bash
evnx sync --check
```

<Callout type="tip" title="Make --dry-run a habit">
Run `--dry-run` before a sync until you're comfortable with the output. It never writes
and never asks.
</Callout>

## Common pitfalls to avoid

### Adding actual values to .env.example

When sync offers "actual values", choose placeholders unless the values are harmless
configuration such as `LOG_LEVEL`. Even then evnx keeps credentials out: each one is
written as a placeholder and named in a warning.

### Forgetting to commit .env.example

```bash
# After a forward sync:
git add .env.example
git commit -m "Add NEW_VAR to template"
```

### Committing .env by accident

```bash
# Check .gitignore first:
cat .gitignore | grep "^\.env$"
# Should output: .env

# If not, add it:
echo ".env" >> .gitignore
```

### Ignoring permission warnings

If other users can read your `.env`, sync says so:

```text
! .env is readable by other users (mode 644)
     →  chmod 600 .env
```

Fix it:

```bash
chmod 600 .env
```
