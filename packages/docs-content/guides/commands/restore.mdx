`evnx restore` decrypts a backup made by [`evnx backup`](/guides/commands/backup) and
writes the `.env` back. It shows what is in a backup without writing anything, never
replaces a file without a yes, keeps the file it replaces, and refuses to write a
file that evnx itself could not read.

<Prerequisites>
  <Prerequisite href="/guides/getting-started/installation">Install evnx</Prerequisite>
  <Prerequisite href="/guides/commands/backup">Create a backup first</Prerequisite>
</Prerequisites>

<Callout type="warning">
**Changed in 0.10.11 — check your scripts.**

- **`--yes` (alias `--force`, `-y`)** replaces an existing output without asking.
  Without it and with no terminal, the run stops with exit `2` and a line naming
  `--yes` and `--output` — it failed with `IO error: not a terminal`. The replaced
  file is kept as `<output>.bak` either way.
- An output that already holds exactly the backup's content is left alone: no
  question, no write, exit `0`.
- **`cloud://` is gone.** `restore cloud://…` exited `6`, "not yet available"; it is
  now a missing file, exit `3`, pointing at `evnx cloud pull`. Exit `6` is retired.
- A backup that will not open says why — truncated, not a backup, made by a newer
  evnx. All of them read "Wrong password or corrupt backup" before.
- `--output` may not be the backup file itself.
- A key file is reported as an info line, like `backup`'s, not a warning.
- The restored file gets the `.gitignore` check `template` has.
</Callout>

## Command signature

```bash
evnx restore <BACKUP> [OPTIONS]
```

| Argument / flag | Default | Description |
|-----------------|---------|-------------|
| `<BACKUP>` | required | The backup file to decrypt, as written by `evnx backup`. A file on disk; for a vault, use [`evnx cloud pull`](/guides/commands/cloud) |
| `--output <PATH>` | `.env` | Where to write the restored file. Not the backup itself |
| `-y`, `--yes` | off | Replace an existing `--output` without asking; the old file is kept as `<output>.bak`. Also accepted as `--force` |
| `--inspect` | off | Show the variable names in the backup — never values — and write nothing |
| `--dry-run` | off | Decrypt and check the content, and write nothing |
| `--password-file <PATH>` | — | Read the passphrase from a file. Also accepted as `--key-file`, the spelling `backup` uses |
| `--gitignore` | off | Add the restored file to `.gitignore` without asking |
| `--no-gitignore` | off | Skip the `.gitignore` check |
| `-v`, `--verbose` | off | Print each step to stderr |
| `-q`, `--quiet` | off | Print nothing on success; warnings and errors still print |

`EVNX_PASSWORD` is read when there is no `--password-file` — see
[The passphrase](#the-passphrase).

## Basic usage

### Restore to `.env`

```bash
evnx restore .env.backup --password-file backup.key
```

```text
  evnx restore  Decrypt and restore from an encrypted backup

✓ Read backup from .env.backup
· Using key file for decryption (non-interactive mode)

Backup information:
  Schema version: v1
  Original file : .env
  Created at    : 2026-10-20T12:14:39Z
  Tool version  : evnx v0.10.11
  Variables     : 5
✓ Decryption successful
  ✓ Decryption key cleared from memory

✓ Restored 5 variable(s) to .env

Next steps:
  1. Run: evnx validate --env .env
  2. Verify your application starts correctly
  3. Delete the backup file once you have confirmed the restore
  Docs: https://docs.evnx.dev/cli/commands/restore
```

Without `--password-file` (and without `EVNX_PASSWORD`) evnx asks once, with no
confirmation: a mistyped passphrase only fails to decrypt.

### Restore somewhere else

```bash
evnx restore .env.backup --output .env.staging
```

A new file is created `0600`.

## Replacing an existing file

An existing output is never replaced silently.

**Already the same.** If the file holds exactly what the backup holds, there is
nothing to do:

```text
✓ Decryption successful
  ✓ Decryption key cleared from memory
✓ .env is already up to date — nothing was written
```

**Different, with a terminal.** evnx asks; Enter means no:

```text
! Output file already exists: .env
Overwrite .env? (the current file is kept as a .bak copy) [y/N] yes
· Kept the previous .env as .env.bak

✓ Restored 5 variable(s) to .env
```

Answering no (or Enter) exits `4` and changes nothing.

**Different, in a script.** With no terminal to ask on, the run stops:

```text
! Output file already exists: .env
Error: there is no terminal to confirm with.

Add --yes to replace it (the current file is kept as a .bak copy), or restore somewhere else with --output <path>:
  evnx restore .env.backup --yes

No verdict: evnx did not finish. This is not a clean result.
```

`--yes` replaces it:

```bash
evnx restore .env.backup --password-file backup.key --yes
```

```text
· Kept the previous .env as .env.bak

✓ Restored 5 variable(s) to .env
```

**The kept copy.** Whichever way the yes came, the file being replaced is copied to
`<output>.bak` first, with its mode. An earlier copy is never overwritten: the next
one is `.env.bak.2`, then `.env.bak.3`. `.bak` files are not offered as environments
by `--env-name`.

The file is replaced atomically — written beside it, then renamed — so an
interrupted restore leaves the old file or the new one, never half of either. A
symlink at `--output` is written through: the link stays, its target is replaced.

**Not over the backup.** Restoring a backup onto itself would replace the only copy
of the ciphertext with the plaintext, so it is refused, even with `--yes`:

```bash
evnx restore .env.backup --password-file backup.key --output .env.backup --yes
```

```text
Error: --output '.env.backup' is the same file as the backup '.env.backup'. Nothing was written; choose another --output.
```

## Inspect and dry run

`--inspect` lists the variable **names** — values are never shown — and writes
nothing:

```bash
evnx restore .env.backup --password-file backup.key --inspect
```

```text
Backup information:
  Schema version: v1
  Original file : .env
  Created at    : 2026-10-20T12:14:39Z
  Tool version  : evnx v0.10.11
  Variables     : 5

Variables in this backup (names only — values never shown):
  DATABASE_URL
  REDIS_URL
  API_KEY
  SECRET_KEY
  PORT

✓ 5 variable(s) found
  To restore: evnx restore <backup-file>
```

`--dry-run` decrypts and checks that the content is a `.env` evnx can read:

```bash
evnx restore .env.backup --password-file backup.key --dry-run
```

```text
✓ Decrypted content appears to be a valid .env file

✓ Dry-run complete — no files were written
```

| | `--inspect` | `--dry-run` |
|---|---|---|
| Decrypts the backup | ✓ | ✓ |
| Shows metadata | ✓ | ✓ |
| Shows key names | ✓ | ✗ |
| Checks the `.env` format | ✗ | ✓ |
| Writes files, asks to overwrite | ✗ | ✗ |

Neither writes, so neither cares where `--output` points. Given both, `--inspect`
runs.

## Content that is not a `.env`

The decrypted content is checked with the parser every evnx command reads `.env`
files with. `export KEY=value` lines and multi-line quoted values (PEM keys, JSON)
pass. Content the parser cannot read — prose, or a key such as `my-key`, which it
rejects — is written to **`<output>.restored`** instead, so it cannot replace a
working file, and the run exits `5`:

```text
! Decrypted content does not look like a valid .env file.
  Writing to notes.env.restored instead of notes.env to protect your current file.
  Inspect the file manually, then rename it if the content looks correct:
    mv notes.env.restored notes.env
! Wrote the backup's content to notes.env.restored, not to notes.env

Next steps:
  1. Inspect the restored file:  cat notes.env.restored
  2. If the content is correct:  mv notes.env.restored notes.env
  3. Validate the result:        evnx validate --env notes.env
```

<Callout type="info">
  Until 0.10.3 the check was a heuristic — 80% of lines had to look like
  assignments — and it sent valid files with `export` lines or long PEM keys to
  `.restored`. Until 0.10.11 the fallback also printed "✓ Restored 0 variable(s)"
  beside exit `5`.
</Callout>

## The passphrase

The same rule as [`backup`](/guides/commands/backup#the-passphrase), highest priority
first:

1. **`--password-file <path>`** (or `--key-file`) — UTF-8 content trimmed of
   surrounding whitespace, binary content Base64-encoded; the reader `backup` uses,
   so one file opens what it locked.
2. **`EVNX_PASSWORD`** — read once, then removed from evnx's environment, with a
   warning: it may already be in a shell history, a process listing or a CI log.
3. **A prompt**, when there is a terminal.

There is **no length floor** for restore: the 8-character minimum applies to new
backups only, so a backup made earlier with a shorter passphrase still opens.

Both a file and `EVNX_PASSWORD` set: the file wins, and a warning says so:

```text
· Using key file for decryption (non-interactive mode)
! EVNX_PASSWORD is set as well; the key file wins, so EVNX_PASSWORD was not used
```

With no file, no variable and no terminal, the error names both, as for `backup`.

## When a backup will not open

Every case is exit `2`. Where the cause is known, the message says it:

| Message | Cause |
|---------|-------|
| `Wrong password or corrupt backup — decryption failed` | The passphrase is wrong, or the file was changed. These stay **one** message on purpose: telling them apart would say which part of the authentication failed |
| `The backup file is truncated or damaged (75 bytes after decoding; an evnx backup is at least 161)` | The file was cut off — an interrupted copy or upload |
| `This file is not an evnx backup: it is not the Base64 text evnx backup writes` | Another file was given |
| `This backup uses format version 2, made by a newer evnx; this version reads format 1. Upgrade evnx to restore it.` | Upgrade evnx |

A missing file is exit `3`:

```text
Error: Backup file not found: nope.backup
```

### `cloud://`

`restore` reads files. A vault in evnx cloud is restored with the cloud commands:

```bash
evnx restore cloud://my-app --password-file backup.key
```

```text
Error: Backup file not found: cloud://my-app

  restore reads a file made by `evnx backup`; it does not read from evnx cloud.
  For a vault, use:  evnx cloud pull --vault <name>
```

`evnx cloud pull --version N` brings back one version; `evnx cloud export` writes
every version to a folder.

## Keeping the restored file out of git

The restored file holds plaintext secrets. In a git repository, evnx asks git
whether it is ignored — the same step `template` and `convert -o` take:

- ignored already: nothing to do;
- not ignored, with a terminal: evnx asks to add it to `.gitignore`;
- not ignored, no terminal: a warning, nothing changed.

```text
✓ Restored 5 variable(s) to prod.env
! 'prod.env' may contain secrets and is not in .gitignore
```

`--gitignore` adds it without asking; `--no-gitignore` skips the check:

```text
✓ Restored 5 variable(s) to prod2.env
✓ Added 'prod2.env' to .gitignore
```

## Automation and CI

```yaml
- name: Check the backup still opens
  run: evnx restore backups/latest.backup --dry-run
  env:
    EVNX_PASSWORD: ${{ secrets.BACKUP_PASSPHRASE }}

- name: Restore .env
  run: evnx restore backups/latest.backup --output .env --yes --no-gitignore
  env:
    EVNX_PASSWORD: ${{ secrets.BACKUP_PASSPHRASE }}
```

### Branch on the exit code

```bash
#!/bin/bash
evnx restore .env.backup --password-file /run/secrets/evnx-pass --yes
code=$?

case $code in
  0) echo "✓ Restored, or already up to date" ;;
  2) echo "✗ Did not run: wrong password, unreadable backup, or an output problem" ; exit 1 ;;
  3) echo "✗ Backup file not found" ; exit 1 ;;
  4) echo "✗ Cancelled at the overwrite question" ; exit 1 ;;
  5) echo "⚠ Content is not a .env: written to .env.restored — inspect it" ; exit 1 ;;
  *) echo "✗ Unexpected exit $code" ; exit 1 ;;
esac
```

### Test your backups regularly

A backup you cannot restore is not a backup. `--dry-run` prints its report even
under `-q` — it is what was asked for — so send it away and keep the exit code:

```bash
for backup in backups/*.backup; do
  if evnx restore "$backup" --dry-run --password-file /run/secrets/evnx-pass >/dev/null 2>&1; then
    echo "✓ $backup"
  else
    echo "✗ $backup (exit $?)"
  fi
done
```

### Change a backup's passphrase

There is no re-key command. Restore to a private file, back up again under the new
passphrase, and remove the plaintext:

```bash
evnx restore old.backup --password-file /run/secrets/old-pass --output /tmp/plain.env
evnx backup /tmp/plain.env --key-file /run/secrets/new-pass --output new.backup --verify
rm /tmp/plain.env
```

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Restored, inspected, checked (`--dry-run`), or already up to date |
| `2` | Could not run: wrong password, unreadable backup, an output problem, no terminal to ask on |
| `3` | Backup file not found (including a `cloud://…` argument) |
| `4` | Cancelled at the overwrite question |
| `5` | Not a `.env` evnx can read: written to `<output>.restored` instead |

<Callout type="info">
  `restore` never exits `1`. ⚠️ Until 0.10.11 this table listed `1` as "generic
  error" (those cases are `2`, with the "No verdict" line) and `6` as "evnx-cloud
  restore not yet available", which is retired with `cloud://`.
</Callout>

## Security notes

- **File permissions.** A new restored file is `0600`. An existing one keeps its
  mode, with a warning when others can read it.
- **Metadata is encrypted.** The original file name, the date and the evnx version
  are inside the ciphertext: without the passphrase nobody can tell which
  environment a backup holds, or when it was made.
- **Memory.** The passphrase, the ciphertext and the decrypted content are zeroized
  after use, on every exit path — cancel and "already up to date" included.

| Passphrase source | Risk | Notes |
|-------------------|------|-------|
| Prompt | lowest | Never stored; not in logs or process listings |
| `--password-file` | medium | Keep it on `tmpfs` or a secrets volume, never beside the backup |
| `EVNX_PASSWORD` | medium-high | May appear in CI logs; removed from evnx's environment after reading |
