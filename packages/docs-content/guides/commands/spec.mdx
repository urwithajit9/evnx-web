`.env.example` is doing three jobs badly. It is the documentation, the contract
and the validation source all at once, and it cannot say any of the things a
contract needs to say: that a variable is **optional**, that it must be a
**URL**, that it is a **secret**, that it only applies in **production**.

A spec can.

  <Prerequisite href="/guides/getting-started/installation">Install evnx</Prerequisite>

</Prerequisites>

evnx spec init --with django,postgresql,stripe
evnx spec check
</CommandSignature>

## The contract

It lives in `[vars]` in `.evnx.toml` — the file your project already has for
per-project policy — rather than in a second file of its own:

```toml
[vars.DATABASE_URL]
required     = true
format       = "url"
secret       = true
description  = "Primary Postgres connection string"

[vars.FEATURE_NEW_CHECKOUT]
required = false
format   = "bool"

[vars.SENTRY_DSN]
environments = ["production"]
secret       = true
```

| Field | Type | Meaning |
|---|---|---|
| `required` | `bool` | Must be present. **Defaults to `true`** — see below |
| `format` | `string` | `url`, `int`, `port`, `bool`, `email`, or `regex:<pattern>` |
| `secret` | `bool` | Declares the value sensitive. Unstated is not the same as `false` |
| `description` | `string` | Shown in `validate`'s suggestion when the variable is missing |
| `environments` | `list` | The variable applies **only** in these |

<Callout type="warning" title="v0.11.0: a regex is written `regex:`">
`format = "^sk_"` used to be compiled as a regular expression, so a misspelt name
(`format = "urll"`) became a pattern that failed every value. Since 0.11.0 a regex is
written `format = "regex:^sk_"`, and any other value must be one of the five names.
An unknown name stops every command that reads the config, with a suggestion:

```text
2 | format = "urll"
  |          ^^^^^^
`urll` is not a format — did you mean `url`?
Formats: url, int, port, bool, email. A regular expression is written `regex:urll` (bare patterns were read as regexes before 0.11.0).
```

**Migrate:** prefix bare patterns, `format = "^sk_"` → `format = "regex:^sk_"`.
</Callout>

`format = "bool"` accepts `true`, `yes`, `on`, `1`, `y` and `false`, `no`, `off`,
`0`, `n`, in any case (**v0.10.6+**; `on`, `off`, `y` and `n` used to fail) — the
same words as `evnx template`'s `|bool`.

<Callout type="info" title="Why `required` defaults to true">
Because that is what `.env.example` already means. `evnx validate` treats every
line in the template as required, so a project writing its first spec keeps the
behaviour it had and relaxes it per variable with `required = false`. Nothing
changes underneath you on the day you adopt a spec.
</Callout>

<Callout type="info" title="Why unstated `secret` is not `secret = false`">
Three states, not two. **Unstated** means "nothing declared, fall back to
`evnx scan`'s heuristics". **`secret = false`** means "I have looked, and this is
not sensitive" — which tells the scanner to stop flagging it. Collapsing the two
would turn every undeclared variable into an assertion nobody made.
</Callout>

### A key evnx does not know is named

**v0.10.6+** — a misspelt key used to be ignored silently: `requird = false` left the
variable required. Every command now warns, with the key you probably meant, and
`evnx validate` counts it as an error, so it exits `1`:

```text
! …/.evnx.toml: unknown key `vars.EXTRA.requird` (ignored) — did you mean `required`?
...
  ✗  Unknown key `requird` in [vars.EXTRA] — evnx ignores it
     .evnx.toml
     →  Did you mean `required`?
```

In `validate --format json` the issue's type is `unknown_spec_key`.

## Generating the first one

Nothing needs writing by hand. Your project already states most of its contract:
`.env.example` says which names are expected, `.env` shows what the values look
like, and evnx's component catalogue knows what a recognised variable is for.

```bash
evnx spec init
```

```text
  evnx spec  Generate the variable contract

✓ wrote 6 variable(s) to .evnx.toml

Next steps:
  1. Read the generated entries — every field is a guess from your files
  2. Mark optional variables with `required = false`
  3. Commit .evnx.toml; the spec is the contract
```

From a `.env.example` listing five names, and a `.env` holding a Postgres URL with a
password, a Stripe key, a port, a retry count and one extra name:

```toml
# ── Variable contract ───────────────────────────────────────────────
# Generated by `evnx spec init`. Every field below is inferred from this
# project's files — review it, then commit it.

[vars.APP_NAME]
required = true

[vars.DATABASE_URL]
required = true
format = "url"
secret = true

[vars.STRIPE_SECRET_KEY]
required = true
secret = true

[vars.PORT]
required = true
format = "port"

[vars.MAX_RETRIES]
required = true
format = "int"

[vars.DEBUG_TOOLBAR]
# only in .env
required = false
format = "bool"
```

- **Entries follow `.env.example`'s order** (**v0.10.6+**; they were alphabetical).
- **A name only in `.env`** follows them as `required = false`, marked
  `# only in .env` (**v0.10.6+**; it was dropped without a word).
- **A URL with a password is a secret** (**v0.10.6+**), as `DATABASE_URL` is here.
- **A name that looks secret** (`*_SECRET_KEY`, `*_PWD`, …) is declared secret by the
  same rule `evnx validate` uses (**v0.10.6+**: `*_PWD` now is; `SENTRY_DSN`, `*_PRIVATE`
  and a bare `TOKEN` no longer are).

<Callout type="warning">
**Read what it wrote.** Every field is inferred. A variable marked required that is
genuinely optional will block a build.

A `format` is written only when the sample value passes it (**v0.10.6+**), so the
contract passes the project it came from. Each one left out is named on stderr,
without the value:

```text
! PORT: left out `format = "port"` — the sample value is not a port between 1 and 65535
! DEBUG: left out `format = "bool"` — the sample value is not a boolean
```

An empty template value or a placeholder like `YOUR_KEY_HERE` produces no `format`
either. It is still a draft, not an answer.
</Callout>

### Which file it writes

The project's one `.evnx.toml` (**v0.10.6+**): the config in force — found at or
above the current folder — or, with none, a new one at the git root. From a
subfolder, the success line names it as you would type it:

```text
✓ wrote 3 variable(s) to ../.evnx.toml
```

It used to read `../.evnx.toml` and then write a new `./.evnx.toml` that shadowed
it. A symlinked `.evnx.toml` is written through to its target, which stays a link,
with a `· wrote through` notice.

### Sample values from another environment

```bash
evnx spec init --env-name staging
```

reads `.env.staging` instead of `.env` (**v0.10.6+**), and `[defaults] env_name` and
`[defaults] example` in `.evnx.toml` apply, as they do for `validate` and `sync`. A
file named by `--env`, `--example` or `[defaults] example` must exist; the default
`.env` and `.env.example` may be absent.

### From the catalogue instead

```bash
evnx spec init --with django,postgresql,stripe
```

This is the higher-quality source: `required` and `description` are **known**
rather than guessed, and each entry records which component it came from.

```toml
[vars.STRIPE_SECRET_KEY]
# from Stripe
description = "Secret key (server-side only)"
required = false
secret = true
```

Run `evnx init --list-components` for the ids. An unknown one is refused with a
suggestion:

```text
Error: unknown component 'djangoo'

Did you mean: django

Run `evnx init --list-components` for the full list.
```

`--with` reads no project file, so it cannot be combined with `--env`, `--example`
or `--env-name`, and `--with ""` — nothing to write — is exit `2` (**v0.10.6+**;
both were accepted and ignored).

## Options

| Flag | Type | Default | Description |
|---|---|---|---|
| `--with` | `list` | — | Build from named components instead of the project's files |
| `--env` | `path` | `.env` | Where to read sample values from, for inferring formats. Must exist when named |
| `--env-name` | `string` | — | **v0.10.6+** — read `.env.<NAME>` instead of `.env` |
| `--example` | `path` | `.env.example` | Which template decides membership and `required`. Must exist when named |
| `--stdout` | `bool` | `false` | Print the block instead of writing it. Only TOML goes to stdout; notes go to stderr |
| `--merge` | `bool` | `false` | Add only the variables `[vars]` does not declare yet (**v0.10.3+**) |
| `--verbose`, `-v` | `bool` | `false` | Verbose output |
| `--quiet`, `-q` | `bool` | `false` | Print nothing on success |

### It appends, and refuses rather than corrupting

`spec init` adds its block to the end of `.evnx.toml`, leaving every other
section — and every comment — byte for byte intact.

A second plain run would write `[vars]` twice, which TOML refuses to read back.
So it stops:

```text
Error: .evnx.toml already has a [vars] section.
  Pass --merge to add only the variables it does not declare yet;
  existing entries are kept as they are.
```

`--merge` (**v0.10.3+**) appends only the names that are not declared yet, under
an `# Added by evnx spec init --merge` comment:

```text
✓ added 1 variable(s) to .evnx.toml; 6 already declared, kept as they are
```

Entries you have edited stay exactly as you wrote them, and the rest of the file
is untouched byte for byte. When every name is already declared it says
`.evnx.toml unchanged` and exits `0`. Nothing is written that would not parse: if
`[vars]` is an inline `vars = { … }` table, which cannot be extended, the file is
left alone and the error says so.

<Callout type="warning" title="`--force` was removed in v0.10.3">
It appended a second `[vars]` block "to be merged by hand", and until someone
did, every command that reads the config exited 2. It now exits 2 with a pointer
to `--merge`.
</Callout>

To regenerate cleanly, delete the existing `[vars]` entries first, or use
`--stdout` and diff:

```bash
evnx spec init --stdout > /tmp/spec.toml && diff <(grep -A99 '^\[vars' .evnx.toml) /tmp/spec.toml
```

## What `validate` does with it

This is the point of the whole thing. With a spec, `evnx validate` stops
counting lines in `.env.example` and starts checking the contract.

```bash
evnx validate                          # the local .env
evnx validate --env-name production    # .env.production
```

**Optional means optional.** A variable declared `required = false` is no longer
reported missing, however it appears in the template.

**Formats are enforced**, with the expectation spelled out:

```text
  ✗  PORT is not a port between 1 and 65535
     .env
     →  Fix the value, or relax `format` in [vars.PORT]
```

⚠️ A format mismatch is deliberately **not** auto-fixable. evnx knows the value
is wrong; it has no idea what the right one is. `--fix` will not touch it.

**Environments narrow the contract** to the file being checked:

```console
$ evnx validate
✓ All required variables present
✓ All checks passed

$ evnx validate --env-name production
  ✗  Missing required variable: SENTRY_DSN
     .env.production
     →  Add SENTRY_DSN=<value> to .env.production
     ·  fixable with --fix
```

<Callout type="info" title="A variable scoped to an environment is not wanted anywhere else">
`environments = ["production"]` means the variable applies **only** there —
including against the plain `.env`. A developer running `evnx validate` locally
is not told they are missing a production-only secret, which is the whole reason
the field exists.
</Callout>

<Callout type="warning">
**With a spec, the template no longer decides what is required.** The two
checks answer the same question, so running both would report a variable twice
and keep the behaviour the spec exists to replace.

`.env.example` does not go away — it is still what a person reads when cloning
the repo, and still what `evnx sync` maintains. The spec says what is *true*
about a variable; the template shows what one *looks like*.
</Callout>

## What `scan` does with it

**v0.5.0+.** `evnx scan` guesses at secrecy from a variable's name and the shape
of its value. Both guesses fail, in opposite directions, and only the project
knows which:

| Input | Without a contract |
|---|---|
| `TENANT_A=9f3a7c21b85e4d0fa62c` | **"✓ No secrets detected", exit 0** — a real credential with a name that gives nothing away |
| `INTERNAL_SECRET=a-long-config-value` | reported **high** — a config string flagged because of its name |

Declaring it settles both:

```toml
[vars.TENANT_A]
secret = true          # report it, whatever it looks like

[vars.INTERNAL_SECRET]
secret = false         # I have looked; this is configuration
```

```text
  ✗  Declared secret                             high
     ./.env:1 (TENANT_A)  9f3a…a62c
     ·  declared `secret = true` in .evnx.toml
```

<Callout type="danger" title="`secret = false` cannot silence a real key">
It retracts a guess made from a variable's **name**. It does **not** retract a
match on the **value**.

```toml
[vars.STRIPE_SECRET_KEY]
secret = false         # the sk_live_… match is still reported
```

A declaration says what a variable is *for*. It cannot make its contents stop
being a live credential — and `.evnx.toml` is committed, so one wrong line would
otherwise silence a real secret for everyone who clones the repository.
</Callout>

<Callout type="info">
Because `secret = false` loosens scanning from a committed file, evnx announces
it on every run, the way it already announces `scan.exclude`:

```text
  config    .evnx.toml (vars.secret=false on 1 variable(s))
```

A declared secret whose value is empty or an obvious placeholder is **not**
reported. The declaration says the variable holds a secret, not that every string
in it is one.
</Callout>

## Keeping it current

**v0.5.0+.** A contract that stops describing the project is worse than none —
it looks authoritative and is not.

### `add` and `init` record what they introduce

```console
$ evnx add service redis --yes
  ✓ added 5 variable(s) to [vars] in .evnx.toml
✓ Added 5 variables for Redis
```

New variables are appended with the same inference `spec init` uses, so an entry
does not depend on which command introduced it:

```toml
[vars.REDIS_PASSWORD]
required = false
secret = true
```

It **only appends**. A name already declared is left exactly as it is, so a
hand-written `required = false` is never reset by an unrelated `evnx add`.

What `evnx add` does depends on the project:

| Project state | What `add` does |
|---|---|
| No `.evnx.toml` | Nothing, silently — you have not opted in |
| `.evnx.toml`, no `[vars]` | A note on stderr: `.evnx.toml has no [vars] section — the new variables are not under contract`, pointing at `evnx spec init` |
| `[vars]` present | Appended, with a count |

`evnx init` opts the project in itself (**v0.10.16+**): it creates `.evnx.toml` on every
run, with the variables it set up in `[vars]`, or with an empty `[vars]` when it set up
none, so that a later `evnx add` records into it:

```console
$ evnx init --with redis --yes
  …
  ✓ created .evnx.toml with 5 variable(s) in [vars]

$ evnx init --yes
  …
  ✓ created .evnx.toml with an empty [vars]: evnx add records new variables there
```

<Callout type="info">
The note is on **stderr** and never fatal, so nothing new can fail a CI job.
Failing to record the contract does not fail the write that already happened —
the variables are on disk either way.
</Callout>

### `sync` can satisfy the contract

`evnx sync --direction reverse` adds declared-but-missing variables to `.env`,
not just the ones in `.env.example`. In a terminal it asks first; `--force` adds
them without asking (and so does a run with no terminal, or with `CI` set):

```console
$ evnx validate
  ✗  Missing required variable: ONLY_IN_SPEC

$ evnx sync --direction reverse --force
┌─ Missing Variables ──────────────────────────────────────────────────────────┐
│ Found 1 variable missing from .env:                                          │
│   • ONLY_IN_SPEC  (required by [vars] in .evnx.toml)                         │
└──────────────────────────────────────────────────────────────────────────────┘

· Force mode: adding the template's values (placeholders where it has none), skipping prompts
✓ Added 1 variable to .env
```

Since 0.10.12 the box says which names come from the spec rather than the template,
and reverse into a **new** `.env` adds them too.

Before v0.5.0 the second command said *".env is up to date"* — two commands
contradicting each other about the same variable.

Only variables that are **required** and **apply to the file being synced** are
added. An optional one being absent is permitted by the contract, so inventing a
placeholder for it would be work nobody asked for.

### `diff` does not read the contract

`evnx diff --env-name production --against staging` reports a variable declared
`environments = ["production"]` as missing from staging, like any other. Earlier
versions of this page described an `explained by [vars] environments` line and a
`by_design` array in the JSON; neither has ever existed in evnx.

## Checking it: `evnx spec check`

**v0.11.0+** — a read-only check of the contract against `.env.example`, and against
`.env` when there is one:

- every variable `[vars]` declares for every environment must be in the template;
- every name in the template must be declared in `[vars]`;
- with a `.env`, every required variable must be in it.

A variable limited to some environments (`environments = [...]`) may live in their
own templates, so it is not required in `.env.example`. It needs no `.env`, so it runs
in CI and in a fresh clone:

```console
$ evnx spec check
  config    .evnx.toml
  ✓ .env.example agrees with [vars] (3 declared)
· .env not found, so only the template was checked
```

```console
$ evnx spec check
  config    .evnx.toml
  ✗ declared in [vars], missing from .env.example: DATABASE_URL
  ✗ in .env.example, not declared in [vars]: DEBUG
  ✗ required by [vars], missing from .env: DATABASE_URL
```

| Option | Default | Description |
|---|---|---|
| `--example` | `.env.example`, or `[defaults] example` | The template to check |
| `--env` | `.env`, or `[defaults] env_name` | The env file; skipped when absent unless named |
| `--env-name` | — | Check `.env.<NAME>` instead of `.env` |

Exit `0`: they agree, or there is no `[vars]` (skipped, and said). Exit `1`: they
disagree. Exit `2`: the template is missing or does not parse, or a file named by
`--env` / `--env-name` does not exist. `-q` prints only what disagrees.

As a pre-commit hook:

```yaml
- repo: https://github.com/urwithajit9/evnx
  rev: v0.11.0
  hooks:
    - id: evnx-spec-check
```

---

## Exit codes

`spec check`'s are above. `spec init`'s:

| Code | Meaning |
|---|---|
| `0` | The spec was written, printed with `--stdout`, or every variable was already declared |
| `2` | Nothing was written — no variables to read, nothing to write, a file named by `--env` or `--example` that does not exist, a file that does not parse, `[vars]` already present without `--merge`, an unknown component, or an argument error |

A format that is not one of the five names or a `regex:` that will not compile is
refused when the **config is read**,
not the first time a value happens to be checked against it — so a broken
contract fails the next command, whatever it is, rather than lying dormant.

---

## A project without a spec is unaffected

A project with no `[vars]` section gets the previous behaviour exactly. Nothing
about `validate`, `scan` or `sync` requires one, and adopting a spec is a decision
you make per project.
