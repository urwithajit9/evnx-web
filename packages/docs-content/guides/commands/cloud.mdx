`evnx cloud` is the sync itself: encrypt a `.env` here, upload the ciphertext, pull it down somewhere else and decrypt it there.

## Commands

<CommandSignature>
evnx cloud [SUBCOMMAND]
evnx cloud link my-api/production
evnx cloud push
evnx cloud pull
evnx cloud run --vault my-api/production -- ./deploy.sh
evnx cloud history
evnx cloud diff
evnx cloud audit
evnx cloud watch
</CommandSignature>

| Subcommand | What it does |
|---|---|
| `push` | Encrypt a `.env` and upload it as a new version |
| `pull` | Download a version and decrypt it |
| `run` | **v0.5.0+** — run a command with a vault's variables in its environment, writing no file |
| `history` | List a vault's versions, newest first |
| `diff` | **v0.10.0+** — which keys changed between two versions |
| `watch` | **v0.10.0+** — report when someone else pushes a new version |
| `audit` | **v0.10.0+** — who pushed, pulled, shared and re-keyed |
| `delete-version` | Delete one version, and its encrypted blob |
| `export` | **v0.8.0+** — write every version to a directory, **decrypted** |
| `link` | Bind this directory to a vault |
| `unlink` | Remove the binding |
| `status` | Show whether this machine is set up for sync |

## Binding a directory

```bash
evnx cloud link my-api/production
```

This writes `[cloud] vault` into `.evnx.toml`, preserving everything else already in the file. After it, `push` and `pull` need no `--vault`.

The file is the project's one `.evnx.toml`: the config in force, found at or above the current folder, or, with none, a new one at the git root — where `evnx spec init` writes too (**v0.10.6+**; run from a subfolder with no config, it used to create one in that subfolder).

<Callout type="tip" title="Safe to commit">
`.evnx.toml` is project-level and meant to be committed — a vault name is not a secret. Credentials never go there; they live in `~/.config/evnx/` at mode 0600.
</Callout>

`evnx cloud unlink` removes the binding and touches nothing else.

## Pushing

```bash
evnx cloud push
evnx cloud push --vault my-api/staging                 # picks up .env.staging
evnx cloud push --vault my-api/staging --env-name staging
evnx cloud push --vault my-api/staging --file .env.staging
```

### Which file gets pushed — **v0.5.0+**

`push` derives the file from the vault's environment: pushing `my-api/production` uses
`.env.production` when that file exists, and `.env` otherwise. **The file chosen is
printed every time:**

```
  file      .env.production (matched the vault environment)
  file      .env (default)
```

<Callout type="warning">
Before v0.5.0 `--file` defaulted to `.env` whatever the vault was, and nothing said which
file had been read — so `evnx cloud push --vault app/production` with a forgotten flag
pushed **local development secrets into the production vault**, encrypted, versioned and
shared with everyone holding a key.

A derived name that does not exist is not an error, because most projects genuinely have
only `.env`. What makes that safe is the reporting, and, from v0.10.18, the question
below.
</Callout>

### Pushing the default `.env` into production asks first — **v0.10.18+**

When the file is the default `.env` and the vault is a production vault, `push` asks
before it encrypts anything:

```text
  file      ./.env (default)
  ! pushing to a production vault from ./.env — pass --env-name or --file if that is not what you meant
Push ./.env into production vault my-api/production? [y/N]
```

With no terminal (a script, a CI job), it is refused with exit 2 instead of pushing:

```text
Error: there is no terminal to confirm with.

./.env is the default file and my-api/production is a production vault, so this is asked first. Name the file you mean (--file or --env-name), or add --yes:
  evnx cloud push --vault my-api/production --yes
```

Only that case asks. A file you named with `--file` or `--env-name` never does, and
neither does a derived `.env.production`. By id, a signed-in session looks the
vault's environment up for the question. A vault-scoped API token cannot look it up,
so it is not asked.

<OptionTable>
  <Option flag="--vault" type="string">Vault to push to: `name`, `name/environment`, or an id. Optional in a bound directory.</Option>
  <Option flag="--file" type="path">File to push. Defaults to `.env.&lt;environment&gt;` when the vault names one and that file exists, otherwise `.env`. Short form `-f`.</Option>
  <Option flag="--env-name" type="string">**v0.5.0+** — push `.env.&lt;NAME&gt;`. Conflicts with `--file`; a name whose file does not exist is an error.</Option>
  <Option flag="--yes" type="flag">**v0.10.18+** — push the default `.env` into a production vault without asking. Short form `-y`.</Option>
  <Option flag="--password-stdin" type="flag">Read the master password from stdin instead of prompting.</Option>
  <Option flag="--server" type="url">Server to talk to. Plain `http://` is refused for anything but loopback.</Option>
</OptionTable>

The file is encrypted **byte for byte**. Comments, blank lines, ordering and quoting all survive the round trip, because evnx encrypts the file rather than a parsed representation of it.

Only the key *names* are sent in the clear, so a dashboard can list what a vault holds without decrypting anything.

## Pulling

```bash
evnx cloud pull
evnx cloud pull --vault my-api/production              # writes .env.production if it exists
evnx cloud pull --env-name production
evnx cloud pull --version 7 --file .env.restored
```

`pull` derives the same way, with one difference: it only uses `.env.<environment>` when
that file **already exists**, so a first pull into a fresh checkout still writes `.env`
rather than inventing a convention the project does not have. Name it explicitly to create
one. The file written is always printed.

<OptionTable>
  <Option flag="--vault" type="string">Vault to pull from. Optional in a bound directory.</Option>
  <Option flag="--file" type="path">Where to write the decrypted file. Derived as above; `-` writes to stdout and creates no file. Short form `-f`.</Option>
  <Option flag="--env-name" type="string">Write `.env.&lt;NAME&gt;` instead of the derived or default file.</Option>
  <Option flag="--version" type="number" default="latest">Version to pull, **1 or more**.</Option>
  <Option flag="--force" type="flag">Overwrite the target without asking.</Option>
  <Option flag="--gitignore" type="flag">**v0.10.18+** — add the pulled file to `.gitignore` without asking.</Option>
  <Option flag="--no-gitignore" type="flag">**v0.10.18+** — skip the `.gitignore` check.</Option>
  <Option flag="--password-stdin" type="flag">Read the master password from stdin instead of prompting.</Option>
</OptionTable>

<Callout type="warning" title="--version here means the vault version">
Because `pull` takes a `--version` of its own, clap's automatic `--version` flag is disabled on this subcommand. For the program version use `evnx --version`.
</Callout>

**v0.10.18+**, `--version` is checked before anything is sent: `0` is a usage error
(exit 2), and a version the vault does not have is named:

```text
Error: version 9 of my-api/production does not exist.
  `evnx cloud history --vault my-api/production` lists the versions it has.
```

### Keeping the pulled file out of git — **v0.10.18+**

In a git repository, `pull` runs the same `.gitignore` step as `template`, `convert`
and `restore`. If the file it wrote is not ignored, it asks on a terminal. With no
terminal it warns and leaves `.gitignore` alone:

```text
  file      ./.env (default)
  ! writing to a production vault from ./.env — pass --env-name or --file if that is not what you meant
  ✓ pulled version 2 of my-api/production into ./.env
! '.env' may contain secrets and is not in .gitignore
```

`--gitignore` adds it without asking (`✓ Added '.env' to .gitignore`), and
`--no-gitignore` skips the check. `--file -` writes no file, so nothing is checked.

Pulling over a file that differs from the version asks first. With no terminal it
stops and names `--force`, the flag that replaces the file.

## Running a command without writing a file

**v0.5.0+.**

```bash
evnx cloud run --vault my-api/production -- ./deploy.sh
```

Everything after `--` is your command. It is run as a child process with the
vault's variables in its environment — `./deploy.sh` is only an example:

```bash
evnx cloud run --vault my-api/production -- npm run build
evnx cloud run --vault my-api/production -- python manage.py migrate
evnx cloud run --vault my-api/staging    -- terraform apply
```

### What it replaces

```bash
evnx cloud pull && ./deploy.sh && rm .env     # a file, and an rm that may not run
export $(cat .env | xargs) && ./deploy.sh     # your shell's environment, and its history
```

The secrets are decrypted in memory, handed to the child, and destroyed. Nothing
is written to disk and nothing enters your shell history.

<Callout type="info" title="Why the values never appear in `ps`">
They travel in the child's **environment block**, never in its argument vector.
That is the difference between this and every `export`-based workaround:

```bash
evnx cloud run --vault my-api/production -- sleep 30 &
ps aux | grep sleep     # shows "sleep 30", and no values
```
</Callout>

<Callout type="danger" title="This removes the file, not the master password">
The vault key is wrapped under **your master key**, so decrypting needs your
password wherever this runs. An API token authenticates you to the server; it
cannot unwrap a vault key, because the server never had one to give.

In CI that means feeding the password from a secret:

```yaml
- run: echo "$EVNX_PASSWORD" | evnx cloud run --vault my-api/production --password-stdin -- ./deploy.sh
  env:
    EVNX_PASSWORD: ${{ secrets.EVNX_MASTER_PASSWORD }}
```

Only the first line of stdin is consumed; the child inherits the rest.

The honest description of the win is **"no file"**, not "no secret to manage".
</Callout>

### The `--` is required

```bash
evnx cloud run --vault x -- npm run build --prod
```

Without the separator, `--prod` would be read as one of evnx's own flags. With
it, everything to the right belongs to the child, and `evnx cloud run echo hi`
is a usage error rather than a guess.

### It does not go through a shell

The command is executed directly, so pipelines, redirections and shell builtins
need one asked for:

```bash
evnx cloud run --vault x -- sh -c 'psql "$DATABASE_URL" < schema.sql'
```

A missing command says so, and says this.

### Narrowing what the child sees

| Flag | Description |
|---|---|
| `--vault <VAULT>` | `name`, `name/environment`, or an id. Optional in a linked directory |
| `--version <N>` | Version to inject. Defaults to the latest |
| `--include <GLOB>` | Inject only names matching these globs, comma-separated |
| `--exclude <GLOB>` | Skip names matching these. Applied after `--include` |
| `--password-stdin` | Read the master password from stdin |

A build step that needs only public configuration has no reason to hold your
database password:

```bash
evnx cloud run --vault my-api/production --include "NEXT_PUBLIC_*" -- npm run build
```

An excluded variable is **never written into the child's environment** — it is
not passed and then unset.

<Callout type="warning">
**A filter that matches nothing is an error**, not a quiet success. Running a
deploy with zero secrets injected is the kind of success that is worse than a
failure, so `evnx cloud run` stops rather than proceeding:

```text
Error: --include/--exclude left nothing to inject — all 12 variable(s) were filtered out.
```

The patterns are case-sensitive globs matched against variable names.
</Callout>

### Exit codes

`evnx cloud run` exits with **the child's own code**, so a pipeline branches on
your command rather than on evnx:

```bash
evnx cloud run --vault x -- ./deploy.sh   # ./deploy.sh returns 2 → this returns 2
```

A child killed by a signal has no code to pass through; that is reported and
becomes `1`. Failures *before* the child starts — not signed in, no such vault,
the wrong password — are evnx's own errors. They exit `2` and end with
`No verdict: evnx did not finish.`, so they cannot be mistaken for a child that
returned 1:

```text
Error: no vault called "no-such-vault". Run `evnx vault list` to see what you have.

No verdict: evnx did not finish. This is not a clean result.
```

A wrong master password is refused straight after the prompt (**v0.10.18+**),
before anything is downloaded or run.

## Version history

```bash
evnx cloud history
evnx cloud history --vault my-api/production --limit 50
```

<TerminalOutput title="evnx cloud history">
  VERSION  KEYS     SIZE  PUSHED BY        PUSHED
        4     3    148 B  you              2026-10-24 21:52
        3     4    185 B  bob@example.com  2026-10-24 21:51
        2     3    159 B  bob@example.com  2026-10-24 21:51
        1     2    158 B  you              2026-10-24 21:51

  Restore one with:  evnx cloud pull --version 4
</TerminalOutput>

`PUSHED BY` names other members by email (**v0.10.18+**; before, everyone but you
was an 8-character id), and the column widens to fit. Your own pushes say `you`.
Someone who has since left the vault keeps the short id.

`history` is **read-only in the strongest sense**: no password prompt, no decryption, no blob download. It reads metadata the server already holds in the clear, which is why it is safe to run from a script or a read-only token.

## What changed between two versions

<Callout type="info">Requires evnx **0.10.0 or newer**.</Callout>

```bash
evnx cloud diff
evnx cloud diff --from 5 --to 7
evnx cloud diff --vault my-api/production --from 1 --to 12
```

With no arguments it compares the two newest versions, which is usually the question: what did that last push change?

<TerminalOutput title="evnx cloud diff">
  evnx cloud diff  my-api/production   v2 → v3

  + SENTRY_DSN
  + STRIPE_KEY
  - LEGACY_TOKEN

  2 added  ·  1 removed  ·  2 unchanged
</TerminalOutput>

<Callout type="warning">
**`+` means the opposite of what it means in `evnx diff`.**

Here `+` is *added in the newer version*. In [`evnx diff`](/guides/commands/diff), which compares a `.env` against a template, `+` is *missing from your `.env`*. The two commands read in opposite directions, which is why this one always prints `v2 → v3` above the list — the header is what tells you which way you are reading.
</Callout>

### It cannot see that a value changed

The server stores key **names** and ciphertext. It has never held a value. So rotating `DATABASE_URL` without renaming it produces two versions whose key sets are identical, and a comparison by name alone would report "no changes" — which would be confidently wrong about the exact thing you asked.

So when the names match, the blob hashes are compared instead:

<TerminalOutput title="evnx cloud diff — a rotated value">
  evnx cloud diff  my-api/production   v1 → v2

  Same keys — but the contents differ.

  Both versions hold the same 2 keys, so something changed inside a
  value. evnx cannot tell you which: the server stores key names and
  ciphertext, never a value, so there is nothing here to compare.
</TerminalOutput>

To see *which* value changed, the comparison has to happen where the values exist — on your machine:

```bash
evnx cloud export --vault my-api/production --all-versions --output ./versions
```

<Callout type="info">
A BLAKE3 digest of ciphertext says only *that* bytes differ, never what they are. Reporting it leaks nothing the server did not already hold.
</Callout>

## Watching for someone else's push

<Callout type="info">Requires evnx **0.10.0 or newer**.</Callout>

```bash
evnx cloud watch
evnx cloud watch --vault my-api/production --interval 30
evnx cloud watch --vault my-api/production --once
```

Runs in the foreground until Ctrl-C, like `tail -f`. It tells you when a new version appears and names what changed:

<TerminalOutput title="evnx cloud watch">
  evnx cloud watch  my-api/production
  At v2. Watching for newer versions.
  Polling every 5s · metadata only, no password · Ctrl-C to stop
  Your own pushes are skipped; --include-mine shows them.

  ▲ v3 · +FEATURE_NEW_CHECKOUT · 2026-10-24 21:51
    evnx cloud pull --vault my-api/production
  ▲ v4 · -SENTRY_DSN · 2026-10-24 21:52
    evnx cloud pull --vault my-api/production
</TerminalOutput>

When the names match but the contents differ, the line reads
`same keys, different contents` instead.

The point is finding out a teammate changed a secret **before** your next deploy picks it up silently — not saving you from typing `pull`.

| Flag | Description |
|---|---|
| `--vault <VAULT>` | Vault to watch. Optional in a bound directory |
| `--interval <SECONDS>` | Seconds between polls. Default `15`, minimum `5` |
| `--once` | Check once and exit. For scripts and tests |
| `--include-mine` | **v0.10.18+** — report your own pushes too |

### Your own pushes are skipped — **v0.10.18+**

A push you made is not news to you, so by default `watch` reports only other
people's. In the run above, a teammate's watcher on the same vault showed v4 and
not v3, because v3 was theirs. `--include-mine` shows every push.

### Failed polls are reported, and it stops after ten — **v0.10.18+**

Before, a failed poll showed only under `--verbose`, so an expired login looked
exactly like a quiet vault. Now, from the third failed poll in a row, it says so on
stderr, it says when polling works again, and after ten in a row it stops with exit 2:

<TerminalOutput title="evnx cloud watch — the server goes away">
  ! 3 polls in a row have failed (stopping at 10): could not reach https://api.evnx.dev: Connection refused (os error 111)
  ! 4 polls in a row have failed (stopping at 10): could not reach https://api.evnx.dev: Connection refused (os error 111)
  ✓ polling again, after 4 failed poll(s)
  …
  ! 9 polls in a row have failed (stopping at 10): could not reach https://api.evnx.dev: Connection refused (os error 111)
Error: stopped after 10 failed polls in a row: could not reach https://api.evnx.dev: Connection refused (os error 111)
  Check the connection and your login (`evnx auth status`), then run `evnx cloud watch` again.
</TerminalOutput>

ⓘ Output from a local test server, shown here as `https://api.evnx.dev`.

<Callout type="warning">
**It never pulls, and that is deliberate.**

Overwriting your `.env` because someone else pushed would destroy local edits with no undo — it is a file you change constantly while working.

And pulling needs your master password. A watcher that auto-pulled would hold the vault key in memory for its whole lifetime — hours, in a terminal pane, on an unlocked laptop. That is a different threat model from a one-shot `evnx cloud pull` that derives a key, uses it and exits.

So it polls **metadata only**: no password, no decryption, no blob download. Taking a change stays a deliberate `evnx cloud pull`.
</Callout>

<Callout type="info">
**`--interval` has a 5-second floor.** A one-second poll against a shared API is a denial of service someone writes by accident, and knowing two seconds sooner is worth nothing.

One or two failed polls are not reported and the loop continues — a watcher that exits on one network blip is one nobody trusts to leave running.
</Callout>

ⓘ Two pushes between polls are reported as one event, compared against the version you last saw rather than the one immediately before — otherwise a key that appeared and vanished would be invisible.

## Who did what — the audit trail

<Callout type="info">Requires evnx **0.10.0 or newer**.</Callout>

```bash
evnx cloud audit
evnx cloud audit --last 7d
evnx cloud audit --vault my-api/production --event pull
```

Pushes, pulls, member changes, re-keys and token creation, newest first. Any member of a vault can read it — the trail is how a team notices something it did not expect.

<TerminalOutput title="evnx cloud audit">
  WHEN                 WHAT            WHO                   DETAIL
  2026-10-05 14:02:11  push            you@example.com       version 3
  2026-10-04 09:41:55  pull            ci@example.com        version 2
  2026-09-24 16:20:03  member_grant    you@example.com       bob@example.com as developer
  2026-09-16 11:07:40  vault_rekey     (deleted account)     re-wrapped for 2 members
</TerminalOutput>

`--event` takes any of `push`, `pull`, `version_deleted`, `member_grant`, `member_role_change`, `member_revoke`, `vault_rekey` or `token_create`.

<Callout type="warning">
**Retention limits what you can see, not what is kept.**

`audit_events` is append-only in the database — nothing prunes it and nothing can. Your plan decides how far back the API will *return*. When events are withheld the command says so and gives the count, because a trail that silently stops is indistinguishable from a vault that was quiet.

Asking for a window wider than your plan is not an error, and the output tells you which one applied:

```
⚠ 14 older events are not shown on this plan.
  This plan shows the last 7 days. The events are kept — this is a
  limit on what the API will return, not on what is stored.

ⓘ You asked for 30 days; this plan shows 7.
```
</Callout>

<Callout type="info">
**What the trail deliberately does not show.** The server records a hashed client address and user agent against each event, and never returns them. They are stable digests, so they would correlate a colleague's activity across events without naming them — worth holding to detect an unfamiliar device, not worth handing to everyone who shares a vault.
</Callout>

Read-only: no password, no decryption.

## Getting everything out

```bash
evnx cloud export --vault my-api/production --all-versions --output ~/evnx-export
```

<Callout type="danger" title="⚠️ This writes your secrets to disk in plain text">
It is the one `cloud` subcommand whose purpose is to do that, and the only one
in evnx. `pull` writes a single file and asks first; `run` writes none at all.

With no `--to` the files are the **exact bytes you pushed** — comments,
ordering and quoting included — because that is how they were encrypted.
`--to json` and the other thirteen `evnx convert` formats are available, and a
conversion keeps only keys and values.

Full guide, including what it refuses and why an export goes stale:
[Getting your secrets out](/guides/reference/getting-your-secrets-out).
</Callout>

This exists so the answer to *what happens when we want to leave?* is a command
rather than a promise. It is not the command for CI — that is `run`, above.

## Conflicts, and why a retry is not enough

Every push carries the version it was based on. If someone else pushed in between, the server answers **409 Conflict**.

<Callout type="danger" title="A 409 requires re-encryption, not a retry">
This is the single most important thing to understand about evnx cloud, and it is not how most sync tools behave.

The version number is **authenticated into the ciphertext** as associated data. A blob sealed as "version 8" is cryptographically bound to being version 8. If the server has moved on to 9, that blob cannot become version 9 — decryption of it as 9 fails by design.

So resending the same bytes does not work and is not supposed to. Pull the new version, reconcile the change, and push again — which re-encrypts against the new number.
</Callout>

This is not bureaucracy. It is what stops a malicious or compromised server replaying an old version as the current one: it cannot relabel version 3 as version 12, because version 3's ciphertext is sealed to the number 3.

## Machine status

```bash
evnx cloud status
```

Reports whether this machine has credentials, whether the directory is bound, and which server it will reach. Compare with `evnx auth status`, which asks the server about your **account**.

By default this reads local files only, so it works offline and never touches the
network.

### `--ping` — use it as a health check

**v0.5.0+.** Adding `--ping` also checks that the server answers:

```bash
evnx cloud status --ping
```

```text
evnx cloud
  server    https://api.evnx.dev
  account   you@example.com
  status    signed in
  token     expired — renewed automatically on the next command

  reachable yes (server ok v0.1.0)
```

The command exits non-zero when the server cannot be reached, which is what makes
it usable as a health check in a script:

```bash
evnx cloud status --ping || echo "evnx cloud is unreachable"
```

<Callout type="warning">
**A non-zero exit does not always mean "unreachable".** `status` checks your
credentials first, so pointing `--server` at somewhere you have never signed in
exits `1` with *"No credentials for this server"* without ever pinging it. When
you are scripting a reachability check, make sure the credential for that server
already exists — otherwise you are testing your credential store, not the server.
</Callout>

## Using it in CI

Never put your master password in a pipeline unless the job genuinely needs plaintext.
Use a token, scoped as narrowly as the job needs:

```bash
evnx auth token create ci-deploy --scope read --vault my-api/production
```

<Callout type="tip" title="Or mint it in the dashboard">
**[app.evnx.dev](https://app.evnx.dev)** → Settings → API tokens does the same thing in a
form, which is less of a context switch when you are already in a browser pasting the
result into your CI provider's secret store.
</Callout>

A token scoped to one vault cannot list vaults, so in a pipeline name the vault by its
**id**, which `evnx vault list --verbose` prints. By name, the command stops with
`a vault-scoped API token cannot list vaults, so "my-api/production" cannot be resolved by name.`
The examples keep the id in a CI variable; it is not a secret.

<CodeTabs defaultTab="GitHub Actions">
  <Tab label="GitHub Actions">
```yaml
- name: Fetch secrets
  env:
    EVNX_TOKEN: ${{ secrets.EVNX_TOKEN }}
    EVNX_PASSWORD: ${{ secrets.EVNX_MASTER_PASSWORD }}
    EVNX_VAULT_ID: ${{ vars.EVNX_VAULT_ID }}
  run: |
    printf '%s' "$EVNX_PASSWORD" | evnx cloud pull --vault "$EVNX_VAULT_ID" --file .env --force --password-stdin
```
  </Tab>
  <Tab label="GitLab CI">
```yaml
fetch-secrets:
  script:
    - printf '%s' "$EVNX_PASSWORD" | evnx cloud pull --vault "$EVNX_VAULT_ID" --file .env --force --password-stdin
  variables:
    EVNX_TOKEN: $EVNX_TOKEN
    EVNX_PASSWORD: $EVNX_MASTER_PASSWORD
    EVNX_VAULT_ID: $EVNX_VAULT_ID
```
  </Tab>
</CodeTabs>

<Callout type="info" title="A read-only token is enough to pull">
Pulling is a GET, so a read-only token handles deploys perfectly. Give a job a read-write token only when it genuinely pushes — a rotation job, say. Scope it to one vault while you are there.
</Callout>

<Callout type="info" title="Scripting cloud commands — v0.10.18+">
- **`-q` prints nothing on success** for every `cloud`, `vault`, `org` and `auth`
  command. Tables you asked for, warnings and errors still print, and
  `evnx auth token create … -q` prints the new token alone on stdout. ⚠️ A script
  that read a `✓ pushed …` line from stdout under `-q` now gets nothing.
- **Every confirmation names its flag when there is no terminal**: `--yes` for
  `delete-version`, and `--force` for a `pull` over a file that differs.
- **A job that pushes the default `.env` into a production vault** needs `--yes`,
  or better, `--file` naming the file it means.
</Callout>

<Callout type="info" title="Pulling still needs the master password">
A token authenticates you to the server. It does not decrypt anything — the vault key is wrapped under your master key, and only your master password unwraps it.

For unattended pipelines this is the real constraint, and it is the honest consequence of zero knowledge: some secret has to reach the runner for decryption to be possible. Supply the master password via `--password-stdin` from your CI's own secret store, and understand exactly what you have granted that runner.
</Callout>

## What survives a round trip

Push then pull and you get the same file back, byte for byte — comments, ordering, both
quote styles, non-ASCII, trailing whitespace and the final newline. All of it, because the
encryption input is the file itself rather than a parsed representation of it.

Verified before each release against a fixture built to break exactly that:

```bash
printf '# leading comment\n\nZEBRA_LAST=ordering-must-survive\nQUOTED="value with  spaces"\nUNICODE=café-日本\nTRAILING=ws   \n' > .env.development
evnx cloud push --vault my-app/development --file .env.development
evnx cloud pull --vault my-app/development --file .env.pulled
cmp .env.development .env.pulled && echo "byte-identical"
```

</Callout>

<Callout type="warning">
Use `cmp`, not `diff`. `diff` treats two files as identical when they differ only in
trailing whitespace or a missing final newline — which is the corruption most worth
