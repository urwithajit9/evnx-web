# evnx migrate — Command Reference

`evnx migrate` reads your `.env`, applies any filtering and prefix rules you ask
for, and **writes out the commands** that would load those variables into a cloud
secret manager or CI platform. You review them and run them.

<Callout type="warning">
**It does not upload — with one exception.** Eight of the nine destinations never
contact the platform at all. They print `aws secretsmanager create-secret …`,
`doppler secrets set …`, `heroku config:set …` and so on, for you to run under
your own already-authenticated CLI.

`github-actions` is the exception: it encrypts each secret with the repository's
public key and PUTs it to the GitHub REST API. That one really does transfer.

This is a deliberate design, not a gap — see
[Why it works this way](#why-it-works-this-way). Before v0.5.0 the summary line
reported `✓ N uploaded` for every destination, which made it easy to believe the
transfer had happened. It now says what it did.
</Callout>

<Prerequisites>
  <Prerequisite href="/guides/getting-started/installation">Install evnx</Prerequisite>
  <Prerequisite href="/guides/getting-started/sync-basic">Understand .env basics</Prerequisite>
</Prerequisites>

<Callout type="info">
**Building from source.** `migrate` is behind a Cargo feature, but the prebuilt
binaries are built with every feature, so Homebrew, Scoop, winget, npm, PyPI and
the GitHub Release all have it. Only `cargo install` needs to ask for it:

```bash
cargo install evnx --all-features
```

Run `evnx migrate --help`. If it prints help, you have it.
</Callout>

<Callout type="warning">
**Changed in 0.10.10 — check your scripts.**

- `--to github-actions --skip-existing`, and `--yes` without `--overwrite`, could
  **replace secrets they promised to keep**: evnx read only the first 30 names of
  GitHub's list, and compared them case-sensitively. Every page is read now, and
  names are compared as GitHub stores them.
- `vercel` printed `--project-id`, which the Vercel CLI does not have, and `railway`
  printed `railway --project … variables set`, which the Railway CLI cannot parse.
  Both now print commands their CLI accepts — see [Destinations](#destinations).
- `gcp-secret-manager` needs `--project` and prints the values.
- Two names that end up as one are an error unless `--allow-collisions`.
- `[defaults] env_name` in `.evnx.toml` now applies, as for every other command.
</Callout>

## What it does, step by step

<Step number={1} title="Reads the source">
A `.env` file — `.env`, `--source-file`, or `.env.<name>` with `--env-name` — or,
with `--from environment`, the variables you select from the process environment.
</Step>

<Step number={2} title="Applies your filters">
`--include`, then `--exclude`, then `--strip-prefix`, then `--add-prefix`. In that
order. Names that end up as one name are refused.
</Step>

<Step number={3} title="Renders the destination's commands">
Each destination knows its platform's syntax, quoting and naming rules. Azure, for instance, rewrites underscores to hyphens because Key Vault will not accept them.
</Step>

<Step number={4} title="Prints them, and stops">
Except `github-actions`, which uploads. Nothing else leaves your machine.
</Step>

---

## Command signature

```bash
evnx migrate [OPTIONS]
```

Run it with no flags for an interactive picker. In a script, name the
destination and what it needs:

```bash
evnx migrate --to doppler --project my-app --doppler-config prd
```

---

## Sources

| Value | Description |
|-------|-------------|
| `env-file` | Read a `.env` file: `.env`, `--source-file PATH`, or `.env.NAME` with `--env-name NAME` (or `[defaults] env_name` in `.evnx.toml`). Used when `--from` is omitted and there is no terminal to ask |
| `environment` | Read the current process environment. **Requires `--include`** — a shell or CI job holds tokens you did not mean to send — and lists the names it will send before printing anything |

The first line of the output names the file it read:

```text
✓ Loaded 2 secrets from .env
```

## Destinations

| Value | Aliases | What evnx produces | Needs | Transfers? |
|-------|---------|--------------------|-------|------------|
| `github-actions` | `github` | Encrypts each secret and PUTs it to the GitHub REST API | `--repo`, `GITHUB_TOKEN` | **Yes** |
| `aws-secrets-manager` | `aws` | One `create-secret` / `update-secret` pair, all variables in a single JSON secret | `--secret-name` | No |
| `gcp-secret-manager` | `gcp` | A script that creates each secret, or adds a version when it exists | `--project` | No |
| `azure-keyvault` | `azure` | One `az keyvault secret set` per variable, with `_` rewritten to `-` | `--vault-name` | No |
| `heroku` | — | One bulk `heroku config:set`, so the dyno restarts once | `--heroku-app` | No |
| `vercel` | — | One `vercel env add` per variable, the value on stdin | — | No |
| `doppler` | — | One `doppler secrets set` per variable | — | No |
| `infisical` | — | One `infisical secrets set` per variable | — | No |
| `railway` | — | One bulk `railway variable set` | — | No |

"Needs" is what evnx cannot print a command without: it asks in a terminal, and
otherwise exits `2` naming the flag. Where the column is empty the command falls
back to the CLI's own context — `vercel link`, `doppler setup`, `railway link`.

Printing a command never needs the platform's CLI installed. (Until 0.10.10,
doppler, infisical and railway refused to print without it.)

The examples below use `--print-only`, which writes the commands and nothing
else; without it the same commands appear between status lines and a summary.

### `aws-secrets-manager`

All variables go into **one** secret as a JSON document — the Secrets Manager
idiom — rather than one secret per variable.

```bash
evnx migrate --to aws --secret-name prod/myapp/config --print-only
```

```text
# Create a new secret:
aws secretsmanager create-secret \
  --name prod/myapp/config \
  --secret-string '{
  "DATABASE_URL": "postgres://user:pw@db/app",
  "API_KEY": "sk_live_abc123"
}'

# Or update an existing secret:
aws secretsmanager update-secret \
  --secret-id prod/myapp/config \
  --secret-string '{
  "DATABASE_URL": "postgres://user:pw@db/app",
  "API_KEY": "sk_live_abc123"
}'
```

Both are printed because evnx cannot know whether the secret exists — it never
talks to AWS. Run the one that applies. `--aws-profile` adds `--profile` to both.

### `gcp-secret-manager`

One secret per variable, from a small script that creates the secret, or adds a
new version when it already exists — so running it again updates the values
instead of failing:

```bash
evnx migrate --to gcp --project my-gcp-project --print-only > gcp-upload.sh
```

```text
# Creates each secret, or adds a new version when it already exists.
upsert_secret() {
  if gcloud secrets describe "$1" --project=my-gcp-project </dev/null >/dev/null 2>&1; then
    gcloud secrets versions add "$1" --data-file=- --project=my-gcp-project
  else
    gcloud secrets create "$1" --data-file=- --project=my-gcp-project
  fi
}

printf '%s' 'postgres://user:pw@db/app' | upsert_secret DATABASE_URL
printf '%s' 'sk_live_abc123' | upsert_secret API_KEY
```

Each value reaches `gcloud` on stdin, exactly as written. Names stay as they are
in your `.env`; [`evnx convert --to gcp-secrets`](/guides/commands/convert) prints
the same script but lowercases names and turns `_` into `-`.

<Callout type="info">
**Changed in 0.10.10.** This destination printed `echo -n "${DATABASE_URL}" | gcloud
secrets create …`: the value came from whatever your shell held under that name —
usually nothing, so an empty secret — `create` failed for a secret that already
existed, and `--project` was accepted and then left out of the commands.
</Callout>

### `azure-keyvault`

Key Vault does not permit underscores in secret names, so evnx rewrites them and
prints a rename log rather than changing names silently:

```text
az keyvault secret set --vault-name my-vault --name DATABASE-URL --value 'postgres://user:pw@db/app'
az keyvault secret set --vault-name my-vault --name API-KEY --value 'sk_live_abc123'

Key renames applied:
  DATABASE_URL → DATABASE-URL (underscores → hyphens)
  API_KEY → API-KEY (underscores → hyphens)
```

⚠️ Your application has to read the new names. Key Vault also ignores case, so
`DB_URL` and `db_url` would be one secret there: evnx refuses that pair (see
[Names that become one](#names-that-become-one)).

### `heroku`

A single bulk command, deliberately:

```text
heroku config:set --app my-app \
  DATABASE_URL='postgres://user:pw@db/app' \
  API_KEY='sk_live_abc123'
```

`heroku config:set` restarts the dyno. One bulk call restarts it once; a loop
would restart it once per variable.

### `vercel`

One command per variable; the value goes to `vercel env add` on stdin, so it is
not an argument:

```text
printf '%s' 'postgres://user:pw@db/app' | vercel env add DATABASE_URL production --project my-app --force --yes
printf '%s' 'sk_live_abc123' | vercel env add API_KEY production --project my-app --force --yes
```

`--vercel-project` becomes `--project`; without it Vercel uses the linked project
(`vercel link`). `--force` replaces a variable that already exists — without it a
second run fails — and `--yes` keeps `env add` from asking how to store the value.
The target environment is always `production`.

### `doppler` and `infisical`

One command per variable:

```text
doppler secrets set --project my-app --config prd DATABASE_URL='postgres://user:pw@db/app'
doppler secrets set --project my-app --config prd API_KEY='sk_live_abc123'
```

```text
infisical secrets set --projectId 6f1c2a --env prod DATABASE_URL='postgres://user:pw@db/app'
infisical secrets set --projectId 6f1c2a --env prod API_KEY='sk_live_abc123'
```

For Infisical, evnx refuses — before printing anything — a value that is empty
(the CLI rejects it) or starts with `@`: signed in with `infisical login`, the CLI
reads `@path` as a **file to upload**, and with a token it does not, so no quoting
is right for both.

```text
Error: these values cannot be passed to `infisical secrets set` as they are:
  KEY_FILE: starts with `@` — read as a file path under `infisical login`, sent as written with a token
  EMPTY: empty — infisical rejects an empty value

Set them in Infisical directly, or leave them out with --exclude. Nothing was printed.
```

### `railway`

One bulk command:

```bash
evnx migrate --to railway --railway-project 4e7a9c --railway-environment production --print-only
```

```text
railway variable set --project 4e7a9c --environment production \
  DATABASE_URL='postgres://user:pw@db/app' \
  API_KEY='sk_live_abc123'
```

Railway requires an environment whenever a command names the project, so
`--railway-project` needs `--railway-environment`; `--railway-service` is optional.
Leave all three out and the command is for a directory linked with `railway link`.
Setting variables redeploys the service.

### `github-actions`

The only destination that transfers. It fetches the repository's public key,
seals each value with it, and PUTs the result — so GitHub receives ciphertext it
can open and evnx never posts a plaintext secret.

```bash
evnx migrate --to github --repo owner/repo
```

- **Token:** read from the `GITHUB_TOKEN` environment variable. It needs the
  repository's **Secrets** permission (read and write), which the token an Actions
  job is given automatically does not have: in a workflow, store a personal access
  token as a secret and pass it in as `GITHUB_TOKEN` for that step.
  `--github-token` works, but puts the token in your shell history and in `ps`;
  evnx says so when you use it.
- **Unattended:** `--yes` skips "Proceed with migration?". Without a terminal and
  without `--yes`, evnx stops before contacting GitHub.
- **Secrets that already exist:** `--skip-existing` leaves them, `--overwrite`
  replaces them. `--yes` never answers "overwrite?" — with neither flag, an
  existing secret is an error and nothing is uploaded. evnx reads every page of
  the repository's secrets and compares names as GitHub stores them (uppercase).
- **Names GitHub refuses** — those starting with `GITHUB_` — and values over 48 KB
  are refused before any request.
- It waits one second between uploads, as GitHub asks for writes. Each request
  times out after 30 seconds.

```bash
# In CI: token from the environment, existing secrets left alone
evnx migrate --to github-actions --repo owner/repo --yes --skip-existing
```

## Save only the commands: `--print-only`

Without it, stdout carries the commands **and** the status lines and summary, so
`> file` saves something `sh` cannot run. With it, stdout is the commands alone and
everything else goes to stderr:

```bash
evnx migrate --to heroku --heroku-app my-app --print-only > upload.sh
```

`--print-only` does not apply to `github-actions`, which prints no commands, and
cannot be combined with `--dry-run`.

---

## Your secrets are in the printed commands

<Callout type="danger">
**Every destination but `github-actions` prints secret values in plaintext**,
because that is what the command needs to contain. Anything you copy into a
terminal lands in your shell history, and a `--secret-string '{…}'` line carries
every variable at once.

Mitigations, in order of preference:

1. **Write the commands to a file instead of scrolling**, review it, run it, delete it:
   `evnx migrate --to aws --secret-name prod/app --print-only > up.sh` — review,
   `sh up.sh`, `shred -u up.sh`.
2. **Prefix the command with a space** if your shell is configured with
   `HISTCONTROL=ignorespace`, so it is not recorded.

`--dry-run` is not a mitigation. It still previews values.
</Callout>

## Options reference

### General options

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--from` | `string` | — | Source: `env-file` or `environment`. Asked in a terminal; `env-file` without one |
| `--source-file` | `path` | `.env` | The `.env` to read. Overrides `[defaults] env_name`; cannot be combined with `--env-name` |
| `--env-name` | `string` | — | Read `.env.NAME`. A name with no file is an error listing the environments there are |
| `--to` | `string` | — | Destination slug. Asked in a terminal; required without one |
| `--dry-run` | `bool` | `false` | Preview the variable set and where it would go, without printing the commands themselves |
| `--print-only` | `bool` | `false` | Write only the commands to stdout; status and summary go to stderr |
| `--skip-existing` | `bool` | `false` | Leave secrets that already exist. **Only `github-actions` can honour this** — the others never ask the platform what exists, and refuse the flag |
| `--overwrite` | `bool` | `false` | Replace existing secrets without asking. Same caveat as above |
| `--yes`, `-y` | `bool` | `false` | Upload without asking "Proceed with migration?" (`github-actions`) |
| `--verbose`, `-v` | `bool` | `false` | Print diagnostic output during the run |
| `--quiet`, `-q` | `bool` | `false` | Leave only the commands, the summary, warnings and errors |

<Callout type="info">
**`--dry-run` needs the names, not the credentials.** It contacts nothing, so
`github-actions` runs without a token. But a name that would be printed into a
command — `--secret-name`, `--vault-name`, `--heroku-app`, `--project` for gcp,
`--repo` — is still required, because a preview with a placeholder in it is a
command that fails when you run it:

```text
Error: GCP project ID is required for this destination. Pass `--project`.
  --dry-run still needs it: without it evnx would print a command
  with a placeholder where the name should be.
```
</Callout>

### Filtering options

Applied before any secret reaches the destination, in this order:
include → exclude → strip prefix → add prefix.

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--include` | `glob,...` | — | Only keys matching at least one pattern are migrated. Example: `"DB_*,AWS_*"` |
| `--exclude` | `glob,...` | — | Keys matching any pattern are dropped. Example: `"*_LOCAL,*_TEST"` |
| `--strip-prefix` | `string` | — | Remove a leading prefix from every key. `APP_` turns `APP_DB_URL` into `DB_URL` |
| `--add-prefix` | `string` | — | Prepend a prefix to every key. `PROD_` turns `DB_URL` into `PROD_DB_URL` |
| `--allow-collisions` | `bool` | `false` | When two names become one, keep the last value instead of stopping |

Both prefixes must be letters, digits and `_`, not starting with a digit, so every
name stays a variable name; a strip that would leave an empty name, or one starting
with a digit, is refused.

<Callout type="success">
**A filter that matches nothing is an error — changed in v0.5.0.** `evnx migrate --to gcp
--project my-gcp-project --include 'DB_ *'` — note the typo — exits `2` and names the file:

```
Error: every one of the 2 variable(s) in .env was filtered out, so there is nothing to migrate.

Check --include / --exclude: a pattern that matches nothing leaves the destination untouched.
```

Until v0.5.0 it printed *"All secrets were filtered out"* and exited `0`, which in a
pipeline read as a completed migration. An empty source file is an error for the same
reason, and `evnx cloud run` treats a filter matching nothing this way too.
</Callout>

### Names that become one

`--strip-prefix API_` turns `API_X` and `X` into one `X`, and Azure Key Vault and
GitHub ignore case, so `DB_URL` and `db_url` are one secret there. One value would
be lost, so evnx stops before printing or sending anything:

```text
Error: these names become the same name after renaming, and one value would be lost:
  API_X, X → X
Rename one in the .env, migrate without --strip-prefix, or pass --allow-collisions to keep the last value. Nothing was printed or sent.
```

With `--allow-collisions` the last value wins, and evnx says which on stderr:

```text
! API_X, X → X: kept the value of X (--allow-collisions)
```

### Destination options

| Flag | Applies to | Description |
|------|-----------|-------------|
| `--repo` | `github-actions` | Repository as `owner/repo` |
| `--github-token` | `github-actions` | A token with the repository's Secrets permission. Prefer the `GITHUB_TOKEN` environment variable |
| `--secret-name` | `aws` | Secret name, e.g. `prod/myapp/config` |
| `--aws-profile` | `aws` | Named AWS CLI profile, added to the printed commands |
| `--project` | `gcp`, `doppler`, `infisical` | GCP project ID (required for gcp), Doppler project, or Infisical project ID |
| `--doppler-config` | `doppler` | Config name, e.g. `dev`, `staging`, `prd` |
| `--infisical-env` | `infisical` | Environment name, e.g. `dev`, `staging`, `prod` |
| `--vault-name` | `azure` | Azure Key Vault name |
| `--heroku-app` | `heroku` | Heroku application name |
| `--vercel-project` | `vercel` | Vercel project ID or name, printed as `--project` |
| `--railway-project` | `railway` | Railway project ID. Needs `--railway-environment` |
| `--railway-environment` | `railway` | Railway environment, e.g. `production` |
| `--railway-service` | `railway` | Railway service; default the linked one, or the project's only one |

Names are checked before anything is printed: a value that is not a valid name for
its platform — `--heroku-app 'x;rm'`, `--repo notarepo` — is refused with exit `2`,
naming the flag.

## Glob pattern syntax

| Pattern | Matches |
|---------|---------|
| `DB_*` | Any key starting with `DB_` |
| `*_SECRET` | Any key ending with `_SECRET` |
| `*_KEY_*` | Any key containing `_KEY_` |
| `P?RT` | `?` matches exactly one character |
| `DATABASE_URL` | Exact match only |
| `*` | Every key |

Patterns are case-sensitive. Multiple patterns are comma-separated.

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Completed — commands generated, or an upload finished |
| `1` | `--to github-actions` ran, and at least one upload failed (**v0.10.3+**) |
| `2` | Did not run. Unknown destination, missing or empty source file, a filter that matched nothing, a missing or invalid name, names that collide, values a destination would misread, a flag the destination cannot honour, or an argument error |

<Callout type="info">
  evnx's contract is `0` clean · `1` findings · `2` could not run. For `migrate`, `1`
  means it ran and some uploads failed: before v0.10.3 it listed "✗ 1 failed" and
  exited `0`, so a step that migrated half its secrets passed. **Gate on non-zero.**

  ⚠️ Until v0.5.0 this table listed a `1` row, and `0` was also returned when filtering
  left nothing to do. Both were wrong.
</Callout>

## Why it works this way

Generating commands instead of uploading is a trade, and it is worth knowing
which side you are on.

**What it buys you.** evnx never needs credentials for the destination. There is
no AWS key, no GCP service account and no Azure client secret for it to ask for,
hold, or leak. The command runs under the CLI you have already authenticated,
with exactly your permissions and your audit trail. For a tool whose premise is
that it cannot read your secrets, not collecting nine more sets of cloud
credentials is the consistent choice.

It also means the output is reviewable. You see precisely what would be created
before anything is, which for a one-time operation against production is worth
more than saving a copy-paste.

**What it costs you.** evnx itself cannot finish the job in a pipeline — it prints;
something has to run what it prints. `--skip-existing` and `--overwrite` cannot
work, because evnx never asks the platform what is already there. And the values
pass through your terminal unless you use `--print-only` and a file.

`github-actions` is uploaded because it can be done without a cloud credential:
one GitHub token scoped to the repository's secrets is enough, and the values are
sealed to the repository's public key before they are sent.

<Callout type="info">
**Wider upload support is not currently planned.** The cheap cases — Doppler,
Infisical, Vercel and Heroku are all token-and-REST — would be a few hundred
lines each. AWS, GCP and Azure would each need their own cloud authentication
flow, which is the part that carries real risk.

The reason it is parked is leverage rather than difficulty: migration happens
roughly once per project, while injecting secrets into a process —
[`evnx cloud run`](/guides/commands/cloud), with no file on disk — happens every
day. If you want upload support for a specific destination, saying which one is
genuinely useful.
</Callout>
