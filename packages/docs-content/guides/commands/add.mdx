# evnx add — Command Reference

Add the variables a service, framework or whole stack needs to `.env.example`
and `.env`, or your own, without retyping them. `add` uses the same catalogue
and section headings as `evnx init`. Names already there are skipped, and a
value you have set is never replaced.

  <Prerequisite href="/guides/getting-started/installation">Install evnx</Prerequisite>

## Command signature

```bash
evnx add <SUBCOMMAND> [ID] [OPTIONS]
evnx add --list
```

### Subcommands

| Subcommand | Takes | Adds |
|------------|-------|------|
| `service` (alias `infra`) | any catalogue id: a service (`postgresql`), an infrastructure target (`vercel`) or a framework (`nextjs`) | that component's variables |
| `framework` | a framework id; `--language` is optional | the framework's variables |
| `blueprint` | one of the stack ids | the whole stack |
| `custom` | `NAME=value` or `NAME` arguments, or nothing to be asked | your own variables |

Leave the id out in a terminal (`evnx add blueprint`) and `add` offers a list
to pick from. `evnx add --list` prints every id.

### Options

| Flag | Description |
|------|-------------|
| `--path`, `-p` | Folder holding `.env.example` and `.env` (default `.`) |
| `--env-name <NAME>` | **v0.11.0+** — write to `.env.<NAME>` instead of `.env`, one file per run (loop over names for several). Defaults to `[defaults] env_name` |
| `--yes`, `-y` | Do not ask; needed in scripts and CI |
| `--dry-run` | Show what would be added, skipped and kept; write nothing |
| `--json` | Print the result as one JSON document (with `--yes` or `--dry-run`) |
| `--list` | List every id `add` takes |
| `--language`, `-l` | `framework` only: check that the framework belongs to this language |
| `--desc`, `--category`, `--required` | `custom` only: applied to every name given |
| `--verbose`, `-v` | Say which files were appended to |
| `--quiet`, `-q` | Print only warnings, conflicts and errors |
| `--no-color` | Plain output (as `NO_COLOR` does) |

---

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | variables added, or nothing to do: they were already there, it was a `--dry-run`, or you answered `n` |
| `2` | stopped: an unknown id or language, a bad argument, no terminal to ask (add `--yes`), or a write error (for example a read-only `.env`, or `--path` pointing at a folder that does not exist) |

<Callout type="info">
Earlier versions of this page said `1` for an unknown service and `2+` for runtime errors. Every one of
those cases exits `2`, the same code evnx uses for "did not finish" across commands. Scripts should test
for non-zero, or for `2`.
</Callout>

## Examples

### A service, then the same one again

```console
$ evnx add service postgresql --yes
✓ Added 6 variables for PostgreSQL

$ evnx add service postgresql --yes
· Nothing to add: 6 variables for PostgreSQL already in .env.example
```

### A framework, and an id from another group

```console
$ evnx add framework nextjs --yes
✓ Added 4 variables for Next.js

$ evnx add infra vercel --yes
· vercel is an infra component; adding it.
✓ Added 4 variables for Vercel

$ evnx add framework --language python nextjs --yes
Error: Unknown framework 'nextjs' for language 'python'.

nextjs is a javascript_typescript framework: use --language javascript_typescript, or leave --language out.
```

### Your own variables

```console
$ evnx add custom API_URL=https://api.example.com DEBUG=false --yes
✓ Added 2 custom variables

$ evnx add custom STRIPE_WEBHOOK_SECRET --desc "Stripe webhook signing secret" --category security --required --yes
✓ Added 1 custom variable
```

```env
# ── Custom Variables ──

# [Security] Stripe webhook signing secret (required)
STRIPE_WEBHOOK_SECRET=YOUR_KEY_HERE
```

A name given without a value gets the same placeholder in both files. Given a value
(`API_URL=https://api.example.com`), the value goes into `.env` only, and
`.env.example` — the file you commit — gets a placeholder (**v0.10.3+**; the value
used to go into both). If `.env` does not exist, it is created, readable by you
only, and `.gitignore` is updated first (**v0.10.4+**; 0.10.3 created this `.env`
without touching `.gitignore`).

A name without `=value` gets a placeholder. When it looks like a secret
(`*_SECRET`, `*_TOKEN`, `*_KEY`, `*_PASSWORD`, `*_PWD`, …) and you run `add` in a
terminal without `--yes`, it asks for the value instead, without echoing it.
Public values such as `SENTRY_DSN` or `API_URL` are not hidden.

<Callout type="warning">
A value given as an argument lands in your shell history. For a real secret,
give the name alone and type the value at the hidden prompt, or fill it in
`.env` afterwards.
</Callout>

With no arguments, `evnx add custom` asks for each variable: its name, its
value, and `More options? (description, category, required)`. An empty name
finishes. A secret-looking name's value is read without echo here too
(**v0.10.4+**), and Enter keeps the placeholder:

```text
Value for STRIPE_WEBHOOK_SECRET (hidden; .env only; Enter for YOUR_KEY_HERE): [hidden]
```

The final question names every file the run writes, for example
`Append these variables to .env.example and .env?`.

### A blueprint, into a project of its own folder

```bash
evnx add blueprint t3_modern --path ./apps/web --yes
```

## What `add` writes

The template is the project's own (**v0.10.16+**): `[defaults] example` in `.evnx.toml`
if set, otherwise whichever of `.env.example`, `.env.sample` or `.env.template` exists,
and `.env.example` when there is none.

| File | What happens |
|------|--------------|
| the template (`.env.example`) | The names it lacks are appended, under the same section headings `init` writes, with a `# Added by evnx add on <date>` line |
| `.env` | The names it lacks are appended with their placeholders. A name it already has is left alone, so a value you set stays the one in effect |
| `.env`, when there is none | Created as a copy of `.env.example`, as `evnx init` does: asked in a terminal, done under `--yes` |
| `.gitignore` | Written only when `add` creates `.env` (`.gitignore` first). Otherwise checked: `add` warns if the `.env` it wrote to could be committed |

```console
$ evnx add service redis --yes
✓ Created .gitignore with .env*, !.env.example, !.env.sample, !.env.template
✓ Created .env from .env.example
✓ Added 5 variables for Redis
```

<Callout type="warning">
**Before 0.10.2, `add` wrote every name again on every run.** A second
`evnx add service redis` put `REDIS_URL` twice into both files, and because
dotenv uses the last assignment, the placeholder appended to `.env` replaced
the value you had set. 0.10.2 checks each file first.
</Callout>

### Names already there, and different values

Each name is checked in each file:

| In `.env.example` | What `add` does |
|-------------------|-----------------|
| missing | appended (and to `.env` if `.env` lacks it) |
| present, same value | skipped |
| present, different value | kept as it is, listed, and not added to `.env` either |

`.env` catches up with names `.env.example` already had. Values in `.env` are
never compared or printed: they are yours, and differ from the placeholders by
design.

```console
$ evnx add service redis --yes
! 1 variable with a different value in .env.example: kept as it is
  • REDIS_URL (existing: "redis://cache.internal:6379/0", new: "redis://localhost:6379/0")
✓ Added 4 variables for Redis, skipped 1 already present
```

### Browser copies

In a Vite, Next.js, SvelteKit, Nuxt or Laravel project (`add` reads
`package.json` the way `init --detect` does), the values a browser may see get
a prefixed copy, exactly as `init --with` writes them:

```console
$ evnx add service supabase --yes
· vite found (package.json): adding 2 VITE_ copies for the browser
✓ Added 6 variables for Supabase
```

Only values designed to be public get a copy (a project URL, an anon or
publishable key, a client id, a DSN). Secrets never do.

## Scripts, CI and agents

Give `--yes`, or check first with `--dry-run`, which needs no terminal and
writes nothing:

```console
$ evnx add service redis --dry-run
Dry run (for Redis): nothing was written.
  .env.example: would add 4 variables: REDIS_DB, REDIS_HOST, REDIS_PASSWORD, REDIS_PORT
  different value, would keep: REDIS_URL (existing: "redis://cache.internal:6379/0", new: "redis://localhost:6379/0")
  .env: would add 4 variables: REDIS_DB, REDIS_HOST, REDIS_PASSWORD, REDIS_PORT
```

`--json` prints one document and nothing else on stdout. This is the same dry run, in a
folder whose `.env.example` already holds a different `REDIS_URL` (evnx 0.10.18):

```console
$ evnx add service redis --dry-run --json
{
  "added": [
    "REDIS_DB",
    "REDIS_HOST",
    "REDIS_PASSWORD",
    "REDIS_PORT"
  ],
  "conflicts": [
    {
      "existing": "redis://cache.internal:6379/0",
      "name": "REDIS_URL",
      "new": "redis://localhost:6379/0"
    }
  ],
  "contract": {
    "action": "none",
    "added": [],
    "file": null
  },
  "dry_run": true,
  "env_added": [
    "REDIS_DB",
    "REDIS_HOST",
    "REDIS_PASSWORD",
    "REDIS_PORT"
  ],
  "env_committable": false,
  "env_created": false,
  "gitignore": [],
  "notices": [],
  "skipped": [],
  "template": ".env.example",
  "written": false
}
```

`template` names the file `add` wrote to (see below), `contract` says what happened to
`[vars]` in `.evnx.toml` (`none` here: the project has no `.evnx.toml`), `gitignore`
lists the lines added to `.gitignore`, and `notices` carries the warnings the pretty
output prints.

Without a terminal and without `--yes`, `add` stops and says what to run:

```console
$ evnx add service twilio
Error: there is no terminal to confirm with.

Add --yes to write without asking:
  evnx add service twilio --yes
```

## Environment variables

| Variable | Values | Default | Description |
|----------|--------|---------|-------------|
| `NO_COLOR` | any value | unset | Disable coloured output ([no-color.org](https://no-color.org/)) |

<Callout type="warning">
This table used to list `CI`. **evnx never read it.** Whether `add` can ask is
decided by whether stdin is a terminal. In CI it is not, so pass `--yes` (or
`--dry-run`); without one, `add` stops with exit 2 and says so.
</Callout>

## Keeping the contract current

When the project has a [contract](/guides/commands/spec), `add` records what it
introduces in `[vars]` of `.evnx.toml`:

```console
$ evnx add service redis --yes
  config    .evnx.toml
  ✓ added 5 variable(s) to [vars] in .evnx.toml
✓ Added 5 variables for Redis
```

The `config` line names the file from where you are (`../.evnx.toml` from a
subfolder); a symlinked config is written through, with a notice. New names are
recorded the way `evnx spec init` infers them (**v0.10.6+**): a format the
catalogue's example value would fail is left out, and a URL with a password in
it, or a `*_PWD` name, is declared secret.

It **only appends**: a name already declared is left exactly as it is, so a
hand-written `required = false` survives an unrelated `evnx add`. With `--path`,
the contract is the nearest `.evnx.toml` at or above that folder. A project with
no `.evnx.toml` sees nothing. One with a config but no `[vars]` gets a note on
stderr pointing at `evnx spec init`, never an error. An inline
`vars = { … }` table cannot be extended, and `add` says so.
