```bash
evnx commands
```

Lists every command **this** binary has, grouped, with the optional features it was compiled with.

<Callout type="warning">
**"This binary" is the whole point.** `cloud`, `migrate` and `backup` are optional Cargo features, so two installs reporting the same version can have very different command sets — and `--version` cannot tell you which one you have.
</Callout>

---

## What it prints

```
  evnx 0.10.0
  built with: net, migrate, backup, cloud

  On this machine
    init         Interactive project setup — generates .env.example
    scan         Detect secrets that look real (AWS keys, tokens, etc.)
    …

  With an evnx account
    auth         Manage your evnx cloud account
    vault        Manage encrypted vaults
    …

  80 commands. `evnx <command> --help` for any of them.
```

## When a command is "missing"

If `evnx vault` reports *unrecognized subcommand*, one of two things is true, and this command tells you which.

### Your build has no cloud feature

```
  ! This build has NO cloud commands — no auth, vault, cloud or org.
    It was compiled without the `cloud` feature.
```

<Callout type="info">
Every prebuilt binary carries the cloud commands — npm, Homebrew, Scoop, winget and the GitHub Release are all built with `--all-features`.

⚠️ **PyPI did not, up to and including 0.9.0.** `pip install evnx` and `pipx install evnx` gave a binary with no `auth`, `vault`, `cloud` or `org` at all, from 0.4.0 onward. Fixed from 0.10.0.

`cargo install evnx` is the other exception, and it is deliberate — it compiles from source with no features. Use `cargo install evnx --features cloud`.
</Callout>

### A different evnx is answering

The commands are there; you are running a different binary.

```bash
which -a evnx
```

If more than one path appears, the first one wins. A package-manager install often sits ahead of `~/.cargo/bin`, so `cargo install` appears to succeed while the old binary keeps answering.

`evnx commands` run through an explicit path tells you what that specific binary has:

```bash
~/.cargo/bin/evnx commands
```

## For tooling

```bash
evnx commands --json
evnx commands --json --compact
```

The whole command tree: paths, flags, aliases, the feature list, and the documentation URL for each top-level command.

<Callout type="info">
⚠️ It is generated by walking the CLI's own argument parser, so it cannot disagree with the binary. That is what it is for — `app.evnx.dev/tour` and the documentation checks are built from it rather than from a hand-written list, because five documentation errors in this project came from exactly such a list drifting.

The payload carries a `schema` number. Check it: the shape may change, and that is not a breaking change to the command.
</Callout>

<Callout type="warning">
**Do not parse the plain output.** It is for people, it carries no compatibility promise, and `--json` exists so you never have to.
</Callout>

ⓘ `evnx surface` is an alias, kept because tooling already calls it that.
