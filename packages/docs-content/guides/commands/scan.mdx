`evnx scan` finds values that look like real secrets — provider keys, tokens, private keys, passwords in connection strings — before they leave your machine. A folder scan reads every file, not only `.env`, and in a git repository it counts what git would commit. It is built for pre-commit hooks and CI, and it never touches the network. Every output on this page is from evnx 0.14.0.

## Upgrading from 0.13

<Callout type="info" title="What changed in 0.14.0">
Run `evnx scan` once on a branch before you rely on it in CI: a project can see **new
findings** (names are now checked in more files, notebooks are read, `ghs_` tokens are
matched) and **fewer false ones**.

| What changed | What to do |
|---|---|
| **Jupyter notebooks are read cell by cell**, so a key in a cell or an output is found, located by cell | A notebook that scanned clean may not. See [Jupyter notebooks](#jupyter-notebooks) |
| **Names are checked in Dockerfiles, Containerfiles, shell scripts and Python modules** | `ENV DB_PASSWORD=<random>` is now a `sensitive-config-key` finding. See [Names in Dockerfiles, shell and Python](#names-in-dockerfiles-shell-scripts-and-python) |
| **A secret behind a public prefix is one severity level higher** (`low` stays `low`) | A `--severity high` gate can start failing on a `NEXT_PUBLIC_` or `VITE_` finding. See [Variables your build publishes to the browser](#variables-your-build-publishes-to-the-browser) |
| **`github-token` matches stateless `ghs_` tokens** (GitHub's Actions `GITHUB_TOKEN` and app installation tokens, since 2026-10-02) | A `ghs_<appid>_<JWT>` token of about 520 characters is reported once, as `github-token` |
| **Fewer false positives**: PEM bodies, public keys, `pk_` keys, Helm and Kubernetes references | A baseline entry for one of these is no longer needed. See [What is not reported](#what-is-not-reported) |
| **Files are scanned in parallel** | Same output at any thread count. `RAYON_NUM_THREADS=N` caps it. See [Scanning a whole project](#scanning-a-whole-project) |
| **`[scan] exclude` patterns with a `/` are read from the folder holding `.evnx.toml`** | See [Configuring scan in `.evnx.toml`](#configuring-scan-in-evnxtoml) |
| The baseline fingerprint of a notebook finding now includes its cell path | Regenerate a baseline that holds notebook findings |
</Callout>

## Upgrading from 0.12

<Callout type="warning" title="⚠️ A --severity high gate can start failing, and JSON consumers must change">
0.13.0 changes what `scan` reports and what its flags mean. Run it once on a branch before
you rely on it in CI.

| What changed | What to do |
|---|---|
| **`--severity` now filters on risk** (how bad if real: `critical`, `high`, `medium`, `low`). Until 0.12 it filtered on confidence | For the old behaviour add `--confidence high`. `--severity high` keeps almost exactly what it kept before |
| **`--format json` is `schema_version: 2`.** Each finding has `rule_id` and `severity`; `confidence` is unchanged | A script that read `confidence` as severity must read `severity` |
| **SARIF `ruleId` is the stable rule id** (`aws-access-key`, was `secret/aws-access-key`) | GitHub code scanning shows existing alerts as new rules once |
| **63 built-in rules** (13 in 0.12) and **names are checked inside YAML, JSON and TOML** | More findings. Adopt them with a [baseline](#a-baseline-for-findings-you-already-have) or [allow markers](#allow-markers-one-rule-one-line-one-reason) |
| **A short value under a secret-like name** (`API_TOKEN=abcd1234`) is now `high` severity | A `--severity high` gate now fails on it. `--confidence high` restores the old result |
| **A `[[scan.patterns]]` rule with no `severity` is `medium`** | Add `severity = "high"` to keep it inside a `--severity high` gate |
| **Clerk and UploadThing `sk_live_` keys have their own rule ids** (`clerk-secret-key`, `uploadthing-secret-key`), no longer `stripe-live-secret-key` | Update baselines and `evnx:allow stripe-live-secret-key` markers on those lines, or the finding comes back |
| **The entropy fallback threshold is 4.3**, was 4.8, and only judges base64 and URL-safe values | Usually fewer findings: lockfile hashes are no longer reported |
</Callout>

## Command signature

```bash
evnx scan [OPTIONS] [PATH]...
evnx scan rules <list|new|test|add|update|remove>
evnx scan hook <install|uninstall|status>
```

A folder literally named `rules` or `hook` is scanned as `evnx scan ./rules`.

**Options:**

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `[PATH]...` | positional | `.` | Files or directories to scan. Repeatable: `evnx scan .env config/`. `-` reads stdin (**v0.11.0+**) |
| `--format` | `pretty\|json\|sarif\|github` | `pretty` | Output format. **An unrecognised value is an error** — it used to fall back to `pretty` silently |
| `--severity` | `critical\|high\|medium\|low` | `low` | **v0.13.0+** — lowest **severity** (how bad if real) worth reporting. Filters the findings, the counts and the exit code together. Until 0.12 this filtered on confidence |
| `--confidence` | `high\|medium\|low` | `low` | **v0.13.0+** — lowest **confidence** (how sure evnx is) worth reporting. Must pass together with `--severity` |
| `--staged` | `bool` | `false` | **v0.13.0+** — scan what the next commit records, read from the git index. See [Staged scans and the pre-commit hook](#staged-scans-and-the-pre-commit-hook) |
| `--baseline` | file | `.evnx/baseline.json` if it exists | **v0.13.0+** — findings accepted earlier; matching ones are `known` and do not fail the run |
| `--update-baseline` | `bool` | `false` | **v0.13.0+** — write this run's findings to the baseline and exit 0 |
| `--rules` | file | — | **v0.13.0+** — a rule file for this run, on top of `.evnx/rules/` and your personal rules. Repeatable |
| `--exit-zero` | `bool` | `false` | Suppress exit 1 (findings). Exit 2 still happens |
| `--exclude` | `string[]` | `.env.example` | Paths to skip in a folder walk. A value with `*`, `?` or `[` is a glob; any other value matches a **whole path component**. Adds to `[scan] exclude` |
| `--max-file-size` | size | `1MiB` | **v0.10.14+** — skip walked files larger than this (`500K`, `5MB`, `2MiB`). A file you name is read whatever its size |
| `--include-ignored` | `bool` | `false` | **v0.10.14+** — count findings in files git ignores and does not track |
| `--extensions` | `string[]` | — | **v0.10.3+** — read only files with these extensions in folders (`env,yml,json`). Opt-in, and announced on every run |
| `--pattern` | `regex[]` | `[]` | Also report values matching this expression. Repeatable. Combines with `[[scan.patterns]]` |
| `--ignore-placeholders` | `bool` | `false` | Skip values that look like placeholders (`changeme`, `your_key_here`) |
| `--no-ignore-placeholders` | `bool` | `false` | Report them even when `[scan] ignore_placeholders` is `true`. The last of the two flags wins |
| `-q`, `--quiet` | `bool` | `false` | Print nothing when clean. Findings, and the line saying a scan was narrowed, still print |
| `-v`, `--verbose` | `bool` | `false` | Show the rules in force, each file read, and the allowed and known findings |

<Callout type="warning">
`--path`, `--recursive`, `--ignore`, `--include-example`, `--output` and `--exit-code`
have appeared on this page in the past. **None of them exist.** Paths are positional,
scanning is already recursive, and the advisory flag is `--exit-zero`.

Redirect instead of `--output`: `evnx scan --format sarif > results.sarif`.
</Callout>

## What evnx scans for

### Built-in rules

evnx ships **63 rules** (**v0.13.0+**; 13 in 0.12). A rule is in the core only when the
provider documents a fixed prefix, or a fixed length and character set. Each has a stable
`id` (`aws-access-key`), a `provider`, a `category` and a test that must match and a near
miss that must not. Providers whose keys have no documented shape (Postmark, Cloudflare,
Datadog) are left out on purpose; add a [pack](/guides/reference/scan-rules-and-packs) or
your own rule for them.

| Category | Rules | Examples |
|---|---:|---|
| `source-ci` | 12 | GitHub, GitLab, npm, PyPI, Docker Hub, Azure DevOps, Bitbucket |
| `cloud` | 8 | AWS, Azure storage and SAS, DigitalOcean, Heroku, Fly.io, Google API key |
| `messaging-email` | 7 | Twilio, SendGrid, Mailgun, Slack, Discord, Telegram |
| `ai` | 7 | OpenAI, Anthropic, Hugging Face, Groq, xAI, Replicate, Perplexity |
| `saas` | 6 | Shopify, Linear, Atlassian, Postman, Notion, UploadThing |
| `observability` | 5 | Sentry, New Relic, Grafana |
| `payments` | 4 | Stripe live, test, restricted and webhook secrets |
| `keys-certificates` | 4 | PEM and OpenSSH private keys, age, JSON Web Token |
| `databases-backends` | 4 | Connection strings with a password, Supabase |
| `infra-secrets` | 4 | HashiCorp Vault, HCP Terraform, Pulumi, Doppler |
| `auth` | 2 | Clerk |

`evnx scan rules list` prints all of them with provider, severity and confidence.
`--category ai` filters (see [Rules](#rules-in-short)). PKCS#12 keystores (`.p12`, `.pfx`)
are reported by their content as `pkcs12-keystore`.

Three more checks are **not** rules, because none can be expressed as one:

| Check | How it decides |
|---|---|
| `Sensitive config key` | The variable's **name** looks like a secret (`*_SECRET`, `*_TOKEN`, `PASSWORD` …). The value was not checked against a provider format, and the output says so |
| `AWS Secret Access Key` | 40 base64-ish characters **and** a variable name containing `AWS` **and** entropy above 4.3. The shape alone matches any 40-character token, so the name is part of the test |
| `High-entropy string` | The last resort: a long random-looking value with no other explanation |

**GitHub's stateless tokens** (**v0.14.0+**). Since GitHub finished its rollout on
2026-10-02, a `ghs_` token (the Actions `GITHUB_TOKEN` among them) is
`ghs_<appid>_<JWT>`, about 520 characters, and the classic 36 to 40 character shape missed
it. The `github-token` rule keeps the classic branch and has a second for this form. It is
reported once, as `github-token`, not also as `jwt` or `high-entropy-string`, and a trailing
`.`, `,` or `)` is not part of the match.

**Stand-ins are never findings** (**v0.10.14+**). AWS's documented example keys
(`AKIAIOSFODNN7EXAMPLE`) and placeholder-shaped values are recognised and skipped, and a
name-only match on a value that is an address (a URL, a host) is dropped.

<Callout type="info" title="Why test keys with a generated value">
Because AWS's example key is skipped, a hook test that uses it passes and proves nothing.
Generate a live-format value on the spot instead, as
[Prevent secret leaks](/guides/use-cases/prevent-secret-leaks) does.
</Callout>

### Names in YAML, JSON and TOML

**v0.13.0+.** A structured file used to be read as plain text, so `password: <a real
password>` in `config.yml` scanned clean. Now each string value in a `.yml`, `.json` or
`.toml` file is checked by its **key and its value**, and reported with its line and key
path:

```text
  ✗  Sensitive config key: password              high, medium confidence
     ./config.yml:2 (db.password)  Hun…Z9q
     ·  flagged by variable name — the value was not checked
```

The line rules still run, comments included, and a value both paths find is one finding.
References (`${VAR}`) and non-string values are skipped, as in a `.env`. A file that does
not parse (a Helm template with `{{- if }}`) is read as text, never an error: `-v` says so,
and the JSON `files[]` entry reads `"read_as": "text"` with a `note`. Files that parsed
report `"read_as": "structured"`.

### Names in Dockerfiles, shell scripts and Python

**v0.14.0+.** A file read as text used to be judged by value alone, so
`ENV DB_PASSWORD=<random>` in a Dockerfile scanned clean. These now get the **name check**,
with the placeholder, empty-value and reference filters a `.env` line gets, and are reported
as `sensitive-config-key` on the right line:

| File | Assignments checked |
|---|---|
| `Dockerfile`, `Containerfile` | `ENV KEY=value`, `ENV KEY value`, `ARG KEY=value`, and continuation lines |
| `.sh`, `.bash`, `.zsh` or a `#!` script | `export KEY="value"` and `KEY=value` |
| `.py` | `KEY = "value"` |

Never flagged: `ARG X` with no value, `$VAR`, `${VAR}`, `$(cmd)`, backticks,
`os.environ[...]`, `os.getenv(...)`, `settings.X`, f-strings, empty strings and placeholders.
A commented-out assignment is left to the value rules. `evnx scan -v` says which reading a
file got:

```text
⋯ Scanning: ./Dockerfile (read as text: value patterns, and names in assignments)
⋯ Scanning: ./analysis.ipynb (read as structured data: names and values checked)
```

Other text files keep `read as text: value patterns only, names not checked`. In JSON,
`read_as` stays `text`.

### Jupyter notebooks

**v0.14.0+.** A notebook is JSON, so a key in a cell or an output sat behind string escapes
and was missed. Each cell's `source` (code and markdown) and each output's `text`,
`data["text/plain"]` and `traceback` are now read unescaped, and a finding is located **by
cell**: the line is within that cell or output, and the path in brackets says which.

```text
  ✗  Stripe Secret Key (LIVE)                    critical
     ./analysis.ipynb:2 (cells[2].outputs[0].text)  sk_l…LRkB
     !  matches a live key format, not a placeholder
     →  revoke at https://dashboard.stripe.com/apikeys
```

Image output is not read. A notebook that does not parse is scanned as text, as before. The
[baseline](#a-baseline-for-findings-you-already-have) fingerprint of a notebook finding
includes its cell path.

### Providers that share a prefix: name-aware rules

**v0.13.0+.** Clerk and UploadThing keys start with `sk_live_`, the same as Stripe's.
A rule can carry `names` — regexes matched against the variable or key name — and then
fires only where the name matches, and wins over an unconstrained rule on the same value:

| The line | Reported as |
|---|---|
| `CLERK_SECRET_KEY=sk_live_…` | `clerk-secret-key` (revoke at Clerk's dashboard) |
| `UPLOADTHING_SECRET=sk_live_…` | `uploadthing-secret-key` |
| `STRIPE_SECRET_KEY=sk_live_…`, any other name, or plain text | `stripe-live-secret-key` |

```text
  ✗  Clerk Secret Key (LIVE)                     critical
     ./clerk.env:1 (CLERK_SECRET_KEY)  sk_l…3dF6
     !  matches a live key format, not a placeholder
     →  revoke at https://dashboard.clerk.com
```

Your own rule files can use `names` too; see the
[rule file format](/guides/reference/scan-rules-and-packs#the-rule-file-format).

### High-entropy detection

The fallback for a secret with no provider prefix reports a value that is long, made of
base64 or URL-safe characters, and has Shannon entropy above **4.3** (**v0.13.0+**; was
4.8). Measured on a corpus, 4.8 caught only 2 to 4 percent of random 32-character keys;
4.3 catches 95 percent or more of them and no hash, UUID or checksum in the test corpus.
npm `sha512-` integrity hashes are excluded, hex values are never judged this way (their
entropy is that of a SHA), and a variable named like a public key (`PUBLIC_KEY`) is not
judged by entropy. On a real repository this lowers the count: evnx-web went from 847
entropy findings to 7.

The threshold is not configurable.

<Callout type="info" title="Why entropy matters">
A string like `wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY` scores high on Shannon entropy because its characters are distributed almost uniformly — a property of cryptographically random strings. Human-readable values like `my-app-name` score low.
</Callout>

<Callout type="warning" title="Multiline values: fixed in v0.8.0">
Before v0.8.0 a secret inside a multiline value, such as a PEM private key, was not reported
at all. If you relied on `scan` in a hook or CI from before then, re-run it once.
</Callout>

### Variables your build publishes to the browser

Some prefixes are instructions to a bundler: inline this value into the JavaScript that
ships to every visitor. A secret behind one of them is not at risk of leaking — it **has
already leaked**, to everyone who has ever loaded the site.

evnx recognises nine: `NEXT_PUBLIC_` (Next.js), `NUXT_PUBLIC_` (Nuxt), `EXPO_PUBLIC_`
(Expo), `REACT_APP_` (Create React App), `STORYBOOK_`, `GATSBY_`, `VUE_APP_` (Vue CLI),
`VITE_` (Vite) and `PUBLIC_` (SvelteKit and Astro).

```text
  ✗  Stripe Secret Key (LIVE)                    critical
     .env.local:1 (NEXT_PUBLIC_STRIPE_KEY)  sk_l…3dF6
     !  matches a live key format, not a placeholder
     !  NEXT_PUBLIC_ is inlined into the client bundle by Next.js — anyone who loads your site can read this
     →  rename to STRIPE_KEY and read it server-side
     →  revoke at https://dashboard.stripe.com/apikeys
```

The finding gains a note, the JSON gains `"public_prefix": "NEXT_PUBLIC_"`, and the remedy
says to rename. **v0.14.0+** — the prefix also **raises the severity one level**: a GitHub
token that is `high` in `GH_TOKEN` is `critical` in `NEXT_PUBLIC_GH_TOKEN`. `low` stays `low`,
because a Maps browser key or a Sentry DSN is meant to ship. (Before 0.14.0 the prefix did
not change a severity.) A Stripe key is already `critical`, so behind `VITE_` it stays so. A value recognised **by shape alone** (the entropy check, an unrecognised token)
is reported at least `medium`, not higher, because plenty of keys behind these prefixes are
meant to be public — a PostHog key, a Sentry DSN, a Supabase anon key. The remedy for those
asks you to check whether they are meant to be public before rotating anything.

[`evnx validate`](/guides/commands/validate#public_secret-a-secret-in-the-client-bundle)
reports the same mistake as an error, `public_secret`, before the value reaches a scan.
`--ignore public_secret` skips it there.

<Callout type="warning" title="Renaming is the fix; rotating alone is not">
While the name carries the prefix, **every build republishes the value.** Revoking and
reissuing without renaming just publishes the new key too. Rename it, read it server-side,
then rotate. `PUBLIC_` is deliberately broad: `PUBLIC_KEY`, the public half of a keypair,
matches it, and a false note costs less than silence on a published secret.
</Callout>

## Severity and confidence

**v0.13.0+.** A finding has two levels that answer different questions:

| | Answers | Values | Flag |
|---|---|---|---|
| **severity** | How bad is it if this is real? | `critical`, `high`, `medium`, `low` | `--severity` |
| **confidence** | How sure is evnx that it is real? | `high`, `medium`, `low` | `--confidence` |

Both filters apply together and change the findings, the counts and the exit code at once.
Defaults are `low` for both (report everything), or `[scan] severity` and `[scan] confidence`
in `.evnx.toml`.

A Google Maps browser key shows why they are separate. Its format is unmistakable, so
confidence is `high`; it is meant to ship in a web page, so severity is `low`:

```text
$ evnx scan maps.env
  ·  Google API Key                              low
     maps.env:1 (GOOGLE_MAPS_KEY)  AIza…5qRs
     !  matches a live key format, not a placeholder
     →  revoke at https://console.cloud.google.com/apis/credentials

  1 finding  ·  1 low

$ evnx scan maps.env --severity high
  ✓  No secrets detected
```

Rough guide: `critical` for cloud, payment and AI keys and private keys; `high` for account
tokens, database passwords and variables named like a secret; `medium` for tokens that are
often public-facing; `low` for test keys and keys meant to ship in a web page. The usual CI
gate is `--severity high`.

`API_TOKEN=abcd1234` is `high` severity at medium confidence, because a variable named like
a secret holds something. Adding `--confidence high` drops it, which is the pre-0.13
behaviour of `--severity high`:

```text
$ evnx scan --severity high --confidence high -q
  ✗  AWS Access Key                              critical
  ✗  Stripe Secret Key (LIVE)                    critical
  ✗  GitHub Token                                high
  ✗  Credentials in a connection string          high
  ✗  Clerk Secret Key (LIVE)                     critical
  5 findings  ·  3 critical  ·  2 high
```

(The `Sensitive config key: API_TOKEN` and `Sensitive config key: password` findings in the same folder are gone: a name match is medium confidence.)

## Output formats

### Pretty (default)

```bash
evnx scan
```

```text
  evnx scan  Checking for exposed secrets

  scanning ./.env, ./.gitignore, ./clerk.env and 2 other files

  ✗  AWS Access Key                              critical
     ./.env:1 (AWS_ACCESS_KEY_ID)  AKIA…5WZC
     !  matches a live key format, not a placeholder
     →  revoke at https://console.aws.amazon.com/iam

  ✗  Credentials in a connection string          high
     ./.env:4 (DATABASE_URL)  post…5432
     !  a password in a postgresql:// URL, not a placeholder

  ✗  Sensitive config key: API_TOKEN             high, medium confidence
     ./.env:5 (API_TOKEN)  ab…34
     ·  flagged by variable name — the value was not checked

  8 findings  ·  3 critical  ·  4 high  ·  1 medium
```

(Three of the eight findings shown.) The level beside a name is the **severity**; when
confidence is not `high` it follows. A value is only ever shown as a short preview
(`AKIA…5WZC`; under 8 characters it is `<n chars>`). Findings are sorted by file and line,
and one credential is one finding. The "Next steps" follow git: for a file git ignores and
does not track, they say nothing was committed instead of telling you to rewrite history.

### JSON

```bash
evnx scan --format json
```

```json
{
  "schema_version": 2,
  "files_scanned": 5,
  "files": [
    { "path": "./.env", "read_as": "dotenv" },

  ],
  "unreadable": [],
  "skipped": [],
  "secrets_found": 8,
  "findings": [
    {
      "rule_id": "aws-access-key",
      "status": "new",
      "fingerprint": "00a61dedd9c3822a221de0a2f30cb7c44aec5d384c1e520d0b7fe508427f94fa",
      "pattern": "AWS Access Key",
      "confidence": "high",
      "severity": "critical",
      "value_preview": "AKIA…5WZC",
      "location": "./.env:1 (AWS_ACCESS_KEY_ID)",
      "variable": "AWS_ACCESS_KEY_ID",
      "action_url": "https://console.aws.amazon.com/iam",
      "matched_by": "value",
      "git": "tracked"
    }
  ],
  "high_confidence": 6,
  "medium_confidence": 2,
  "low_confidence": 0,
  "summary": {
    "total": 8,
    "high": 6,
    "medium": 2,
    "low": 0,
    "severity": { "critical": 3, "high": 4, "medium": 1, "low": 0 },
    "files_scanned": 5,
    "files_unreadable": 0,
    "files_skipped": 0
  }

```

(Trimmed to one file entry and one finding.) What `schema_version: 2` means:

| Field | Meaning |
|---|---|
| `rule_id` | The stable rule id, the same one in `scan rules list`, SARIF `ruleId`, baselines and allow markers |
| `severity` | How bad if real. **New in 2.** `summary.severity` counts by severity |
| `confidence` | How sure. Unchanged, as are `high_confidence`, `medium_confidence`, `low_confidence` and `summary.high/medium/low` (those count confidence) |
| `status` | `new`, `known` (in the baseline) or `allowed` (inline marker) |
| `fingerprint` | The baseline's identity for the finding. No value goes into it |
| `matched_by` | `value` or `name`, so CI can tell a key match from a name heuristic |
| `allowed`, `known` | The findings that do not count. Each array is present only when it has entries. `findings` and `summary.total` are exactly what fails the run |
| `git` | `tracked`, or `staged` under `--staged`. In a repository the document also carries `ignored_by_git` |
| `files[].read_as` | `dotenv`, `structured` or `text` |

Useful with `jq`:

```bash
# Variables holding critical or high findings
evnx scan --format json | jq -r '[.findings[] | select(.severity == "critical" or .severity == "high") | .variable] | join(", ")'

# Count everything that fails the run
evnx scan --format json | jq '.summary.total'

# Where to revoke each one
evnx scan --format json | jq -r '.findings[] | "\(.variable): \(.action_url // "rotate at source")"'
```

Simpler than any of these: `evnx scan --severity high` already exits `1` when there is a
finding at that level and `0` when there is not, so a gate usually needs no `jq` at all.

### SARIF (GitHub Security tab)

```bash
evnx scan --format sarif --exit-zero > results.sarif
```

Each result's `ruleId` is the stable rule id (`"ruleId": "aws-access-key"`) and its `level`
comes from the severity. **v0.13.0 changed `ruleId`** from `secret/aws-access-key`, so GitHub
code scanning shows existing alerts as belonging to new rules once.

```yaml
- name: Scan for secrets
  run: evnx scan --format sarif --exit-zero > results.sarif

- name: Upload SARIF results
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: results.sarif
  if: always()
```

Findings appear in **Security → Code scanning alerts**.

### GitHub Actions annotations

```bash
evnx scan --format github
```

```text
::error file=./docs/b.env,line=2,title=Secret detected (critical)::STRIPE_SECRET_KEY matches Stripe Secret Key (LIVE). Rotate it at https://dashboard.stripe.com/apikeys
```

The title carries the severity. A finding reached by the variable's **name** is worded
differently and does not tell you to rotate anything: it says the value was not checked
against a known key format.

## Allow markers: one rule, one line, one reason

**v0.13.0+.** Some findings are real matches you have decided to keep: a documented dummy
key, a fixture that tests the scanner. A comment on the finding's line, or the line above,
accepts that one rule there and nowhere else, in any comment style:

```bash
# evnx:allow stripe-live-secret-key — documented dummy, not a real account
STRIPE_SECRET_KEY=sk_live_…
```

```text
$ evnx scan docs
  scanning docs/example.env

  ✓  No new secrets

  1 file scanned
  ·  1 allowed inline — not counted; -v lists them
```

| Marker | Result |
|---|---|
| `evnx:allow <rule-id> — reason` | The finding is `allowed`. `-v` lists it with the reason |
| `evnx:allow <rule-id>` with no reason | Works, and warns: `evnx:allow stripe-live-secret-key has no reason; say why after it` |
| A bare `evnx:allow` | Allows nothing, and says so: `a bare evnx:allow allows nothing; name the rule` |
| A marker naming another rule | Allows nothing, and says so |

There is no marker that silences every rule on a line, on purpose. Allowed findings do not
count toward the exit code.

## A baseline for findings you already have

**v0.13.0+.** The first scan of a real repository rarely comes back clean. Record what is
there once, and the gate fails only on what is new:

```text
$ evnx scan --update-baseline
✓ wrote /tmp/scandoc/.evnx/baseline.json with 9 finding(s); they are reported as known from now on
```

`--update-baseline` writes `.evnx/baseline.json` (or the file named by `--baseline`) and
exits 0. The file holds, per finding, a fingerprint, the rule id, the file and the date:

```json
{
  "schema_version": 1,
  "findings": [
    {
      "fingerprint": "00a61dedd9c3822a221de0a2f30cb7c44aec5d384c1e520d0b7fe508427f94fa",
      "rule": "aws-access-key",
      "file": ".env",
      "added": "2026-11-08"
    }
  ]
}
```

**It never holds a value or a preview**, so it is safe to commit. The fingerprint is a
BLAKE3 hash of the rule, the file, and the variable name or line text. A line inserted
above keeps it; a changed value is a new finding.

From then on:

```text
$ evnx scan
  ✓  No new secrets

  7 files scanned
  ·  9 known (baseline) — not counted; -v lists them
```

A new secret fails the run as it should. `-v` lists every known finding, so the cleanup
list stays visible. When you fix one it stops matching; run `--update-baseline` again to
prune it. `.evnx/baseline.json` is found beside the `.evnx.toml` in force, so a scan from a
subfolder uses the project's.

Use the baseline for "we know, we will fix it" and an allow marker for "this is
intentional". The recommended order for a repository that already has findings is in
[Prevent secret leaks](/guides/use-cases/prevent-secret-leaks).

## Staged scans and the pre-commit hook

**v0.13.0+.** `evnx scan --staged` scans what the next commit records, read from the git
index and not from disk. A secret staged and then edited out on disk is still found; an
unstaged one is not. Paths limit it to staged files under them, and staged files are
scanned whatever `.gitignore` says. Nothing staged exits 0 (`nothing staged, nothing
scanned`); outside a repository it exits 2. Findings carry `"git": "staged"`, and the next
steps say `git restore --staged`, never `git filter-repo`.

`evnx scan hook` manages a git `pre-commit` hook that runs it:

```text
$ evnx scan hook status
not installed: /tmp/hk/.git/hooks/pre-commit (run `evnx scan hook install`)

$ evnx scan hook install
✓ /tmp/hk/.git/hooks/pre-commit runs `evnx scan --staged` before every commit

$ git add .env.prod && git commit -m "add service"
  evnx scan  Checking what is staged for commit

  scanning .env.prod

  ✗  OpenAI API Key                              critical
     .env.prod:1 (OPENAI_API_KEY)  sk-p…C9dE
     !  matches a live key format, not a placeholder
     →  revoke at https://platform.openai.com/api-keys

  1 finding  ·  1 critical

evnx scan: commit blocked, secrets are staged (see above).
  To commit anyway: git commit --no-verify. To turn the hook off: git config hooks.evnx-scan false
```

| Command | Does |
|---|---|
| `scan hook install` | Adds a managed block to the repository's `pre-commit` hook (`core.hooksPath` is honoured). Your own lines are kept; a reinstall replaces the block |
| `scan hook status` | Says whether it is installed here and whether it is turned off |
| `scan hook uninstall` | Removes the block and nothing else |

- The commit is blocked when secrets are staged, when the scan cannot run, and ⚠️ **when
  evnx is not on `PATH`** — an unchecked commit is not let through quietly.
- A hook that pre-commit or prek generated is left alone; `install` prints the
  `.pre-commit-config.yaml` snippet to add instead.
- `git config hooks.evnx-scan false` turns it off; `git commit --no-verify` skips it once.
  The baseline and allow markers apply here too.

## Rules, in short

**v0.13.0+.** Rule files, packs from a catalogue, and importing gitleaks or Betterleaks
files are covered in [Scan rules: the core, your own, and packs](/guides/reference/scan-rules-and-packs).
The commands:

| Command | Does |
|---|---|
| `scan rules list [--category <name>] [--json]` | Every rule a scan here would use, grouped by category, with id, provider, severity, confidence and source. An unknown category exits 2 and lists the 12 allowed |
| `scan rules new <id> [--personal]` | Writes `.evnx/rules/<id>.toml` to fill in |
| `scan rules test [<file>]` | Runs each rule against its own `positive` and `near_miss` values. Exit 1 on any failure |
| `scan rules add <name\|url\|path> [--format gitleaks] [--personal]` | Adds a rule pack and pins its sha256 in `.evnx/rules.lock` |
| `scan rules update [<name>] [-y]` | Fetches a pack again, shows rules added and removed, asks before replacing |
| `scan rules remove <name>` | Removes a pack and its lock entry |

```text
$ evnx scan rules list --category ai
  ai
    openai-api-key       OpenAI        critical  high    evnx
    anthropic-api-key    Anthropic     critical  high    evnx
    huggingface-token    Hugging Face  high      high    evnx
    groq-api-key         Groq          critical  high    evnx
    xai-api-key          xAI           critical  high    evnx
    replicate-api-token  Replicate     critical  high    evnx
    perplexity-api-key   Perplexity    critical  high    evnx

  7 rules
```

`scan rules new` writes a file with the fields to fill in, then you check it with `scan rules test`:

```bash
evnx scan rules new acme-api-key
```

```text
✓ wrote /path/to/project/.evnx/rules/acme-api-key.toml: set its regex and fixtures, then `evnx scan rules test`
```

The file starts with `regex = 'REPLACE-ME-[A-Z0-9]{32}'`, `confidence = "high"`, `severity = "high"`
and empty `positive` and `near_miss` lists. `--personal` writes it to your personal rules instead,
which are never committed.

Rules only **add**: an id that evnx or another file already uses is an error naming both,
never an override. Personal rules (`~/.config/evnx/rules/`) always show in the scan's
header. A scan itself never downloads anything.

## Teaching it your own formats

The durable way to add a format is a [rule file](/guides/reference/scan-rules-and-packs)
in `.evnx/rules/`. For a quick one-off, or a rule in `.evnx.toml`, two older forms still
work.

`--pattern` takes a regular expression and reports anything matching it, named
`Custom pattern 1`, `Custom pattern 2` by position:

```bash
evnx scan --pattern 'ACME-[A-Z0-9]{32}'
```

`[[scan.patterns]]` in `.evnx.toml` is the project's standing set:

```toml
[[scan.patterns]]
id         = "acme-api-key"
name       = "Acme API key"
regex      = "ACME-[A-Z0-9]{32}"
severity   = "high"                          # critical | high | medium | low
confidence = "high"                          # high | medium | low
entropy    = 3.5                             # optional: drop matches below this
url        = "https://acme.example/settings/keys"   # optional: where to revoke it
```

| Key | Required | Meaning |
|-----|----------|---------|
| `name` | yes | What the finding is called in every output format |
| `regex` | yes | The expression. Anchor it yourself if you want it anchored |
| `id` | no | **v0.13.0+** — the stable id for JSON, SARIF, baselines and markers. Default: the name, kebab-cased |
| `severity` | no | **v0.13.0+** — `critical`, `high`, `medium`, `low`. ⚠️ Default **`medium`**, so a rule with none falls out of a `--severity high` gate |
| `confidence` | no | `high` (default), `medium` or `low` |
| `entropy` | no | **v0.13.0+** — drop matches whose Shannon entropy is below this |
| `url` | no | Where to go and revoke a match |

How your rule interacts with the built-ins: a rule that matches something nothing else
recognises is reported under your name; it beats the *name* heuristic (`ACME_TOKEN=ACME-…`
is `Acme API key`, not `Sensitive config key`); a built-in *provider* rule wins over yours
on the same value, because only it can link to where you revoke; and it fires even on a
variable declared `secret = false`. A rule that re-rates a built-in by name keeps its id and
severity.

<Callout type="danger">
**An expression that does not compile exits `2`, and `--exit-zero` does not suppress it.**

```text
$ evnx scan . --pattern '('
Error: 'Custom pattern 1' is not a valid regular expression
  (

regex parse error:
    (
    ^
error: unclosed group

No verdict: evnx did not scan anything. This is not a clean result.
```

A pattern that matches the empty string (`.*`) is refused too, and a typo in `confidence`
or `severity` is an error, not a silent downgrade.
</Callout>

A pattern does not match its own `regex = "…"` line in `.evnx.toml` (**v0.10.14+**).

### Declaring what the heuristics cannot know

`scan` guesses at secrecy from a variable's name and the shape of its value. A project can
settle a wrong guess with a [contract](/guides/commands/spec):

```toml
[vars.TENANT_A]
secret = true          # a real credential whose name gives nothing away

[vars.INTERNAL_SECRET]
secret = false         # configuration, flagged only because of its name
```

`secret = false` cannot silence a real key: it retracts a guess made from a *name*, not a
match on the *value*. evnx announces it on every run.

### Files that are not `.env`

Which checks run depends on how a file is read. A file named like a `.env` (`.env`,
`.env.*`, `app.env`) is read as assignments and checked by name and value. A `.yml`,
`.json` or `.toml` file is **structured** (**v0.13.0+**): names and values, by key path.
Anything else — source code, `.txt`, `.ini` — is **text**: value patterns only, matched
against the whole line. `-v` says which for each file:

```text
⋯ Scanning: ./config.txt (read as text: value patterns only, names not checked)
⋯ Scanning: ./v.env (read as .env: names and values checked)
```

## Ignoring false positives

Pick the narrowest tool. In order of precision:

1. **An [allow marker](#allow-markers-one-rule-one-line-one-reason)** for one rule on one line, with a reason.
2. **The [baseline](#a-baseline-for-findings-you-already-have)** for everything that is there today.
3. **`[scan] disable`** in `.evnx.toml` to switch a built-in rule off by name or id. It weakens the scan for everyone, so evnx announces it on every run.
4. **`--exclude`** to skip paths:

```bash
evnx scan --exclude 'fixtures/**' --exclude '*.test.js'
```

A value with `*`, `?` or `[` is a glob, tried against the path from the folder and against
the file name. Any other value matches a **whole path component** (**v0.10.14+**):
`fixtures` skips `./fixtures/.env` and `./test/fixtures/.env`, but `env` no longer skips
`.env`. A file you name on the command line is read whatever `--exclude` says.

`.git/`, `node_modules/`, `target/`, `dist/`, `build/`, `.env.example`, `.env.sample`,
`.env.template`, editor swap files and `evnx backup` output are skipped already. An `evnx
backup` file is recognised by its **content** (**v0.11.0+**), so a plaintext
`cp .env .env.backup` is scanned.

5. **`--ignore-placeholders`** drops filler such as `changeme` and `your_api_key_here`.
6. **`--severity high`** is usually the better answer for a noisy first run: report what
   matters rather than enumerating exceptions.

<Callout type="warning">
Inline `# evnx-ignore` comments do **not** exist, and there is no `[scan] ignore` key.
The marker is `# evnx:allow <rule-id> — reason`.
</Callout>

### What is not reported

**v0.14.0+** — a corpus of 60 labelled files (37 whose secrets must be found, 23 look-alikes
that must not be) runs against `evnx scan` in evnx's own test suite, and it found these false
positives, now fixed:

- **A PEM or OpenSSH private key is one `private-key` finding.** Its base64 body lines are no
  longer also `high-entropy-string`.
- **Public material is not a secret.** The body of a `PUBLIC KEY`, `RSA PUBLIC KEY` or
  `CERTIFICATE` block, and the blob of an `ssh-rsa` or `ssh-ed25519` public key line, are not
  reported.
- **Digests used as identifiers.** `CACHE_KEY`, `ETAG_KEY` and `IDEMPOTENCY_KEY` holding a
  32, 40 or 64 digit hex digest are not credentials. Any other word in the name
  (`CACHE_API_KEY`, `API_KEY`, `HASH_KEY`) or any other value keeps the check.
- **A Stripe publishable key** (`pk_live_`, `pk_test_`) is public by design and is not
  reported by name or by entropy. A *secret* key under `NEXT_PUBLIC_` still is.
- **References are not values** in YAML, JSON and TOML: a whole-value template
  (`{{ .Values.apiToken }}`, `${{ secrets.TOKEN }}`), anything under a Kubernetes
  `secretKeyRef` or `secretRef`, and a lowercase secret name in a `secrets:` list
  (`- db_password`).
- **Password names ending in `_PASS`** (`RABBITMQ_DEFAULT_PASS`, `DB_PASS`) are checked, for
  `scan` and for masking. `BYPASS_CACHE` and `COMPASS` are not.
- **The Neon sample URL** that `evnx init --with neon` writes is no longer a finding. A host
  with an `example` label is a placeholder host, as `localhost` and `example.com` already
  were; a real host with `user:password`, or a real password on an example host, is still one.

A rule's `names` also beats a built-in rule in YAML and JSON now, as it does in `.env`. They
stay case-sensitive regexes in every format: write `(?i)` or both spellings to cover
`SECRET_KEY` and `secret_key`.

## Scanning a whole project

`evnx scan` is already recursive and reads **every file** in a folder (since **v0.10.3**).
Binary files and files over 1 MiB (`--max-file-size`) are skipped, and the scan says how
many on stderr (`-v` lists each, with the reason). A file you name is always read:

```bash
evnx scan                          # this directory and everything under it
evnx scan config/.env.production   # one file
evnx scan .env config/ src/        # several paths
```

### Parallel scanning

**v0.14.0+** — files are scanned on all cores and reported **in path order**, so text, JSON,
SARIF and GitHub output, the exit code and the notes on stderr are the same as before, and
the same at any thread count. `RAYON_NUM_THREADS=N` caps the threads; `1` is the old
one-at-a-time behaviour:

```bash
RAYON_NUM_THREADS=2 evnx scan .
```

On a 4,500-file, 51 MB tree on two cores the scan went from 9.4 s to 4.9 s with the
built-in rules, and from 10.9 s to 6.2 s with the gitleaks pack. One difference: `-v` lines
and `evnx:allow` warnings are printed together after the scan, rather than as each file is
read.

### Scanning stdin — `evnx scan -`

**v0.11.0+** — scan text that is not a file, without writing it to disk: a diff before
you commit it, a log before you paste it, a file an agent is about to write.

```bash
git diff | evnx scan -
kubectl logs deploy/api | evnx scan - --format json
evnx scan . -            # stdin beside paths
```

Stdin is read as a `.env` when it parses as one and as text otherwise (`-v` and
`files[].read_as` say which); findings are labelled `<stdin>`. **Empty stdin is an
error, exit 2**, not a clean result, so `cat missing-file | evnx scan -` cannot pass a
CI step. A finding in stdin gets no `git filter-repo` advice; it is told to keep the key
out of wherever that text was going.

### In a git repository

**v0.10.14+.** A folder walk counts what git would commit. A filled-in `.env` that
`.gitignore` covers is where secrets belong, so its findings are summarised in one line and
do not fail the scan:

```text
  evnx scan  Checking for exposed secrets

  scanning ./.env, ./.gitignore

  ✓  No secrets in files git would commit

  2 files scanned
  ·  git ignores ./.env — 2 findings there are not counted, because it is not committed (--include-ignored lists them)
```

That exits `0`. `--include-ignored` counts them, and naming the file reports it in full:

```text
$ evnx scan .env
  …
  2 findings  ·  2 critical

Next steps:
  1. git ignores .env and does not track it, so nothing was committed
  2. Rotate a key only if the file was shared another way — a copy, an archive, a container image
```

A file git **tracks** is always counted, ignored or not, because it is in the history.

<Callout type="warning" title="Before v0.10.3 a folder scan read only some extensions">
The walk read only files whose extension was on a built-in list, so `config/id_rsa.pem`
— a private key — or a live key in `app.swift` was never opened, and the scan said
"No secrets detected" and exited `0`. To limit a walk on purpose, opt in:

```bash
evnx scan --extensions env,yml,json
```

```toml
# .evnx.toml
[scan]
extensions = ["env", "yml", "json"]
```

Either way the run says it is limited — `scanning only files ending in .env, .yml, .json
in folders` — so a narrowed scan is never mistaken for a full one.
</Callout>

<Callout type="success">
A path that cannot be scanned is an error, exit `2`, not a clean result.
`evnx scan ./typo` used to print "No secrets detected" and exit `0`; it now names every
path it could not read and says plainly that there is no verdict.
</Callout>

## CI/CD usage

<Callout type="warning" title="Counts change after v0.13.0">
More rules, names in structured files and the new entropy threshold change what a repository
reports. Run `evnx scan` once on a branch, then either fix the findings or record them with
`--update-baseline` before you turn a blocking gate on.
</Callout>

### Block commits

Either use the built-in hook (`evnx scan hook install`, see
[above](#staged-scans-and-the-pre-commit-hook)) or the pre-commit framework, which shares the
setup through the repository:

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/urwithajit9/evnx
    rev: v0.13.0
    hooks:
      - id: evnx-scan-installed   # the evnx on PATH; no first-run build (v0.13.0+)
      - id: evnx-scan-push        # a SARIF scan before each push
```

`evnx-scan` is the same hook but builds evnx on first use; `evnx-scan-installed`
(`language: system`) uses the binary on `PATH`. Both run on the files being committed. To
block only on serious findings add `args: [--severity high]`. `scan` already exits `1` when
it reports something, so no extra flag makes the hook fail.

### GitHub Actions: block PRs

```yaml
# .github/workflows/security.yml
name: Security scan

on:
  pull_request:
  push:
    branches: [main]

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install evnx
        run: curl -fsSL https://dotenv.space/install.sh | bash

      # Annotations land on the PR diff. Fails the job on a high or critical finding.
      - name: Scan for secrets
        run: evnx scan --format github --severity high

      # SARIF must be redirected: there is no --output flag.
      - name: Generate SARIF
        if: always()
        run: evnx scan --format sarif --exit-zero > results.sarif

      - name: Upload SARIF
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: results.sarif
        if: always()
```

The SARIF step carries `--exit-zero` deliberately: it exists to produce the file, and the
preceding step fails the build. A committed `.evnx/baseline.json` is picked up
automatically, so only new findings fail. If you use packs, commit `.evnx/rules/` and
`.evnx/rules.lock` too: CI downloads nothing.

## Configuring scan in `.evnx.toml`

```toml
[scan]
severity            = "high"        # --severity
confidence          = "medium"      # --confidence
exclude             = ["fixtures"]  # added to --exclude
ignore_placeholders = false
disable             = ["sentry-dsn"] # built-in rules to switch off, by name or id
builtins            = true          # false: only this project's rules
extensions          = ["env", "yml", "json"]
max_file_size       = "1MiB"

[[scan.patterns]]                    # see "Teaching it your own formats"
name  = "Acme API key"
regex = "ACME-[A-Z0-9]{32}"
```

| Key | Merge with the flag |
|---|---|
| `exclude`, `patterns` | Added together |
| `ignore_placeholders` | The flag wins in either direction |
| `severity`, `confidence`, `max_file_size`, `extensions` | The flag wins, else the config |

### Monorepos: paths are read from the folder that holds `.evnx.toml`

**v0.14.0+** — a relative path in `.evnx.toml` means "from the folder holding this file",
wherever evnx runs below it. That was already so for `[defaults] example` and
`[cloud] file`; `[scan] exclude` patterns with a `/` now are too. With this `.evnx.toml` at
the repository root:

```toml
[scan]
exclude = ["apps/web/fixtures/**"]
```

`evnx scan` run inside `apps/web` skips `apps/web/fixtures/`:

```text
  config    ../../.evnx.toml (scan.exclude=1 patterns)
  scanning ./.env
  ✓  No secrets detected
```

A pattern as you wrote it still matches too (the two are a union), and a pattern with no `/`
matches anywhere, as before. **Flags** (`--exclude`) are relative to where you run.

`severity`, `confidence`, `exclude` and `disable` can weaken a scan, and the file is
committed, so evnx prints which are in force:

```text
  config    .evnx.toml (scan.severity=high, scan.confidence=medium, scan.exclude=1 patterns)
```

Rule files and the baseline are not `[scan]` keys: they live in `.evnx/rules/` and
`.evnx/baseline.json`, found beside the `.evnx.toml` in force. See the
[`.evnx.toml` reference](/guides/reference/configuration-file).

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Clean: nothing new at or above `--severity` and `--confidence` in files git would commit; or nothing staged; or `--update-baseline` wrote the baseline; or `--exit-zero` was set |
| `1` | Findings reported, or a file that could not be read |
| `2` | The scan could not be completed, so there is no verdict: a bad path or flag, a broken config, a pattern that does not compile, an unknown `--category`, a pack that no longer matches `.evnx/rules.lock`, empty stdin, `--staged` outside a repository |

**`2` is not a louder `1`.** "I found nothing" and "I could not look" are different
answers. Allowed and known findings do not count toward the exit code.

```bash
evnx scan .
case $? in
  0) echo "clean" ;;
  1) echo "secrets found — blocking" ;;
  2) echo "scan did not run — fix the setup" ;;
esac
```

`--exit-zero` suppresses `1` only. Use it for advisory runs and first-pass onboarding; for
a gate that adopts existing findings, prefer a baseline over `--exit-zero`.
