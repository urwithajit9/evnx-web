`evnx scan` finds values that look like real secrets — provider keys, tokens, private keys, passwords in connection strings — before they leave your machine. A folder scan reads every file, not only `.env`, and in a git repository it counts what git would commit. It is built for pre-commit hooks and CI. Every output on this page is from evnx 0.10.18.

<Prerequisites>
  <Prerequisite href="/guides/getting-started/installation">Install evnx</Prerequisite>
</Prerequisites>

## Command signature

```bash
evnx scan [OPTIONS] [PATH]...
```

**Options:**

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `[PATH]...` | positional | `.` | Files or directories to scan. Repeatable: `evnx scan .env config/` |
| `--format` | `pretty\|json\|sarif\|github` | `pretty` | Output format. **An unrecognised value is an error** — it used to fall back to `pretty` silently |
| `--severity` | `high\|medium\|low` (`all` = `low`) | `low` | **v0.5.0+** — lowest confidence worth reporting. Filters the findings, the counts and the exit code together |
| `--exit-zero` | `bool` | `false` | Always exit 0 (advisory mode) |
| `--exclude` | `string[]` | `.env.example` | Paths to skip in a folder walk. A value with `*`, `?` or `[` is a glob; any other value matches a **whole path component**. Adds to `[scan] exclude` |
| `--max-file-size` | size | `1MiB` | **v0.10.14+** — skip walked files larger than this (`500K`, `5MB`, `2MiB`). A file you name is read whatever its size |
| `--include-ignored` | `bool` | `false` | **v0.10.14+** — count findings in files git ignores and does not track. See [In a git repository](#in-a-git-repository) |
| `--extensions` | `string[]` | — | **v0.10.3+** — read only files with these extensions in folders (`env,yml,json`). Opt-in, and announced on every run. `[scan] extensions` in `.evnx.toml` sets it per project |
| `--pattern` | `regex[]` | `[]` | **v0.5.0+** — also report values matching this expression. Repeatable. Combines with `[[scan.patterns]]` |
| `--ignore-placeholders` | `bool` | `false` | Skip values that look like placeholders (`changeme`, `your_key_here`) |
| `--no-ignore-placeholders` | `bool` | `false` | Report them even when `[scan] ignore_placeholders` is `true`. The last of the two flags wins |
| `-q`, `--quiet` | `bool` | `false` | Print nothing when clean. Findings, and the line saying a scan was narrowed, still print |
| `-v`, `--verbose` | `bool` | `false` | Show the rules in force and each file read |

<Callout type="warning">
`--path`, `--recursive`, `--ignore`, `--include-example`, `--output` and `--exit-code`
have appeared on this page in the past. **None of them exist.** Paths are positional,
scanning is already recursive, and the advisory flag is `--exit-zero`.

Redirect instead of `--output`: `evnx scan --format sarif > results.sarif`.

`--pattern` **did** nothing until v0.5.0 — it was accepted by the parser and discarded.
It works now; see [Teaching it your own formats](#teaching-it-your-own-formats).
</Callout>

## What evnx scans for

### Known credential patterns

evnx ships with these thirteen rules. `evnx scan --help` lists them by name, and `-v` prints
the ones in force:

| Rule | Severity | Expression |
|---|---|---|
| `AWS Access Key` | high | `AKIA[0-9A-Z]{16}` |
| `AWS Temporary Access Key (STS)` | high | `ASIA[0-9A-Z]{16}` |
| `GitHub Fine-grained PAT` | high | `github_pat_[A-Za-z0-9_]{40,}` |
| `Slack Token` | high | `xox[abprs]-[0-9A-Za-z-]{10,}\|xapp-[0-9]-[A-Za-z0-9-]{10,}` |
| `Google API Key` | medium | `AIza[0-9A-Za-z_\-]{35}` |
| `JSON Web Token` | medium | `eyJ[A-Za-z0-9_\-]{8,}\.eyJ[A-Za-z0-9_\-]{8,}\.[A-Za-z0-9_\-]{8,}` |
| `Stripe Secret Key (LIVE)` | high | `sk_live_[0-9a-zA-Z]{24,}` |
| `Stripe Secret Key (test)` | medium | `sk_test_[0-9a-zA-Z]{24,}` |
| `GitHub Token` | high | `\b(?:ghp\|gho\|ghu\|ghs)_[A-Za-z0-9]{36,40}\b` |
| `OpenAI API Key` | high | `sk-(?:proj-[0-9a-zA-Z_-]{40,}\|[0-9a-zA-Z]{48})` |
| `Anthropic API Key` | high | `sk-ant-api[0-9]{2}-[0-9a-zA-Z\-_]{95}` |
| `Private Key` | high | `-----BEGIN [A-Z0-9 ]*PRIVATE KEY-----` |
| `Credentials in a connection string` | high | `[a-zA-Z][a-zA-Z0-9+.\-]*://[^\s/?#@]+:[^\s/?#@]+@[^\s/?#]+` |

`Google API Key` and `JSON Web Token` are `medium` on purpose: many Google keys are browser
keys meant to ship in a page, and many JWTs are public ID tokens.

Three further checks are **not** rules, because none can be expressed as one:

| Check | Severity | How it decides |
|---|---|---|
| `Sensitive config key` | high | The variable's **name** looks like a secret (`*_SECRET`, `*_TOKEN`, `STRIPE_SECRET_KEY` …). The value was not checked, and the output says so |
| `AWS Secret Access Key` | medium, **high** under an `AWS_SECRET_*` name | 40 base64-ish characters **and** a variable name containing `AWS` **and** entropy > 4.5. Its shape alone matches any 40-character token, so the name is part of the test |
| `High-entropy string` | low | 32+ characters with entropy > 4.8. The last resort |

**Stand-ins are never findings** (**v0.10.14+**). AWS's documented example keys
(`AKIAIOSFODNN7EXAMPLE`) and placeholder-shaped values are recognised and skipped, and a
name-only match on a value that is an address (a URL, a host) is dropped. Under
`--severity high`, a long value under a secret-like name is still kept.

<Callout type="warning">
  ⚠️ **This list previously named three patterns that do not exist** — a Stripe
  *publishable* key (`pk_…`), SendGrid (`SG.…`) and Twilio (`[0-9a-f]{32}`) — and omitted
  two that do, Anthropic and `Private Key`. Corrected in v0.5.3 against the source.

  It mattered more than a wrong table usually does. A leaked `pk_…` or `SG.…` key is caught
  only by the generic high-entropy check, which is **low** severity — so
  `evnx scan --severity high` in CI does not fail on it, while this page implied it would.
  If you relied on either, add your own rule:

  ```toml
  [[scan.patterns]]
  name  = "SendGrid API key"
  regex = "SG\\.[A-Za-z0-9_-]{22}\\.[A-Za-z0-9_-]{43}"
  url   = "https://app.sendgrid.com/settings/api_keys"
  ```
</Callout>

<Callout type="warning" title="The connection-string rule is new in v0.7.0, and it will fail builds that used to pass">
`DATABASE_URL=postgresql://admin:s3cr3t@db.example.com:5432/main` scanned **clean**
before v0.7.0, and structurally so: the provider rules are all prefix formats and a
connection string has none, the sensitive-key heuristic keys off names containing
`secret`/`token`/`key` and `DATABASE_URL` has none of them, and the entropy check
scores a whole URL below threshold.

A live database password in `DATABASE_URL` is among the most common things in a `.env`,
so this is caught now — which means **a repository with one now fails
`evnx scan --severity high`** where it did not before. That is the point, but re-run
your pipeline once after upgrading rather than discovering it on a release branch.

Things it deliberately does **not** flag: `postgresql://reader@host/db`, which is a
username with no password; `https://api.example.com/users/me@example.com`, where the `@` is
in the path rather than the authority; and (**v0.10.14+**) stand-ins such as
`postgres://user:password@localhost:5432/app` and documentation hosts, which is what a
template holds.
</Callout>

These are the formats evnx ships with. For the ones only your project knows — an internal
token, a vendor key shape — see [Teaching it your own formats](#teaching-it-your-own-formats).

### High-entropy detection

Beyond known patterns, `evnx scan` flags any value of 32 characters or more whose Shannon entropy exceeds 4.8. It is the low-confidence last resort, for:

- Custom API keys that don't match a known format
- Base64-encoded secrets embedded in `.env`

JWTs and private keys have rules of their own (`JSON Web Token`, `Private Key`).

<Callout type="warning" title="Multiline values: fixed in v0.8.0">
⚠️ **Before v0.8.0 a secret inside a multiline value was not reported at all** —
`scan` exited 0 and printed "No secrets detected". A PEM private key is the
common multiline value, and it is the example this very list invites.

The cause was that `scan` split each `.env` line on `=` itself instead of using
the parser the rest of evnx uses; a continuation line has no `=`, so it was
skipped. If you have been relying on `scan` in a pre-commit hook or CI, re-run it
once after upgrading — it may find something it was quietly passing over.
</Callout>

<Callout type="warning">
The threshold is **not configurable**. This page and the `.evnx.toml` reference both
described `entropy_threshold` as a setting; no such setting is read by anything. 4.8 for
the generic check, and 4.5 for the gate on AWS secret keys, are compiled in.
</Callout>

<Callout type="info" title="Why entropy matters">
A string like `wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY` scores high on Shannon entropy because its characters are distributed almost uniformly — a property of cryptographically random strings. Human-readable values like `my-app-name` score low.
</Callout>

### Variables your build publishes to the browser

**New in v0.6.0.** Some prefixes are instructions to a bundler: inline this value
into the JavaScript that ships to every visitor. A secret behind one of them is not
at risk of leaking — it **has already leaked**, to everyone who has ever loaded the
site, and it stays leaked in every build artefact and CDN cache that still exists.

evnx recognises nine:

| Prefix | Inlined by |
|---|---|
| `NEXT_PUBLIC_` | Next.js |
| `NUXT_PUBLIC_` | Nuxt |
| `EXPO_PUBLIC_` | Expo |
| `REACT_APP_` | Create React App |
| `STORYBOOK_` | Storybook |
| `GATSBY_` | Gatsby |
| `VUE_APP_` | Vue CLI |
| `VITE_` | Vite |
| `PUBLIC_` | SvelteKit and Astro |

```text
$ evnx scan .env.local
  ✗  Stripe Secret Key (LIVE)                    high
     .env.local:1 (NEXT_PUBLIC_STRIPE_KEY)  sk_l…1234
     !  matches a live key format, not a placeholder
     !  NEXT_PUBLIC_ is inlined into the client bundle by Next.js — anyone who loads your site can read this
     →  rename to STRIPE_KEY and read it server-side
     →  revoke at https://dashboard.stripe.com/apikeys
```

### It raises the severity, and why only sometimes

The prefix changes the severity **before** the `--severity` filter runs, so a
finding it escalates cannot be filtered out by the gate it was escalated for:

| The finding | Becomes | Why |
|---|---|---|
| A **named provider format** — Stripe, AWS, GitHub | `high` | This is a real credential and it is already public. Nothing about it is low risk |
| **Shape alone** — the entropy check, an unrecognised token | at least `medium` | Enough to be seen and read, not enough to fail `--severity high` |

<Callout type="info" title="Why shape alone stops at medium">
Plenty of keys behind these prefixes are **meant** to be public. A PostHog key, a
Sentry DSN and a Supabase anon key are all designed to ship in the bundle — the
Supabase one is protected by row-level security, not by secrecy. evnx cannot tell
those from a secret it does not recognise, so it reports them and says so rather
than failing your build.

The remedy text follows the same distinction. With no recognised provider among
them, it asks you to **check whether they are meant to be public** before rotating
anything. With one, it tells you to revoke — a Stripe key behind `VITE_` is not
ambiguous.
</Callout>

<Callout type="warning" title="Renaming is the fix; rotating alone is not">
While the name carries the prefix, **every build republishes the value.** Revoking
and reissuing without renaming just publishes the new key too. Rename it to drop the
prefix, read it server-side, and then rotate.
</Callout>

<Callout type="warning" title="`PUBLIC_` is deliberately broad">
SvelteKit and Astro use a bare `PUBLIC_` prefix, so `PUBLIC_KEY` — an ordinary name
for the public half of a keypair, which is *supposed* to be public — matches it.
That is the trade: the prefix genuinely does mean "inline this" in two popular
frameworks, and a false note on a public key costs less than silence on a published
secret.
</Callout>

## Output formats

### Pretty (default)

Human-readable, color-coded output for terminal use:

```bash
evnx scan
```

```text
  evnx scan  Checking for exposed secrets

  scanning ./.env

  ✗  AWS Access Key                              high
     ./.env:1 (AWS_ACCESS_KEY_ID)  AKIA…LKEY
     !  matches a live key format, not a placeholder
     →  revoke at https://console.aws.amazon.com/iam

  ✗  Stripe Secret Key (LIVE)                    high
     ./.env:2 (STRIPE_SECRET_KEY)  sk_l…hijk
     !  matches a live key format, not a placeholder
     →  revoke at https://dashboard.stripe.com/apikeys

  ✗  GitHub Token                                high
     ./.env:3 (GITHUB_TOKEN)  ghp_…Q7r8
     !  matches a live key format, not a placeholder
     →  revoke at https://github.com/settings/tokens

  ✗  Credentials in a connection string          high
     ./.env:4 (DATABASE_URL)  post…5432
     !  a password in a postgres:// URL, not a placeholder

  4 findings  ·  4 high


Next steps:
  1. Revoke or rotate the keys above — assume they are compromised
  2. Remove them from history: git filter-repo --path .env --invert-paths
  3. Force push, after coordinating with everyone who has a clone
```

A value is only ever shown as a short preview (`AKIA…LKEY`). Findings are sorted by file
and line, and one credential is one finding. The "Next steps" follow git: for a file git
ignores and does not track, they say nothing was committed instead of telling you to
rewrite history.

### JSON

For programmatic processing, piping to `jq`, or custom reporting:

```bash
evnx scan --format json
```

```json
{
  "files_scanned": 1,
  "unreadable": [],
  "skipped": [],
  "secrets_found": 1,
  "findings": [
    {
      "pattern": "AWS Access Key",
      "confidence": "high",
      "value_preview": "AKIA…LKEY",
      "location": "./.env:1 (AWS_ACCESS_KEY_ID)",
      "variable": "AWS_ACCESS_KEY_ID",
      "action_url": "https://console.aws.amazon.com/iam",
      "matched_by": "value"
    }
  ],
  "high_confidence": 1,
  "medium_confidence": 0,
  "low_confidence": 0,
  "summary": {
    "total": 1,
    "high": 1,
    "medium": 0,
    "low": 0,
    "files_scanned": 1,
    "files_unreadable": 0,
    "files_skipped": 0
  }
}
```

(One finding of the four shown.) In a git repository the document also carries
`ignored_by_git` — `[{"path": "./.env", "findings": 1}]` — and `summary.ignored_by_git`,
the findings in files git ignores, which are not in `findings` or the totals.

<Callout type="warning">
⚠️ **The recipes on this page used to name fields that do not exist.** A finding carries
`confidence` and `variable`, not `severity` and `key`, so the documented filter

```bash
jq '[.findings[] | select(.severity == "high") | .key]'   # ← returns []
```

returned an **empty list over a live AWS key** — a CI gate built on it reported clean on a
repo with a committed credential. `summary` did not exist at all before **v0.5.0**, so
`jq -e '.summary.errors == 0'` failed builds that had nothing wrong with them.

The corrected recipes are below. If you copied any of the old ones, they are worth
re-checking.
</Callout>

`confidence` is deliberately not called `severity`: it answers *"how sure are we this is a
real credential"*, not *"how bad is it"*.

Useful with `jq`:

```bash
# List the variables holding high-confidence findings
evnx scan --format json | jq -r '[.findings[] | select(.confidence == "high") | .variable] | join(", ")'

# Count everything reported
evnx scan --format json | jq '.summary.total'

# Exit non-zero if anything was found
evnx scan --format json | jq -e '.summary.total == 0'

# Where to revoke each one
evnx scan --format json | jq -r '.findings[] | "\(.variable): \(.action_url // "rotate at source")"'
```

<Callout type="info">
Simpler than any of these: `evnx scan --severity high` already exits `1` when there is a
high-confidence finding and `0` when there is not, so a gate usually needs no `jq` at all.
</Callout>

### SARIF (GitHub Security tab)

SARIF (Static Analysis Results Interchange Format) is the standard format for security tools integrating with GitHub's Security tab:

```bash
evnx scan --format sarif --exit-zero > results.sarif
```

In GitHub Actions, upload as a security artifact:

```yaml
- name: Scan for secrets
  run: evnx scan --format sarif --exit-zero > results.sarif

- name: Upload SARIF results
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: results.sarif
  if: always()   # Upload even if scan finds issues
```

Findings appear in the **Security → Code scanning alerts** tab of your repository.

### GitHub Actions annotations

Inline annotations appear directly on pull request diffs:

```bash
evnx scan --format github
```

```
::error file=./.env,line=1,title=Secret detected (high)::AWS_SECRET_ACCESS_KEY matches AWS Secret Access Key. Rotate it at https://console.aws.amazon.com/iam
::error file=./.env,line=2,title=Secret detected (high)::STRIPE_SECRET_KEY matches Stripe Secret Key (LIVE). Rotate it at https://dashboard.stripe.com/apikeys
```

A finding reached by the variable's **name** rather than its value is worded
differently, and does not tell you to rotate anything:

```
::error file=./.env,line=1,title=Secret detected (high)::NEXTAUTH_SECRET is named like a secret (Sensitive config key: NEXTAUTH_SECRET). The value was not checked against a known key format — confirm before rotating
```

<Callout type="info">
  **`matched_by` in v0.5.0+.** `--format json` carries `"value"` or `"name"` per finding,
  so CI can tell a real key match from a name heuristic. Before that the two were
  indistinguishable in every machine format, and the GitHub annotation told you to rotate
  a credential nothing had read.
</Callout>

## CI/CD usage

<Callout type="warning" title="Counts change after v0.6.0 — in your favour">
In files other than `.env`, one credential used to be reported **twice** — once by
the entropy check and once by the pattern that identified it — because the two reach
a source file by different routes and nothing reconciled them. A key appearing twice
in a `.json` counted four times, and it inflated `secrets_found` as well as the
`high`/`low` totals.

One credential is now one finding. If you assert on exact counts rather than on
`--severity`, re-baseline them once after upgrading. `.env` files were never
affected.
</Callout>

### Block commits with pre-commit

evnx ships the hooks:

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/urwithajit9/evnx
    rev: v0.10.18
    hooks:
      - id: evnx-scan        # the staged files, before each commit
      - id: evnx-scan-push   # a SARIF scan before each push
```

`evnx-scan` runs `evnx scan` on the files being committed, which are always read and
reported in full. To block only on high-confidence findings, add
`args: [--severity high]` to the hook. `scan` already exits `1` when it reports something,
so no extra flag is needed to make the hook fail.

<Callout type="warning">
This hook used to read `evnx scan --exit-code --severity high`. **`--exit-code` does not
exist**, so the hook failed with a clap argument error on *every* commit — clean or not —
and the message said "secrets detected". `--severity` needs **v0.5.0+**; on earlier
versions drop it and the hook blocks on any finding.
</Callout>

### GitHub Actions — block PRs

```yaml
# .github/workflows/security.yml
name: Security scan

on:
  pull_request:
  push:
    branches: [main]

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install evnx
        run: curl -fsSL https://dotenv.space/install.sh | bash

      # Annotations land on the PR diff. Fails the job on any finding.
      - name: Scan .env files
        run: evnx scan --format github

      # SARIF must be redirected — there is no --output flag.
      - name: Generate SARIF
        if: always()
        run: evnx scan --format sarif --exit-zero > results.sarif

      - name: Upload SARIF
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: results.sarif
        if: always()
```

The SARIF step carries `--exit-zero` deliberately: it exists to produce the file, and the
preceding step is what fails the build.

## Declaring what the heuristics cannot know

**v0.5.0+.** `scan` guesses at secrecy from a variable's name and the shape of
its value, and both guesses fail in opposite directions:

- `TENANT_A=9f3a7c21b85e4d0fa62c` — a real credential whose name gives nothing
  away. Reported as **"✓ No secrets detected"**, exit `0`.
- `INTERNAL_SECRET=a-long-config-value` — configuration, flagged **high**
  because of its name.

A project can settle either with a [contract](/guides/commands/spec):

```toml
[vars.TENANT_A]
secret = true

[vars.INTERNAL_SECRET]
secret = false
```

<Callout type="danger">
**`secret = false` cannot silence a real key.** It retracts a guess made from a
variable's *name*; it does not retract a match on the *value*. A variable holding
`sk_live_…` is still reported however it is declared, because `.evnx.toml` is
committed and one wrong line would otherwise silence a live credential for
everyone who clones.

Since it does loosen scanning, evnx announces it on every run:
`config .evnx.toml (vars.secret=false on 1 variable(s))`.
</Callout>

## Teaching it your own formats

**v0.5.0+.** The built-in patterns know AWS, Stripe, GitHub, OpenAI and the rest. They do
not know your company's internal token, or the key shape of a vendor nobody else uses —
and a credential evnx cannot name is a credential it reports as `✓ No secrets detected`.

`--pattern` takes a regular expression and reports anything matching it:

```bash
evnx scan --pattern 'ACME-[A-Z0-9]{32}'
```

```
  ✗  Custom pattern 1                            high
     ./.env:2 (TENANT_A)  ACME…A539
     !  matches a live key format, not a placeholder
```

It is repeatable, and it takes an expression and **nothing else** — there is no
`--pattern 'Name=regex'` form. `=` is legal inside a character class, so a pattern like
`[A-Za-z0-9+/=]{40}` would split into a nonsense name and a broken expression. Flag
patterns are named by position instead: `Custom pattern 1`, `Custom pattern 2`.

### The durable form — `[[scan.patterns]]`

For a rule the whole team should scan with, and for a name that means something, declare it
in `.evnx.toml`:

```toml
[[scan.patterns]]
name = "Acme API key"
regex = "ACME-[A-Z0-9]{32}"
url = "https://acme.example/settings/keys"   # optional: where to revoke it

[[scan.patterns]]
name = "Ring handle"
regex = "RING-[0-9]{4}"
confidence = "medium"                        # optional: high | medium | low
```

```
  ✗  Acme API key                                high
     ./.env:2 (TENANT_A)  ACME…A539
     !  matches a live key format, not a placeholder
     →  revoke at https://acme.example/settings/keys

  !  Ring handle                                 medium
     ./src/client.ts:2  RI…21
```

| Key | Required | Meaning |
|-----|----------|---------|
| `name` | yes | What the finding is called, in every output format. Becomes the SARIF rule id — `secret/acme-api-key` |
| `regex` | yes | The expression. Anchor it yourself if you want it anchored |
| `confidence` | no | `high` (default), `medium` or `low`. Feeds `--severity`, the counts and the exit code together |
| `url` | no | Where to go and revoke a match |

The two sets **combine** — `--pattern` is this run's rule, `[[scan.patterns]]` is the
project's standing set — the same way `--exclude` combines with `[scan] exclude`. The
default confidence is `high` because you wrote the rule deliberately; a rule you want to be
advisory says `confidence = "medium"` and drops out of `--severity high`.

### A broken expression is not a clean scan

<Callout type="danger">
**An expression that does not compile exits `2`, and `--exit-zero` does not suppress it.**

```
$ evnx scan . --pattern '('
Error: 'Custom pattern 1' is not a valid regular expression
  (

regex parse error:
    (
    ^
error: unclosed group

No verdict: evnx did not scan anything. This is not a clean result.
```

Exit `0` there would mean CI reads a search that never ran as a pass. A pattern that matches
the empty string — `.*`, `a?` — is refused on the same grounds: it would flag every line in
the project.

The same applies to a typo in `confidence`. `confidence = "hgih"` is an error, not a silent
downgrade to `low`, because a quiet downgrade would drop the rule out of a `--severity high`
gate that used to catch it.
</Callout>

### How it interacts with the built-in detectors

| Situation | What is reported |
|-----------|------------------|
| Your rule matches a value nothing else recognises | Your rule, under your name |
| Your rule and the *name* heuristic both match | **Your rule.** `ACME_TOKEN=ACME-…` reports as `Acme API key`, not `Sensitive config key: ACME_TOKEN` |
| Your rule and a built-in *provider* pattern both match | **The built-in.** A real AWS key stays `AWS Access Key`, because only it can link you to IAM to revoke it |
| Your rule matches a variable declared `secret = false` | **Your rule.** It read the value, and no declaration about what a variable is *for* can make its contents stop being a credential |

### Files that are not `.env`

Rules — yours and the built-in ones alike — are matched against the whole line in
non-`.env` files, so a short or multi-word format is found where the entropy heuristics
could not see it:

```ts
// src/client.ts
const ring = "RING-4821";
```

```bash
evnx scan ./src --pattern 'RING-[0-9]{4}'   # found
evnx scan ./src                             # ✓ No secrets detected
```

The two heuristics split each line into tokens and discard anything 20 characters or
shorter, which is right for "this looks random" and wrong for "this is exactly what I am
looking for".

⚠️ **Before v0.5.3 the built-in rules were subject to that floor too**, and it made them
weaker than a rule you could write yourself. `-----BEGIN RSA PRIVATE KEY-----` is a phrase,
never one token, so the `Private Key` rule could not fire in any file that was not a
`.env` — including the `.pem` files private keys live in. Built-ins and custom rules now
run on the same engine, so both see the whole line.

⚠️ That applied to a `.pem` file you **named**. A folder scan did not open `.pem` files
at all until **v0.10.3** — see *Scanning a whole project*.

### Performance

Declaring rules is close to free. Every pattern is compiled into a single automaton that
reports which of them match in one pass, so a line with no secret in it costs the same
whether you declared one rule or two hundred — the same approach GitHub's scanner and
gitleaks use.

Measured over 400 files, 60,000 lines, 6.3 MB, no findings:

| patterns | scan time |
|---------:|----------:|
| 0 | 55 ms |
| 1 | 56 ms |
| 10 | 59 ms |
| 50 | 58 ms |
| 200 | 68 ms |

Expressions are also matched without backtracking, so a pattern committed to `.evnx.toml`
cannot hang the scan for everyone who clones the repository.

<Callout type="info">
**A pattern does not match its own declaration** (**v0.10.14+**). `.evnx.toml` is still
scanned like any other file, so a secret pasted into it is found, but the `regex = "…"` line
of a `[[scan.patterns]]` entry is not reported. Before 0.10.14 a literal pattern matched
itself there.
</Callout>

<Callout type="info" title="Not to be confused with `evnx validate --pattern`">
`validate`'s `--pattern` was **removed** in the same release. It named a file to validate
and its entire implementation was a discarded argument. `scan --pattern` names a secret
format and works. Same word, opposite directions — see
[evnx validate](/guides/commands/validate).
</Callout>

### When to use which

| You want | Use |
|----------|-----|
| A named variable treated as secret, whatever it holds | `[vars] secret = true` — see [Declaring what the heuristics cannot know](#declaring-what-the-heuristics-cannot-know) |
| Any value of a given *shape* found, wherever it appears | `[[scan.patterns]]` |
| To try an expression once, without committing it | `--pattern` |

The first is about a variable, the other two about a format. A spec entry will not find your
token pasted into a `.ts` file; a pattern will not know that `TENANT_A` is a credential if
its value has no distinctive shape.

## Ignoring false positives

Some values look like secrets but are not — test fixtures, sample values, generated
tokens in a seed file.

<Callout type="warning">
⚠️ **Inline `# evnx-ignore` comments do not work.** This page has documented them; no
command reads them. A value marked `# evnx-ignore: test fixture` is still reported, and
there is no `[scan] ignore` key either.

`.evnx.toml`'s `[scan]` section **does** work — `severity`, `exclude`,
`ignore_placeholders`, `patterns`, `disable`, `builtins`, `extensions` and `max_file_size`
are all read, and `[vars] secret = false` retracts a name-based guess. On v0.4.x the loader
existed but nothing called it, which is where the older claim came from. See the
[`.evnx.toml` reference](/guides/reference/configuration-file).

The mechanisms below are the ones that exist.
</Callout>

### Skip files and paths — `--exclude`

Repeatable. Combines with `[scan] exclude` from `.evnx.toml` rather than replacing it — the
config holds the project's standing exclusions, the flag is this run's.

```bash
evnx scan --exclude 'fixtures/**' --exclude '*.test.js'
```

A value **with** `*`, `?` or `[` is a glob, tried against the path from the folder and
against the file name — so `fixtures/**`, `*fixtures*` and `*.log` all work. Any other value
matches a **whole path component** (**v0.10.14+**): `fixtures` skips `./fixtures/.env` and
`./test/fixtures/.env`, but `env` no longer skips `.env`. Before 0.10.14 a plain value
matched as a substring anywhere in the path. A file you name on the command line is read
whatever `--exclude` says.

<Callout type="warning">
**v0.5.0+.** Before this, a glob was only ever matched against the whole path *including*
its leading `./`, so `fixtures/**` and `*.log` matched nothing and did so silently. If you
worked around that with `*fixtures*` or a bare substring, those still behave exactly as they
did — the matching was widened, never redefined.
</Callout>

`.git/`, `node_modules/`, `target/`, `dist/`, `build/`, `.env.example`, `.env.sample`,
`.env.template`, editor swap files and `evnx backup` output are excluded already.

### Skip obvious placeholders — `--ignore-placeholders`

Drops values evnx recognises as filler — `changeme`, `your_api_key_here`, `xxx`, and the
like — before they are reported.

```bash
evnx scan --ignore-placeholders
```

### Raise the bar — `--severity` (v0.5.0+)

Usually the better answer for a noisy first run: report only what evnx is confident about,
rather than enumerating exceptions.

```bash
evnx scan --severity high
```

## Scanning a whole project

`evnx scan` is **already recursive**, and since **v0.10.3** it reads **every file** in a
folder. Binary files and files over 1 MiB (`--max-file-size`, **v0.10.14+**) are skipped,
and the scan says how many on stderr (`-v` lists each, with the reason; `--format json` has
a `skipped` list). A file you name is always read. Paths are positional:

```bash
# The default: this directory and everything under it
evnx scan

# One file
evnx scan config/.env.production

# Several paths
evnx scan .env config/ src/
```

`.git/`, `node_modules/`, `target/`, `dist/`, `build/`, the `.env.example` family, editor
swap files and `evnx backup` output are always skipped.

### In a git repository

**v0.10.14+.** A folder walk counts what git would commit. A filled-in `.env` that
`.gitignore` covers is where secrets belong, so its findings are summarised in one line and
do not fail the scan:

```text
  evnx scan  Checking for exposed secrets

  scanning ./.env, ./.env.bak, ./.gitignore

  ✓  No secrets in files git would commit

  3 files scanned
  ·  git ignores ./.env and ./.env.bak — 8 findings there are not counted, because they are not committed (--include-ignored lists them)
```

That exits `0`. `--include-ignored` counts them, and naming the file reports it in full:

```text
$ evnx scan .env
  …
  4 findings  ·  4 high

Next steps:
  1. git ignores .env and does not track it, so nothing was committed
  2. Rotate a key only if the file was shared another way — a copy, an archive, a container image
```

A file git **tracks** is always counted, ignored or not, because it is in the history.

<Callout type="warning" title="Before v0.10.3 a folder scan read only some extensions">
The walk read only files whose extension was on a built-in list, so `config/id_rsa.pem`
— a private key — or a live key in `app.swift` was never opened, and the scan said
"No secrets detected" and exited `0`. To limit a walk on purpose, opt in:

```bash
evnx scan --extensions env,yml,json
```

```toml
# .evnx.toml
[scan]
extensions = ["env", "yml", "json"]
```

Either way the run says it is limited — `scanning only files ending in .env, .yml, .json
in folders` — so a narrowed scan is never mistaken for a full one.
</Callout>

<Callout type="success">
**v0.5.0+** — a path that cannot be scanned is an error, exit `2`, not a clean result.
`evnx scan ./typo` used to print "No secrets detected" and exit `0`; it now names every
path it could not read and says plainly that there is no verdict.
</Callout>

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Clean — nothing at or above `--severity` in files git would commit, or `--exit-zero` was set |
| `1` | Findings reported, or a file that could not be read |
| `2` | **v0.5.0+** — the scan could not be completed, so there is no verdict |

**`2` is not a louder `1`.** "I found nothing" and "I could not look" are different
answers, and collapsing them is what let `evnx scan ./typo` report success. A gate written
as `evnx scan .` still fails on either; one that branches on the code can now tell a
finding from a broken setup.

```bash
evnx scan .
case $? in
  0) echo "clean" ;;
  1) echo "secrets found — blocking" ;;
  2) echo "scan did not run — fix the setup" ;;
esac
```

<Callout type="warning">
**`--exit-zero` suppresses `1` only.** Trouble still exits `2`: the flag means "do not fail
my build over findings", not "never tell me the scan was impossible".

Before v0.5.0 the table here claimed `1` meant *high-severity* findings and `2` meant a
scan error. Neither was true then — **any** finding exited `1`, errors exited `1` too, and
`scan` never returned `2`. It does now, and only for trouble.

To block only on high-confidence findings, say so: `evnx scan --severity high`.
</Callout>

<Callout type="tip" title="Advisory mode">
Use `--exit-zero` in environments where you want to report findings without blocking the pipeline. Good for first-pass onboarding when a codebase has known issues you're working through.
</Callout>
