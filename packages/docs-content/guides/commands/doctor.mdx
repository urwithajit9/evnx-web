`evnx doctor` checks the **setup around** your env files in one folder: that git
ignores them and does not track them, that they parse, that only you can read them,
that a template is committed beside them, and what kind of project they sit in. It
prints one line per check, a verdict, and an exit code a script can use. `--fix`
repairs the two things that can be repaired safely: `.gitignore` and file modes.

It does not look for secrets (that is [`evnx scan`](/guides/commands/scan)) and it
does not compare keys (that is [`evnx diff`](/guides/commands/diff) or
`evnx sync --check`). Every output on this page is from evnx 0.10.18.

## Command signature

```bash
evnx doctor [OPTIONS] [PATH]
```

| Argument | Default | Description |
|----------|---------|-------------|
| `PATH` | `.` | Project directory to check. `--path <PATH>` is the same thing; giving both is an error |

| Flag | Description |
|------|-------------|
| `--fix` | Repair what can be repaired: `.gitignore` entries and file modes. See [`--fix`](#--fix) |
| `--strict` | Count warnings as problems, so they affect the exit code |
| `--skip-without-env` | **v0.10.15+** — with no env file, skip (exit 0) and say so. For pre-commit hooks, **not** for CI |
| `--format <FORMAT>` | `pretty` (default) or `json`. An unknown value is an error, exit 2 |
| `-v`, `--verbose` | Show the detail line under every check, passed ones included |
| `-q`, `--quiet` | Print nothing on a healthy project. Problems and errors still print |
| `--no-color` | Disable colour |

| Environment variable | Same as |
|---|---|
| `EVNX_AUTO_FIX=1` | `--fix`. Either saying yes is enough; stderr says when the variable turned repair on |
| `EVNX_OUTPUT_JSON=1` | `--format json`. An explicit `--format` wins |

## What evnx doctor checks

Five checks, always in this order. The name in the first column is the one JSON uses.

| Check | What it looks at | Fails as |
|---|---|---|
| `env_file` | every env file: ignored by git, **not tracked**, valid dotenv | error |
| `env_example` | the template exists and is tracked by git | warning |
| `project_structure` | the project type, and whether it loads `.env` | warning (one case) |
| `docker_config` | Docker and Compose files | never fails |
| `file_permissions` | every env file is private: no access for group or others | warning |

### Which files count as env files

`.env` and `.env.<name>` — `.env.production`, `.env.local`, `.env.ci` — and
**plaintext copies** of them: `.env.bak`, `.env.backup`, `.env.old`, `.env.save`,
`.env~`. A copy holds the same secrets, so an unignored one is reported as an error.

Not env files: `.envrc`, `.environment`, `.env-notes.md`, and the template family
below, which is meant to be committed. An `evnx backup` file is recognised by its
content and left alone, because it is ciphertext.

### `env_file`

```text
  ✗  Validate .env file existence, security, and syntax
     .env is tracked by git: its values are in the repository history
     → git rm --cached .env, commit, then rotate every secret it held (`evnx scan .` lists them)
     .env.bak is NOT in .gitignore (security risk): a plaintext copy of an env file
     .env.production is NOT in .gitignore (security risk)
     .env.production: Line 2: invalid syntax 'this line is not dotenv'
```

Each of these is an **error**:

- **Tracked by git.** Ignoring a file that is already committed does not remove it:
  its values are in the history. doctor says so separately from "not in
  .gitignore", with the commands that fix it, including rotating the secrets.
- **Not ignored.** doctor asks git (`git check-ignore`), so patterns and negations
  count exactly as git counts them.
- **Invalid syntax**, named by file and line. A file that cannot be read, or is not
  UTF-8, is an error that says which. `.env.json` and `.env.yaml` get no dotenv check.

**With no env file at all**, what doctor says depends on what else is there:

| The folder has | doctor says | Exit |
|---|---|---|
| a template, no `.env` (a fresh clone) | error: `.env not found, though .env.example is here: this project expects one`, with `evnx sync --direction reverse` to create it | 1 |
| project files, no template | warning | 0 |
| nothing evnx recognises | `nothing to diagnose here` | 2 |

### `env_example` — the template

The template is `[defaults] example` from the project's `.evnx.toml` if set, otherwise
whichever of `.env.example`, `.env.sample` or `.env.template` is there. Messages name
the real file. It should exist and be tracked; if it is not tracked, doctor prints the
`git add` to run. It never runs it for you.

### `project_structure`

The first project type found is reported: Node.js (`package.json`), Python
(`requirements.txt`, `pyproject.toml`), Rust (`Cargo.toml`), Go (`go.mod`) or PHP
(`composer.json`). One case is a warning — a `requirements.txt` without
`python-dotenv`:

```text
  !  Detect project type and validate dependencies
     ✓ Detected Python project (Python (requirements))
     python-dotenv not in requirements.txt
```

Everything else here passes, and further hints appear only with `-v`.

### `docker_config`

Reports `Dockerfile`, `Containerfile`, `docker-compose.yml`, `docker-compose.yaml`,
`compose.yaml`, `compose.yml` and `.dockerignore` when present. It never fails.

### `file_permissions`

Every env file and plaintext copy must be **private**: no bits for group or others.
`600`, `400`, `700` and `500` pass; `640` and `644` do not. Each file is named:

```text
  !  Check file permissions for sensitive files
     .env.bak: permissions 644 (recommended: 600)
     .env.production: permissions 644 (recommended: 600)
```

On Windows the check is skipped and says so: it needs a Unix-like system.

### What doctor does not check

| Question | Command |
|---|---|
| Does `.env` have every key the template declares? | `evnx diff`, `evnx sync --check` |
| Is there a real-looking secret anywhere? | `evnx scan` |
| Are the values placeholders, weak, or malformed? | `evnx validate` |
| What about the other folders in this repository? | one `evnx doctor <dir>` per folder — it does not recurse |

## `--fix`

```bash
evnx doctor --fix
```

```text
✓ Fixed: .gitignore: added .env*, !.env.example, !.env.sample, !.env.template
  ✗  Validate .env file existence, security, and syntax
     .env is tracked by git: its values are in the repository history
     → git rm --cached .env, commit, then rotate every secret it held (`evnx scan .` lists them)
     .env.production: Line 2: invalid syntax 'this line is not dotenv'
     ! not fixed: --fix changed what it could; the problem above remains

  …

✓ Fixed: .env.bak mode 644 → 600
✓ Fixed: .env.production mode 644 → 600
  ✓  Check file permissions for sensitive files

  1 error  ·  1 warning  ·  2 checks passed
```

What it repairs:

| Problem | Repair |
|---|---|
| an env file git does not ignore | adds `.env*`, `!.env.example`, `!.env.sample`, `!.env.template` to `.gitignore` — the lines `evnx init` writes |
| an env file or plaintext copy that others can read | `chmod 600`, never on the template. A symlinked file only when its target is inside the project; otherwise the `chmod` to run is printed |

Every fix is **checked again** afterwards and reported on stderr as `✓ Fixed: …`. A
problem that remains says `not fixed`, and the run still exits 1 — above, the tracked
`.env` and the syntax error are for you to fix. Nothing is deleted, nothing is staged or
committed, and **no file's contents are edited**.

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Healthy. Warnings pass unless `--strict` |
| `1` | Problems found: an error, or a warning under `--strict`. Also a fix that did not work |
| `2` | No verdict |

`2` has three causes, and none of them is a clean result:

- **A bad path or flag** — `is not a directory evnx can read`, `--format xml`.
- **Nothing to diagnose** — a folder with no env file, no template and no project
  files:

  ```text
  Error: . has no env file, no .env.example and no project files: nothing to diagnose here

  No verdict: doctor examined nothing. This is not a clean result.
  ```

- **A check that could not finish** — `No complete verdict: 1 check could not run.`
  The JSON marks it with `"ran": false`.

```bash
evnx doctor
case $? in
  0) echo "healthy" ;;
  1) echo "problems — see the report" ;;
  2) echo "doctor did not run — fix the path or the folder" ;;
esac
```

## In CI

The exit code is the gate. Use `--strict` if warnings should fail the build too:

```yaml
# .github/workflows/env-health.yml
name: Environment Health Check

on: [pull_request]

jobs:
  doctor:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install evnx
        run: curl -fsSL https://dotenv.space/install.sh | bash

      - name: Run diagnostics
        run: evnx doctor --strict --format json > report.json

      - name: Upload report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: doctor-report
          path: report.json
```

`if: always()` keeps the report when the check fails, which is when you want it.

<Callout type="warning" title="A CI checkout usually has no .env">
In CI the `.env` is not in the repository, so a project with a template gets the
"`.env` not found" error. That is correct for a job that is supposed to have one.
Do **not** add `--skip-without-env` to make it pass: in CI a check that never ran
must not pass. Run doctor where the env file exists, or run
`evnx scan` and `evnx sync --check` instead.
</Callout>

## As a pre-commit hook

Use the hook evnx ships:

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/urwithajit9/evnx
    rev: v0.10.18
    hooks:
      - id: evnx-doctor
```

Its entry is `evnx doctor --skip-without-env`: errors fail the commit, warnings do
not, and a fresh clone with only a template is skipped instead of failing every new
contributor's first commit.

<Callout type="warning" title="A hand-written `entry: evnx doctor` fails fresh clones">
Since v0.10.15 a template without a `.env` is an error. A local hook that runs plain
`evnx doctor` therefore blocks the first commit in every fresh clone. Add
`--skip-without-env`, or switch to the shipped `evnx-doctor` hook.
</Callout>

## More than one folder

doctor checks one folder. For a repository with several services, run it once per
folder:

```bash
for dir in services/*/; do
  evnx doctor "$dir" || echo "issues in $dir"
done
```

## Troubleshooting

### "NOT in .gitignore" but it is

doctor asks git, so the usual causes are git's rules, not a typo:

- a later line un-ignores it — `!.env` after `.env*`;
- the file is **tracked**: git keeps tracking a committed file whatever `.gitignore`
  says. doctor reports that separately as "tracked by git".

```bash
git check-ignore -v .env      # which rule applies, if any
git ls-files .env             # prints .env if it is tracked
```

### "tracked by git: its values are in the repository history"

Follow the arrow line: `git rm --cached .env`, commit, then rotate every secret the
file held. `evnx scan .` lists them. Removing the file from the index does not remove
it from history.

### "nothing to diagnose here"

You ran doctor in a folder with no env file, no template and no project files, or in
the wrong folder. It exits 2 on purpose: an empty checkout must not pass as healthy.

### "not fixed"

`--fix` changed what it could, and the problem that remains is not one it repairs:
a tracked file, a syntax error, or a symlink target outside the project.

### Permission check on Windows

It is skipped, and says so: Windows has no Unix mode bits to read.
