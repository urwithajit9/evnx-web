This is the guide I wish had existed before my incident. It walks through the exact layered setup I now run on every project — multiple independent checks so that if one layer fails, the next catches it.

<Callout type="danger" title="Defense in depth">
No single tool is enough. Pre-commit hooks can be bypassed with `--no-verify`. CI can be skipped on certain branches. This guide sets up multiple independent layers so you'd have to actively defeat each one.
</Callout>

---

## The threat model

You're protecting against:

1. **Accidental commits** — you typed `git add .` when you meant `git add src/`
2. **Gitignore drift** — you added a new service directory but forgot to cover its `.env`
3. **Dependency confusion** — a new developer clones the repo and commits a real `.env`
4. **Rushed hotfixes** — 2 AM, production is down, you skip your usual process

The setup below catches all four.

---

## Layer 1 — gitignore (foundational)

Before anything else, make sure every `.env` in your project is covered. `evnx doctor`
checks the folder you run it in:

```bash
evnx doctor
```

It reports each env file git would commit, and each one it already tracks, as an error:

```text
  ✗  Validate .env file existence, security, and syntax
     .env is tracked by git: its values are in the repository history
     → git rm --cached .env, commit, then rotate every secret it held (`evnx scan .` lists them)
```

Let it fix what it can:

```bash
evnx doctor --fix
```

`--fix` adds `.env*`, `!.env.example`, `!.env.sample` and `!.env.template` to
`.gitignore` and makes readable env files `600`. It does not untrack a committed file,
create a template, or edit any file's contents: the arrow line above tells you what to
run for those.

<Callout type="warning" title="Monorepo gotcha: doctor does not recurse">
The most common failure mode is a monorepo where the root `.gitignore` covers `/.env`
but not `packages/*/.env` or `apps/*/.env`. **`evnx doctor` checks one folder**, so at
the root it can pass while `packages/api/.env` is committed. Run it in each folder that
has env files:

```bash
for dir in . packages/*/ apps/*/; do
  evnx doctor "$dir" || echo "issues in $dir"
done
```

`evnx scan` at the root does walk every folder, and reports secrets it finds anywhere.
</Callout>

Verify nothing is tracked that shouldn't be:

```bash
git ls-files | grep '\.env$'
# If this returns any real .env files, they're tracked — remove them:
git rm --cached packages/api/.env
```

## Layer 2 — pre-commit hook

The pre-commit hook is your primary defense. It runs before every `git commit` and blocks commits that contain secrets.

### Setup with the pre-commit framework (recommended for teams)

```bash
# Install pre-commit
pip install pre-commit
# or: brew install pre-commit
```

Create `.pre-commit-config.yaml` in your repo root, using the hooks evnx ships:

```yaml
repos:
  - repo: https://github.com/urwithajit9/evnx
    rev: v0.10.18
    hooks:
      # Layer 2a: secrets in the files being committed
      - id: evnx-scan
      # Layer 2b: env files git would commit (skipped in a clone with no .env)
      - id: evnx-doctor
```

`evnx-scan` runs `evnx scan` on the staged files. `evnx-doctor` runs
`evnx doctor --skip-without-env`: since v0.10.15 a template without a `.env` is an
error, so a hand-written `entry: evnx doctor` blocks the first commit in every fresh
clone. The shipped hook skips that case instead.

Install:

```bash
pre-commit install
# pre-commit installed at .git/hooks/pre-commit
```

Test it works. The test key is generated on the spot, in the live AWS format:

```bash
printf 'AWS_ACCESS_KEY_ID=AKIA%s\n' "$(LC_ALL=C tr -dc 'A-Z2-7' </dev/urandom | head -c 16)" > leak-test.txt

git add leak-test.txt
git commit -m "test: should be blocked"
```

```text
evnx — Secret Scanner.....................................Failed
- hook id: evnx-scan
- exit code: 1

  scanning leak-test.txt

  ✗  AWS Access Key                              high
     leak-test.txt:1  AKIA…XXXX
     !  matches a live key format, not a placeholder
     →  revoke at https://console.aws.amazon.com/iam

  1 finding  ·  1 high
```

Then clean up with `git rm --cached leak-test.txt && rm leak-test.txt`.

<Callout type="info" title="Why not AWS's example key?">
`AKIAIOSFODNN7EXAMPLE` is the key from AWS's own documentation. evnx recognises it as a
stand-in and does not report it, so a test that uses it passes the hook and proves
nothing.
</Callout>

### Setup for individual developers (simpler)

If you don't want to use the pre-commit framework:

```bash
cat > .git/hooks/pre-commit << 'HOOK'
#!/bin/bash
set -e

echo "evnx: scanning for secrets..."
evnx scan --severity high

echo "evnx: checking environment health..."
evnx doctor --skip-without-env

echo "evnx: all checks passed"
HOOK

chmod +x .git/hooks/pre-commit
```

<Callout type="info" title="Team distribution">
The `.git/hooks/` directory is not committed to the repo — each developer needs to run the setup individually. The `pre-commit` framework approach is better for teams because `.pre-commit-config.yaml` is committed, and `pre-commit install` is a one-time setup.
</Callout>

## Layer 3 — CI/CD gate

Pre-commit hooks can be bypassed with `git commit --no-verify`. CI cannot be bypassed.

Set up a GitHub Actions workflow that runs on every PR:

```yaml
# .github/workflows/evnx-security.yml
name: Secret scan

on:
  pull_request:
  push:
    branches: [main]

jobs:
  scan:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write

    steps:
      - uses: actions/checkout@v4

      - name: Install evnx
        run: curl -fsSL https://dotenv.space/install.sh | bash

      - name: Scan for secrets
        run: evnx scan --format sarif --severity high > evnx.sarif

      - name: Upload SARIF
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with:
          sarif_file: evnx.sarif
        continue-on-error: true
```

The scan step exits `1` when it finds something, which fails the job, and `if: always()`
still uploads the report to the Security tab. `--format github` instead prints
`::error` annotations on the pull request; it writes no SARIF file.

Set this workflow as a **required status check** in your branch protection rules:
`Settings → Branches → Branch protection rules → Require status checks`.

Now `git push --no-verify` still gets caught at the PR level.

## Layer 4 — .env.example discipline

Keep `.env.example` in sync with `.env`. When a developer clones the repo and copies `.env.example` to `.env`, they should get a complete list of required variables (with no real values).

```bash
# Generate .env.example from .env, values replaced by placeholders
evnx sync

# Check if they've drifted (exits 1 when the keys differ)
evnx diff
```

With no terminal, `evnx sync` writes placeholders without asking; `--force` does the
same on purpose. (`--placeholder` is deprecated: it does what `--force` does.)

Add the shipped hooks to the pre-commit config:

```yaml
  - repo: https://github.com/urwithajit9/evnx
    rev: v0.10.18
    hooks:
      # .env has every key .env.example declares
      - id: evnx-diff
      # .env.example declares every variable .env has
      - id: evnx-sync
```

`evnx-diff` runs `evnx diff --fail-on missing --skip-without-env` and `evnx-sync` runs
`evnx sync --check --direction forward --skip-without-env`. Both skip a clone that has
no `.env`. A hand-written `evnx diff` hook fails on extra keys as well as missing ones,
and exits 2 in a fresh clone.

## Layer 5 — migrate to a secret manager (optional but ideal)

The ultimate fix: stop storing secrets in `.env` files at all.

<Callout type="warning">
**`evnx migrate` generates the commands; it does not push, and it does not touch
your `.env`.** For eight of its nine destinations it prints the platform's own
CLI commands for you to run — only `github-actions` uploads. Nothing rewrites
`.env` into references; that is a migration you perform yourself once the secrets
are in the manager. See [`evnx migrate`](/guides/commands/migrate).
</Callout>


```bash
# Save the AWS Secrets Manager commands as a script you can read, then run
evnx migrate --to aws-secrets-manager --secret-name /myapp/prod --print-only > aws-upload.sh

# Print the Doppler commands
evnx migrate --to doppler --project myapp --doppler-config prod

# Upload to GitHub Actions secrets (token from the GITHUB_TOKEN environment variable)
evnx migrate --to github-actions --repo myorg/myapp
```

`--print-only` (new in 0.10.10) keeps evnx's status lines out of the file, so
`aws-upload.sh` holds only the commands. The GitHub upload asks before it starts;
without a terminal, add `--yes` and either `--skip-existing` or `--overwrite`.
Give it the token through `GITHUB_TOKEN` rather than `--github-token`, which
lands in your shell history.

Once the secrets are in the manager, you rewrite `.env` yourself to hold
references rather than values, in whatever form your application's loader
reads. **evnx does not do this step** — `migrate` only reads `.env`, and never
writes to it:

```bash
# illustrative: keys inside the JSON secret /myapp/prod
DATABASE_URL=secret:aws:///myapp/prod/DATABASE_URL
STRIPE_SECRET_KEY=secret:aws:///myapp/prod/STRIPE_SECRET_KEY
```

Your application reads the actual values at runtime from the secret manager — the `.env` file no longer contains anything sensitive.

## Verification checklist

After completing this setup, verify:

```bash
# 1. No .env files tracked by git
git ls-files | grep '\.env$'   # should return nothing

# 2. Doctor passes clean, in every folder that has env files
evnx doctor

# 3. Pre-commit hook is installed
ls .git/hooks/pre-commit       # should exist and be executable

# 4. Test the hook actually blocks (a generated key, not AWS's example key)
printf 'AWS_ACCESS_KEY_ID=AKIA%s\n' "$(LC_ALL=C tr -dc 'A-Z2-7' </dev/urandom | head -c 16)" > leak-test.txt
git add leak-test.txt && git commit -m "test"   # should be blocked
git rm --cached leak-test.txt && rm leak-test.txt

# 5. CI workflow exists
ls .github/workflows/evnx-security.yml
```

## Common failure modes

**"I bypassed the hook with --no-verify"** — That's why CI exists (Layer 3). The workflow catches what the hook misses.

**"My teammate didn't install the hook"** — Use the pre-commit framework and document it in your `CONTRIBUTING.md`. Make CI the mandatory gate.

<Callout type="warning">
Commands on this page previously used `--exit-code` on `scan`, `doctor` and `diff`. **That
flag does not exist on any of them** — all three already exit non-zero when they have
something to report.

`evnx doctor --fix` was also listed here as not existing. It does as of **v0.5.0**, and so
does `evnx doctor --strict`, which makes warnings count toward the exit code.
`EVNX_AUTO_FIX=1` still works. `--severity` needs **v0.5.0+**.
</Callout>

**"I have 200 existing issues in a legacy repo"** — Use `--exit-zero` mode in CI first to audit without blocking. Fix findings progressively, then drop `--exit-zero`, or raise `--severity`.

**"The hook is too slow and developers disable it"** — the `evnx-scan` hook reads only the staged files. If a scan is slow, it is reading more than you meant to — `node_modules`, `target` and `dist` are skipped automatically, so narrow it with `--exclude` or by naming paths explicitly.
