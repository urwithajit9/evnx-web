## The team sync workflow

### Key principles

1. **`.env.example` is the source of truth** for variable names
2. **`.env` is personal**: never committed, always gitignored
3. **Sync forward** shares a new variable with the team
4. **Sync reverse** brings the team's new variables into your `.env`

### Which check runs where

| Where | Command | Fails when |
|-------|---------|------------|
| Your own machine, before a PR | `evnx sync --check` | either file has a name the other lacks |
| Pre-commit hook | `evnx sync --check --direction forward --skip-without-env` (the shipped `evnx-sync` hook) | your `.env` has a name the template lacks |
| CI | `evnx sync --check --direction forward` | the template lacks a name `.env` has, or, with no `.env`, one the spec requires |

The two-way check also catches a `.env` that has fallen behind the template. That is
useful on your own machine and wrong in a hook: a teammate who has not pulled a new
variable into their `.env` yet should still be able to commit. Naming a direction makes
the check one-way.

## Scenario 1: Adding a new variable

**Context:** Alice needs `STRIPE_WEBHOOK_SECRET` for a new feature.

**Step 1: Alice adds it to her .env**

```bash
echo "STRIPE_WEBHOOK_SECRET=whsec_abc123" >> .env
```

**Step 2: Alice previews the template change**

```bash
evnx sync --direction forward --dry-run
```

```text
┌─ Variables to Add ───────────────────────────────────────────────────────────┐
│ Found 1 variable in .env missing from .env.example:                          │
│   • STRIPE_WEBHOOK_SECRET                                                    │
└──────────────────────────────────────────────────────────────────────────────┘


Preview:
Target: .env.example (action: Add)

  · STRIPE_WEBHOOK_SECRET = YOUR_KEY_HERE

(dry-run: no files were modified)
```

`·` marks a placeholder: the real value stays in her `.env`.

**Step 3: Alice applies it**

```bash
evnx sync --direction forward
```

At a terminal, sync asks:

```text
Add these to .env.example?:
> Yes, add with placeholder values (recommended)
  Yes, add with actual values ! SECURITY RISK
  Let me choose individually
  No, skip
```

She keeps the first answer and declines the optional comment:

```text
Add these to .env.example?: Yes, add with placeholder values (recommended)
Add a comment explaining these variables? no
✓ Updated .env.example (+1 variable)
```

**Step 4: Commit and push**

```bash
git add .env.example
git commit -m "feat: add STRIPE_WEBHOOK_SECRET to template"
git push
```

**Result for teammates:**

```text
APP_NAME=shop
DATABASE_URL=postgres://user:password@localhost:5432/dbname
STRIPE_SECRET_KEY=YOUR_KEY_HERE

# Synced from .env
STRIPE_WEBHOOK_SECRET=YOUR_KEY_HERE
```

<Callout type="warning" title="Don't commit secrets">
Alice's real value `whsec_abc123` stays in her `.env` only. The template gets the
placeholder `YOUR_KEY_HERE`, because the name has the word `SECRET`. Even the
"actual values" choice keeps a credential like this one out of the template.
</Callout>

## Scenario 2: Onboarding a new developer

**Context:** Bob joins the team and clones the repo. It has `.env.example`, committed,
and no `.env`, which is gitignored.

**Step 1: Bob clones and enters the project**

```bash
git clone git@github.com:team/project.git
cd project
```

**Step 2: Bob creates his .env from the template**

```bash
evnx sync --direction reverse
```

```text
· .env not found, creating from .env.example
✓ Created .env
! Replace placeholder values with real credentials!

Next steps:
  1. Edit .env and replace placeholder values with real credentials
  2. Never commit .env to version control
```

The new `.env` holds the template's values, working defaults included, and is created
readable by Bob only (`0600`), so there is no `chmod` to remember. If the project has a
[spec](/guides/commands/spec), the variables it requires are added too, under
`# Added by evnx sync: required by [vars] in .evnx.toml`.

**Step 3: Bob asks validate what is left to fill in**

```bash
evnx validate
```

```text
  ✗  STRIPE_SECRET_KEY looks like a placeholder
     .env
     →  Get from Stripe Dashboard

  ✗  STRIPE_WEBHOOK_SECRET looks like a placeholder
     .env
     →  Get from Stripe Dashboard

  2 errors
```

**Step 4: Bob fills in real values from the team's password manager**

```bash
nano .env
```

**Step 5: Bob validates again**

```bash
evnx validate
```

```text
✓ All required variables present
✓ All checks passed
```

✅ **Bob is ready to code.**

<Callout type="tip" title="Document the onboarding flow">
Add this to your README:

1. Clone the repo
2. Run `evnx sync --direction reverse` to create `.env`
3. Fill in the values `evnx validate` reports, from [password manager]
4. Run `evnx validate` until it passes
</Callout>

## Scenario 3: Handling merge conflicts in .env.example

**Context:** Alice and Bob both add different variables and push around the same time.

**Step 1: Alice pushes first; Bob's push is rejected**

```bash
git push
# ✗ rejected: remote contains work you don't have
```

**Step 2: Bob pulls and sees a conflict**

```bash
git pull
# CONFLICT (content): Merge conflict in .env.example
```

**Step 3: Bob keeps both new variables and removes the conflict markers**

```bash
nano .env.example
```

**Step 4: Bob checks his own pair, both ways**

```bash
evnx sync --check
```

```text
┌─ Only in .env.example ───────────────────────────────────────────────────────┐
│ Found 1 variable in .env.example that .env does not have:                    │
│   • STRIPE_WEBHOOK_SECRET                                                    │
└──────────────────────────────────────────────────────────────────────────────┘

✗ Out of sync.
  · 1 variable in .env.example is not in .env: remove it from .env.example, or add it to .env with `evnx sync --direction reverse`.
```

Alice's variable is now in the template and not yet in Bob's `.env`. Exit `1`.

**Step 5: Bob brings it into his .env, then completes the merge**

```bash
evnx sync --direction reverse
git add .env.example
git commit -m "Resolve merge conflict in .env.example"
git push
```

<Callout type="success" title="Why this works">
`.env.example` holds names and placeholders, no secrets, so a conflict in it is safe to
resolve by hand.
</Callout>

## Scenario 4: Syncing before a pull request

**Best practice:** check your own pair before you open a PR that adds environment
variables.

```bash
evnx sync --check
```

**If it reports a variable missing from `.env.example`:**

```bash
# 1. Add it to the template, with a placeholder
evnx sync --direction forward

# 2. Commit the template change
git add .env.example
git commit -m "chore: sync .env.example with new variables"

# 3. Now create your PR
gh pr create --title "feat: add new feature"
```

**In your PR description:**

```markdown
### Environment changes
- Added `NEW_API_KEY` to `.env.example` (placeholder: `YOUR_KEY_HERE`)
- No secrets committed: all values are placeholders

Preview (`evnx sync --direction forward --dry-run`):
  · NEW_API_KEY = YOUR_KEY_HERE
```

## Communication best practices

### When to notify the team

| Change | Notify team? | How |
|--------|-------------|-----|
| New required variable | Yes | Slack/PR description |
| Removed variable | Yes | Deprecation notice in PR |
| Changed placeholder pattern | Maybe | Update `.evnx/placeholders.json` + docs |
| Security-related variable | Yes | Direct message + PR |

### Template for team notifications

```markdown
**Environment update** 🔄

A new environment variable has been added:

- **Name:** `NEW_SERVICE_URL`
- **Purpose:** URL for the new analytics service
- **Template value:** `https://your-api-url-here.com`
- **Required:** Yes (the app won't start without it)

**Action needed:**
1. Pull the latest changes: `git pull`
2. Add it to your .env: `evnx sync --direction reverse`
3. Replace the value with the real URL from [password manager]
4. Validate: `evnx validate`

Questions? Reply here or ping @env-team.
```

## Avoiding common team pitfalls

### "It works on my machine"

**Problem:** a developer has a variable locally that is not in `.env.example`.

**Prevention:** the shipped pre-commit hook, which blocks the commit until the template
declares every name in your `.env`:

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/urwithajit9/evnx
    rev: v0.10.18
    hooks:
      - id: evnx-sync
```

It runs `evnx sync --check --direction forward --skip-without-env`. On a fresh clone with
no `.env` and no spec there is nothing to compare, so it says it skipped and lets the
commit through. In CI, run the same check without `--skip-without-env`; there a check
that compared nothing must fail:

```bash
evnx sync --check --direction forward
```

### Secrets in .env.example

**Problem:** someone commits real values to the template.

**Prevention:**

1. Preview with `--dry-run` before every forward sync, and read the value column
2. Keep the "actual values" choice and `allow_actual` for configuration such as
   `LOG_LEVEL`; evnx refuses credentials in both, but the template is still a public file
3. Use custom placeholders that look fake: `sk_demo_XXXXXXXX`
4. Add a CI check: `grep -E "(sk_live|password)" .env.example && exit 1`

### .env in Git

**Problem:** `.env` should never be in Git, but someone commits it.

**Prevention:**

1. Ensure `.env` is in `.gitignore` from day one
2. Add a pre-commit hook that blocks `.env` commits
3. Teach the team: if you see `.env` in `git status`, do not add it

## Advanced: custom placeholders for teams

Create `.evnx/placeholders.json` for consistent team patterns:

```json
{
  "patterns": {
    ".*_API_KEY$": "sk_demo_XXXXXXXXXXXXXXXX",
    ".*_SECRET$": "demo_secret_placeholder",
    "^DATABASE_URL$": "postgresql://demo:demo@localhost:5432/demo_db"
  },
  "default": "REPLACE_IN_PRODUCTION"
}
```

**Team workflow:**

1. Commit `.evnx/placeholders.json` to the repo
2. Use it on every run, CI included: `evnx sync --template-config .evnx/placeholders.json`
3. Document in the README: "We use custom placeholders — see `.evnx/`"

A misspelt key in the file is an error (exit `2`), so a typo cannot quietly switch a
rule off. The [configuration reference](/guides/reference/sync-configuration) has the
full format.

## Checklist: team sync health

Run this monthly or when onboarding:

```bash
# 1. My own pair, both ways (exit 1 if either file has a name the other lacks)
evnx sync --check

# 2. Look for secrets in the template
grep -iE "(sk_live|password|secret)" .env.example | grep -v "YOUR_\|placeholder\|demo" && echo "⚠️  Potential secrets found!"

# 3. Names sync would add follow UPPER_SNAKE_CASE (exit 2 names the first that does not)
evnx sync --dry-run --naming-policy error

# 4. Confirm .gitignore is correct
git check-ignore .env  # Should output: .env

# 5. Test the onboarding flow in a fresh clone
mkdir /tmp/test-onboarding && cd /tmp/test-onboarding
git clone <repo> .
evnx sync --direction reverse   # creates .env from the template
evnx sync --check               # exit 0
```

<Callout type="info">
`--naming-policy error` checks the names sync would write: names new to the template,
or all of them when it creates one. A name already in both files passes. With nothing
to add, step 3 says `.env.example is up to date` and exits `0`.
</Callout>
