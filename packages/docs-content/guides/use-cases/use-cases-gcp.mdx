# Migrate to GCP Secret Manager

`evnx migrate --to gcp-secret-manager --project my-gcp-project` prints a short `gcloud` script: one line per variable, each piping its value to `gcloud` on stdin. The script creates each secret, or adds a new version when the secret already exists, so you can run it again after a value changes.

  <Prerequisite href="/guides/getting-started/installation">Install evnx</Prerequisite>

</Prerequisites>

## What you need

- `gcloud` CLI installed and authenticated (`gcloud auth login`)
- The ID of the GCP project that will hold the secrets — evnx needs it as `--project`
- The Secret Manager API enabled in that project (`gcloud services enable secretmanager.googleapis.com --project=my-gcp-project`)

evnx does not need GCP credentials and contacts nothing — it only prints the script. You run it.

---

## What evnx generates

Unlike AWS (one JSON object), GCP Secret Manager stores **one secret per variable**. For a `.env` with three variables, evnx prints:

```bash
# Creates each secret, or adds a new version when it already exists.
upsert_secret() {
  if gcloud secrets describe "$1" --project=my-gcp-project </dev/null >/dev/null 2>&1; then
    gcloud secrets versions add "$1" --data-file=- --project=my-gcp-project
  else
    gcloud secrets create "$1" --data-file=- --project=my-gcp-project
  fi
}

printf '%s' 'postgres://user:pass@host:5432/db' | upsert_secret DATABASE_URL
printf '%s' 'sk_test_example' | upsert_secret STRIPE_SECRET_KEY
printf '%s' 'redis://localhost:6379/0' | upsert_secret REDIS_URL
```

- `upsert_secret` asks `gcloud secrets describe` whether the secret exists. If it does, it runs `gcloud secrets versions add`; if not, `gcloud secrets create`. Every `gcloud` call names the project.
- Each value is written into the script in single quotes, exactly as it is in your `.env`, and reaches `gcloud` on stdin (`--data-file=-`). `printf` is a shell builtin, so the value is not in any process's argument list.
- Names stay exactly as they are in the `.env`: `DATABASE_URL` is stored as `DATABASE_URL`.
- There is no `--replication-policy` flag. `gcloud secrets create` uses an automatic replication policy when none is given — see [Replication policy](#replication-policy).

<Callout type="warning">
  <strong>The script contains your secret values.</strong> They are printed to your terminal, and written to the file if you save the script. Delete the file once it has run, and never commit it.
</Callout>

<Callout type="info">
  <strong>Changed in 0.10.10.</strong> Earlier versions printed <code>{'echo -n "${DATABASE_URL}" | gcloud secrets create DATABASE_URL --data-file=- --replication-policy=automatic'}</code>. That took the value from a shell variable of the same name — usually unset, so the secret was created empty — failed on a second run because the secret already existed, and left out <code>--project</code>. If you kept a script made by an older version, generate it again.
</Callout>

<Callout type="info">
  <strong>evnx convert prints the same script with different names.</strong> <code>evnx convert --to gcp-secrets --project my-gcp-project {">"} upload.sh</code> writes the same <code>upsert_secret</code> script, but names secrets in lowercase with <code>-</code> (<code>DATABASE_URL</code> becomes <code>database-url</code>), where <code>migrate</code> keeps the names as they are. Pick one, or the two will create differently named secrets.
</Callout>

## Basic usage

```bash
evnx migrate --to gcp-secret-manager --project my-gcp-project
```

`gcp` is accepted as a shorthand:

```bash
evnx migrate --to gcp --project my-gcp-project
```

`--project` is required. In a terminal, evnx asks for it (`GCP project ID:`) when you leave it out. Without a terminal, or with `--dry-run`, a missing `--project` is an error, exit 2, and nothing is printed:

```text
✓ Loaded 5 secrets from .env
Error: GCP project ID is required. Pass `--project`.
  evnx would normally ask, but stdin is not a terminal.
```

evnx also checks the ID's shape — 6–30 lowercase letters, digits and hyphens, starting with a letter and not ending with a hyphen — and refuses anything else before printing.

## Step-by-step walkthrough

<Step title="Authenticate and enable the API">
```bash
gcloud auth login
gcloud services enable secretmanager.googleapis.com --project=my-gcp-project
```
</Step>

<Step title="Validate your .env">
```bash
evnx validate --strict
```
</Step>

<Step title="Preview the migration">
```bash
evnx migrate --to gcp --project my-gcp-project --dry-run
```

```text
  evnx migrate  Generate destination commands from your .env

· Requires Google Cloud CLI (`gcloud`)
  Install: https://cloud.google.com/sdk/docs/install

Dry-run — would upload to GCP Secret Manager:
  Project : my-gcp-project
  Secrets : 5

Summary:
  ·  5 secret(s) previewed
     dry run — nothing was uploaded and nothing was written
…
```

A dry run prints the count, not the script.
</Step>

<Step title="Filter what you need">
```bash
evnx migrate \
  --to gcp \
  --project my-gcp-project \
  --exclude "*_LOCAL,*_TEST" \
  --dry-run
```

```text
✓ Loaded 5 secrets from .env
· After filtering: 3 of 5 secrets remain.
…
Dry-run — would upload to GCP Secret Manager:
  Project : my-gcp-project
  Secrets : 3
…
```
</Step>

<Step title="Generate and run the script">
Save only the script with `--print-only`, read it, then run it:

```bash
evnx migrate \
  --to gcp \
  --project my-gcp-project \
  --exclude "*_LOCAL,*_TEST" \
  --print-only > gcp-upload.sh

cat gcp-upload.sh    # inspect
bash gcp-upload.sh   # run
rm gcp-upload.sh     # it holds every value
```

With `--print-only`, stdout carries only the script; the status lines and the summary still appear in your terminal, on stderr. You can also pipe it straight into a shell:

```bash
evnx migrate --to gcp --project my-gcp-project --exclude "*_LOCAL" --print-only | bash
```

Use `--print-only` whenever the output goes to a file or a shell. Without it, stdout also holds the status lines and the summary, so `> gcp-upload.sh` does not save a script, and `| bash` stops at a syntax error on the `· Requires Google Cloud CLI` line before it reaches the first `gcloud` call. (Earlier versions of this page showed both without the flag, plus `set -a && source .env` to export the values first. The values are in the script now, so nothing needs exporting.)
</Step>

<Step title="Grant access to your service accounts">
Each secret must be granted to the service account your application runs as:

```bash
gcloud secrets add-iam-policy-binding DATABASE_URL \
  --project=my-gcp-project \
  --member="serviceAccount:myapp@my-gcp-project.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"
```
</Step>

## Updating existing secrets

Run the script again. For a secret that already exists it runs `gcloud secrets versions add` instead of `create`, so a second run adds a new version rather than failing. evnx itself decides nothing here — it never contacts GCP; the script checks each secret when it runs.

A re-run adds a version to every secret in the script, including those whose value did not change. To send only what changed, select it with `--include`:

```bash
evnx migrate \
  --to gcp \
  --project my-gcp-project \
  --include "DATABASE_URL" \
  --print-only > gcp-update.sh
```

## Replication policy

The script names no replication policy, so `gcloud secrets create` uses an automatic one, which lets GCP choose the storage regions. (Earlier versions printed `--replication-policy=automatic` explicitly; the result is the same.) For a specific region, edit the `create` line inside `upsert_secret` before running the script:

```bash
    gcloud secrets create "$1" --data-file=- --project=my-gcp-project \
      --replication-policy=user-managed --locations=us-central1
```

The `versions add` line takes no replication flag: a secret's replication is set when it is created.

## Reading secrets in your application

GCP-native applications can use the Secret Manager client library:

```python
from google.cloud import secretmanager

client = secretmanager.SecretManagerServiceClient()
name = "projects/PROJECT_ID/secrets/DATABASE_URL/versions/latest"
response = client.access_secret_version(request={"name": name})
DATABASE_URL = response.payload.data.decode("UTF-8")
```

Or in Cloud Run / GKE, mount secrets as environment variables via the `--set-secrets` flag or a pod spec — no code changes needed.

## Minimum IAM permissions

For running the script (migration time):

| Role | When |
|------|------|
| `roles/secretmanager.admin` | Any secret in the script is new — it is checked with `describe`, then created |
| `roles/secretmanager.secretVersionAdder` | Adding versions to existing secrets |

The script treats any failure of `gcloud secrets describe` as "does not exist", because it discards that command's output. If the account may add versions but not describe the secret, the script falls through to `gcloud secrets create`, which then fails because the secret already exists.

For reading secrets (application runtime):

| Role | Scope |
|------|-------|
| `roles/secretmanager.secretAccessor` | Grant per secret or at project level |
