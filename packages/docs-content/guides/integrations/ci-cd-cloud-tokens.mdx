Pipelines are the main reason a `.env` sync tool exists. This guide covers getting secrets into one safely — and, just as importantly, what you are actually granting when you do.

## Read this before you configure anything

<Callout type="danger" title="A token authenticates. It does not decrypt.">
This is the part that surprises people, and it is a consequence of zero-knowledge rather than a gap in the tooling.

An API token proves to the server *who you are*. It does not open anything. Your vault key is wrapped under a key derived from your master password, and **only that password unwraps it**.

So a pipeline that needs plaintext needs the master password too. There is no arrangement in which the server hands a runner usable secrets on a token alone — if there were, the server could decrypt your vaults itself, and the whole guarantee would be theatre.
</Callout>

What this buys you, and what it costs:

| | |
|---|---|
| **The token** | Scoped, revocable, safe to rotate. Limits *which vault* and *whether writes are allowed* |
| **The master password** | Not scopeable. Whatever reaches the runner can decrypt every vault you own |

Treat the master password in CI as a decision with a blast radius, not a config value.

## The recommended setup: three secrets

**v0.14.0+** — A pipeline that decrypts needs three things, and each is a CI secret:

| CI secret | What it is | Made with |
|-----------|-----------|-----------|
| `EVNX_TOKEN` | The API token. Authenticates, scoped to a vault | `evnx auth token create` |
| `EVNX_MASTER_PASSWORD` | Your master password. Unlocks the vault key | You already have it |
| `EVNX_KEY_BUNDLE` | Your sealed key material (`evnxkb1_…`) | `evnx auth token create` prints it, or `evnx auth key-bundle` |

With all three set, `evnx cloud pull`, `cloud run` and the rest need no prompt and no
`--password-stdin`:

```bash
export EVNX_TOKEN=evnx_tok_…
export EVNX_MASTER_PASSWORD=…
export EVNX_KEY_BUNDLE=evnxkb1_…
evnx cloud run --vault "$EVNX_VAULT_ID" -- ./deploy.sh
```

**The key bundle** is your sealed keypair and the Argon2 salt, and it contains **no
plaintext secret**: the master password still opens it, and the bundle alone opens nothing.
Store it like the token (a CI secret, not a committed file, not a log line). It is the same
sealed material your account holds, exported once from a signed-in machine so that a token
does not need to fetch it.

Create it when you create the token. `evnx auth token create` prints both, once:

```bash
evnx auth token create ci-deploy --scope read --vault my-api/production
```

and `--no-key-bundle` skips the bundle. With `-q`, only the token is printed, so a script can
capture it. For the bundle on its own, on a machine where you are signed in:

```bash
evnx auth key-bundle
evnx auth key-bundle -q       # the bundle alone, nothing else
```

`key-bundle` needs a real login, not a token. It prints the bundle and a short reminder to
store it as `EVNX_KEY_BUNDLE`. Run it again to rotate CI, or after a master-password change.

### From a file

Where a secret is easier to mount as a file than to set as a variable, name the file instead.
`EVNX_KEY_BUNDLE_FILE` holds the path; the **first line** of the file is the bundle. The
variable `EVNX_KEY_BUNDLE` is read first.

```bash
export EVNX_KEY_BUNDLE_FILE=/run/secrets/evnx-key-bundle
```

The master password has the same two spellings. `EVNX_MASTER_PASSWORD_FILE` names a file whose
first line is the password; it is read before `EVNX_MASTER_PASSWORD`, and `--password-stdin`
beats both. evnx says on stderr that it is using the variable or file, without the value.

### After you change your master password

A bundle made before a master-password change no longer opens. The run stops with:

```text
Error: that master password did not open the key bundle in EVNX_KEY_BUNDLE.
  If the master password was changed after the bundle was made, the old bundle no longer unlocks: regenerate the key bundle with `evnx auth key-bundle` on a signed-in machine and replace the CI secret. Otherwise check the password.
```

Run `evnx auth key-bundle`, replace `EVNX_KEY_BUNDLE`, and update `EVNX_MASTER_PASSWORD` in the
same step.

### Without a bundle

A token with no `EVNX_KEY_BUNDLE` (or `EVNX_KEY_BUNDLE_FILE`) has no key material to unlock
with. evnx asks the server for it once; when the server will not give it to a token, the run
exits `11`:

```text
Error: this server no longer gives key material to API tokens: create a key bundle with `evnx auth key-bundle` on a signed-in machine and store it as EVNX_KEY_BUNDLE
```

That is the signal to add the third secret. A value that is not a bundle gets one of three
messages instead: it does not start with `evnxkb1_` (or was cut short when pasted), its body
is damaged, or it is a version this evnx does not read. In every case, create a new one with
`evnx auth key-bundle`.

`evnx auth status` under a token shows whether the bundle is there:

```text
evnx account
  server    https://api.evnx.dev
  client    evnx 0.14.0
  using     API token (from EVNX_TOKEN)
  key bundle  set (EVNX_KEY_BUNDLE)
  account   details need a signed-in session (`evnx auth login`)
```

(`not set` and `from file (EVNX_KEY_BUNDLE_FILE)` are the other two readings.)

## Minting a token

<CodeTabs defaultTab="CLI">
  <Tab label="CLI">
```bash
evnx auth token create ci-deploy --scope read --vault my-api/production --expires-in-days 90
evnx auth token list
evnx auth token revoke ci-deploy
```

The name is **positional**. `--scope` is `read` or `read_write`; omitting `--expires-in-days`
mints a token that never expires. **v0.14.0+** — `create` also prints the
[key bundle](#the-recommended-setup-three-secrets) to store as `EVNX_KEY_BUNDLE`; both are
shown once, and `--no-key-bundle` leaves the bundle out. With `-q` (**v0.10.18+**) the new
token is the only thing printed, alone on stdout, so it can go straight into your CI
provider's secret store:

```bash
evnx auth token create ci-deploy --scope read --vault my-api/production -q
```
  </Tab>
  <Tab label="Dashboard">
**[app.evnx.dev](https://app.evnx.dev)** → Settings → API tokens → New token.

Name, scope, vault and an expiry in days — the same four inputs as the CLI flags, hitting
the same endpoint and producing the same credential. The expiry field defaults to 90 days;
blank or `0` means never.

The list view adds one thing the CLI shows too but is easier to scan here: a **last-used**
timestamp per token, which is how you find the credential that has been sitting unused in a
retired pipeline.
  </Tab>
</CodeTabs>

<Callout type="warning" title="Shown once">
`create` prints the token exactly once. The server stores only a BLAKE3 hash, so there is no command that shows it again. Lose it and you revoke and re-mint. (The key bundle is different: `evnx auth key-bundle` prints it again.)
</Callout>

**Minting requires a real login.** Token creation sits behind a session-only guard, so a leaked CI token cannot quietly mint itself a longer-lived, wider-scoped replacement and survive revocation of the original. If you rotate a compromised token, it stays rotated.

## Scope it down

Two limits are enforced on the server, in the auth middleware rather than in each handler:

<Step number={1} title="Read-only unless the job genuinely writes">
Anything that is not GET, HEAD or OPTIONS is refused for a read-only token. Deploys only pull, so read-only covers them. Reserve read-write for a job that actually pushes — a rotation task, say.
</Step>

<Step number={2} title="One vault, not the account">
A vault-scoped token reaches only that vault. Routes with no vault in the path — listing vaults, creating one — are refused outright, because enumerating your account is outside what a deploy token was issued for.
</Step>

### Name the vault by its id

Because a vault-scoped token cannot list vaults, it cannot turn a **name** into a vault
either. Pass the vault's **id** in a pipeline. By name, the command stops and says so:

```text
Error: a vault-scoped API token cannot list vaults, so "my-api/production" cannot be resolved by name.
  Pass the vault's id in place of its name.
  Find it with `evnx vault list --verbose` from a normal login. The restriction is deliberate — a token issued for one vault should not be able to enumerate the others.
```

Find the id once, from your own login:

```bash
evnx vault list --verbose
```

```text
  0453e5f6-f1fd-476c-b083-626430cb7639 my-api/production
```

By id, a vault-scoped token works with `cloud pull`, `run`, `export`, `history`,
`diff`, `watch` and `audit`, and with `evnx vault members` (**v0.10.18+**; before, it
failed with a bare "Insufficient permissions"). `cloud push` works by id with a
`read_write` token. The examples below keep the id in a CI variable, `EVNX_VAULT_ID`.
It is not a secret.

A push by id with a token is **not** asked the production question that a push of the
default `.env` asks a signed-in user: the token cannot look up the vault's environment.
Name the file with `--file` anyway, so the job pushes what you mean.

<Callout type="info" title="Why refusals are 403 and not 401">
A token that reaches an account-management route gets **403**, deliberately distinct from 401. The credential was recognised; it is the wrong *kind*. That distinction is what tells you "rotate the scope" rather than "the token is broken".
</Callout>

## GitHub Actions

<CodeTabs defaultTab="Read-only deploy">
  <Tab label="Read-only deploy">
```yaml
name: Deploy

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install evnx
        run: curl -fsSL https://dotenv.space/install.sh | bash

      - name: Fetch secrets
        env:
          EVNX_TOKEN:           ${{ secrets.EVNX_TOKEN }}
          EVNX_MASTER_PASSWORD: ${{ secrets.EVNX_MASTER_PASSWORD }}
          EVNX_KEY_BUNDLE:      ${{ secrets.EVNX_KEY_BUNDLE }}
          EVNX_VAULT_ID:        ${{ vars.EVNX_VAULT_ID }}
        run: evnx cloud pull --vault "$EVNX_VAULT_ID" --file .env --yes

      - name: Deploy
        run: ./deploy.sh
```
  </Tab>
  <Tab label="Audit only — no password">
```yaml
# History and metadata need no password and no decryption, so this job
# cannot leak a secret even if the runner is compromised.
- name: Check what changed
  env:
    EVNX_TOKEN: ${{ secrets.EVNX_TOKEN }}
    EVNX_VAULT_ID: ${{ vars.EVNX_VAULT_ID }}
  run: evnx cloud history --vault "$EVNX_VAULT_ID" --limit 5
```
  </Tab>
  <Tab label="GitLab CI">
```yaml
deploy:
  script:
    - curl -fsSL https://dotenv.space/install.sh | bash
    - evnx cloud pull --vault "$EVNX_VAULT_ID" --file .env --yes
  variables:
    EVNX_TOKEN: $EVNX_TOKEN
    EVNX_MASTER_PASSWORD: $EVNX_MASTER_PASSWORD
    EVNX_KEY_BUNDLE: $EVNX_KEY_BUNDLE
    EVNX_VAULT_ID: $EVNX_VAULT_ID
```
  </Tab>
</CodeTabs>

<Callout type="tip" title="Reading the password from a pipe instead">
`EVNX_MASTER_PASSWORD` is the simplest way to hand evnx the password, and evnx says on stderr that it used it. If you would rather keep it out of the environment, `--password-stdin` still works and beats the variable. Use `printf '%s'`, not `echo`: `printf` writes the password with no trailing newline and no interpretation of backslashes, and a passphrase containing a backslash can silently become a different password under `echo`.

```bash
printf '%s' "$MASTER_PASSWORD" | evnx cloud pull --vault "$EVNX_VAULT_ID" --file .env --yes --password-stdin
```
</Callout>

## Prefer `evnx cloud run` over writing a file

**Added in v0.5.0.** Every example above ends with `--file .env`, which writes your
decrypted secrets to the runner's filesystem. They then live there for the rest of the
job, readable by every later step, and land in any artifact or cache that picks up the
working directory.

`evnx cloud run` hands them to one process instead:

```yaml
- name: Deploy
  env:
    EVNX_TOKEN: ${{ secrets.EVNX_TOKEN }}
    EVNX_MASTER_PASSWORD: ${{ secrets.EVNX_MASTER_PASSWORD }}
    EVNX_KEY_BUNDLE: ${{ secrets.EVNX_KEY_BUNDLE }}
    EVNX_VAULT_ID: ${{ vars.EVNX_VAULT_ID }}
  run: evnx cloud run --vault "$EVNX_VAULT_ID" -- ./deploy.sh
```

Nothing is written to disk, nothing enters shell history, and nothing appears in `ps` —
the values travel in the child's environment block, never in its argument vector. evnx's own
variables (`EVNX_TOKEN`, `EVNX_MASTER_PASSWORD`, `EVNX_KEY_BUNDLE` and the `_FILE` forms) are
not passed on to the child. The
child's exit code is returned unchanged (**v0.13.0+**: `10`–`15` can only come from a
failure before the child starts), so it gates the job exactly as the script would on its
own.

`--include` and `--exclude` narrow what the child sees, and a filter matching nothing is
an error rather than a silent run with no secrets.

**v0.13.0+** — `--vault` can be repeated: `evnx cloud run --vault "$SHARED_ID" --vault "$APP_ID" -- ./deploy.sh`
opens every vault with one password unlock and merges them left to right. A key held by
two of them stops the run with exit `2` before the command starts, unless you add
`--allow-override` (the later vault wins). `--version` is refused with more than one
vault, and `cloud pull` takes repeated `--vault` the same way.

<Callout type="warning">
  ⚠️ **This removes the plaintext *file*, not the master password.** The vault key is
  wrapped under your master key, so decryption still needs it wherever this runs — feed it
  with `EVNX_MASTER_PASSWORD` (or `--password-stdin`) exactly as `pull` does. The token scopes what can be read; the
  password is what decrypts it.
</Callout>

The command runs directly rather than through a shell. For a pipeline or a shell builtin,
ask for one: `-- sh -c 'a | b'`.

Use `cloud pull --file` when something later in the job genuinely needs a file on disk —
a container build context, a tool that only reads `.env`. Otherwise `cloud run` is
strictly less exposure for the same result.

## Retry by exit code

**v0.13.0+** — A cloud command that fails because of the server exits with a code that
says which kind of failure it was, so a job can retry the ones worth retrying and stop
on the rest, without reading the message:

| Code | Meaning | In a pipeline |
|-----:|---------|---------------|
| `10` | not signed in, or the token was refused | stop: the token is wrong, expired or revoked |
| `11` | forbidden: role too low, not a member, token scope, or email not verified | stop: fix the token's vault or scope |
| `12` | plan limit reached | stop: a human has to change the plan or delete something |
| `13` | server unreachable, or a proxy or firewall answered instead | retry |
| `14` | conflict, or the account is locked | stop: pull and reconcile; a retry of the same push cannot succeed |
| `15` | server error, or rate limited | retry, after the `Try again in N s.` the message gives |

```bash
for attempt in 1 2 3; do
  evnx cloud pull --vault "$EVNX_VAULT_ID" --file .env --yes
  code=$?
  case "$code" in
    0)        break ;;
    13|15)    sleep $((attempt * 10)) ;;   # transient: wait, then try again
    *)        exit "$code" ;;              # 10, 11, 12, 14 and everything else: do not retry
  esac
done
[ "$code" -eq 0 ] || exit "$code"
```

`evnx cloud run` is different. Once the command has started, `run` returns **the
command's own exit code**, so a `13` or `15` from `run` means the child chose it. The
codes above can only come from a failure before it started (for example, the token was
refused). Do not wrap `run` in a retry loop that treats `13` and `15` as "try again" if the
command may already have done part of its work; fetch with `pull` and retry that, or make
the command safe to run twice.

A script that tested for exactly `1` or `2` after a cloud command needs to accept these
codes. The full table, and what the `403` reasons say, are in
[evnx cloud](/guides/commands/cloud#exit-codes-for-server-failures).

## Reducing what you expose

**Prefer a job that needs no password at all.** `evnx cloud history` is read-only in the strongest sense: no password prompt, no decryption, no blob download. Drift checks and audit steps can run with a read-only token and nothing else.

**Give each pipeline its own token.** One token per pipeline means revoking one does not break the others, and the audit trail tells you which pipeline did what.

**Write the `.env` and delete it.** On a container runner the filesystem is discarded anyway, but on a self-hosted runner it is not:

```bash
trap 'rm -f .env' EXIT
evnx cloud pull --vault "$EVNX_VAULT_ID" --file .env --yes
```

**Use `-q` in jobs.** **v0.10.18+** every cloud command prints nothing on success under
`-q`, while warnings and errors still reach the log. A step that read a `✓ pulled …`
line from stdout gets nothing under `-q`; check the exit code instead (`0` done, `2`
refused or failed locally, and **v0.13.0+** `10`–`15` when the server refused or failed;
see [Retry by exit code](#retry-by-exit-code)).

**Never `cat` the file.** A `.env` echoed into a build log is a `.env` in your CI provider's log retention, readable by everyone with repository access.

## Rotating a token

```bash
evnx auth token revoke ci-deploy
evnx auth token create ci-deploy-2026-09 --scope read --vault my-api/production
```

Revocation takes effect immediately — the server checks the hash on every request, so there is no cache to wait out.

Dating the name is a small habit that pays off: `evnx auth token list` then tells you at a glance which credential has been sitting in a pipeline for eighteen months.

## When something leaks

In order:

<Step number={1} title="Revoke the token">
`evnx auth token revoke <name>`. Immediate. This stops further access with that credential.
</Step>

<Step number={2} title="Decide whether the master password leaked too">
If the runner had `EVNX_MASTER_PASSWORD`, assume it did. (The key bundle alone opens nothing, but replace it too after a leak: `evnx auth key-bundle`.) A token is scoped; the master password is not — it opens every vault you own.
</Step>

<Step number={3} title="Rotate the secrets themselves">
This is the step people skip. Revoking evnx credentials stops future reads; it does nothing about the database password that was already pulled. Rotate the underlying secrets at their source, push the new values, and treat the old ones as public.
</Step>

<Callout type="info" title="Changing your master password — what it does to this pipeline">
It rotates the key that wraps every vault key, so every wrapped copy has to be re-wrapped atomically. Available in the CLI since **0.7.0**, and on the dashboard.

⚠️ **Note what it does to this pipeline.** Your API tokens keep working — a token authenticates, it does not decrypt — but every runner holding `EVNX_MASTER_PASSWORD` starts failing on the next run, because that secret no longer derives the right key. **v0.14.0+** — and so does a stored `EVNX_KEY_BUNDLE`, which was made under the old password: run `evnx auth key-bundle` and replace it along with the password. Changing the master password means updating those secrets everywhere they are set, and evnx cannot tell you where those places are.

It is also not a substitute for step 3. Re-wrapping your vault keys does nothing about the database password a runner already pulled.
</Callout>
