<Callout type="tip" title="Why automate sync checks?">
Automating `evnx sync --check` ensures:
- `.env.example` declares every variable the code needs
- Placeholder rules and naming conventions are enforced across the team
- A broken template config fails the pipeline, not the next developer's sync
- New team members can onboard from the template reliably
</Callout>

## The command for automation

```bash
evnx sync --check --direction forward
```

| Flag | Why |
|------|-----|
| `--check` | Writes nothing, asks nothing, and reports the verdict through the exit code |
| `--direction forward` | One-way: fail only on a name the template lacks. Without it the check is two-way, and a `.env` that has not caught up with the template fails too. That is right on a developer's own machine and wrong in a hook or a pipeline |
| `--naming-policy error` | Optional: stop on a name sync would write that is not `UPPER_SNAKE_CASE` |
| `--template-config FILE` | Optional: load your placeholder rules, so a broken file fails here |
| `--format json` | Optional: say *which* names drifted, on stdout |

`--force` and `--dry-run` do not belong in a gate: `--check` already never prompts or
writes, and `--dry-run` exits `0` whatever it finds.

### Exit codes

| Code | Meaning |
|------|---------|
| `0` | In sync |
| `1` | Out of sync: the message names the command that fixes it |
| `2` | No verdict: a file will not parse, the config is wrong, or there was nothing to compare |

Full detail in the [`evnx sync` reference](/guides/commands/sync#exit-codes).

### CI usually has no `.env`

A runner checks out the repository, and `.env` is gitignored. `--check` then compares
`.env.example` with the **spec**: every required `[vars]` name in `.evnx.toml` must be in
the template.

With no spec either there is nothing to compare, and the answer is exit `2`, not a pass:

```text
Error: nothing to compare: .env does not exist, and .evnx.toml declares no required [vars] to check .env.example against.
```

So a CI gate needs a spec. Generate one from the template, review it, and commit it:

```bash
evnx spec init
```

```text
✓ wrote 3 variable(s) to .evnx.toml
```

From then on, the gate fails when someone adds a required variable to the spec and
forgets the template:

```text
· .env not found: checking .env.example against the spec ([vars] in .evnx.toml)
✗ .env.example is missing 1 required variable(s):
  • DATABASE_URL

✗ Out of sync. Add them to .env.example and commit the result.
```

`--skip-without-env` would turn "nothing to compare" into a pass. It exists for
pre-commit hooks on a fresh clone; do not use it in CI.

## GitHub Actions

### Basic check

```yaml
# .github/workflows/env-sync.yml
name: Environment Sync Check

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  validate-sync:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Check .env.example is up to date
        run: |
          docker run --rm -v "$PWD:/work" ghcr.io/urwithajit9/evnx:0.10.12 \
            sync --check --direction forward \
            --naming-policy error \
            --template-config .evnx/placeholders.json
```

The [container image](/guides/getting-started/installation) needs no install step, and
pinning its version keeps the gate from changing under you. The check only reads files,
so it needs no `--user`.

To report the two failure modes differently:

```yaml
      - name: Check .env.example is up to date
        run: |
          set +e
          docker run --rm -v "$PWD:/work" ghcr.io/urwithajit9/evnx:0.10.12 \
            sync --check --direction forward
          case $? in
            0) ;;
            1) echo "::error::.env.example is missing a variable — run 'evnx sync' and commit it"; exit 1 ;;
            *) echo "::error::evnx could not check the files"; exit 1 ;;
          esac
```

`set +e` matters: GitHub's default shell stops at the first failing command, so without
it the `case` never runs.

### Name the missing variables in the log

```yaml
      - name: Check .env.example is up to date
        run: |
          set +e
          docker run --rm -v "$PWD:/work" ghcr.io/urwithajit9/evnx:0.10.12 \
            sync --check --direction forward --format json > drift.json
          status=$?
          if [ "$status" -eq 1 ]; then
            jq -r '.missing[] | "::error::.env.example is missing \(.)"' drift.json
          fi
          exit "$status"
```

Only the report goes to stdout; the banner and any error go to stderr, so `drift.json`
is clean JSON. On exit `2` it is empty.

### Block secrets in .env.example

```yaml
      - name: Check for secrets in template
        run: |
          if grep -iE "(sk_live|sk_test|password|secret|token)" .env.example | \
             grep -v "YOUR_\|placeholder\|demo\|sk_demo_"; then
            echo "::error ::Potential secrets found in .env.example!"
            echo "Use placeholders like YOUR_KEY_HERE instead."
            exit 1
          fi
```

## GitLab CI

```yaml
# .gitlab-ci.yml
env-sync:
  stage: test
  image:
    name: ghcr.io/urwithajit9/evnx:0.10.12
    entrypoint: [""]
  script:
    - evnx sync --check --direction forward --naming-policy error --template-config .evnx/placeholders.json
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"
```

The image's entrypoint is `evnx` itself; `entrypoint: [""]` gives GitLab the shell it
runs `script:` in. The check fails the job by itself; there is no `git diff` to add, since
`--check` never writes.

To print the drifted names in the job log as well:

```yaml
env-sync-report:
  stage: test
  image:
    name: ghcr.io/urwithajit9/evnx:0.10.12
    entrypoint: [""]
  script:
    - evnx sync --check --direction forward --format json
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

## Pre-commit hooks

### The shipped hook

evnx ships a hook for the [pre-commit](https://pre-commit.com) framework:

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/urwithajit9/evnx
    rev: v0.10.12
    hooks:
      - id: evnx-sync
```

It runs `evnx sync --check --direction forward --skip-without-env`:

- **Your `.env` has a name the template lacks**: the commit stops, exit `1`, and the
  message names the fix: run `evnx sync --direction forward` and commit `.env.example`.
- **The template has a name your `.env` lacks**: the commit goes through. You have not
  pulled a teammate's variable into your `.env` yet; that is not a reason to block you.
- **A fresh clone with no `.env`**: if `.evnx.toml` has a spec, the template is checked
  against it; if not, the hook says
  `nothing to check, skipped` and exits `0`, so a new contributor's first commit is not
  blocked.

<Callout type="info" title="Changed in 0.10.12">
This hook used to run `evnx sync --direction forward --placeholder`. pre-commit gives a
hook no terminal, so on any drift it failed with `IO error: not a terminal`, and on a
clone with no `.env` it failed `file not found`. It now checks instead of writing.

The writing variant is `evnx-sync-fix` (`evnx sync --force --skip-without-env`): it adds
missing names to `.env.example` with placeholder values. pre-commit stops a commit when a
hook changes a file, so stage the updated template and commit again.
</Callout>

### A local hook

Without the framework, the same check in `.git/hooks/pre-commit`:

```bash
#!/bin/bash
# .git/hooks/pre-commit

if git diff --cached --name-only | grep -qx "\.env"; then
  echo "🚫 .env should not be committed!"
  echo "Remove it from staging:  git reset .env"
  exit 1
fi

evnx sync --check --direction forward --skip-without-env || exit 1
```

Errors stay visible: a hook that hides stderr also hides *why* it stopped the commit.

## Advisory vs blocking modes

### Blocking (fail the pipeline)

```bash
evnx sync --check --direction forward --naming-policy error
```

### Advisory (report, never fail)

```bash
evnx sync --check --direction forward --format json || true
```

<Callout type="tip" title="When to use advisory mode">
Use advisory mode for:
- The first week of a rollout
- Legacy projects with many existing violations
- Debugging why a pipeline is failing

Switch to blocking once the team is used to the workflow.
</Callout>

## Multi-service repositories

For monorepos with one template per service:

```bash
failed=0
for dir in services/*/; do
  echo "🔍 Checking $dir..."
  (cd "$dir" && evnx sync --check --direction forward) || failed=$((failed+1))
done

if [ "$failed" -gt 0 ]; then
  echo "🚫 $failed service(s) failed sync validation"
  exit 1
fi
```

Each service with no `.env` in CI needs its own spec (`.evnx.toml` beside its template),
or its check exits `2`.

## Troubleshooting CI failures

### Exit 2: "nothing to compare"

CI has no `.env` and `.evnx.toml` declares no required `[vars]`. Commit a spec
(`evnx spec init`, then review it). Do not add `--skip-without-env` to the CI command:
it makes the gate pass without checking anything.

### Exit 2 from the template config

```text
Error: tc.json has a key evnx does not read: `allow_actaul` (did you mean `allow_actual`?)
```

Since 0.10.12 a misspelt key, a missing file or an invalid pattern in `--template-config`
fails, in CI as locally. Fix the file; see the
[configuration reference](/guides/reference/sync-configuration).

### Command not found: evnx

Use the container image as above, or install a release binary on the runner. The archive
holds one file named after its target:

```yaml
- name: Install evnx
  run: |
    curl -fsSL -o evnx.tar.gz https://github.com/urwithajit9/evnx/releases/download/v0.10.12/evnx-x86_64-unknown-linux-musl.tar.gz
    tar -xzf evnx.tar.gz
    sudo install -m 0755 evnx-x86_64-unknown-linux-musl /usr/local/bin/evnx
    evnx --version
```

`cargo install evnx --all-features` works too, but compiles from source on every run.

### Machine-readable output for the surrounding checks

`evnx sync --check --format json` covers sync. For the rest of the setup (gitignore,
permissions, project structure), `evnx doctor` has its own JSON:

```bash
evnx doctor --format json | jq '.summary.errors'
```

## Best practices checklist

### For CI configuration
- [ ] Use `evnx sync --check --direction forward`, never `--dry-run` or `--force`, as the gate
- [ ] Commit a spec (`.evnx.toml` with `[vars]`) so the check has something to compare with
- [ ] Never add `--skip-without-env` to a CI command
- [ ] Set `--naming-policy error` to enforce conventions
- [ ] Pass `--template-config` if you use custom placeholders
- [ ] Pin the evnx version (image tag or release)

### For team adoption
- [ ] Add the `evnx-sync` pre-commit hook
- [ ] Start with advisory mode (`|| true`) for the first week
- [ ] Document the CI check in CONTRIBUTING.md
- [ ] Tell people the local command that reproduces it: `evnx sync --check`

### For security
- [ ] Never log `.env` contents in CI output
- [ ] Scan `.env.example` for accidental secrets
- [ ] Use custom placeholders that look fake (`sk_demo_XXX`)
- [ ] Rotate any test credentials used in examples
