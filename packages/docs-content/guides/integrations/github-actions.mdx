Integrating evnx into GitHub Actions lets you automatically scan every pull request and push for secrets and misconfigurations — blocking merges before issues reach `main`.

<Prerequisites>
  <Prerequisite href="/guides/commands/scan">Understand evnx scan output formats</Prerequisite>
</Prerequisites>

## What you'll set up

By the end of this guide your repository will have:

1. A workflow that blocks PRs containing secrets (exit code `1`)
2. SARIF results uploaded to the **Security → Code scanning** tab
3. Inline annotations on PR diffs highlighting the exact line with a finding
4. A separate validation workflow checking for misconfiguration

---

## Basic scan workflow

Create `.github/workflows/evnx-security.yml`:

```yaml
name: evnx security scan

on:
  pull_request:
  push:
    branches: [main, develop]

jobs:
  scan:
    name: Scan for secrets
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write   # Required to upload SARIF

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Install evnx
        run: curl -fsSL https://dotenv.space/install.sh | bash

      - name: Scan .env files
        run: |
          evnx scan \
            --format github \
            --severity high

      - name: Generate SARIF report
        if: always()   # Run even when scan finds issues
        run: |
          evnx scan \
            --format sarif \
            --exit-zero > evnx-results.sarif

      - name: Upload SARIF to GitHub Security tab
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with:
          sarif_file: evnx-results.sarif
          category: evnx-secret-scan
```

<Callout type="info" title="permissions: security-events: write">
The `security-events: write` permission is required to upload SARIF files. Without it the upload step will fail with a 403 error.
</Callout>

<Callout type="info" title="Upgrading to 0.13.0">
`--severity high` now filters on how bad a finding is (`critical`, `high`, `medium`,
`low`); the old meaning, how sure evnx is, is `--confidence`. With 63 built-in rules
instead of 13, a `--severity high` gate can start failing on findings it never saw.
Adopt them with `evnx scan --update-baseline`, or `evnx:allow` markers (see below).
The SARIF `ruleId` is now the rule's stable id (`aws-access-key`, was
`secret/aws-access-key`), so GitHub code scanning shows existing alerts as new rules once.
</Callout>

## Validate workflow

Run `evnx validate` separately — validation checks for misconfiguration (placeholders, weak secrets, type issues) and doesn't need to block merges in the same way scanning does:

```yaml
name: evnx validate

on:
  pull_request:
    paths:
      - '**.env*'       # Only run when .env files change
      - '.evnx.toml'

jobs:
  validate:
    name: Validate .env configuration
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Install evnx
        run: curl -fsSL https://dotenv.space/install.sh | bash

      - name: Validate environment files
        run: evnx validate --fail-on warning --format github-actions
        # Exits 1 on errors and on warnings, with ::error annotations on the PR.
        # Drop --fail-on warning to fail on errors only; add --exit-zero for advisory-only.
```

## Caching evnx binary

If you run evnx across many workflows, cache the binary to avoid re-downloading:

```yaml
- name: Cache evnx binary
  uses: actions/cache@v4
  id: cache-evnx
  with:
    path: ~/.local/bin/evnx
    key: evnx-${{ runner.os }}-0.13.0

- name: Install evnx (if not cached)
  if: steps.cache-evnx.outputs.cache-hit != 'true'
  run: curl -fsSL https://dotenv.space/install.sh | bash

- name: Add to PATH
  run: echo "$HOME/.local/bin" >> $GITHUB_PATH
```

## Install via Cargo (slower but version-pinned)

For reproducible builds where you need to pin an exact version:

```yaml
- name: Install Rust toolchain
  uses: dtolnay/rust-toolchain@stable

- name: Install evnx
  run: cargo install evnx --locked
```

<Callout type="warning" title="Compile time">
`cargo install` compiles from source — adds ~90 seconds to your workflow on first run. Use the install script or binary cache for faster CI.
</Callout>

---

<Callout type="warning">
Steps on this page previously used `--exit-code` and `--output`. **Neither flag exists** —
both fail with an argument error, so the step failed regardless of what was in the repo.
`--format github` was documented before it was implemented, and until **v0.5.0** it
silently produced human-readable output and exited `0`: a gate that looked configured and
checked nothing. SARIF is produced by redirecting stdout.
</Callout>

## PR annotations in action

`--format github` needs **v0.5.0+**. Findings appear as inline annotations on pull request
file diffs:

```
evnx scan --format github
```

Outputs:

```
::error file=./.env.local,line=1,title=Secret detected (high)::DATABASE_URL matches Credentials in a connection string. Rotate this credential at its source
::error file=./.env.production,line=2,title=Secret detected (critical)::AWS_ACCESS_KEY_ID matches AWS Access Key. Rotate it at https://console.aws.amazon.com/iam
::error file=./.env.production,line=3,title=Secret detected (critical)::STRIPE_SECRET_KEY matches Stripe Secret Key (LIVE). Rotate it at https://dashboard.stripe.com/apikeys
```

The value is never included — only the variable name and the matched pattern. Annotations
appear on the PR and persist in the workflow log, so putting the credential in one would
be the scanner doing the leaking.

GitHub Actions renders these as annotations directly on the PR diff — reviewers see the exact line flagged without reading the workflow log.

## Full production workflow

This combines everything above into one robust workflow:

```yaml
name: evnx — security & validation

on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  security:
    name: Secret scan
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write

    steps:
      - uses: actions/checkout@v4

      - name: Cache evnx
        uses: actions/cache@v4
        id: cache-evnx
        with:
          path: ~/.local/bin/evnx
          key: evnx-${{ runner.os }}-0.13.0

      - name: Install evnx
        if: steps.cache-evnx.outputs.cache-hit != 'true'
        run: curl -fsSL https://dotenv.space/install.sh | bash

      - run: echo "$HOME/.local/bin" >> $GITHUB_PATH

      - name: Scan (PR annotations)
        run: evnx scan --format github --severity high

      - name: Scan (SARIF report)
        if: always()
        run: evnx scan --format sarif --exit-zero > evnx.sarif

      - name: Upload SARIF
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with:
          sarif_file: evnx.sarif

      - name: Validate configuration
        run: evnx validate --fail-on warning --format github-actions
```

## Ignoring known false positives

If your repo contains test fixtures that look like secrets, say so where evnx can read it.
Keep a whole path out of the folder walk with `exclude` in `.evnx.toml`:

```toml
# .evnx.toml
[scan]
exclude = [
  "fixtures",         # a name with no glob characters matches a whole path component
  "*.sample.env",     # a glob
]
```

To silence one finding, put `evnx:allow` with the rule id on its line or the line above,
in any comment style:

```env
# evnx:allow connection-string-credentials — local fixture, not a real database
DATABASE_URL=postgres://admin:fixture-pass@db.internal:5432/app
```

To adopt a repository that already has findings, **v0.13.0+** `evnx scan --update-baseline`
records them in `.evnx/baseline.json` (it holds no values, so it is safe to commit); from
then on they are reported as `known` and do not fail the run. Commit `.evnx.toml` and
`.evnx/` so CI picks them up. The `.env.example` family is skipped without any setting.
