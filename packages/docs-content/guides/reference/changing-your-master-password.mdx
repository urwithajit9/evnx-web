Your master password is not a login credential that happens to also unlock things.
It **is** the key: everything in your vaults is encrypted under a key derived from
it, and the server has never held either one.

So changing it is not a settings toggle. Every vault key wrapped under the old key
has to be re-wrapped under the new one, on your machine, and swapped in a single
step. That is what this command does.

## Before you start

**Know which pipelines hold your master password.** They will break. See
*[What it breaks](#what-it-breaks)* below — this is the part people do not predict.

**You do not need a backup of your vaults**, but having one costs nothing:
`evnx cloud pull` each vault before you start. The change is reversible for a
window, and the CLI writes its own recovery file, but a local copy is the one form
of safety that depends on nobody else.

## From the app

**[app.evnx.dev](https://app.evnx.dev) → Settings → Master password.**

You are asked for your current password, the new one twice, and a 2FA code if you
have two-factor enabled. Everything is re-derived and re-wrapped in the browser
before anything is sent; the tab stays signed in afterwards.

## From the CLI

<Callout type="info" title="Requires evnx 0.7.0">
`evnx auth rotate-master-password` and `evnx auth undo-password-change` shipped in
**0.7.0**. `evnx --version` will tell you what you have; on an earlier version, use
the app above.
</Callout>

```bash
evnx auth rotate-master-password
```

```
  Changing your evnx master password.
  account   you@example.com

  Deriving your current key on this machine…

  2 vault key(s) will be re-wrapped
  every other signed-in device will be signed out

  An undo stays available for a limited window, by proving your OLD password.

  Deriving your new key on this machine…
  Verifying the new wraps open… ok
  Recovery file  ~/.config/evnx/rotation-20260930T154000Z.json
  Confirming against the server… 2 ok

  ✓ master password changed
  2 vault key(s) re-wrapped
  2 other session(s) signed out
```

Two of those lines are doing real work and are worth understanding.

**`Verifying the new wraps open… ok`** — before anything is sent, evnx unwraps
every key it just re-wrapped, with the new key, and checks it gets back exactly
what it started with. The server cannot do this: it holds ciphertext, so a
wrong-but-well-formed wrap looks identical to a correct one and would be stored
without complaint. You would find out when a vault stopped opening.

**`Confirming against the server… 2 ok`** — afterwards, every key is read back and
unwrapped again. The first check proves the wraps were built correctly; this one
proves the server stored the ones that were sent.

### The recovery file

`~/.config/evnx/rotation-<timestamp>.json`, mode `0600`, written **before** the
request. It holds your previous wrapped keys — still ciphertext, still useless
without the old password, so it is no more sensitive than what the server already
stores.

Keep it until you have pulled a vault with the new password. Then delete it.

## What it breaks

<Callout type="warning" title="Every pipeline holding your master password will fail">
An API token authenticates; it does not decrypt. So your tokens keep working
untouched — and every pipeline that also holds `EVNX_PASSWORD` starts failing on
the next run, because that secret no longer derives the right key.

Update the master-password secret in each CI provider **before** or immediately
after you change it. `evnx auth token list` shows which tokens exist; it cannot
tell you which pipelines carry the password, so that list is yours to keep.
</Callout>

**Every other session is signed out.** That is the point rather than a side effect:
a session established under the old password should not outlive it.

## What it does not do

**It does not re-key your vaults.** The vault key itself is unchanged — only the
wrapping around it moves. Someone who was removed from a vault and kept a copy of
its key is entirely unaffected by this, and confusing the two is the mistake worth
avoiding here.

Rotating a vault key is what [`evnx vault revoke`](/guides/commands/vault) does when
it removes a member: it re-encrypts every version under a fresh key and re-wraps it
for everyone who stays. There is no command to re-key a vault on its own yet — if you
need one today, the way to get it is to remove a member and add them back.

**It does not touch vaults shared *with* you.** Those keys are wrapped to your
identity keypair, which a password change re-seals rather than replaces. They keep
working, and they are not part of the swap.

**It does not recall anything anyone has already read.** No server-side action
does.

## The undo window

A password change can be reversed for **72 hours**, and the only thing that
authorises it is your **previous master password** — the one credential that
separates you from whoever changed it.

From the app: **[app.evnx.dev/undo-password-change](https://app.evnx.dev/undo-password-change/)**,
linked from the sign-in page. No session needed, because someone locked out of
their account cannot sign in to reach it.

```bash
evnx auth undo-password-change
```

You are asked for your email and the password you used *before* the change.

<Callout type="warning" title="A vault created after the change cannot be restored">
Its key is wrapped under the password being undone, so it will not open afterwards.
The undo names any such vault rather than leaving you to discover it. Delete it, or
change the password again to reach it.
</Callout>

### When you do not want an undo

If your old password is the thing that leaked, an undo is a liability: it would
hand the account back to whoever has it.

```bash
evnx auth rotate-master-password --compromised
```

In the app, tick **"My current password may be known to someone else."** Either way
no snapshot is kept, the change takes effect immediately, and there is no way back.

## If you get an email you did not expect

Every change sends one, naming the undo deadline. If it was not you, someone knows
your master password — undo it with the old password, then change it again with
`--compromised` so the leaked one cannot be used to reverse you a second time.

## Why there is no "forgot password"

There is nothing to reset. Your master password is not stored anywhere, in any
form, by anyone — the server holds a verifier that proves you know it and cannot be
run backwards. A reset link would have to decrypt your vaults to re-encrypt them,
and the server has never been able to do the first half.

This is the same property that makes evnx worth using, seen from the other side.
A password change is possible precisely because **you** supply the old password and
the work happens on your machine.
