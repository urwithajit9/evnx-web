<Callout type="tip" title="Who this is for">
This reference is for teams that want their own placeholder conventions in
`.env.example`, real values for harmless configuration, or a naming policy enforced in
CI.
</Callout>

  <Prerequisite href="/guides/commands/sync">Review sync command reference</Prerequisite>

`evnx sync` takes its settings from two places:

| Setting | Where |
|---------|-------|
| Placeholder rules: `patterns`, `default`, `allow_actual` | A JSON file passed with `--template-config` |
| Naming policy | `--naming-policy`, or `[sync] naming_policy` in [`.evnx.toml`](/guides/reference/configuration-file) |

---

## The placeholder JSON file

Commit it beside the template, for example as `.evnx/placeholders.json`, and pass it on
every run:

```bash
evnx sync --template-config .evnx/placeholders.json
```

```json
{
  "$schema": "https://evnx.dev/schemas/placeholders.v1.json",
  "description": "Team-specific placeholder conventions",
  "patterns": {
    ".*_API_KEY$": "sk_demo_XXXXXXXXXXXXXXXX",
    ".*_SECRET$": "demo_secret_placeholder",
    "^DATABASE_URL$": "postgresql://demo:demo@localhost:5432/demo_db",
    "^REDIS_URL$": "redis://localhost:6379/0",
    ".*_PORT$": "8080",
    "^ENVIRONMENT$": "development"
  },
  "default": "REPLACE_IN_PRODUCTION",
  "allow_actual": ["APP_NAME", "APP_VERSION", "LOG_LEVEL"]
}
```

### Keys

| Key | Type | Description |
|-----|------|-------------|
| `$schema` | `string` | Accepted and ignored by evnx. Point your editor at it for completion and inline validation: [`evnx.dev/schemas/placeholders.v1.json`](https://evnx.dev/schemas/placeholders.v1.json) |
| `description` | `string` | Accepted and ignored. A note for whoever reads the file |
| `patterns` | `object` | Regular expression → placeholder. See [Patterns](#patterns) |
| `default` | `string` | The placeholder for a key no pattern or built-in rule matches. Without it, `YOUR_VALUE_HERE` |
| `allow_actual` | `string[]` | Keys whose **real value** is written to the template. A credential is refused. See [`allow_actual`](#allow_actual) |
| `naming_convention` | `object` | **Not read.** Accepted with a warning; see [Naming policy](#naming-policy) |

**Any other key is an error** (since 0.10.12). A misspelt key used to be ignored, which
left the setting it named silently off:

```text
Error: tc.json has a key evnx does not read: `allow_actaul` (did you mean `allow_actual`?)
  Accepted keys: $schema, description, patterns, default, allow_actual, naming_convention.
  Nothing was written: a misspelt key would leave the setting it names off.

No verdict: evnx did not finish. This is not a clean result.
```

Exit `2`, nothing written. The same goes for a file that is missing, is not valid JSON,
has a value of the wrong type, or holds a pattern that is not a valid regular expression.
Since 0.10.12 the file is loaded on every path, including `--check` with no `.env` in CI,
so a mistake fails there as it does locally.

### Which rule a key gets

The first that applies wins:

1. `allow_actual` lists the key: its real value.
2. A `patterns` entry matches it: that placeholder.
3. The [built-in rules](/guides/commands/sync#placeholder-rules), by whole words of the
   name (`SECRET`/`KEY`/`TOKEN` → `YOUR_KEY_HERE`, a URL by its scheme, and so on).
4. `default`, or `YOUR_VALUE_HERE`.

To see which placeholder each key would get, preview:

```bash
evnx sync --dry-run --template-config .evnx/placeholders.json
```

Reverse sync uses the same file: where the template's value for a missing key is empty
or a placeholder, the placeholder written into `.env` follows these rules.

## Patterns

Each key of `patterns` is a [Rust regular expression](https://docs.rs/regex/latest/regex/#syntax),
matched **case-insensitively** against the variable name. It is not anchored: `DATABASE_URL`
as a pattern also matches `DATABASE_URL_RO`. Anchor it (`^DATABASE_URL$`) to mean one
variable.

| Pattern | Matches |
|---------|---------|
| `.*_API_KEY$` | `STRIPE_API_KEY`, `AWS_API_KEY` |
| `^DATABASE_URL$` | `DATABASE_URL` only |
| `DATABASE_URL` | `DATABASE_URL`, `DATABASE_URL_RO`, `OLD_DATABASE_URL` |
| `.*_PORT$` | `SERVER_PORT`, `DB_PORT`, `REDIS_PORT` |
| `^DEBUG` | `DEBUG`, `DEBUG_MODE`, `DEBUG_LEVEL` |
| `.*(PASSWORD\|PASS).*` | `DB_PASSWORD`, `ADMIN_PASS`, and also `PASSPORT_ID` |

<Callout type="warning" title="A pattern is a substring match">
The built-in rules match whole words of a name; a pattern does not. `PASS` as a pattern
matches `PASSPORT_ID` and `BYPASS_CACHE`. Anchor and delimit what you mean:
`(^|_)PASS(_|$)`.
</Callout>

### Pattern precedence

More than one pattern often matches a key. `STRIPE_SECRET_KEY` matches `SECRET`, `_KEY$`
and `^STRIPE_` at once. evnx picks the most specific, in this order:

1. **An exact key match**: a pattern that is simply the variable's name.
2. **The longest pattern.** `.*_SECRET_KEY$` beats `SECRET`; anything beats `.*`.
3. **Declaration order**: the first one written in the file wins.

```json
{
  "patterns": {
    "SECRET": "<any-secret>",
    "_KEY$": "<any-key>",
    "^STRIPE_": "<stripe-thing>",
    "STRIPE_SECRET_KEY": "<the-exact-key>"
  }
}
```

`STRIPE_SECRET_KEY` gets `<the-exact-key>`, whatever order you write them in.

<Callout type="info" title="Deterministic since 0.7.0">
On v0.6.0 and earlier the winner depended on internal hash ordering, so the same `.env`
could produce a different `.env.example` on each run. If you pinned a template config
against the old behaviour, check the result once after upgrading.
</Callout>

A pattern that is not a valid regular expression stops the run and is named:

```text
Error: tc5.json declares a placeholder pattern that is not a valid regular expression: "("
  regex parse error:
    (?i)(
        ^
error: unclosed group
  Nothing was written. Fix the pattern, or remove it.
```

## `allow_actual`

Every value in `.env.example` is normally a placeholder. `allow_actual` lists keys that
keep their **real value** instead:

```json
{
  "default": "REPLACE_IN_PRODUCTION",
  "allow_actual": ["APP_NAME", "LOG_LEVEL"]
}
```

With a `.env` holding `APP_NAME=my-app`, `LOG_LEVEL=debug` and a live
`STRIPE_API_KEY`, `evnx sync --template-config placeholders.json` creates:

```text
# Generated from .env
# Replace all placeholder values with real credentials

APP_NAME=my-app
LOG_LEVEL=debug
STRIPE_API_KEY=YOUR_KEY_HERE
```

`STRIPE_API_KEY` got `YOUR_KEY_HERE`, not the `default`: the built-in rule for `KEY`
comes before `default`.

This is for the part of a `.env` that is **configuration rather than credentials**. For
`APP_NAME` or `LOG_LEVEL` the real value is the useful example, and `YOUR_VALUE_HERE`
is strictly worse. It also means `evnx sync --direction reverse` gives a new teammate
working defaults in their `.env`, because reverse copies the template's values.

### A credential is refused, not warned about

Before anything is written, every listed value is checked with the detectors
`evnx scan` uses, plus a check for credentials in a connection string. One hit fails
the whole run: nothing is written, every offending key is named, exit `2`.

```text
Error: `allow_actual` would copy a real credential into .env.example, which is a committed file. Nothing was written.

  DATABASE_URL — Credentials in a connection string
  JWT_SECRET — Sensitive config key: JWT_SECRET

  `allow_actual` is for configuration whose real value is the useful example — APP_NAME, LOG_LEVEL, ENVIRONMENT.
  Remove these keys from it and they will be written as placeholders.

No verdict: evnx did not finish. This is not a clean result.
```

<Callout type="warning" title="No audit line for allow_actual in 0.10.12">
The interactive "actual values" choice prints
`[AUDIT] actual values written to .env.example for: …` to stderr. Values written through
`allow_actual` print no such line, the run still says it used placeholder values, and
the `--dry-run` preview marks them `·` like placeholders. The credential check above
still runs; only the record is missing. Read the template to see what it wrote.
</Callout>

On v0.6.0 and earlier, `allow_actual` was parsed and never read: listed keys got
placeholders like any other. If you set it then, your next sync writes real values for
those keys.

## Naming policy

Variable names outside `UPPER_SNAKE_CASE` are checked against a policy:

| Policy | Behaviour |
|--------|-----------|
| `warn` (default) | `! Variable 'myCamelVar' doesn't follow convention (UPPERCASE_WITH_UNDERSCORES)`, and the run continues |
| `error` | The run stops with no verdict, exit `2`, in every mode |
| `ignore` | Nothing |

Set it on the command line, or for the project in `.evnx.toml`. The flag wins:

```toml
[sync]
naming_policy = "error"
```

An invalid value in the file is exit `2` even when `--naming-policy` overrides it, so a
typo cannot sit unnoticed:

```text
  config    .evnx.toml
Error: .evnx.toml [sync] naming_policy: unknown naming policy 'strict' — expected one of: warn, error, ignore

No verdict: evnx did not finish. This is not a clean result.
```

The policy covers the names sync would **write**: names new to the template, or every
name when it creates the template. Names already in both files are not checked.

### `naming_convention` in the JSON file

`naming_convention` is accepted in the placeholder file, because earlier versions of
this page documented it, and is **not read**. evnx warns once and carries on:

```text
! tc3.json sets `naming_convention`, which evnx does not read from this file. Use --naming-policy, or [sync] naming_policy in .evnx.toml.
```

There is no prefix allowance or alternative style: the only rule is `UPPER_SNAKE_CASE`.

## Environment variables

| Variable | Effect |
|----------|--------|
| `CI` | Set to anything but empty, `0` or `false`: no prompts, placeholder values, and the output says `CI is set`. Read by `sync` only (since 0.10.12) |
| `NO_COLOR` | Plain output, as `--no-color` |

```bash
# Plain output in CI logs
NO_COLOR=1 evnx sync --check --direction forward
```

<Callout type="info">
Until 0.10.12 evnx read none of the environment variables this page once listed: `CI`,
`EVNX_SYNC_DRY_RUN`, `EVNX_SYNC_FORCE`. `CI` is read now; the other two still do not
exist. Use `--dry-run`, `--check` or `--force`.
</Callout>

## How sync writes files

Every file is written to a temporary file beside it and renamed into place, so an
interrupted run leaves the old file intact rather than half a new one.

- A new `.env` is created readable by you only (`0600`); a new `.env.example` is `0644`,
  because it is meant to be committed.
- An existing file keeps the mode you gave it.
- A symlink is written through to its target, and the link stays. The run says so:
  `· wrote through .env.example -> real/tmpl`.

## Exit codes

| Code | Meaning | Typical cause |
|------|---------|---------------|
| `0` | Done | Sync wrote or had nothing to write; a `--dry-run`; under `--check`, the files are in sync |
| `1` | Out of sync | `--check` only. The message names the command that fixes each side |
| `2` | No verdict | A missing source file (`.env` forward, `.env.example` reverse) or an unparseable one; a template config that is missing, not JSON, holds an unknown key or an invalid pattern; an invalid `[sync] naming_policy`; `--naming-policy error` refusing a name; a credential in `allow_actual`; under `--check`, nothing to compare or an empty `.env` |

An error is an `Error:` line on stderr, then the line every evnx command ends a run
without a verdict with:

```text
Error: Failed to parse placeholder config as JSON: key must be a string at line 1 column 2

No verdict: evnx did not finish. This is not a clean result.
```

## Recipes

### Gate a pull request

```bash
evnx sync --check --direction forward --template-config .evnx/placeholders.json
case $? in
  0) echo "✓ in sync" ;;
  1) echo "🚫 .env.example is missing a variable — run 'evnx sync' and commit it"; exit 1 ;;
  2) echo "🚫 evnx could not check the files"; exit 1 ;;
esac
```

Passing `--template-config` in CI is worth it even though `--check` writes nothing: a
broken config file fails the job instead of the next developer's sync.

### Report what drifted

```bash
evnx sync --check --direction forward --format json > drift.json
status=$?
if [ "$status" -eq 1 ]; then
  echo "Missing from .env.example:"
  jq -r '.missing[]' drift.json
fi
exit "$status"
```

### Several environments, one template

```bash
for env in staging production; do
  echo "Checking .env.$env…"
  evnx sync --env-name "$env" --check --direction forward || exit 1
done
```

Each `.env.<name>` must declare nothing the template lacks. A missing file is exit `2`,
naming the environments that do exist.

## Troubleshooting

### A pattern is not applied

1. Check the key in the file is `patterns`, spelt so: any other key is an error now, so
   if the run succeeds, the key is right.
2. Remember a pattern is a case-insensitive, unanchored regular expression, and a more
   specific pattern (an exact name, then the longest) wins over yours.
3. Preview the result: `evnx sync --dry-run --template-config .evnx/placeholders.json`
   lists the placeholder every key would get. `--verbose` does not show pattern matching.
4. `allow_actual` outranks `patterns`: a key listed there keeps its real value.

### The naming policy does not fire

The policy only checks names sync would write. A name already in `.env.example` passes,
whatever its spelling. Check the effective policy: `--naming-policy` on the command line
wins over `[sync] naming_policy`.
