## PlaceholderConfig JSON schema

Create `.evnx/placeholders.json` to customize placeholder generation:

```json
{
  "$schema": "https://evnx.dev/schemas/placeholders.v1.json",
  "description": "Team-specific placeholder conventions",
  "patterns": {
    ".*_API_KEY$": "sk_demo_XXXXXXXXXXXXXXXX",
    ".*_SECRET$": "demo_secret_placeholder",
    "DATABASE_URL": "postgresql://demo:demo@localhost:5432/demo_db",
    "REDIS_URL": "redis://localhost:6379/0",
    ".*_PORT$": "8080",
    ".*_HOST$": "localhost",
    ".*_URL$": "https://api.demo.example.com",
    "DEBUG": "true",
    "ENVIRONMENT": "development",
    "LOG_LEVEL": "debug"
  },
  "default": "REPLACE_IN_PRODUCTION",
  "allow_actual": [
    "APP_NAME",
    "APP_VERSION",
    "ENVIRONMENT",
    "LOG_LEVEL"
  ],
  "naming_convention": {
    "style": "SCREAMING_SNAKE_CASE",
    "allow_prefixes": ["MY_APP_", "SERVICE_"],
    "warn_on_lowercase": true
  }
}
```

### Schema reference

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `$schema` | `string` | No | Accepted and ignored by evnx. Point your editor at it for completion and inline validation: [`evnx.dev/schemas/placeholders.v1.json`](https://evnx.dev/schemas/placeholders.v1.json) |
| `description` | `string` | No | Accepted and ignored. A note for whoever reads the file |
| `patterns` | `object` | No | Regex pattern to placeholder mappings. See [Pattern precedence](#pattern-precedence) when more than one matches |
| `default` | `string` | No | Fallback placeholder for unmatched keys |
| `allow_actual` | `string[]` | No | Keys whose **real value** is written to the template. Guarded since 0.7.0 — see [allow_actual](#allow_actual) |
| `naming_convention` | `object` | No | ⚠️ **Not read from this file.** Set naming policy with `--naming-policy` or `[sync] naming_policy` in `.evnx.toml`. Since 0.7.0 evnx warns if you set it here |

## Pattern matching syntax

Patterns use **Rust regex** with implicit case-insensitive matching.

### Pattern examples

| Pattern | Matches | Example output |
|---------|---------|---------------|
| `.*_API_KEY$` | `STRIPE_API_KEY`, `AWS_API_KEY` | `sk_demo_XXXXXXXXXXXXXXXX` |
| `^DATABASE_URL$` | Exact match only: `DATABASE_URL` | `postgresql://demo:demo@localhost:5432/demo_db` |
| `.*_PORT$` | `SERVER_PORT`, `DB_PORT`, `REDIS_PORT` | `8080` |
| `^DEBUG` | `DEBUG`, `DEBUG_MODE`, `DEBUG_LEVEL` | `true` |
| `.*(PASSWORD|PASS).*` | `DB_PASSWORD`, `ADMIN_PASS` | `YOUR_PASSWORD_HERE` |

### Regex cheat sheet

```regex
.*      Match any characters (zero or more)
.+      Match any characters (one or more)
^       Start of string
$       End of string
|       OR operator
()      Grouping
[]      Character class
?       Zero or one of preceding
*       Zero or more of preceding
+       One or more of preceding
```

<Callout type="warning" title="Case sensitivity">
All patterns are matched case-insensitively. `.*_api_key$` matches `STRIPE_API_KEY`, `stripe_api_key`, and `Stripe_Api_Key`.
</Callout>

### Pattern precedence

More than one pattern usually matches a given key. `STRIPE_SECRET_KEY` matches
`SECRET`, `_KEY$` and `^STRIPE_` all at once. evnx picks the most specific, in this
order:

1. **An exact key match** — a pattern that is simply the variable's name.
2. **The longest pattern.** `.*_SECRET_KEY$` beats `SECRET`; anything beats `.*`.
3. **Declaration order** — the first one written in the file wins.

```json
{
  "patterns": {
    "SECRET": "<any-secret>",
    "_KEY$": "<any-key>",
    "^STRIPE_": "<stripe-thing>",
    "STRIPE_SECRET_KEY": "<the-exact-key>"
  }
}
```

`STRIPE_SECRET_KEY` gets `<the-exact-key>`, whatever order you write them in.

<Callout type="warning" title="Deterministic since 0.7.0 — before it, it was not">
On v0.6.0 and earlier the winner depends on internal hash ordering, so the
same `.env` can produce a different `.env.example` on each run — and
`.env.example` is a committed file, so `git diff` showed changes nobody made. If
you pinned a template config against the old behaviour, check the result once after
upgrading.
</Callout>

<Callout type="warning" title="A pattern that is not valid regex is an error">
Since 0.7.0, `evnx sync` refuses to run and names the pattern, and nothing is
written. On v0.6.0 and earlier it is skipped silently, and the key fell through to
`default` — so the template looked fine and did not follow your rules.
</Callout>

## `allow_actual`

Every value in `.env.example` is normally replaced by a placeholder. `allow_actual`
lists keys that keep their **real value** instead.

```json
{
  "default": "REPLACE_IN_PRODUCTION",
  "allow_actual": ["APP_NAME", "APP_VERSION", "ENVIRONMENT", "LOG_LEVEL"]
}
```

```bash
# .env                          # .env.example, after evnx sync
APP_NAME=my-app                 APP_NAME=my-app
LOG_LEVEL=debug                 LOG_LEVEL=debug
STRIPE_API_KEY=sk_live_…        STRIPE_API_KEY=REPLACE_IN_PRODUCTION
```

This is for the part of a `.env` that is **configuration rather than credentials**.
For `APP_NAME` or `LOG_LEVEL` the real value is the useful example, and
`YOUR_VALUE_HERE` is strictly worse. It also means `evnx sync --reverse` gives a new
teammate working defaults in their `.env`, leaving only the genuine secrets to
obtain.

### Listing a secret is refused, not warned about

<Callout type="warning" title="evnx checks every value before writing">
A listed key whose value looks like a credential **fails the sync**. Nothing is
written, every offending key is named at once, and the exit code is `2`.

```
Error: `allow_actual` would copy a real credential into .env.example, which is a
committed file. Nothing was written.

  DATABASE_URL — a password embedded in a URL
  JWT_SECRET — Sensitive config key: JWT_SECRET
```

Remove those keys from `allow_actual` and they are written as placeholders again.
The check uses the same detectors as `evnx scan`, plus a check for a password
embedded in a connection string.
</Callout>

<Callout type="warning" title="On v0.6.0 and earlier this field does nothing">
On v0.6.0 and earlier, `allow_actual` is parsed and never read: listed keys get
placeholders like any other. The behaviour described above arrives in the next
release. Nothing leaked — the failure was in the safe
direction — but the documented behaviour did not happen. If you have been relying on
it, check your `.env.example` after upgrading, because values that were previously
placeholders will now be real.
</Callout>

## Naming convention configuration

Control how variable names are validated.

<Callout type="warning" title="Not read from placeholders.json">
`naming_convention` in this file is **ignored**. Naming policy comes from
`--naming-policy` on the command line, or `[sync] naming_policy` in `.evnx.toml`.
Since 0.7.0, `evnx sync` warns when it finds `naming_convention` here rather than
discarding it silently. The fields below describe the intended shape and are kept
for when the file does support it.
</Callout>

### `naming_convention` object

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `style` | `enum` | `SCREAMING_SNAKE_CASE` | Expected naming style |
| `allow_prefixes` | `string[]` | `[]` | Prefixes exempt from style check |
| `warn_on_lowercase` | `bool` | `true` | Warn if any lowercase letters found |

### Supported styles

| Style | Pattern | Examples |
|-------|---------|----------|
| `SCREAMING_SNAKE_CASE` | `^[A-Z][A-Z0-9_]*$` | `DATABASE_URL`, `API_KEY` |
| `snake_case` | `^[a-z][a-z0-9_]*$` | `database_url`, `api_key` |
| `camelCase` | `^[a-z][a-zA-Z0-9]*$` | `databaseUrl`, `apiKey` |
| `PascalCase` | `^[A-Z][a-zA-Z0-9]*$` | `DatabaseUrl`, `ApiKey` |
| `kebab-case` | `^[a-z][a-z0-9-]*$` | `database-url`, `api-key` |

### Example: Allow project prefixes

```json
{
  "naming_convention": {
    "style": "SCREAMING_SNAKE_CASE",
    "allow_prefixes": ["MY_APP_", "SERVICE_", "LEGACY_"],
    "warn_on_lowercase": true
  }
}
```

**Valid with this config:**

```
MY_APP_DATABASE_URL=...
SERVICE_API_KEY=...
LEGACY_OLD_VAR=...
DATABASE_URL=...
```

**Invalid (would warn/error):**

```
myApp_databaseUrl=...
```

## Environment variables

Control sync behavior via environment variables.

| Variable | Values | Default | Description |
|----------|--------|---------|-------------|
| `NO_COLOR` | `1`, `true` | `false` | Disable colored terminal output |

**Usage:**

```bash
# Disable colors for CI logs
NO_COLOR=1 evnx sync --verbose
```

<Callout type="warning" title="Corrected in v0.10.3">
This table listed `CI`, `EVNX_SYNC_DRY_RUN` and `EVNX_SYNC_FORCE`. evnx has never
read any of them. Use `--dry-run`, `--check` or `--force`; a run without a
terminal never prompts.
</Callout>

## How sync writes files

Every file is written to a temporary file beside it and renamed into place, so an
interrupted run leaves the old file intact rather than half a new one.

- A new `.env` is created readable by you only (0600); a new `.env.example` is 0644,
  because it is meant to be committed.
- An existing file keeps the mode you gave it (**v0.10.3+**; sync used to force 0600
  onto a `.env` you had set to 0640).
- A symlink is written through to its target, and the link stays (**v0.10.3+**; it
  used to be replaced by a plain file).

## Security audit logging

Whenever real values are written into `.env.example` — through the interactive
"actual values" choice or `allow_actual` — one line goes to stderr, with or without
`--verbose`, and `-q` does not hide it (**v0.10.3+**):

```
[AUDIT] actual values written to .env.example for: APP_NAME, LOG_LEVEL
```

A credential never gets there, by the same detectors `evnx scan` uses: the
interactive choice writes it as a placeholder and names it in a warning, and
`allow_actual` refuses the whole run (exit 2, nothing written).

<Callout type="warning" title="Corrected in v0.10.3">
An earlier version of this page showed audit lines with a timestamp, a user and an
action. evnx has never written those; the line above is the whole of it.
</Callout>

## Exit codes and error handling

### Exit code reference

| Code | Meaning | Typical cause |
|------|---------|--------------|
| `0` | Success | Sync completed; under `--check`, the files are in sync |
| `1` | Out of sync | `--check` only: run `evnx sync` and commit the result |
| `2` | Could not run | A missing or unparseable file, invalid JSON in `--template-config`, `--naming-policy error` refusing a name, a credential in `allow_actual` |

### Error message format

An error is one `Error:` line on stderr, then the line every evnx command ends a
failed run with, and exit `2`:

```
✗ File not found: .env
Error: .env file not found - run 'evnx init' to get started

No verdict: evnx did not finish. This is not a clean result.
```

```
Error: Failed to parse placeholder config as JSON: key must be a string at line 1 column 2

No verdict: evnx did not finish. This is not a clean result.
```

## Advanced usage patterns

### Conditional sync in scripts

```bash
#!/bin/bash
if git diff --quiet HEAD -- .env; then
  echo "✓ .env unchanged, skipping sync"
  exit 0
fi

echo "🔄 .env changed, updating template..."
# --check writes nothing and reports the verdict through the exit code (v0.5.0+).
# `git diff` cannot be used here: --dry-run never writes, so it is always quiet.
if ! evnx sync --direction forward --check; then
  echo "⚠️  .env.example needs updates"
  echo "Run: evnx sync --direction forward"
  exit 1
fi
```

### Sync with custom error handling

<Callout type="warning">
`evnx sync` does not emit JSON — `EVNX_OUTPUT_JSON=1` is read by `evnx doctor` only, so the
recipe that used to sit here piped human-readable text into `jq`. Use `--check`'s exit code
instead; it distinguishes the two failures that mattered.
</Callout>

```bash
evnx sync --direction forward --check
case $? in
  0) echo "✓ in sync" ;;
  1) echo "🚫 .env.example is stale — run 'evnx sync --direction forward'" ; exit 1 ;;
  2) echo "🚫 evnx could not check the files" ; exit 1 ;;
esac

warnings=$(echo "$output" | jq -r '.warnings | length')
if [ "$warnings" -gt 0 ]; then
  echo "⚠️  $warnings warnings (non-blocking):"
  echo "$output" | jq -r '.warnings[]'
fi
```

### Multi-environment sync

```bash
for env in development staging production; do
  echo "🔄 Syncing $env environment..."
  evnx sync \
    --direction forward \
    --template-config ".evnx/placeholders-$env.json" \
    --naming-policy error \
    --dry-run
done
```

## Troubleshooting advanced issues

### Custom pattern not matching

**Debug steps:**

```bash
# 1. Validate JSON syntax
cat .evnx/placeholders.json | jq . || echo "Invalid JSON"

# 2. Test regex pattern manually
echo "STRIPE_API_KEY" | grep -iE ".*_API_KEY$"

# 3. Run sync with verbose to see pattern evaluation
evnx sync --template-config .evnx/placeholders.json --verbose 2>&1 | grep -i "pattern|match"
```

**Common fixes:**

- Escape special regex chars: `.*_API_KEY$` not `.*_API_KEY*`
- Remember patterns are case-insensitive by default
- Ensure pattern key exists in `patterns` object

### Naming policy not enforcing

**Check:**

```bash
evnx sync --naming-policy error --verbose 2>&1 | grep "naming_policy"
cat .evnx/placeholders.json | jq '.naming_convention'
```

**Fix:** CLI flags override config file. Use `--naming-policy error` explicitly in CI.

### Atomic write failing on Windows

**Cause:** File rename semantics differ on Windows.

**Workaround:**

```bash
# Use WSL or Git Bash for sync operations
# Or ensure no other process has .env open during sync
evnx sync
```
