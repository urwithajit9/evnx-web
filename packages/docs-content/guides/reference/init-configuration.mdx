<Callout type="warning" title="Configuration scope">
Unlike `evnx sync`, `init` reads no runtime configuration file such as `placeholders.json`.
What it can generate comes from a component catalogue compiled into the binary; how it
runs comes from its flags and `CI`. See [what init does not support](#what-init-does-not-support).
</Callout>

## The component catalogue

Every language, framework, service, piece of infrastructure and blueprint `init` knows is
in `src/assets/schema.json`, embedded at compile time with `include_str!`. There is no
runtime override. To see what your installed version knows:

```bash
evnx init --list-components
```

0.10.18 knows **56 components** and **ten blueprints**.

### Its shape

An abridged excerpt of the real file:

```json
{
  "languages": {
    "javascript_typescript": {
      "display_name": "JavaScript / TypeScript",
      "frameworks": {
        "nextjs": {
          "display_name": "Next.js",
          "vars": ["NEXT_PUBLIC_API_URL", "NEXTAUTH_SECRET", "NEXTAUTH_URL", "NEXT_PUBLIC_APP_URL"],
          "defaults": { "NEXTAUTH_URL": "http://localhost:3000" },
          "descriptions": { "NEXTAUTH_URL": "Canonical URL for your app" },
          "categories": { "NEXTAUTH_URL": "Application" }
        }
      }
    }
  },
  "services": {
    "databases": {
      "postgresql": {
        "display_name": "PostgreSQL",
        "vars": ["DB_HOST", "DB_PORT", "DB_USER", "DB_PASSWORD", "DB_NAME", "DATABASE_URL"],
        "defaults": { "DB_PORT": "5432", "DATABASE_URL": "postgresql://user:password@localhost:5432/dbname" },
        "category": "Database",
        "required": ["DB_NAME", "DB_USER"]
      }
    }
  },
  "infrastructure": {
    "vercel": {
      "display_name": "Vercel",
      "vars": ["VERCEL_TOKEN", "VERCEL_ORG_ID", "VERCEL_PROJECT_ID", "NEXT_PUBLIC_VERCEL_ENV"],
      "category": "Deployment Platform"
    }
  },
  "stacks": {
    "t3_modern": {
      "name": "T3 Turbo (Next.js + Clerk + Prisma)",
      "description": "The 2026 standard for type-safe fullstack apps.",
      "components": {
        "language": "javascript_typescript",
        "framework": "nextjs",
        "services": ["postgresql", "clerk", "aws_s3", "stripe"],
        "infrastructure": ["github_actions", "vercel"]
      },
      "tags": ["fullstack", "typescript", "auth", "payments", "saas"]
    }
  }
}
```

### Fields

| Where | Field | Meaning |
|---|---|---|
| language, framework, service, infrastructure | `display_name` | The name shown in menus and previews |
| framework, service, infrastructure | `vars` | The variable **names**, as a list, in output order |
| framework, service, infrastructure | `defaults` | Name → placeholder value for `.env.example`. A name without one gets a generated placeholder |
| framework, service, infrastructure | `descriptions` | Name → the comment written above it |
| framework | `categories` | Name → its section heading |
| service, infrastructure | `category` | One section heading for all its variables |
| service | `required` | The names marked `(required)` in the template and `required = true` in `[vars]` |
| stack | `name`, `description`, `tags` | What the blueprint menu shows |
| stack | `components` | `language`, `framework`, `services`, `infrastructure`: a blueprint is a component list, so `--blueprint t3_modern` is `--with nextjs,postgresql,clerk,aws_s3,stripe,github_actions,vercel` |

Services are grouped under `databases`, `messaging_queues`, `auth_providers`, `storage`,
`monitoring_logging`, `payments`, `ai_ml` and `email_sms`.

⚠️ Earlier versions of this page described a per-variable object with `required`,
`default`, `sensitive` and `pattern` fields. That shape has never existed.

### What is not in the catalogue

Some behaviour is Rust code, not data, and cannot be changed by editing the file:
component **aliases** (`postgres`, `pg`, `next`, `k8s` …), the browser-variable copies
(`NEXT_PUBLIC_*` on Next.js), generated placeholders, **project detection**
(`package.json`, `docker-compose.yml`, `fly.toml` and friends) and the `--from-source`
scanner.

## Flags

| Flag | Description |
|------|-------------|
| `--path`, `-p <PATH>` | Output directory. Default `.` |
| `--yes`, `-y` | Skip all prompts. Blank files unless `--blueprint` or `--with` names a stack; beside an existing template, keeps it and creates `.env` from it |
| `--blueprint <ID>` | Generate from a named stack, e.g. `t3_modern`. An unknown id lists the valid ones |
| `--with <LIST>` | Name the components, e.g. `nextjs,postgresql,stripe`. Repeatable and comma-separated; an unknown name suggests near matches |
| `--list-components` | Print every name `--with` accepts, and exit |
| `--detect` | Accept what the project declares, without asking |
| `--from-source` | Build the template from the variables the code reads. Only appends; not valid with `--force` |
| `--force` | Replace an existing `.env.example`. Without it, `--with` / `--blueprint` over a template exits 2. `.env` is never replaced |
| `--dry-run` | **v0.10.16+** — show what would be written, write nothing |
| `--json` | **v0.10.16+** — one JSON document on stdout, with the same fields as `evnx add --json`. Needs `--yes` or `--dry-run` |
| `--verbose`, `-v` | More detail |
| `--quiet`, `-q` | Print nothing on success. Findings, warnings, errors and requested data still print |
| `--no-color` | Disable colour |

`--dry-run` lists every file it would touch:

```text
Dry run: nothing was written.
  .env.example: would be created with 5 variables: REDIS_DB, REDIS_HOST, REDIS_PASSWORD, REDIS_PORT, REDIS_URL
  .env: would be created (0600) with 5 variables
  .gitignore: would add .env*, !.env.example, !.env.sample, !.env.template
  .evnx.toml: would be created with 5 variables in [vars]
```

## Environment variables

| Variable | Values | Description |
|----------|--------|-------------|
| `NO_COLOR` | any value | Disable coloured output |
| `CI` | any value except `0` / `false` | **v0.10.16+** — never ask, even at a terminal. With nothing named, exit 2 and list the forms to use |

```text
Error: CI is set, so init does not ask.
Name what you want instead:
  evnx init --yes                     blank files
  evnx init --yes --blueprint <id>    a named stack
  evnx init --yes --with <a,b,c>      components (evnx init --list-components)
```

Without `CI`, a run with no terminal stops the same way. Before 0.10.16 init did not read
`CI`, and this page said so.

## The files init writes

| File | When | Behaviour |
|------|------|-----------|
| the template | always | The project's template is `[defaults] example` in `.evnx.toml` if set, else whichever of `.env.example`, `.env.sample` or `.env.template` exists, else a new `.env.example`. An existing one is **kept** by `--yes`, and **refused** under `--with` / `--blueprint` unless `--force` |
| `.env` | always | Created from the template, mode `0600`. If it exists and a stack is named, the names it lacks are appended (`✓ Added 5 variables to .env; the values already there are kept`). Never overwritten |
| `.gitignore` | when the lines are missing | The block below, appended |
| `.evnx.toml` | always, **v0.10.16+** | The variable contract: the variables init set up under `[vars]`, or an empty `[vars]` for blank files |

The `.gitignore` block:

```gitignore
# ── evnx generated ─────────────────────────────────────────
# Written by evnx. These files may contain secrets — do not commit.
.env*
!.env.example
!.env.sample
!.env.template
```

The refusal names the commands that add to a template instead of replacing it:

```text
Error: ./.env.example already exists.

Refusing to overwrite it without being asked to — it is a tracked file and the contents may be hand-maintained.
Re-run with --force to replace it, or remove it first.
To add the variables to it instead, keeping what is there: evnx add blueprint <id> or evnx add service <id>.
```

## What init does NOT support

| Feature | Status | Instead |
|---------|--------|---------|
| `--template-config` (custom placeholder JSON) | ❌ | Edit `.env.example` after init, or `evnx sync --template-config` |
| `--naming-policy` | ❌ | `evnx sync --naming-policy` |
| `--placeholder` | ❌ | Placeholders come from the catalogue's `defaults`, or are generated |
| An external schema (`--schema-path`) | ❌ | Fork, edit `src/assets/schema.json`, rebuild |
| Overriding a value with `evnx add` | ❌ | `add` keeps a value already there and says so (`kept as it is`) |
| `--dry-run` | ✅ **v0.10.16+** | — |
| `--force` | ✅ a separate flag | `--yes` does not imply it |

## Customising placeholder values

### Edit the template after init (simplest)

```bash
evnx init --yes --blueprint t3_modern
nano .env.example     # change the placeholders your team prefers
```

The template is a committed file you own; init never touches it again unless you pass
`--force`.

### Change the catalogue (needs a rebuild)

Placeholders live in the `defaults` map of the component that declares the variable:

```json
"nextjs": {
  "display_name": "Next.js",
  "vars": ["NEXTAUTH_SECRET", "NEXTAUTH_URL"],
  "defaults": {
    "NEXTAUTH_SECRET": "your_team_prefix_XXXXXXXX",
    "NEXTAUTH_URL": "http://localhost:3000"
  }
}
```

Then rebuild with every feature, as the release does:

```bash
cargo build --release --all-features
```

<Callout type="info" title="Why not evnx add?">
`evnx add` adds names a template lacks. For a name that is already there with a
different value it keeps the existing one and reports it
(`! 1 variable with a different value in .env.example: kept as it is`), so it cannot be
used to override a placeholder.
</Callout>

## Advanced usage patterns

### Monorepo initialization

```bash
# One template, .env and .evnx.toml per package
for pkg in packages/*; do
  evnx init --path "$pkg" --yes
done
```

### Docker build integration

```dockerfile
RUN evnx init --yes --path /app/config
# /app/config now holds .env.example, .env (0600), .gitignore and .evnx.toml
```

### Pre-commit hook validation

```bash
#!/bin/bash
# .git/hooks/pre-commit
if [ ! -f .env.example ]; then
  echo "⚠️  .env.example missing. Run: evnx init --yes"
  exit 1
fi
evnx validate --quiet || exit 1
```

`validate` exits 1 for problems and 2 when it cannot run (no `.env`, for instance), so
the hook blocks on both.

## Troubleshooting

### Catalogue changes not reflecting

The catalogue is embedded at compile time. Rebuild after editing:

```bash
cargo build --release --all-features
```

### `.env` was not changed

`init` never overwrites a value. With a stack named it appends only the names `.env`
lacks; with `--yes` alone it leaves an existing `.env` as it is and says
`already set up`. To bring `.env` up to date with the template, use
`evnx sync --direction reverse`.

### `CI is set, so init does not ask`

Name what you want: `evnx init --yes`, `--blueprint <id>` or `--with <a,b,c>`.

### Permission denied on write

The output path is not writable. Check it with `ls -ld`, or choose another with `--path`.
