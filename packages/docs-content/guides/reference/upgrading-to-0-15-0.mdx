evnx 0.15.0 is a minor release with breaking changes. Three kinds of change can break a script:

- **Flags were renamed**, so that the same idea has the same spelling in every command. The old
  spellings are **removed, not aliased**: a script that uses one stops with exit `2` before it does
  anything, and the message tells you the new spelling.
- **Exit codes follow one table**, and a command that needs a confirmation with no terminal exits `4`.
- **Several defaults are safer**: refused names in `run`, tokens that expire, shares that are read-only,
  deletions that ask first, files that hold secrets that are private.

If you only call evnx from a terminal, run the command again with the spelling in the
error. If you call it from CI, hooks or scripts, work through [Fix your CI](#fix-your-ci) and
[Everything else that changed](#everything-else-that-changed) before you upgrade.

<Callout type="warning" title="Pin the old version until your scripts are fixed">
A job that installs `latest` picks up 0.15.0 on the day it is released and fails at the
first removed flag. Pin the version while you fix the scripts, for example
`npm install -g @evnx/cli@0.14.1`, and move the pin once they pass.
</Callout>

## Why one vocabulary

Before 0.15.0 the same idea had several spellings, and no spelling was used by every
command. The folder a command works in was `--path` in one place and `-p` in another. The
env file was `--env` on `validate` and `sync`, `--file` or `-f` on `cloud` and `platform`,
and `--source-file` on `migrate`. "Do not ask" was `--yes` on most commands, `--force` on
`restore` and `cloud pull`, and `--force` or `--placeholder` on `sync`. Machine output was
`--format json` in one command and `--json` in the next, and the plain format was called
`text` on some commands and `pretty` on others.

That is hard to remember and harder to script. It is also how a flag gets documented onto
the wrong command. In 0.15.0 each idea has one name, everywhere it applies, and a test
fails the build when a new command invents a spelling of its own.

| Idea | One spelling |
|------|--------------|
| The folder a command works in | `-C` / `--dir` |
| The env file | `--env FILE`, on every command, `cloud` and `platform` included |
| Which `.env.NAME` | `--env-name NAME` |
| Do not ask | `--yes` / `-y` |
| Show what would change | `--dry-run` / `-n` |
| Machine-readable output | `--format json`, or `--json` for short |
| Human output | `--format pretty` |
| Annotations on a pull request | `--format github` |

We removed the old spellings instead of keeping them as aliases. An alias keeps the old
name working for years, and then every page, example and answer shows two names for one
thing. A hard error with the new spelling in it costs you one failed run, once.

## What the error looks like

A removed spelling exits `2` before evnx reads a file or contacts a server, so nothing is
half-done:

```console
$ evnx sync --force
error: '--force' was removed from 'evnx sync' in 0.15.0; use '--yes'
$ echo $?
2
```

The message has the same shape for every command: the spelling you typed, the command, the
version, and what to type instead.

```text
error: '--format github-actions' was removed from 'evnx validate' in 0.15.0; use '--format github'
error: '-p' was removed from 'evnx init' in 0.15.0; use '-C/--dir'
error: '--env-name' was removed from 'evnx platform push' in 0.15.0; use '--target'
```

`evnx commands --json` lists the same table for the binary you run, under `removed` on each
command, so a script can check itself against it.

Notes on the table:

- `-C/--dir` is `-C` or `--dir`. `add` and each of its subcommands take it.
- `evnx platform` keeps `--to`, which is still required. `--target` names the Vercel
  environment (`production`, `preview`, `development`, or a custom one). The local file
  is `--env`.
- `evnx migrate --github-token` still works, but it is hidden from `--help` and prints a
  warning, because a token on the command line lands in shell history and in `ps`. Export
  `GITHUB_TOKEN` instead; evnx reads it when the flag is absent.
- `evnx migrate --to` takes the full destination name only: `github`, `aws-secrets-manager`,
  `gcp-secret-manager`, `azure-keyvault`, `doppler`, `infisical`, `vercel`, `heroku`,
  `railway`.
- `evnx convert --to` keeps its other short names (`aws`, `gcp`, `k8s`, `tf`, `yml`).
  Only `github-actions` and `gh-actions` went, for `github`.

## Fix your CI

First find every use. In a repository:

```bash
grep -rnE -e '--format (text|github-actions)' -e '--to (github-actions|gh-actions)' \
  -e '--(source-file|placeholder|env-name)' -e 'evnx.* (-f|--file|--force|--path|-p) ' \
  .github .gitlab-ci.yml scripts Makefile .pre-commit-config.yaml 2>/dev/null
```

That over-matches on purpose. `--env-name` is still correct on most commands, and the
hits are a list to read, not a list to replace blindly.

These `sed` one-liners cover the common cases. They use GNU `sed`; on macOS use `sed -i ''`.
Each acts only on lines that mention `evnx` and the command, so it leaves `docker compose -f`
and `rm -f` alone. Run them from the repository root and read `git diff` afterwards.

```bash
FILES=$(git ls-files '.github/*' '*.yml' '*.yaml' '*.sh' 'Makefile' | tr '\n' ' ')

# GitHub annotations, and the plain format
sed -i -E '/evnx (validate|scan)/ s/--format github-actions/--format github/' $FILES
sed -i -E '/evnx / s/--format text/--format pretty/' $FILES

# convert, migrate and cloud export: the GitHub destination
sed -i -E '/evnx (convert|migrate|cloud export)/ s/--to (github-actions|gh-actions)/--to github/' $FILES

# the folder a command works in
sed -i -E '/evnx (init|add|remove|doctor)/ s/ (--path|-p)( |=)/ --dir\2/' $FILES

# the env file on cloud and platform
sed -i -E '/evnx (cloud|platform) (push|pull|diff|link)/ s/ (--file|-f)( |=)/ --env\2/' $FILES

# the Vercel environment on platform
sed -i -E '/evnx platform/ s/--env-name/--target/' $FILES

# "do not ask"
sed -i -E '/evnx sync/ s/ (--force|-f|--placeholder)( |$)/ --yes\2/' $FILES
sed -i -E '/evnx (restore|cloud pull)/ s/ --force( |$)/ --yes\1/' $FILES

# migrate
sed -i -E '/evnx migrate/ s/--source-file/--env/; s/--from env( |$)/--from env-file\1/' $FILES
sed -i -E '/evnx migrate/ s/--to aws( |$)/--to aws-secrets-manager\1/; s/--to gcp( |$)/--to gcp-secret-manager\1/; s/--to azure( |$)/--to azure-keyvault\1/' $FILES

# parse and vault create
sed -i -E '/evnx parse/ s/ (-y|--yes)( |$)/ --show-values\2/' $FILES
sed -i -E '/evnx vault create/ s/ (-e|--env)( |=)/ --environment\2/' $FILES
```

Two limits. The commands only see an invocation written on one line, so a command split
with `\` needs a manual pass; the grep above still finds its lines. And `scan rules add
--format` became `--from`, which is rare enough to change by hand.

When the scripts pass, run each changed command once. A remaining old spelling fails
immediately with the message above.

### A GitHub Actions workflow

Before:

```diff
-      - name: Validate .env
-        run: evnx validate --fail-on warning --format github-actions
```

After:

```diff
+      - name: Validate .env
+        run: evnx validate --fail-on warning --format github
```

The `scan` step is the same change. `evnx scan --format github` has been the spelling since
v0.5.0; only `github-actions` was removed:

```yaml
      - name: Scan for secrets
        run: evnx scan --format github --severity high
```

### A pre-commit hook

The hooks that evnx ships, `evnx-sync-fix` among them, use the new spellings from 0.15.0.
A local hook of your own that runs `sync --force --skip-without-env` becomes
`evnx sync --yes --skip-without-env`.

## Everything else that changed

The flag renames are the part that fails loudly. These changes do not: the command still runs, and
something about it differs. Each row says what a script must change. `Fix` is what to do.

### Exit codes and `--yes`

evnx has one exit-code table, printed in every `--help`, in `evnx commands --json` and in the CLI's
`docs/exit-codes.md`: `0` clean, `1` findings, `2` could not run, `4` declined or needs `--yes`, `10` to
`15` cloud and platform failures.

| Before | In 0.15.0 | Fix |
|---|---|---|
| `backup` failures exited `3`, `4`, `5` or `6` | All are `2`; the message still names what failed | Test for `2`, not `3` to `6` |
| `restore` with a missing backup exited `3` | `2`. `4` (cancelled) and `5` (written to `.restored`) stay | Test for `2` |
| A command that needs a confirmation, with no terminal and no `--yes`, exited `2` on `migrate` and some others | Exits **`4`** everywhere, and the message names `--yes` | Add `--yes` to scripts that run without a terminal; treat `4` as "not confirmed", not "could not run" |
| A current folder that cannot be read exited `1` | `2` | Treat it as "could not run" |
| `run` and `cloud run` returned `1` for a command killed by a signal | **128+n** (`143` for `SIGTERM`), with a note on stderr | Do not read `1` from `run` as "killed"; test `>= 128` |

Where `--yes` is now needed in CI: `cloud push` that removes most of a vault's keys, `org seats --set` and
`--unlimited`, `vault delete`, `set` replacing a value, `platform push --prune`, and everything that
already asked before.

### `run` and `cloud run`

| Change | Fix |
|---|---|
| More names are refused because they start a program or load code: `EDITOR`, `PAGER`, `VISUAL`, `GIT_PAGER`, `GIT_ASKPASS`, `SSH_ASKPASS`, `RUSTC_WRAPPER`, `CLASSPATH`, `PERL5DB`, `PYTHONINSPECT` and the prefixes `npm_config_`, `NPM_CONFIG_`, `GIT_CONFIG_`. A `.env` or vault that holds one stops with exit `2` and the command never runs | Remove the name from the file, `--exclude` it, or pass `--allow-unsafe-names` as you would for `PATH` and `LD_*` |
| On Unix, without masking the command replaces evnx (`exec`); with masking evnx forwards `SIGTERM`, `SIGHUP`, `SIGQUIT` and `SIGINT` | A command that counts interrupts runs with `--no-mask`, because a terminal Ctrl-C reaches it twice when masking |
| Proxy and certificate names (`HTTPS_PROXY`, `SSL_CERT_FILE`, …) now print one warning that names them, never the values | Nothing breaks; `-q` hides it |

### Cloud and platform defaults

| Change | Fix |
|---|---|
| `auth token create` expires in **90 days** and needs a scope: `--vault VAULT`, or `--all-vaults`. A bare `auth token create NAME` exits `2` | Pass `--vault` or `--all-vaults`; pass `--no-expiry` or `--expires-in-days N` if 90 days is wrong, and put a reminder in the calendar for the rotation |
| `vault share` gives `viewer`, not `developer` | Pass `--role developer` where the recipient must write |
| `vault delete` needs the full `name/environment` (or an id) at the prompt and with `--yes`; `vault delete myapp --yes` exits `2` | Pass `my-api/production` |
| `org seats --set` and `--unlimited` print `seats purchased X -> N` and ask (default No) | Add `--yes`; without a terminal and without it they exit `4` |
| `org accept TOKEN` is deprecated: it still works, with a warning that the token is in shell history and `ps` | Use `--token-stdin` or the prompt. It will stop working in a later release |
| `cloud push` asks before removing more than half of the previous version's keys (when it had at least 4) | A deploy that shrinks a vault passes `--yes` |
| `platform push --prune` stops with exit `2` when it would remove more than half of an environment (at least 4) | Pass `--prune-all` when that is what you mean. `--dry-run` is unaffected |
| `cloud pull` and `platform pull` write the pulled file `600`, whatever mode it had | Nothing, unless a tool in another account reads the file |
| `platform` warns about a token file that others can read, and prints an `API` line when the API address is overridden | `chmod 600` the token file |
| `platform --env-name` is `--target` (see the table above) | Rename |

### Windows

`.env`, backups and `credentials.json` become **owner-only** through an ACL: evnx runs `icacls <file>
/reset`, then `/inheritance:r` and a grant for you, SYSTEM and Administrators. Every other entry,
inherited or explicit, is removed. SYSTEM and Administrators keep access, as root does for a `0600` file,
so backup and antivirus tools keep working. If `icacls` fails, a file is still written with a warning;
`credentials.json` is not written. **Fix:** a setup that reads these files from another account must grant
it access again.

### Local files

| Change | Fix |
|---|---|
| `--env-name prod` pairs with `.env.prod.example` (or `.sample`, `.template`) when it exists, not the shared `.env.example`. The order is `--example`, the environment's own template for an `--env-name` given on the command line, `[defaults] example`, the own template for `[defaults] env_name`, then the project template | A project that relied on `.env.example` with `--env-name` sets `[defaults] example` |
| `--env-name` takes a **name**, not a path. `--env-name .env.prod` means `prod` (it used to create `.env..env.prod`); a path or a template name is refused and names the flag that takes it | Use `--env` for a path, `--example` for a template |
| Outside a git repository only the working folder's `.evnx.toml` applies; a parent's is no longer read or written | Put `.evnx.toml` in the folder you run from. `-v` names one that was skipped |
| `init` and `spec init` mark a name `required = true` only when the template gives it no default: `PORT=8080` or `DEBUG=false` makes it optional | Review a newly generated contract. Existing `.evnx.toml` entries are never rewritten |
| Templates never turn debugging on: `sync`, `add` and `init` write `DEBUG=false`, and a non-secret number keeps its type (`MAX_CONN=0`) | Nothing, unless you relied on `DEBUG=True` |
| `template` does not replace an existing output without `--force`, and refuses an output that is a symlink to a file outside the folder without `--follow-symlinks`. A dry run reports the same refusal | A script that regenerates a file on every run adds `--force` |
| `remove` refuses to leave dangling `${NAME}` references, and `remove '*'` needs `--all-names` | Pass `--allow-dangling`, or `--all-names`; `--yes` alone is not enough for a pattern that matches every variable |
| `add` and `init --from-source` write no dated `# Added by evnx … on <date>` line; `add custom` adds to the existing "Custom Variables" section | A check that matched the date line needs another marker |
| `convert --to yaml` quotes every value, so `yes`, `on`, `No` and `2026-01-01` stay strings | Nothing for a YAML reader; a text comparison against old output differs |
| `doctor --format json` has one more check, `empty_sections` | A script that expects exactly six checks must accept seven |

### `diff`, `validate`, `migrate`

| Change | Fix |
|---|---|
| `evnx diff A B` compares two files (keys and values), and the **left** file's value is listed before the right one in "Different values". The JSON keeps `env_value` (left) and `example_value` (right) | Read the file names under each value, not the position |
| `validate` runs the URL, port and email checks **by default**, always as warnings (the port finding was an error). A default `validate` still exits `0` for them | Add `--fail-on warning` to gate on them, or `--no-formats` (or `[validate] validate_formats = false`) to keep the old behaviour. `--validate-formats` is accepted and changes nothing |
| `migrate --to vercel` prints `--force` only with `--overwrite`. Vercel stops on a variable that exists | A script that re-runs the printed commands to change a value passes `--overwrite` |

### `doctor`, `parse`, `restore`

| Change | Fix |
|---|---|
| `EVNX_AUTO_FIX` is no longer read: `doctor` prints `EVNX_AUTO_FIX is no longer read; pass --fix` and repairs nothing | A CI image that exported it passes `evnx doctor --fix` |
| `parse --format json` is `run.schema_version` 2. Additive: each entry gains `quoted`, `exported`, `multiline`, `duplicate`, `expands` and `length`; no key changed or went. `doctor --all --format json` is schema 2 as well; `doctor` alone is still 1 | Nothing for a reader that ignores unknown keys. A strict schema validator needs the new fields |
| `restore --output -` writes the decrypted text to stdout (it was refused). Status lines go to stderr, nothing is written to disk, and a terminal refuses it unless `--show-values` | Nothing breaks. A script that treated `--output -` as an error no longer gets one |
| `--key-file` is the name `backup` and `restore` show again; `--password-file` is a hidden alias that still works | Nothing |

### The install address

The install URL is **`https://evnx.dev/install.sh`** everywhere: `evnx update` prints `curl -fsSL
https://evnx.dev/install.sh | bash` for a copy the script installed, the `scan hook` message names the same
address, and the README, the guides and the release notes use it, in place of `dotenv.space/install.sh`,
the `raw.githubusercontent.com` link and `evnx.dev/install`. A pinned old address keeps working only while its
redirect does.

```bash
curl -fsSL https://evnx.dev/install.sh | bash
```

**Fix:** replace the old address in Dockerfiles, CI images and onboarding docs. In CI, pin the version with
`EVNX_VERSION=0.15.0` as well.

### JSON for scripts

Every `--format json` / `--json` document has a top-level `run` object (`tool`, `version`,
`schema_version`, `ruleset`, `features`), with no timestamp. The keys each command already printed stay
where they were. `scan rules list --json` (a top-level array) and `scan --format sarif` have no `run`.
`org list|members|invites|billing`, `vault list|members`, `cloud history|audit|diff` and `auth sessions
list|devices list` gain `--format json`, and `auth status --check` and `cloud status --check` exit `10`
when signed out, without a request.

## What is new

The same release adds the other half of the vocabulary:

- `--json` is a visible shorthand for `--format json` on every command that has `--format`.
- `-n` is the short form of `--dry-run` everywhere.
- `-C/--dir` names the project folder on `init`, `add`, `remove` and `doctor`.
- `--env FILE` names the env file on `cloud` and `platform` as well, as it does elsewhere.
- `evnx sync --yes` works without `--prune`, and `sync --json` works in every mode, not only
  with `--check`. `--yes` replaces both `--force` and `--placeholder`.
- `evnx sync --to example|env` is another spelling of `--direction forward|reverse`.
- `evnx validate --fix --yes`, and `evnx convert --yes` and `--dry-run`.
- `evnx auth key-bundle` and `evnx auth token create` take `--format pretty|json`.
- `evnx vault create --environment` replaces `-e/--env`.
- [`evnx set`](/guides/commands/set) and [`evnx get`](/guides/commands/get) change and read one
  variable in place; `PORT=$(evnx get PORT)` works.
- [`evnx align`](/guides/commands/align), [`evnx history`](/guides/commands/history) and
  [`evnx undo`](/guides/commands/undo) are documented.
- [`evnx doctor --all`](/guides/commands/doctor#--all) runs the doctor checks, `validate`, `sync --check`
  and `scan` as one report with one verdict. Run it once in each project after you upgrade.
- [`run --prefer env|vault`](/guides/commands/run#which-value-wins), `cloud run --min-version N`,
  `scan --policy`, `--exit-only` and `--strict`, `convert --from json` and `--kind`, `template INPUT OUTPUT`.

See the page for each command: [`sync`](/guides/commands/sync),
[`validate`](/guides/commands/validate), [`convert`](/guides/commands/convert),
[`migrate`](/guides/commands/migrate), [`cloud`](/guides/commands/cloud),
[`platform`](/guides/commands/platform), [`backup`](/guides/commands/backup) and
[`restore`](/guides/commands/restore).
