AJ, a tech lead, encrypts a `.env` on their laptop, pushes it to a vault and adds Joy, a backend developer. Joy pulls
it and reads it. AJ never shared their password, and the server never saw the file.
So **which key does Joy use to decrypt it?**

This page answers that one step at a time. Each step has the command, what happens on
the machine, what is sent to the server, and a diagram. The diagrams are pieces of one
larger diagram: they share the same columns and their arrows are numbered straight
through, so step 3 starts where step 2 stopped. The whole thing is assembled at the end.

<Callout type="tip" title="The short answer">
Each vault has **one random vault key**, and every version of the `.env` is encrypted
with it, never with anyone's personal key.

The server keeps **one locked copy of that vault key per member**. AJ's copy is
locked with AJ's master key. Joy's copy is locked to Joy's public keys; AJ made it
when sharing the vault.

When Joy pulls, Joy types **their own** master password. It opens Joy's private key,
that private key opens Joy's copy of the vault key, and the vault key decrypts the
file. All of it happens on Joy's machine.
</Callout>

## The cast

| Person | Job | Vault role | In this story |
|---|---|---|---|
| **AJ** `aj@example.test` | tech lead | owner | creates the vault `myapp/production`, pushes, shares, removes people |
| **Joy** `joy@example.test` | backend developer | developer | pulls the secrets to run the app, and pushes a new variable |
| **Roy** `roy@example.test` | QA contractor | viewer | pulls the secrets to run the test environment; removed when the contract ends |

The server enforces these roles on every request:

| Role | Pull | Push | Share, change roles, revoke | Delete the vault |
|---|---|---|---|---|
| viewer | yes | no | no | no |
| developer | yes | yes | no | no |
| admin | yes | yes | yes | no |
| owner | yes | yes | yes | yes |

An admin shares as viewer or developer; only the owner makes someone an admin. Any
member except the owner can leave with `evnx vault leave` (v0.10.18+).

A role decides what the server will **hand you**. It cannot give anyone the ability to
**decrypt**, because the server never holds an unlocked key to give.

<Callout type="info" title="Everything on this page was run">
Every command and every output below comes from the evnx 0.10.18 release binary
against a local evnx-server built from the same commit as `api.evnx.dev`, with three
throw-away accounts. The values in the example file are made up. Where an output
names the server, it shows `https://api.evnx.dev`, the address you will see, in place
of the local test server's.
</Callout>

## Four keys, and who holds each

| Key | Where it lives | What it protects |
|---|---|---|
| **Master password** | Only in the person's head. Never sent anywhere. | It is turned into the master key. |
| **Master key** | Made on the device each time, from the password, with Argon2id (64 MiB, 3 passes). Never leaves the device. | Locks the person's private key, and the creator's own copy of a vault key. |
| **Account keypair** | Public half on the server. Private half on the server too, but **locked under the master key**. | Opens vault keys that someone shared with this person. It is two keypairs: X25519 and ML-KEM-768. |
| **Vault key** | Only in locked form on the server, one copy per member. | Encrypts every version of the file with AES-256-GCM. |

Two different paths lead to the same vault key. This picture is the whole answer:

```mermaid
flowchart TB
  PA["AJ's master password"] -->|"Argon2id, AJ's salt"| MKA["AJ's master key"]
  MKA -->|"unlocks (XChaCha20)"| CA["AJ's copy of the vault key"]
  PJ["Joy's master password"] -->|"Argon2id, Joy's salt"| MKJ["Joy's master key"]
  MKJ -->|"unlocks"| SKJ["Joy's private keys"]
  SKJ -->|"hybrid unwrap, X25519 + ML-KEM-768"| CJ["Joy's copy of the vault key"]
  CA --> VK(("the vault key: the same 256 bits"))
  CJ --> VK
  VK -->|"AES-256-GCM decrypt"| ENV[".env.production"]
```

AJ's copy and Joy's copy are two different locked boxes with the same key inside.
AJ opens theirs with AJ's master key. Joy opens theirs with Joy's private keys, which
Joy first opens with Joy's master key.

## Step 1: everyone registers and signs in

Each person does this once, on their own machine, with their own password:

```bash
evnx auth register --email joy@example.test
evnx auth login --email joy@example.test
```

```
  Deriving keys on this machine…
  ✓ account created on https://api.evnx.dev
```

What happens on Joy's laptop:

1. Joy's master password goes through Argon2id with a random salt. The result is Joy's
   **master key**.
2. The CLI generates Joy's **account keypair** (X25519 and ML-KEM-768) and locks the
   private half under Joy's master key.
3. It computes an **SRP verifier**: a value that lets the server check the password
   later without ever receiving it.
4. After Joy clicks the link in the verification email, `evnx auth login` proves the
   password to the server with SRP. Nothing that crosses the wire can be replayed or
   turned back into the password.

| Sent to the server | Never sent |
|---|---|
| SRP verifier, two salts, public keys, the **locked** private key | the password, the master key, the private key in the clear |

```mermaid
sequenceDiagram
    autonumber
    actor A as AJ
    actor J as Joy
    actor R as Roy
    participant S as evnx server
    participant B as Blob storage
    A->>A: master key = Argon2id(password, salt)
    A->>A: new keypair, private half locked under the master key
    A->>S: auth register (verifier, salts, public keys, locked private key)
    J->>S: auth register (same steps, Joy's own password)
    R->>S: auth register (same steps, Roy's own password)
    Note over A,S: Each verifies their email, then signs in with SRP. No password is sent.
```

## Step 2: AJ creates the vault

```bash
evnx vault create myapp --env production
```

```
  ✓ created myapp/production

  Push a .env into it with:  evnx cloud push --vault myapp/production
```

Before any of this, AJ's password has to open AJ's own locked keypair. A mistyped
password is refused here, so no vault is ever sealed under a typo (v0.10.18+).

1. AJ's machine generates a random 256-bit **vault key**.
2. It locks the vault key under **AJ's master key** (XChaCha20-Poly1305).
3. The server stores that locked copy as AJ's member row, with the role `owner`.

```mermaid
sequenceDiagram
    autonumber 6
    actor A as AJ
    actor J as Joy
    actor R as Roy
    participant S as evnx server
    participant B as Blob storage
    A->>A: vault key = 256 random bits
    A->>A: lock it under AJ's master key
    A->>S: vault create myapp/production, with AJ's locked copy
    Note over S: one member row: AJ, owner, a locked copy
```

## Step 3: AJ pushes the file

```bash
evnx cloud push --vault myapp/production
```

```
  file      ./.env.production (matched the vault environment)
  ✓ pushed ./.env.production to myapp/production as version 1
```

1. AJ types their master password. The CLI makes AJ's master key, fetches AJ's locked
   copy of the vault key and unlocks it.
2. It reads `.env.production`, the default file for a production vault, and encrypts
   it byte for byte with AES-256-GCM.
3. The vault id and the version number are bound into the encryption. If a server
   tried to serve version 1 as if it were version 2, decryption would fail.

| Sent to the server | Never sent |
|---|---|
| the ciphertext, a BLAKE3 hash, and the variable **names** (so the dashboard can list them) | any value from the file, the vault key, the master key |

```mermaid
sequenceDiagram
    autonumber 9
    actor A as AJ
    actor J as Joy
    actor R as Roy
    participant S as evnx server
    participant B as Blob storage
    A->>S: GET my-key for myapp/production
    S-->>A: AJ's locked copy of the vault key
    A->>A: unlock it, encrypt the file (AES-256-GCM, vault id + version 1)
    A->>S: cloud push (ciphertext, hash, variable names)
    S->>B: store the blob as version 1
```

## Step 4: AJ shares with Joy and Roy

```bash
evnx vault share myapp/production --with joy@example.test --role developer -v
evnx vault share myapp/production --with roy@example.test --role viewer
```

```
  ✓ shared myapp/production with joy@example.test as developer
  vault id  bed17154-430e-4e6f-aebf-32a7cdb40931
  key wrap  hybrid X25519 + ML-KEM-768
  ml-kem ct 1452 chars

  They can pull it with:  evnx cloud pull --vault myapp/production
```

This is the step that makes sharing possible, and it happens entirely on AJ's laptop:

1. The CLI asks the server for **Joy's public keys**.
2. AJ types their master password, and AJ's machine unlocks **AJ's** copy of the vault key.
3. It locks the vault key again, this time **to Joy's public keys**. This lock is a
   *hybrid*: a one-time X25519 key exchange and an ML-KEM-768 encapsulation, mixed
   into one wrapping key. It stays shut as long as either algorithm holds, including
   against a future quantum computer working on a recording made today.
4. The server stores Joy's locked copy as Joy's member row. Roy's share repeats the
   same steps with Roy's public keys.

| Sent to the server | Never sent |
|---|---|
| Joy's locked copy, the one-time public key, the ML-KEM ciphertext, Joy's role | the unlocked vault key, AJ's master key or password |

```mermaid
sequenceDiagram
    autonumber 14
    actor A as AJ
    actor J as Joy
    actor R as Roy
    participant S as evnx server
    participant B as Blob storage
    A->>S: GET public keys for joy@example.test
    S-->>A: Joy's X25519 and ML-KEM-768 public keys
    A->>A: unlock AJ's copy, then lock the vault key to Joy's public keys
    A->>S: vault share, Joy as developer, with Joy's locked copy
    A->>S: vault share, Roy as viewer (same steps, Roy's public keys)
    Note over S: three locked copies of one vault key
```

<Callout type="info" title="There is no invite link for a vault">
The vault key has to be locked to a public key that already exists, so the other
person registers first. Sharing with an address that has no account stops before
anything is sent:

```
Error: no evnx account for nobody@example.test.
  They need to register first — the vault key is wrapped to their
  public key, so there has to be one.
```

Organisation invites are a separate feature, and they cannot grant access to a vault.
</Callout>

## Step 5: Joy pulls and decrypts

This is the step the question was about. On Joy's laptop:

```bash
evnx vault list
evnx cloud pull --vault myapp/production --file .env.production
```

```
  NAME   ENVIRONMENT  ROLE       VERSIONS  UPDATED
  myapp  production   developer         1  2026-10-22
```

```
  file      .env.production (--file)
  ✓ pulled version 1 of myapp/production into .env.production
```

1. Joy types **their own** master password. With Joy's salt, it becomes Joy's master key.
2. The CLI fetches Joy's locked private key and unlocks it with that master key.
3. It fetches **Joy's** copy of the vault key, the one AJ made in step 4.
4. Joy's private keys unwrap it. Out comes **the same vault key** AJ used in step 3.
5. The CLI downloads the encrypted file, decrypts it, and writes `.env.production`
   readable by Joy only (mode `600`). It is byte-for-byte the file AJ pushed.

```mermaid
sequenceDiagram
    autonumber 19
    actor A as AJ
    actor J as Joy
    actor R as Roy
    participant S as evnx server
    participant B as Blob storage
    J->>J: master key = Argon2id(Joy's password, Joy's salt)
    J->>S: GET auth/me
    S-->>J: Joy's locked private key
    J->>J: unlock it with Joy's master key
    J->>S: GET my-key for myapp/production
    S-->>J: Joy's locked copy of the vault key
    J->>J: hybrid unwrap with Joy's private keys
    Note over J: the same vault key AJ holds
    J->>S: cloud pull, latest version
    S->>B: fetch version 1
    B-->>S: ciphertext
    S-->>J: ciphertext
    J->>J: decrypt, write .env.production (mode 600)
```

A wrong password fails at the first lock, before anything is downloaded:

```
Error: that master password did not open your keypair, so it is not the one this account was registered with. Nothing has been changed.
  If you have already changed it on another machine, use the new one.
```

<Callout type="tip" title="Which file a pull writes">
Without `--file`, a first pull into a folder that has no `.env.production` yet writes
`.env` and warns that it came from a production vault:

```
  file      ./.env (default)
  ! writing to a production vault from ./.env — pass --env-name or --file if that is not what you meant
```

Pass `--file .env.production` to keep the same name as on AJ's machine.
</Callout>

## Step 6: Joy pushes a change

```bash
evnx cloud push --vault myapp/production --file .env.production
```

```
  ✓ pushed .env.production to myapp/production as version 2
```

Joy unlocks Joy's copy exactly as in step 5 and encrypts version 2 with it. There is
one vault key, so AJ and Roy decrypt Joy's version with their own copies. Roy is
a viewer, so the server refuses Roy's push:

```
Error: Insufficient permissions
```

Joy can't pass the vault on, either. Sharing needs the admin role, and the CLI says
so before asking for a password:

```
Error: sharing myapp/production needs the admin or owner role; you are a developer on it.
  Ask its owner, or an admin, to share it.
```

If AJ made Joy an admin, Joy could share it as viewer or developer, from Joy's own
copy of the vault key (v0.10.18+).

<Callout type="info" title="Sharing again is refused">
Sharing with someone already in the vault never rewrites their row (v0.10.18+). If
AJ shares with Joy again at the same role, nothing changes:

```
  joy@example.test is already a developer on myapp/production — nothing changed.
```

At another role, AJ gets the command that does change it:

```
Error: joy@example.test is already a developer on myapp/production.
  To make them admin:  evnx vault role myapp/production --user joy@example.test --role admin
```

And Joy sharing with AJ, the owner, is refused:
`aj@example.test owns myapp/production. Sharing cannot change the owner's role or key.`
Before this, a share was an overwrite: it replaced the member's role and key, so an
owner sharing with themselves became a developer. The server refuses these too, for
every client.
</Callout>

```mermaid
sequenceDiagram
    autonumber 31
    actor A as AJ
    actor J as Joy
    actor R as Roy
    participant S as evnx server
    participant B as Blob storage
    J->>S: cloud push version 2 (developer, so allowed)
    S->>B: store version 2
    A->>S: cloud pull
    S-->>A: ciphertext of version 2
    A->>A: decrypt with AJ's own copy of the vault key
    R->>S: cloud push (viewer)
    S--xR: Insufficient permissions
```

## Step 7: AJ removes Roy

Roy's QA contract has ended, so Roy should lose access to the vault.

```bash
evnx vault revoke myapp/production --user roy@example.test
```

```
  Re-encrypting 2 version(s)…
  Re-wrapping for 2 member(s)…

  ✓ removed roy@example.test from myapp/production and rotated the vault key
  2 version(s) re-encrypted, 2 member(s) re-wrapped

  They can no longer read anything pushed from now on.
  They may still hold copies of what they could already read —
  rotate those secrets at their source.
```

Deleting Roy's row would not be enough. Roy may have kept the unlocked vault key,
and it would open every blob, including ones pushed later. So `revoke` **rotates the
key**:

1. AJ's machine generates a **new** vault key.
2. It downloads every version, decrypts it with the old key and encrypts it with the
   new one.
3. It locks the new key for everyone who stays: AJ's copy under AJ's master key,
   Joy's with the hybrid lock to Joy's public keys.
4. One request swaps in all the new blobs and copies at once and deletes Roy's row.
   If anything fails, nothing changes.

Roy could also have left on his own with `evnx vault leave myapp/production`. That
deletes Roy's row and nothing else: the key is **not** rotated, so it is the polite
way to go, not a substitute for this step.

Roy's next pull finds nothing, and Joy's next pull works unchanged:

```
Error: no vault called "myapp/production". Run `evnx vault list` to see what you have.
```

```mermaid
sequenceDiagram
    autonumber 38
    actor A as AJ
    actor J as Joy
    actor R as Roy
    participant S as evnx server
    participant B as Blob storage
    A->>A: new vault key
    A->>S: fetch every version
    S-->>A: ciphertexts
    A->>A: decrypt with the old key, encrypt with the new key
    A->>A: lock the new key for AJ and for Joy
    A->>S: vault revoke, one atomic swap, Roy's row deleted
    R->>S: cloud pull
    S--xR: no vault called myapp/production
    J->>S: cloud pull
    S-->>J: works, Joy's copy was re-locked in the same swap
```

<Callout type="warning" title="What revoke cannot do">
It cannot reach into Roy's laptop. The `.env.production` Roy pulled before step 7
is still on Roy's disk, and any value Roy copied is still Roy's. **Rotate those secrets
where they are issued**: the database password, the Stripe key, and so on. evnx can
stop handing a secret out. Only the provider can make the old value worthless.
</Callout>

## What the server actually holds

After step 4, the vault's member rows on the test server look like this. Lengths only;
the bytes themselves are random-looking and useless without a master password.

| Member | Role | Locked vault key | One-time public key | ML-KEM ciphertext |
|---|---|---|---|---|
| aj@example.test | owner | 96 characters | none | none |
| joy@example.test | developer | 96 characters | present | 1452 characters |
| roy@example.test | viewer | 96 characters | present | 1452 characters |

AJ's row has no one-time key and no ML-KEM ciphertext, because AJ's copy is locked
symmetrically under AJ's own master key: there is no key exchange to record. Every
shared copy has both. A database rule refuses a row that has one without the other,
so a weakened, X25519-only share can't be stored even by mistake.

The stored versions hold the variable **names** in the clear, and nothing else readable.
On the test server, a search of every stored blob and of a full database dump for any
value from the file found nothing.

```mermaid
flowchart TB
  DUMP["A full copy of the server: database dump and every blob"] --> CT["encrypted files"]
  DUMP --> WK["locked vault-key copies, one per member"]
  DUMP --> PK["locked private keys"]
  DUMP --> VF["SRP verifiers and salts"]
  DUMP --> NM["variable names, versions, who pushed when"]
  CT -.->|"needs a vault key"| WK
  WK -.->|"needs a master key or a private key"| PK
  PK -.->|"needs a master key"| PW(["a master password, which the server never received"])
  VF -.->|"cannot be turned back into"| PW
```

Every dotted arrow ends at a master password. That's why a breach of the server,
or anyone with full access to it, gets ciphertext and names but no values.

## Questions people ask

**Can the server read the secrets?**
Not passively. A breach, a database dump or a curious operator gets what the diagram
above shows: nothing that opens without a master password.

**Is there any way the server could get in?**
Yes: by lying during a share. In step 4 AJ's CLI gets Joy's public keys **from the
server**. A malicious server could hand over its own keys instead, and receive a copy
it can open. evnx doesn't yet let you compare key fingerprints out of band, so the
precise claim is that the server cannot read your secrets **passively**. Sharing is
the one moment that trusts the server to be honest about who is who.

**Does AJ have to be online when Joy pulls?**
No. AJ's part ended when AJ stored Joy's locked copy in step 4. From then on Joy
needs only Joy's own password and the server.

**What if Joy forgets the master password?**
Then Joy's copy can't be opened, by Joy, by AJ, or by the server. That password is
the only thing that opens Joy's private key, and it is never stored.

**How does a CI pipeline read a vault?**
An [API token](/guides/integrations/ci-cd-cloud-tokens) lets a pipeline reach the
server, but the server holds only locked copies. To decrypt, the pipeline also needs
the master password, kept as a CI secret and piped in:
`echo "$EVNX_PASSWORD" | evnx cloud pull --vault myapp/production --password-stdin`.
On the runner it becomes the master key, exactly as on a laptop.

**Why isn't AJ's own copy locked with the public-key method too?**
It doesn't need to be, and it is safer this way. A copy locked symmetrically under
the master key involves no key exchange, so there's nothing for a quantum computer to
attack later. Only copies made for someone else need the hybrid lock.
