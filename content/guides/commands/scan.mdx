`evnx scan` detects secrets and sensitive data in your `.env` files before they leave your machine. It runs in under 200ms and integrates directly into pre-commit hooks and CI/CD pipelines.

<Prerequisites>
  <Prerequisite href="/guides/getting-started/installation">Install evnx</Prerequisite>
</Prerequisites>

## Command signature

```bash
evnx scan [OPTIONS] [PATH]
```

**Options:**

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `[PATH]...` | positional | `.` | Files or directories to scan. Repeatable: `evnx scan .env config/` |
| `--format` | `pretty\|json\|sarif\|github` | `pretty` | Output format. **An unrecognised value is an error** — it used to fall back to `pretty` silently |
| `--severity` | `high\|medium\|low` (`all` = `low`) | `low` | **v0.5.0+** — lowest confidence worth reporting. Filters the findings, the counts and the exit code together |
| `--exit-zero` | `bool` | `false` | Always exit 0 (advisory mode) |
| `--exclude` | `string[]` | `[]` | Glob or substring patterns to skip |
| `--pattern` | `regex[]` | `[]` | **v0.5.0+** — also report values matching this expression. Repeatable. Combines with `[[scan.patterns]]` |
| `--ignore-placeholders` | `bool` | `false` | Skip values that look like placeholders (`changeme`, `your_key_here`) |

<Callout type="warning">
`--path`, `--recursive`, `--ignore`, `--include-example`, `--output` and `--exit-code`
have appeared on this page in the past. **None of them exist.** Paths are positional,
scanning is already recursive, and the advisory flag is `--exit-zero`.

Redirect instead of `--output`: `evnx scan --format sarif > results.sarif`.

`--pattern` **did** nothing until v0.5.0 — it was accepted by the parser and discarded.
It works now; see [Teaching it your own formats](#teaching-it-your-own-formats).
</Callout>

## What evnx scans for

### Known credential patterns

evnx ships with built-in patterns for the most common credentials:

```
AWS_ACCESS_KEY_ID     — /AKIA[0-9A-Z]{16}/
AWS_SECRET_ACCESS_KEY — high entropy, 40 chars
STRIPE_SECRET_KEY     — /sk_(live|test)_[a-zA-Z0-9]{24}/
STRIPE_PUBLIC_KEY     — /pk_(live|test)_[a-zA-Z0-9]{24}/
GITHUB_TOKEN          — /ghp_[a-zA-Z0-9]{36}/
OPENAI_API_KEY        — /sk-[a-zA-Z0-9]{48}/
SENDGRID_API_KEY      — /SG\.[a-zA-Z0-9_-]{22}\.[a-zA-Z0-9_-]{43}/
TWILIO_AUTH_TOKEN     — /[0-9a-f]{32}/
```

These are the formats evnx ships with. For the ones only your project knows — an internal
token, a vendor key shape — see [Teaching it your own formats](#teaching-it-your-own-formats).

### High-entropy detection

Beyond known patterns, `evnx scan` flags any value of 32 characters or more whose Shannon entropy exceeds 4.8. This catches:

- Custom API keys that don't match a known format
- Base64-encoded secrets embedded in `.env`
- JWTs (which contain base64-encoded payloads)
- Private keys accidentally pasted as values

<Callout type="warning">
The threshold is **not configurable**. This page and the `.evnx.toml` reference both
described `entropy_threshold` as a setting; no such setting is read by anything. 4.8 for
the generic check, and 4.5 for the gate on AWS secret keys, are compiled in.
</Callout>

<Callout type="info" title="Why entropy matters">
A string like `wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY` scores high on Shannon entropy because its characters are distributed almost uniformly — a property of cryptographically random strings. Human-readable values like `my-app-name` score low.
</Callout>

## Output formats

### Pretty (default)

Human-readable, color-coded output for terminal use:

```bash
evnx scan
```

```
[SCAN] Scanning .env...

[ERROR] AWS_SECRET_ACCESS_KEY
        Pattern: aws_secret_access_key (confidence: high)
        Line 8
        Recommendation: Use `evnx migrate --to aws-secrets-manager`

[WARNING] STRIPE_SECRET_KEY
          Pattern: stripe_live_key (confidence: medium)
          Value appears to be a placeholder — verify before deploying

[SUMMARY] 1 error, 1 warning — run `evnx migrate` to move secrets to a manager
```

### JSON

For programmatic processing, piping to `jq`, or custom reporting:

```bash
evnx scan --format json
```

```json
{
  "files_scanned": 1,
  "secrets_found": 2,
  "findings": [
    {
      "pattern": "AWS Secret Access Key",
      "confidence": "high",
      "value_preview": "wJalrXUt...KEYab",
      "location": "./.env:1 (AWS_SECRET_ACCESS_KEY)",
      "variable": "AWS_SECRET_ACCESS_KEY",
      "action_url": "https://console.aws.amazon.com/iam"
    },
    {
      "pattern": "Stripe Secret Key (LIVE)",
      "confidence": "high",
      "value_preview": "sk_live_...defXY",
      "location": "./.env:2 (STRIPE_SECRET_KEY)",
      "variable": "STRIPE_SECRET_KEY",
      "action_url": "https://dashboard.stripe.com/apikeys"
    }
  ],
  "high_confidence": 2,
  "medium_confidence": 0,
  "low_confidence": 0,
  "summary": { "total": 2, "high": 2, "medium": 0, "low": 0, "files_scanned": 1 }
}
```

<Callout type="warning">
⚠️ **The recipes on this page used to name fields that do not exist.** A finding carries
`confidence` and `variable`, not `severity` and `key`, so the documented filter

```bash
jq '[.findings[] | select(.severity == "high") | .key]'   # ← returns []
```

returned an **empty list over a live AWS key** — a CI gate built on it reported clean on a
repo with a committed credential. `summary` did not exist at all before **v0.5.0**, so
`jq -e '.summary.errors == 0'` failed builds that had nothing wrong with them.

The corrected recipes are below. If you copied any of the old ones, they are worth
re-checking.
</Callout>

`confidence` is deliberately not called `severity`: it answers *"how sure are we this is a
real credential"*, not *"how bad is it"*.

Useful with `jq`:

```bash
# List the variables holding high-confidence findings
evnx scan --format json | jq -r '[.findings[] | select(.confidence == "high") | .variable] | join(", ")'

# Count everything reported
evnx scan --format json | jq '.summary.total'

# Exit non-zero if anything was found
evnx scan --format json | jq -e '.summary.total == 0'

# Where to revoke each one
evnx scan --format json | jq -r '.findings[] | "\(.variable): \(.action_url // "rotate at source")"'
```

<Callout type="info">
Simpler than any of these: `evnx scan --severity high` already exits `1` when there is a
high-confidence finding and `0` when there is not, so a gate usually needs no `jq` at all.
</Callout>

### SARIF (GitHub Security tab)

SARIF (Static Analysis Results Interchange Format) is the standard format for security tools integrating with GitHub's Security tab:

```bash
evnx scan --format sarif --exit-zero > results.sarif
```

In GitHub Actions, upload as a security artifact:

```yaml
- name: Scan for secrets
  run: evnx scan --format sarif --exit-zero > results.sarif

- name: Upload SARIF results
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: results.sarif
  if: always()   # Upload even if scan finds issues
```

Findings appear in the **Security → Code scanning alerts** tab of your repository.

### GitHub Actions annotations

Inline annotations appear directly on pull request diffs:

```bash
evnx scan --format github
```

```
::error file=.env,line=8,title=Secret detected::AWS_SECRET_ACCESS_KEY matches aws_secret pattern
::warning file=.env,line=12,title=Possible secret::STRIPE_SECRET_KEY may be a live key
```

## CI/CD usage

### Block commits with pre-commit

```yaml
# .pre-commit-config.yaml
repos:
  - repo: local
    hooks:
      - id: evnx-scan
        name: evnx — scan for secrets
        entry: evnx scan --severity high
        language: system
        files: '\.env'
        pass_filenames: false
```

`--severity high` means only high-confidence findings block the commit; anything below is
neither reported nor counted. `scan` already exits `1` when it reports something, so no
extra flag is needed to make the hook fail.

<Callout type="warning">
This hook used to read `evnx scan --exit-code --severity high`. **`--exit-code` does not
exist**, so the hook failed with a clap argument error on *every* commit — clean or not —
and the message said "secrets detected". `--severity` needs **v0.5.0+**; on earlier
versions drop it and the hook blocks on any finding.
</Callout>

### GitHub Actions — block PRs

```yaml
# .github/workflows/security.yml
name: Security scan

on:
  pull_request:
  push:
    branches: [main]

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install evnx
        run: curl -fsSL https://dotenv.space/install.sh | bash

      # Annotations land on the PR diff. Fails the job on any finding.
      - name: Scan .env files
        run: evnx scan --format github

      # SARIF must be redirected — there is no --output flag.
      - name: Generate SARIF
        if: always()
        run: evnx scan --format sarif --exit-zero > results.sarif

      - name: Upload SARIF
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: results.sarif
        if: always()
```

The SARIF step carries `--exit-zero` deliberately: it exists to produce the file, and the
preceding step is what fails the build.

## Declaring what the heuristics cannot know

**v0.5.0+.** `scan` guesses at secrecy from a variable's name and the shape of
its value, and both guesses fail in opposite directions:

- `TENANT_A=9f3a7c21b85e4d0fa62c` — a real credential whose name gives nothing
  away. Reported as **"✓ No secrets detected"**, exit `0`.
- `INTERNAL_SECRET=a-long-config-value` — configuration, flagged **high**
  because of its name.

A project can settle either with a [contract](/guides/commands/spec):

```toml
[vars.TENANT_A]
secret = true

[vars.INTERNAL_SECRET]
secret = false
```

<Callout type="danger">
**`secret = false` cannot silence a real key.** It retracts a guess made from a
variable's *name*; it does not retract a match on the *value*. A variable holding
`sk_live_…` is still reported however it is declared, because `.evnx.toml` is
committed and one wrong line would otherwise silence a live credential for
everyone who clones.

Since it does loosen scanning, evnx announces it on every run:
`config .evnx.toml (vars.secret=false on 1 variable(s))`.
</Callout>

## Teaching it your own formats

**v0.5.0+.** The built-in patterns know AWS, Stripe, GitHub, OpenAI and the rest. They do
not know your company's internal token, or the key shape of a vendor nobody else uses —
and a credential evnx cannot name is a credential it reports as `✓ No secrets detected`.

`--pattern` takes a regular expression and reports anything matching it:

```bash
evnx scan --pattern 'ACME-[A-Z0-9]{32}'
```

```
  ✗  Custom pattern 1                            high
     ./.env:2 (TENANT_A)  ACME…A539
     !  matches a live key format, not a placeholder
```

It is repeatable, and it takes an expression and **nothing else** — there is no
`--pattern 'Name=regex'` form. `=` is legal inside a character class, so a pattern like
`[A-Za-z0-9+/=]{40}` would split into a nonsense name and a broken expression. Flag
patterns are named by position instead: `Custom pattern 1`, `Custom pattern 2`.

### The durable form — `[[scan.patterns]]`

For a rule the whole team should scan with, and for a name that means something, declare it
in `.evnx.toml`:

```toml
[[scan.patterns]]
name = "Acme API key"
regex = "ACME-[A-Z0-9]{32}"
url = "https://acme.example/settings/keys"   # optional: where to revoke it

[[scan.patterns]]
name = "Ring handle"
regex = "RING-[0-9]{4}"
confidence = "medium"                        # optional: high | medium | low
```

```
  ✗  Acme API key                                high
     ./.env:2 (TENANT_A)  ACME…A539
     !  matches a live key format, not a placeholder
     →  revoke at https://acme.example/settings/keys

  !  Ring handle                                 medium
     ./src/client.ts:2  RI…21
```

| Key | Required | Meaning |
|-----|----------|---------|
| `name` | yes | What the finding is called, in every output format. Becomes the SARIF rule id — `secret/acme-api-key` |
| `regex` | yes | The expression. Anchor it yourself if you want it anchored |
| `confidence` | no | `high` (default), `medium` or `low`. Feeds `--severity`, the counts and the exit code together |
| `url` | no | Where to go and revoke a match |

The two sets **combine** — `--pattern` is this run's rule, `[[scan.patterns]]` is the
project's standing set — the same way `--exclude` combines with `[scan] exclude`. The
default confidence is `high` because you wrote the rule deliberately; a rule you want to be
advisory says `confidence = "medium"` and drops out of `--severity high`.

### A broken expression is not a clean scan

<Callout type="danger">
**An expression that does not compile exits `2`, and `--exit-zero` does not suppress it.**

```
$ evnx scan . --pattern '('
Error: 'Custom pattern 1' is not a valid regular expression
  (

regex parse error:
    (
    ^
error: unclosed group

No verdict: evnx did not scan anything. This is not a clean result.
```

Exit `0` there would mean CI reads a search that never ran as a pass. A pattern that matches
the empty string — `.*`, `a?` — is refused on the same grounds: it would flag every line in
the project.

The same applies to a typo in `confidence`. `confidence = "hgih"` is an error, not a silent
downgrade to `low`, because a quiet downgrade would drop the rule out of a `--severity high`
gate that used to catch it.
</Callout>

### How it interacts with the built-in detectors

| Situation | What is reported |
|-----------|------------------|
| Your rule matches a value nothing else recognises | Your rule, under your name |
| Your rule and the *name* heuristic both match | **Your rule.** `ACME_TOKEN=ACME-…` reports as `Acme API key`, not `Sensitive config key: ACME_TOKEN` |
| Your rule and a built-in *provider* pattern both match | **The built-in.** A real AWS key stays `AWS Access Key`, because only it can link you to IAM to revoke it |
| Your rule matches a variable declared `secret = false` | **Your rule.** It read the value, and no declaration about what a variable is *for* can make its contents stop being a credential |

### Files that are not `.env`

Custom patterns are matched against the whole line in non-`.env` files, so a short format is
found where the entropy heuristics could not see it:

```ts
// src/client.ts
const ring = "RING-4821";
```

```bash
evnx scan ./src --pattern 'RING-[0-9]{4}'   # found
evnx scan ./src                             # ✓ No secrets detected
```

The generic detectors split each line into tokens and discard anything 20 characters or
shorter, which is right for "this looks random" and wrong for "this is exactly what I am
looking for".

### Performance

Declaring rules is close to free. Every pattern is compiled into a single automaton that
reports which of them match in one pass, so a line with no secret in it costs the same
whether you declared one rule or two hundred — the same approach GitHub's scanner and
gitleaks use.

Measured over 400 files, 60,000 lines, 6.3 MB, no findings:

| patterns | scan time |
|---------:|----------:|
| 0 | 55 ms |
| 1 | 56 ms |
| 10 | 59 ms |
| 50 | 58 ms |
| 200 | 68 ms |

Expressions are also matched without backtracking, so a pattern committed to `.evnx.toml`
cannot hang the scan for everyone who clones the repository.

<Callout type="warning">
**A pattern made only of literal text will match its own declaration**, because `.evnx.toml`
is scanned like any other file. `--exclude .evnx.toml` if that bothers you — but note that
excluding it also means a secret pasted into that file would never be found, which is why
evnx does not exclude it for you. Expressions with metacharacters do not self-match.
</Callout>

<Callout type="info" title="Not to be confused with `evnx validate --pattern`">
`validate`'s `--pattern` was **removed** in the same release. It named a file to validate
and its entire implementation was a discarded argument. `scan --pattern` names a secret
format and works. Same word, opposite directions — see
[evnx validate](/guides/commands/validate).
</Callout>

### When to use which

| You want | Use |
|----------|-----|
| A named variable treated as secret, whatever it holds | `[vars] secret = true` — see [Declaring what the heuristics cannot know](#declaring-what-the-heuristics-cannot-know) |
| Any value of a given *shape* found, wherever it appears | `[[scan.patterns]]` |
| To try an expression once, without committing it | `--pattern` |

The first is about a variable, the other two about a format. A spec entry will not find your
token pasted into a `.ts` file; a pattern will not know that `TENANT_A` is a credential if
its value has no distinctive shape.

## Ignoring false positives

Some values look like secrets but are not — test fixtures, sample values, generated
tokens in a seed file.

<Callout type="warning">
⚠️ **Inline `# evnx-ignore` comments do not work.** This page has documented them; no
command reads them. A value marked `# evnx-ignore: test fixture` is still reported, and
there is no `[scan] ignore` key either.

`.evnx.toml`'s `[scan]` section **does** work as of v0.5.0 — `severity`, `exclude`,
`ignore_placeholders` and `patterns` are all read. On v0.4.x the loader existed but nothing
called it, which is where the older claim came from.

The three mechanisms below are the ones that exist.
</Callout>

### Skip files and paths — `--exclude`

Glob or substring; repeatable. Combines with `[scan] exclude` from `.evnx.toml` rather than
replacing it — the config holds the project's standing exclusions, the flag is this run's.

```bash
evnx scan --exclude 'fixtures/**' --exclude '*.test.js'
```

A pattern **without** `*` matches anywhere in the path, so `fixtures` skips
`./fixtures/.env` and `./test/fixtures/.env` alike. A pattern **with** `*` is a glob, and is
tried against the path as walked, the path relative to the scan root, and the file name —
so `fixtures/**`, `./fixtures/**`, `*fixtures*` and `*.log` all work.

<Callout type="warning">
**v0.5.0+.** Before this, a glob was only ever matched against the whole path *including*
its leading `./`, so `fixtures/**` and `*.log` matched nothing and did so silently. If you
worked around that with `*fixtures*` or a bare substring, those still behave exactly as they
did — the matching was widened, never redefined.
</Callout>

`.git/`, `node_modules/`, `target/`, `dist/`, `build/`, `.env.example`, `.env.sample`,
`.env.template` and `evnx backup` output are excluded already.

### Skip obvious placeholders — `--ignore-placeholders`

Drops values evnx recognises as filler — `changeme`, `your_api_key_here`, `xxx`, and the
like — before they are reported.

```bash
evnx scan --ignore-placeholders
```

### Raise the bar — `--severity` (v0.5.0+)

Usually the better answer for a noisy first run: report only what evnx is confident about,
rather than enumerating exceptions.

```bash
evnx scan --severity high
```

## Scanning a whole project

`evnx scan` is **already recursive**, and it scans every text file it recognises — not
only `.env` files. Paths are positional:

```bash
# The default: this directory and everything under it
evnx scan

# One file
evnx scan config/.env.production

# Several paths
evnx scan .env config/ src/
```

`.git/`, `node_modules/`, `target/`, `dist/`, `build/`, the `.env.example` family and
`evnx backup` output are always skipped.

<Callout type="success">
**v0.5.0+** — a path that cannot be scanned is an error, exit `2`, not a clean result.
`evnx scan ./typo` used to print "No secrets detected" and exit `0`; it now names every
path it could not read and says plainly that there is no verdict.
</Callout>

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Clean — nothing at or above `--severity`, or `--exit-zero` was set |
| `1` | Findings reported |
| `2` | **v0.5.0+** — the scan could not be completed, so there is no verdict |

**`2` is not a louder `1`.** "I found nothing" and "I could not look" are different
answers, and collapsing them is what let `evnx scan ./typo` report success. A gate written
as `evnx scan .` still fails on either; one that branches on the code can now tell a
finding from a broken setup.

```bash
evnx scan .
case $? in
  0) echo "clean" ;;
  1) echo "secrets found — blocking" ;;
  2) echo "scan did not run — fix the setup" ;;
esac
```

<Callout type="warning">
**`--exit-zero` suppresses `1` only.** Trouble still exits `2`: the flag means "do not fail
my build over findings", not "never tell me the scan was impossible".

Before v0.5.0 the table here claimed `1` meant *high-severity* findings and `2` meant a
scan error. Neither was true then — **any** finding exited `1`, errors exited `1` too, and
`scan` never returned `2`. It does now, and only for trouble.

To block only on high-confidence findings, say so: `evnx scan --severity high`.
</Callout>

<Callout type="tip" title="Advisory mode">
Use `--exit-zero` in environments where you want to report findings without blocking the pipeline. Good for first-pass onboarding when a codebase has known issues you're working through.
</Callout>
