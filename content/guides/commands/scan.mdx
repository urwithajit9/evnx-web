`evnx scan` detects secrets and sensitive data in your `.env` files before they leave your machine. It runs in under 200ms and integrates directly into pre-commit hooks and CI/CD pipelines.

<Prerequisites>
  <Prerequisite href="/guides/getting-started/installation">Install evnx</Prerequisite>
</Prerequisites>

## Command signature

```bash
evnx scan [OPTIONS] [PATH]
```

**Options:**

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `[PATH]...` | positional | `.` | Files or directories to scan. Repeatable: `evnx scan .env config/` |
| `--format` | `pretty\|json\|sarif\|github` | `pretty` | Output format. **An unrecognised value is an error** — it used to fall back to `pretty` silently |
| `--severity` | `high\|medium\|low` (`all` = `low`) | `low` | **v0.5.0+** — lowest confidence worth reporting. Filters the findings, the counts and the exit code together |
| `--exit-zero` | `bool` | `false` | Always exit 0 (advisory mode) |
| `--exclude` | `string[]` | `[]` | Glob or substring patterns to skip |
| `--ignore-placeholders` | `bool` | `false` | Skip values that look like placeholders (`changeme`, `your_key_here`) |

<Callout type="warning">
`--path`, `--recursive`, `--ignore`, `--include-example`, `--output` and `--exit-code`
have appeared on this page in the past. **None of them exist.** Paths are positional,
scanning is already recursive, and the advisory flag is `--exit-zero`. `--pattern` is
accepted by the parser but currently does nothing — it is reserved and has no effect.

Redirect instead of `--output`: `evnx scan --format sarif > results.sarif`.
</Callout>

## What evnx scans for

### Known credential patterns

evnx ships with built-in patterns for the most common credentials:

```
AWS_ACCESS_KEY_ID     — /AKIA[0-9A-Z]{16}/
AWS_SECRET_ACCESS_KEY — high entropy, 40 chars
STRIPE_SECRET_KEY     — /sk_(live|test)_[a-zA-Z0-9]{24}/
STRIPE_PUBLIC_KEY     — /pk_(live|test)_[a-zA-Z0-9]{24}/
GITHUB_TOKEN          — /ghp_[a-zA-Z0-9]{36}/
OPENAI_API_KEY        — /sk-[a-zA-Z0-9]{48}/
SENDGRID_API_KEY      — /SG\.[a-zA-Z0-9_-]{22}\.[a-zA-Z0-9_-]{43}/
TWILIO_AUTH_TOKEN     — /[0-9a-f]{32}/
```

### High-entropy detection

Beyond known patterns, `evnx scan` flags any value of 32 characters or more whose Shannon entropy exceeds 4.8. This catches:

- Custom API keys that don't match a known format
- Base64-encoded secrets embedded in `.env`
- JWTs (which contain base64-encoded payloads)
- Private keys accidentally pasted as values

<Callout type="warning">
The threshold is **not configurable**. This page and the `.evnx.toml` reference both
described `entropy_threshold` as a setting; no such setting is read by anything. 4.8 for
the generic check, and 4.5 for the gate on AWS secret keys, are compiled in.
</Callout>

<Callout type="info" title="Why entropy matters">
A string like `wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY` scores high on Shannon entropy because its characters are distributed almost uniformly — a property of cryptographically random strings. Human-readable values like `my-app-name` score low.
</Callout>

## Output formats

### Pretty (default)

Human-readable, color-coded output for terminal use:

```bash
evnx scan
```

```
[SCAN] Scanning .env...

[ERROR] AWS_SECRET_ACCESS_KEY
        Pattern: aws_secret_access_key (confidence: high)
        Line 8
        Recommendation: Use `evnx migrate --to aws-secrets-manager`

[WARNING] STRIPE_SECRET_KEY
          Pattern: stripe_live_key (confidence: medium)
          Value appears to be a placeholder — verify before deploying

[SUMMARY] 1 error, 1 warning — run `evnx migrate` to move secrets to a manager
```

### JSON

For programmatic processing, piping to `jq`, or custom reporting:

```bash
evnx scan --format json
```

```json
{
  "files_scanned": 1,
  "secrets_found": 2,
  "findings": [
    {
      "pattern": "AWS Secret Access Key",
      "confidence": "high",
      "value_preview": "wJalrXUt...KEYab",
      "location": "./.env:1 (AWS_SECRET_ACCESS_KEY)",
      "variable": "AWS_SECRET_ACCESS_KEY",
      "action_url": "https://console.aws.amazon.com/iam"
    },
    {
      "pattern": "Stripe Secret Key (LIVE)",
      "confidence": "high",
      "value_preview": "sk_live_...defXY",
      "location": "./.env:2 (STRIPE_SECRET_KEY)",
      "variable": "STRIPE_SECRET_KEY",
      "action_url": "https://dashboard.stripe.com/apikeys"
    }
  ],
  "high_confidence": 2,
  "medium_confidence": 0,
  "low_confidence": 0,
  "summary": { "total": 2, "high": 2, "medium": 0, "low": 0, "files_scanned": 1 }
}
```

<Callout type="warning">
⚠️ **The recipes on this page used to name fields that do not exist.** A finding carries
`confidence` and `variable`, not `severity` and `key`, so the documented filter

```bash
jq '[.findings[] | select(.severity == "high") | .key]'   # ← returns []
```

returned an **empty list over a live AWS key** — a CI gate built on it reported clean on a
repo with a committed credential. `summary` did not exist at all before **v0.5.0**, so
`jq -e '.summary.errors == 0'` failed builds that had nothing wrong with them.

The corrected recipes are below. If you copied any of the old ones, they are worth
re-checking.
</Callout>

`confidence` is deliberately not called `severity`: it answers *"how sure are we this is a
real credential"*, not *"how bad is it"*.

Useful with `jq`:

```bash
# List the variables holding high-confidence findings
evnx scan --format json | jq -r '[.findings[] | select(.confidence == "high") | .variable] | join(", ")'

# Count everything reported
evnx scan --format json | jq '.summary.total'

# Exit non-zero if anything was found
evnx scan --format json | jq -e '.summary.total == 0'

# Where to revoke each one
evnx scan --format json | jq -r '.findings[] | "\(.variable): \(.action_url // "rotate at source")"'
```

<Callout type="info">
Simpler than any of these: `evnx scan --severity high` already exits `1` when there is a
high-confidence finding and `0` when there is not, so a gate usually needs no `jq` at all.
</Callout>

### SARIF (GitHub Security tab)

SARIF (Static Analysis Results Interchange Format) is the standard format for security tools integrating with GitHub's Security tab:

```bash
evnx scan --format sarif --exit-zero > results.sarif
```

In GitHub Actions, upload as a security artifact:

```yaml
- name: Scan for secrets
  run: evnx scan --format sarif --exit-zero > results.sarif

- name: Upload SARIF results
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: results.sarif
  if: always()   # Upload even if scan finds issues
```

Findings appear in the **Security → Code scanning alerts** tab of your repository.

### GitHub Actions annotations

Inline annotations appear directly on pull request diffs:

```bash
evnx scan --format github
```

```
::error file=.env,line=8,title=Secret detected::AWS_SECRET_ACCESS_KEY matches aws_secret pattern
::warning file=.env,line=12,title=Possible secret::STRIPE_SECRET_KEY may be a live key
```

## CI/CD usage

### Block commits with pre-commit

```yaml
# .pre-commit-config.yaml
repos:
  - repo: local
    hooks:
      - id: evnx-scan
        name: evnx — scan for secrets
        entry: evnx scan --severity high
        language: system
        files: '\.env'
        pass_filenames: false
```

`--severity high` means only high-confidence findings block the commit; anything below is
neither reported nor counted. `scan` already exits `1` when it reports something, so no
extra flag is needed to make the hook fail.

<Callout type="warning">
This hook used to read `evnx scan --exit-code --severity high`. **`--exit-code` does not
exist**, so the hook failed with a clap argument error on *every* commit — clean or not —
and the message said "secrets detected". `--severity` needs **v0.5.0+**; on earlier
versions drop it and the hook blocks on any finding.
</Callout>

### GitHub Actions — block PRs

```yaml
# .github/workflows/security.yml
name: Security scan

on:
  pull_request:
  push:
    branches: [main]

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install evnx
        run: curl -fsSL https://dotenv.space/install.sh | bash

      # Annotations land on the PR diff. Fails the job on any finding.
      - name: Scan .env files
        run: evnx scan --format github

      # SARIF must be redirected — there is no --output flag.
      - name: Generate SARIF
        if: always()
        run: evnx scan --format sarif --exit-zero > results.sarif

      - name: Upload SARIF
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: results.sarif
        if: always()
```

The SARIF step carries `--exit-zero` deliberately: it exists to produce the file, and the
preceding step is what fails the build.

## Ignoring false positives

Some values look like secrets but are not — test fixtures, sample values, generated
tokens in a seed file.

<Callout type="warning">
⚠️ **Inline `# evnx-ignore` comments and `.evnx.toml` `[scan]` keys do not work.** This
page has documented both; neither is read by anything, and `.evnx.toml` as a whole is not
loaded by any command except the cloud vault binding. A value marked
`# evnx-ignore: test fixture` is still reported.

The two mechanisms below are the ones that exist.
</Callout>

### Skip files and paths — `--exclude`

Glob or substring; repeatable.

```bash
evnx scan --exclude 'fixtures/*' --exclude '*.test.js'
```

`.git/`, `node_modules/`, `target/`, `dist/`, `build/`, `.env.example`, `.env.sample`,
`.env.template` and `evnx backup` output are excluded already.

### Skip obvious placeholders — `--ignore-placeholders`

Drops values evnx recognises as filler — `changeme`, `your_api_key_here`, `xxx`, and the
like — before they are reported.

```bash
evnx scan --ignore-placeholders
```

### Raise the bar — `--severity` (v0.5.0+)

Usually the better answer for a noisy first run: report only what evnx is confident about,
rather than enumerating exceptions.

```bash
evnx scan --severity high
```

## Scanning a whole project

`evnx scan` is **already recursive**, and it scans every text file it recognises — not
only `.env` files. Paths are positional:

```bash
# The default: this directory and everything under it
evnx scan

# One file
evnx scan config/.env.production

# Several paths
evnx scan .env config/ src/
```

`.git/`, `node_modules/`, `target/`, `dist/`, `build/`, the `.env.example` family and
`evnx backup` output are always skipped.

<Callout type="warning">
⚠️ A path that does not exist is reported as **clean**, exit `0` — `evnx scan ./typo`
prints "No secrets detected". Check your paths in CI.
</Callout>

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Nothing reported — no findings at or above `--severity`, or `--exit-zero` was set |
| `1` | Findings reported, **or** the command failed (bad `--format`, bad `--severity`) |

<Callout type="warning">
This table previously claimed `1` meant *high-severity* findings and `2` meant a scan
error. Neither was true: **any** reported finding exits `1`, and errors exit `1` as well —
`scan` never returns `2`.

To block only on high-confidence findings, say so: `evnx scan --severity high`.

⚠️ A path that does not exist is currently reported as **clean**, with exit `0`:
`evnx scan ./typo` prints "No secrets detected". Check your paths.
</Callout>

<Callout type="tip" title="Advisory mode">
Use `--exit-zero` in environments where you want to report findings without blocking the pipeline. Good for first-pass onboarding when a codebase has known issues you're working through.
</Callout>
