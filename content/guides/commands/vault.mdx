A **vault** is one encrypted `.env` file plus its full version history. It has a name, an environment, and its own 256-bit key.

<Prerequisites>
  <Prerequisite href="/guides/commands/auth">Sign in with evnx auth</Prerequisite>
</Prerequisites>

## Commands

<CommandSignature>
evnx vault [SUBCOMMAND]
evnx vault create my-api --env production
evnx vault list
evnx vault share my-api/production --with alice@example.com
evnx vault members my-api/production
evnx vault role my-api/production --user alice@example.com --role admin
evnx vault revoke my-api/production --user bob@example.com
evnx vault delete my-api/production
</CommandSignature>

## Creating a vault

```bash
evnx vault create my-api --env production
```

<OptionTable>
  <Option flag="NAME" type="string" required>Vault name — letters, digits and hyphens.</Option>
  <Option flag="--env" type="enum" default="development" options="production, staging, development, test">Which environment this vault holds.</Option>
  <Option flag="--password-stdin" type="flag">Read the master password from stdin instead of prompting.</Option>
  <Option flag="--server" type="url">Server to talk to. Overrides `EVNX_SERVER` and `.evnx.toml`.</Option>
</OptionTable>

What happens, in order:

<Step number={1} title="A fresh 256-bit key is generated here">
Not on the server, and not derived from anything. Every vault gets an independent random key, so compromising one vault key tells an attacker nothing about any other.
</Step>

<Step number={2} title="That key is wrapped under your master key">
XChaCha20-Poly1305, under an HKDF subkey of your master key. The server receives only the wrapped form and has no way to open it.
</Step>

<Step number={3} title="The server stores the wrapped key and nothing else">
It knows a vault exists, who owns it, and what it is called. It does not know the key, and cannot obtain it.
</Step>

<Callout type="info" title="Why your own copy is post-quantum safe">
Your copy of a vault key is wrapped **symmetrically** — XChaCha20 under a key derived from your password. Grover's algorithm halves a symmetric key's effective strength, which for 256 bits leaves 128: still out of reach.

Sharing a vault with a teammate is **also** post-quantum safe, as of the hybrid
wrap. `evnx vault share` (**v0.5.0+**) re-wraps the vault key under a key derived from an
X25519 exchange *and* an ML-KEM-768 encapsulation together, so the wrap holds as
long as **either** primitive does. Shor's algorithm breaks X25519 outright, which
is why the ML-KEM half is there.

There is no X25519-only path left — not in the crate, not in the CLI, and not in
the database, where a constraint makes a half-formed wrap unstorable. Sharing
with an account that has no ML-KEM key on file is refused rather than quietly
downgraded; that account registers one on its next sign-in.
</Callout>

<Callout type="warning" title="Sharing weakens the guarantee from active attack">
The recipient's public keys are fetched **from the server**. A malicious server
could hand you its own keys instead and read what you share. There is no third
party to check them against, and out-of-band fingerprint verification is not
built yet.

So for a vault you share, "the server cannot read your secrets" narrows to
"cannot read them *passively*". A vault you never share is unaffected — its key
never goes near a key exchange.
</Callout>

## Listing vaults

```bash
evnx vault list
```

<TerminalOutput title="evnx vault list">
NAME              ENVIRONMENT    VERSIONS   UPDATED
my-api            production     12         2 hours ago
my-api            staging        4          3 days ago
internal-tools    development    1          last week
</TerminalOutput>

Names are scoped by environment, so `my-api/production` and `my-api/staging` are two separate vaults with two separate keys. Anywhere a vault is accepted you can write `name`, `name/environment`, or the raw id.

<Callout type="info" title="A vault-scoped API token cannot run this">
`vault list` has no vault in its path, so a token issued for one vault is refused rather than being allowed to enumerate your account. That is by design, not a gap.
</Callout>

## Roles

**v0.5.0+.** Every member of a vault holds one of four roles. They form a ladder,
and permission is a **minimum rank** rather than a list — so a role added later
slots into the ladder instead of being quietly missing from checks written before
it existed.

| Role | Can |
|---|---|
| `viewer` | Pull, list versions, read history, see who else is a member |
| `developer` | Everything a viewer can, **plus push** |
| `admin` | Everything a developer can, plus share, change roles, and revoke with a re-key |
| `owner` | Everything, plus **delete the vault**. Exactly one per vault |

Mapped onto the commands you actually run:

| Command | Minimum role |
|---|---|
| `evnx cloud pull`, `evnx cloud history` | `viewer` |
| `evnx vault members` | `viewer` |
| `evnx cloud push` | `developer` |
| `evnx vault share` | `admin` |
| `evnx vault role` | `admin` |
| `evnx vault revoke` | `admin` |
| `evnx vault delete` | `owner` |

<Callout type="info" title="Two rules that fall out of the ladder">
**Removing someone requires outranking them, not merely being an admin.** The
check is a rank comparison, and `admin > admin` is false — so two admins cannot
evict each other, and a disagreement between them is resolved by the owner.

**The owner cannot be removed by anyone, including themselves.** A vault with no
owner has nobody who can delete it or promote a replacement, and there is no
transfer-ownership command yet. `owner` is also not assignable through
`evnx vault role`; it is set once, by whoever created the vault.
</Callout>

## Sharing a vault

```bash
evnx vault share my-api/production --with alice@example.com
```

```text
  ✓ shared my-api/production with alice@example.com as developer

  They can pull it with:  evnx cloud pull --vault my-api/production
```

The role defaults to `developer`. Pass `--role viewer` for read-only access, or
`--role admin` to let them manage members too.

| Flag | Description |
|---|---|
| `--with <EMAIL>` | **Required.** The evnx account to share with |
| `--role <ROLE>` | `viewer`, `developer` or `admin`. Default `developer` |
| `--password-stdin` | Read the master password from stdin instead of prompting |
| `--server <URL>` | Override the server for this command |

Your master password opens the vault key **on your machine**, and it is re-wrapped
to the recipient's public keys before it leaves. The server never sees it
unwrapped and cannot grant access by itself.

<Callout type="warning" title="The recipient has to exist, and has to have signed in recently">
Sharing wraps the vault key to the recipient's **public keys**, so there must be
an account holding them. Two refusals you may hit, both deliberate:

- *"no evnx account for …"* — they have not registered. There are no invitations
  for non-registered users, because a person who has not registered has no public
  key to wrap to.
- *"… has no post-quantum sharing key yet"* — they registered before v0.5.0.
  Signing in once with evnx 0.5 or later, or at `app.evnx.dev`, registers it
  automatically.

Both are checked **before** the master-password prompt, so a share that cannot
work fails without asking you for anything.

evnx does not fall back to an X25519-only wrap in either case. That wrap would be
one a quantum computer opens, including from a recording made today, and it would
stay that way for as long as the row exists.
</Callout>

## Listing members

```bash
evnx vault members my-api/production
```

```text
  my-api/production — 3 member(s)

  owner      you@example.com (you)
  admin      alice@example.com
  developer  bob@example.com
             no post-quantum key — they must sign in once before the vault can be re-keyed
```

Any member can run this, including a `viewer`. That is deliberate: seeing who
else holds a key to a vault you hold a key to is how you notice a grant that
should not be there.

`--verbose` adds each member's user id and when they were granted access.

The *no post-quantum key* line is worth acting on before you need it — that
member cannot be re-wrapped to, so `evnx vault revoke` will refuse to run on this
vault until they sign in once.

## Changing a role

```bash
evnx vault role my-api/production --user alice@example.com --role admin
```

```text
  ✓ alice@example.com is now admin on my-api/production
```

| Flag | Description |
|---|---|
| `--user <EMAIL>` | **Required.** The member whose role is changing |
| `--role <ROLE>` | **Required.** `viewer`, `developer` or `admin` |

You can only set a role below your own, and only for someone you already outrank.
So an admin moves people between `viewer` and `developer`, and only the owner
makes or unmakes an admin.

Setting the role someone already has is not an error — it says so and changes
nothing.

## Revoking access

```bash
evnx vault revoke my-api/production --user bob@example.com
```

This is the expensive one, and the only command here that touches every version:

<Step number={1} title="Your copy of the current vault key is opened">
Locally, with your master password. Nothing has changed on the server yet.
</Step>

<Step number={2} title="A fresh vault key is generated">
Also locally.
</Step>

<Step number={3} title="Every version is re-encrypted under it">
Downloaded, decrypted, re-encrypted preserving that version's associated data, and staged on the server. Still nothing swapped.
</Step>

<Step number={4} title="The new key is wrapped for everyone who stays">
Symmetrically for your own copy; hybrid X25519 + ML-KEM-768 for everyone else's.
</Step>

<Step number={5} title="One request swaps all of it and removes the member">
Atomically. This is the first point at which anything changes.
</Step>

```text
  About to remove bob@example.com from my-api/production.
  Every version will be re-encrypted under a fresh key and re-wrapped
  for the 2 remaining member(s).

  This stops them reading anything pushed from now on. It cannot
  recall copies of what they could already read — rotate those
  secrets at their source.
? Remove bob@example.com from my-api/production? (y/N)

  Re-encrypting 12 version(s)…
  Re-wrapping for 2 member(s)…

  ✓ removed bob@example.com from my-api/production and rotated the vault key
  12 version(s) re-encrypted, 2 member(s) re-wrapped
```

| Flag | Description |
|---|---|
| `--user <EMAIL>` | **Required.** The member to remove |
| `--yes`, `-y` | Skip the confirmation prompt |
| `--no-rekey` | Remove them **without** rotating the key — see below |
| `--password-stdin` | Read the master password from stdin instead of prompting |

<Callout type="danger" title="What rotation achieves, and what it cannot">
Re-keying stops the removed member reading anything pushed **from now on**.

It cannot recall copies of what they could already read. If they had access to a
secret, treat that secret as theirs and **rotate it at its source** — the same
advice that applies to a leaked API token, and the step people skip because the
`✓` looks like completion.

This is also why evnx does **not** delete the old blobs. Doing so would throw away
version history for every remaining member in order to punish one departure, and
it would not un-ring the bell: the person being removed could already read those
versions.
</Callout>

<Callout type="warning" title="--no-rekey removes the member and nothing else">
`--no-rekey` skips steps 1–4 entirely. It is fast, and it leaves the removed
member able to decrypt **every version they already had access to, including ones
pushed after the revocation** — because the key never changed.

Use it only when you are re-keying separately, or when the member never held the
key. The confirmation prompt and the success message both say so, in yellow,
rather than reporting a revocation that did not revoke.
</Callout>

<Callout type="info" title="Two things revoke refuses to do">
**It will not run if a remaining member has no post-quantum key.** They could not
receive the new vault key, so re-keying would lock them out of the vault
entirely. Checked *before* any work and before the password prompt, so you are
not told after fifty versions have been re-encrypted. `evnx vault members` shows
who is affected.

**You cannot remove yourself.** Re-keying a vault you can no longer open cannot
work, so `revoke` refuses and tells you to ask an admin.

⚠️ Note this also means **there is currently no way to leave a vault from the
CLI**, even with `--no-rekey`, where re-keying is not involved and self-removal
would be safe. The API allows it; the CLI does not expose it. Ask an admin to
remove you.
</Callout>

## Deleting a vault

```bash
evnx vault delete my-api/production
```

This removes the vault and **every version in it**. You are asked to confirm.

| Flag | Effect |
|------|--------|
| `-y`, `--yes` | Skip the confirmation prompt — what a teardown script needs |

<Callout type="info">
**There is no `--password-stdin` here**, unlike `create`, `share` and `revoke`. Deleting is
a server-side operation on an authenticated session; nothing is decrypted, so there is no
password to give. Passing the flag is an argument error and the vault is **not** deleted —
worth knowing, because a cleanup step that silently fails leaves the vault on your account.
</Callout>

<Callout type="danger" title="Deleting a vault destroys the only copy of its key">
Your wrapped vault key lives in one place: the server's database. The CLI does not cache it — it fetches and unwraps it on each command.

So deleting a vault does not merely hide the blobs. It destroys the wrapped key that opens them, and the ciphertext becomes unrecoverable **even by you, even with the right master password**. Pull anything you still want before you delete.
</Callout>

## Choosing how to split vaults

One vault per `.env` file per environment is the grain that works. Some guidance that follows from how keys work rather than from taste:

- **Split by environment, always.** Separate vaults mean separate keys, so a production key never has to travel to anyone who only needs staging.
- **Split by blast radius, not by convenience.** Members are granted access per vault. Anything you might one day want to share with a narrower group belongs in its own vault from the start, because moving secrets later means re-encrypting them.
- **Don't split per developer.** Vaults are for secrets that differ, not for people who differ.

## What the server knows

Worth being precise, because "zero knowledge" is often used loosely:

| The server holds | The server does **not** hold |
|---|---|
| Vault name and environment | Any secret value |
| The wrapped vault key | The unwrapped vault key |
| Version numbers, timestamps, sizes | Your master password or master key |
| **Key names** — `DATABASE_URL`, `STRIPE_KEY` | Key **values** |
| BLAKE3 hash of each ciphertext | Anything that reveals the plaintext |

Key *names* are sent deliberately, so a dashboard can show what a vault holds without decrypting it. If your key names are themselves sensitive, that is a real trade-off to know about rather than discover.
