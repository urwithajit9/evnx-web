# CI/CD Integration for Sync Validation

<Callout type="tip" title="Why automate sync checks?">
Automating `evnx sync` in CI/CD ensures:
- `.env.example` stays up to date with code changes
- No secrets accidentally committed to templates
- Naming conventions enforced across the team
- New team members can onboard reliably
</Callout>

## Core CI flags for automation

When using `evnx sync` in CI/CD, always include these flags:

| Flag | Purpose | Example |
|------|---------|---------|
| `--check` | **v0.5.0+** — write nothing, and report the verdict through the exit code | `--check` |
| `--force` | Skip interactive prompts | `--force` |
| `--dry-run` | Preview without writing. ⚠️ Always exits `0` — not a gate | `--dry-run` |
| `--naming-policy error` | Fail on non-standard names | `--naming-policy error` |
| `--template-config` | Use team placeholder config | `--template-config .evnx/placeholders.json` |

**Base command for CI — v0.5.0+:**

```bash
evnx sync --direction forward --check --naming-policy error
```

`--check` implies `--dry-run`, so `--force` is no longer needed to get past the interactive
prompt.

<Callout type="warning">
**If you are on v0.4.0 or earlier, there is no working gate.** The command this page used
to recommend — `evnx sync --direction forward --force --dry-run --naming-policy error` —
exits `0` whether or not `.env.example` is stale, so any `if !` around it can never fire.
Upgrade to v0.5.0 for `--check`; until then, treat sync validation as advisory and read the
output rather than the exit code.
</Callout>

### Exit codes under `--check`

| Code | Meaning |
|------|---------|
| `0` | In sync |
| `1` | Out of sync — run `evnx sync` and commit the result |
| `2` | Error — a source file is missing, or a file will not parse |

Three rather than two, so a pipeline can distinguish a stale template from a broken run.
Full detail in the [`evnx sync` reference](/guides/commands/sync#exit-codes).

## GitHub Actions

### Basic sync validation

```yaml
# .github/workflows/env-sync.yml
name: Environment Sync Check

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  validate-sync:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install evnx
        run: cargo install evnx --all-features

      - name: Check .env.example is up to date
        run: |
          evnx sync \
            --direction forward \
            --check \
            --naming-policy error \
            --template-config .evnx/placeholders.json
```

`--check` fails the step by itself, so no `git diff` afterwards is needed — and the old
version of this example could not have worked: `--dry-run` writes nothing, so
`git diff --quiet .env.example` was always quiet and the gate never fired.

To report the two failure modes differently:

```yaml
      - name: Check .env.example is up to date
        run: |
          evnx sync --direction forward --check --naming-policy error
          case $? in
            0) ;;
            1) echo "::error::.env.example is stale — run 'evnx sync' and commit"; exit 1 ;;
            2) echo "::error::evnx could not check the files"; exit 1 ;;
          esac
```

### Block secrets in .env.example

```yaml
      - name: Check for secrets in template
        run: |
          if grep -iE "(sk_live|sk_test|password|secret|token)" .env.example | \
             grep -v "YOUR_\|placeholder\|demo\|sk_demo_"; then
            echo "::error ::Potential secrets found in .env.example!"
            echo "Use placeholders like YOUR_KEY_HERE instead."
            exit 1
          fi
```

### Upload diagnostic report

```yaml
      - name: Generate sync report
        if: failure()
        run: |
          evnx sync --direction forward --verbose --dry-run > sync-report.txt

      - name: Upload report
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: sync-diagnostics
          path: sync-report.txt
```

## GitLab CI

### Basic pipeline

```yaml
# .gitlab-ci.yml
env-sync:
  stage: test
  image: rust:latest
  script:
    - cargo install evnx
    - evnx sync \
        --direction forward \
        --force \
        --dry-run \
        --naming-policy error \
        --template-config .evnx/placeholders.json
    - git diff --quiet .env.example || (echo ".env.example out of sync!" && exit 1)
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"
```

### Collect diagnostics on failure

```yaml
env-sync-report:
  stage: test
  image: rust:latest
  script:
    - cargo install evnx
    - evnx sync --direction forward --verbose --dry-run > sync-report.txt 2>&1 || true
  artifacts:
    paths: [sync-report.txt]
    when: always
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

## Pre-commit hooks

### Local hook (per-developer)

```bash
#!/bin/bash
# .git/hooks/pre-commit

if git diff --cached --name-only | grep -qE "^(\.env|\.env\.example)"; then

  if git diff --cached --name-only | grep -q "^\.env$"; then
    echo "🚫 .env should not be committed!"
    echo "Add it to .gitignore or remove from staging:"
    echo "  git reset .env"
    exit 1
  fi

  if git diff --cached --name-only | grep -q "^\.env\.example$"; then
    echo "🔍 Validating .env.example changes..."

    if ! evnx sync --direction forward --check 2>/dev/null; then
      echo "⚠️  Sync validation failed. Run:"
      echo "  evnx sync --direction forward"
      exit 1
    fi
  fi
fi

exit 0
```

### Shared hook via pre-commit framework

```yaml
# .pre-commit-config.yaml
repos:
  - repo: local
    hooks:
      - id: env-sync-check
        name: Environment Sync Validation
        entry: bash -c 'evnx sync --direction forward --check --naming-policy error'
        language: system
        pass_filenames: false
        files: '^(\.env\.example|\.evnx/placeholders\.json)$'
```

## JSON output for advanced parsing

<Callout type="warning">
**Not implemented.** `EVNX_OUTPUT_JSON=1` is honoured by `evnx doctor` only. Setting it on
`evnx sync` changes nothing, so the `jq` recipes this section used to carry —
`EVNX_OUTPUT_JSON=1 evnx sync --dry-run --force | jq '.changes | length'` — pipe
human-readable text into `jq` and fail with a parse error.

The envelope below is kept as the intended shape, not as something you can use today.
Until it exists, **`--check`'s exit code is the supported machine interface** for sync.
</Callout>

The planned output:

```json
{
  "direction": "forward",
  "dry_run": true,
  "changes": [
    {
      "file": ".env.example",
      "action": "add",
      "variables": [
        {"key": "NEW_API_KEY", "placeholder": "YOUR_KEY_HERE"}
      ]
    }
  ],
  "warnings": [],
  "errors": []
}
```

### What to use instead, today

```bash
evnx sync --direction forward --check
case $? in
  0) echo "in sync" ;;
  1) echo "stale — run 'evnx sync --direction forward' and commit" ; exit 1 ;;
  2) echo "evnx could not check the files" ; exit 1 ;;
esac
```

`evnx doctor` does support the JSON envelope, if you need machine-readable output for the
surrounding checks:

```bash
EVNX_OUTPUT_JSON=1 evnx doctor | jq '.summary.errors'
```

## Advisory vs blocking modes

### Blocking mode (fail pipeline on issues)

```bash
evnx sync --check --naming-policy error
```

Pipeline fails if `.env.example` is out of sync.

### Advisory mode (report but don't fail)

```bash
evnx sync --check --naming-policy error || true
```

Or filter output for logging only:

```bash
evnx sync --dry-run 2>&1 | grep -E "✗|⚠️" >> deploy-log.txt
```

<Callout type="tip" title="When to use advisory mode">
Use advisory mode for:
- Initial rollout of sync checks
- Legacy projects with many violations
- Debugging why a pipeline is failing

Switch to blocking mode once the team is comfortable with the workflow.
</Callout>

## Multi-service repositories

For monorepos with multiple services:

```bash
for dir in services/*/; do
  echo "🔍 Checking $dir..."
  (cd "$dir" && evnx sync --direction forward --check) || \
    echo "❌ Issues in $dir" >> sync-errors.txt
done

if [ -s sync-errors.txt ]; then
  echo "🚫 Sync validation failed for some services:"
  cat sync-errors.txt
  exit 1
fi
```

**GitHub Actions example:**

```yaml
      - name: Check all services
        run: |
          ERRORS=0
          for dir in services/*/; do
            echo "Checking $dir..."
            (cd "$dir" && evnx sync --direction forward --check) || ERRORS=$((ERRORS+1))
          done
          if [ $ERRORS -gt 0 ]; then
            echo "::error ::$ERRORS service(s) failed sync validation"
            exit 1
          fi
```

## Troubleshooting CI failures

### Command not found: evnx

**Fix:** Ensure evnx is installed in the CI environment:

```yaml
- name: Install evnx
  run: cargo install evnx --all-features
```

Or use a pre-built binary:

```yaml
- name: Install evnx
  run: |
    curl -L https://github.com/your-org/evnx/releases/latest/download/evnx-x86_64-unknown-linux-gnu.tar.gz | tar xz
    sudo mv evnx /usr/local/bin/
```

### File not found: .env.example

**Fix:** Ensure the file exists in the repo:

```yaml
- name: Verify template exists
  run: |
    if [ ! -f .env.example ]; then
      echo "::error ::.env.example not found!"
      echo "Create it with: evnx init or evnx add custom"
      exit 1
    fi
```

### `jq` reports a parse error on sync output

**Cause:** `evnx sync` does not emit JSON. `EVNX_OUTPUT_JSON=1` is read by `evnx doctor`
only, so the pipe carries human-readable text and `jq` chokes on the first line.

**Fix:** use `--check`'s exit code for sync, and `evnx doctor` when you need JSON:

```bash
evnx sync --direction forward --check   # 0 in sync · 1 stale · 2 error
EVNX_OUTPUT_JSON=1 evnx doctor | jq '.summary.errors'
```

### Permission denied on .env

**Fix:** CI shouldn't need .env — ensure it's gitignored:

```yaml
- name: Verify .env is ignored
  run: |
    if git check-ignore .env | grep -q "^\.env$"; then
      echo "✓ .env is properly ignored"
    else
      echo "::warning ::.env should be in .gitignore"
    fi
```

## Best practices checklist

### For CI configuration
- [ ] Use `--force --dry-run` to skip prompts and avoid file writes
- [ ] Set `--naming-policy error` to enforce conventions
- [ ] Include `--template-config` if using custom placeholders
- [ ] Upload diagnostics as artifacts on failure
- [ ] Test the workflow locally before committing

### For team adoption
- [ ] Start with advisory mode (`|| true`) for first week
- [ ] Document the CI check in CONTRIBUTING.md
- [ ] Add a "Why did my PR fail?" section to docs
- [ ] Provide a local command to reproduce CI checks

### For security
- [ ] Never log `.env` contents in CI output
- [ ] Scan `.env.example` for accidental secrets
- [ ] Use custom placeholders that look fake (`sk_demo_XXX`)
- [ ] Rotate any test credentials used in examples
