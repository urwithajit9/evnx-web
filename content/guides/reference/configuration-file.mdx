evnx works with no configuration at all. `.evnx.toml` is optional, and exists for settings
that are **true of the project** and would otherwise be retyped on every invocation and in
every CI job.

Put it in your project root, next to `.env`, and commit it — that is the point. Everyone who
clones the repository gets the same policy.

<Callout type="warning">
**This page was rewritten for v0.5.0, and most of what it used to describe never existed.**

Before v0.5.0, `.evnx.toml` was documented here, defined in the CLI's source, and **read by
no command** — the only key with any effect was `[cloud] vault`, written by
`evnx cloud link`. The old version of this page listed `[project]`, `[output]`, `[convert]`,
`[doctor]` and `[[scan.custom_patterns]]`, along with keys like `scan.entropy_threshold` and
`validate.required`. None of them were ever read.

The sections below are the whole schema. If you copied a config from the old page, evnx will
now tell you which keys it does not recognise rather than pretending to honour them.
</Callout>

## What belongs in it

A setting belongs in `.evnx.toml` if it describes **the project**. It does not belong there
if it describes **this particular run**.

| Belongs in the file | Stays on the command line |
|---|---|
| `[scan] severity` — this repo's reporting floor | `--exit-zero` — how *this* CI step should behave |
| `[validate] strict` — the standard this repo holds itself to | `--fix` — change the files *now* |
| `[defaults] env_name` — which environment this project means | `--format json` — what *this* invocation should emit |

That rule is what keeps the schema decidable as commands are added, rather than a matter of
taste each time.

## Where evnx looks for it

Walking **up** from the working directory, stopping once it has examined a directory
containing `.git`.

```
my-repo/
├── .git/
├── .evnx.toml          ← found from anywhere in the repo
└── packages/
    └── api/
        └── .env        ← `evnx validate` here uses the root config
```

Two consequences worth knowing:

**A config above your repository is never used.** Walking further would let a file in a
parent directory — or in `$HOME` — silently apply to every project on the machine, and
`scan.exclude` is exactly the setting you would least want to leak that way.

**The first file found wins; configs do not merge.** A `.evnx.toml` in `packages/api/`
replaces the root one for commands run there rather than layering on top of it.

<Callout type="info">
The filename is `.evnx.toml` exactly. Bare `evnx.toml` is not accepted — two spellings would
need a rule about which one wins, for no gain.
</Callout>

## How config combines with flags

**Precedence is flag > config > built-in default**, with three different rules depending on
what kind of setting it is.

| Kind | Rule | Example |
|---|---|---|
| Values | The flag wins outright | `--severity low` overrides `[scan] severity = "high"` |
| Booleans | Either one saying `true` wins | `--strict` turns strict on even if config says `false` |
| Lists | The two are **combined** | `--exclude dist` scans with `dist` *and* the project's excludes |

Booleans can be tightened by a flag but never loosened. There is no `--no-strict`, so "off"
and "unspecified" arrive identically, and evnx resolves that ambiguity toward the stricter
reading — these booleans are all guards.

Lists combine because `[scan] exclude` is the project's standing exclusions and `--exclude`
is this run's. A flag silently discarding the project's list would be a surprising way to
widen a scan.

<Callout type="warning">
**If you are on v0.4.x, `.evnx.toml` does nothing.** The loader existed but nothing called
it, so a project with `[validate] strict = true` validated non-strictly and said nothing.
Upgrade to 0.5.0 before relying on any of this.
</Callout>

## Every section

All sections and all keys are optional. Omit anything you do not need.

```toml
# .evnx.toml

# ─── Cross-command defaults ──────────────────────────────────────────────────
[defaults]
env_name = "production"        # which .env.<name> commands operate on
example  = ".env.template"     # the template path, if not .env.example

# ─── evnx scan ───────────────────────────────────────────────────────────────
[scan]
severity            = "high"        # "high" | "medium" | "low"
exclude             = ["fixtures"]  # paths this project never scans
ignore_placeholders = true          # skip values that look like filler

# Secret formats this project recognises beyond the built-in ones.
# Repeat the block for each rule.
[[scan.patterns]]
name       = "Acme API key"
regex      = "ACME-[A-Z0-9]{32}"
confidence = "high"                 # optional; "high" | "medium" | "low"
url        = "https://acme.example/settings/keys"   # optional

# ─── evnx validate ───────────────────────────────────────────────────────────
[validate]
strict           = true
validate_formats = true
ignore           = ["boolean_trap"] # issue types to suppress

# ─── evnx sync ───────────────────────────────────────────────────────────────
[sync]
naming_policy = "warn"         # "warn" | "error" | "ignore"

# ─── evnx diff ───────────────────────────────────────────────────────────────
[diff]
ignore_keys = ["BUILD_ID"]     # keys that always differ here

# ─── evnx backup ─────────────────────────────────────────────────────────────
[backup]
keep = 3                       # previous backups to retain

# ─── evnx cloud ──────────────────────────────────────────────────────────────
[cloud]
vault = "my-app/production"    # written by `evnx cloud link` — see below

# ─── The variable contract ───────────────────────────────────────────────────
[vars]
PORT         = { format = "port", description = "HTTP listen port" }
STRIPE_KEY   = { secret = true, environments = ["production"] }
DEBUG_BANNER = { required = false }
```

### `[defaults]`

| Key | Type | Default | Effect |
|---|---|---|---|
| `env_name` | string | — | Resolves to `.env.<name>` for every command that takes `--env`. The file must exist; a name that resolves to nothing is an error, not a quiet fall back to `.env` |
| `example` | string | `.env.example` | The template `validate`, `sync` and `diff` compare against |

`env_name` is the one to reach for in a project whose real file is `.env.production`. It is
overridden by `--env-name`, and by an explicit `--env` path.

### `[scan]`

| Key | Type | Default | Effect |
|---|---|---|---|
| `severity` | `"high"` \| `"medium"` \| `"low"` | `"low"` | Lowest confidence worth reporting. `"high"` reports only detections matching a known provider format |
| `exclude` | list of strings | `[]` | Paths this project never scans |
| `ignore_placeholders` | bool | `false` | Skip values that look like filler |
| `patterns` | list of tables | `[]` | **v0.5.0+** — secret formats this project recognises beyond the built-in ones. See below |

<Callout type="info">
**`exclude` entries without `*` are substrings; entries with `*` are globs.**

A pattern with no `*` matches anywhere in the path, so `"fixtures"` excludes
`./fixtures/.env` and `./test/fixtures/.env` alike.

A pattern containing `*` is tried against the path as walked, the path relative to the scan
root, and the file name — so `"fixtures/**"`, `"./fixtures/**"`, `"*fixtures*"` and
`"*.log"` all work.

⚠️ Before v0.5.0 a glob was matched only against the whole path *including* its leading
`./`, so `"fixtures/**"` matched nothing and said nothing about it. Patterns written around
that limitation still behave identically.
</Callout>

#### `[[scan.patterns]]`

An **array of tables** — repeat the `[[scan.patterns]]` header once per rule.

| Key | Type | Default | Effect |
|---|---|---|---|
| `name` | string | *required* | What the finding is called in every output format. Becomes the SARIF rule id: `secret/acme-api-key` |
| `regex` | string | *required* | The expression. Anchor it yourself if you want it anchored |
| `confidence` | `"high"` \| `"medium"` \| `"low"` | `"high"` | Feeds `severity`, the counts and the exit code together |
| `url` | string | none | Where to go and revoke a match |

```toml
[[scan.patterns]]
name = "Acme API key"
regex = "ACME-[A-Z0-9]{32}"
url = "https://acme.example/settings/keys"

[[scan.patterns]]
name = "Ring handle"
regex = "RING-[0-9]{4}"
confidence = "medium"
```

These combine with `--pattern` rather than being replaced by it, the same way `exclude`
does. The default confidence is `high` on the grounds that you wrote the rule deliberately.

<Callout type="warning">
⚠️ **`name` and `regex` are required, and a missing one fails the whole file** — every
command, not just `scan`, because the config is parsed before any command runs. That is
louder than the usual treatment of a mistake here: an *unrecognised* key such as
`secretGroup` only warns.

An expression that does not **compile** behaves differently again — it fails `evnx scan`
alone, with exit `2`, and leaves other commands working. Full behaviour in
[evnx scan](/guides/commands/scan#teaching-it-your-own-formats).
</Callout>

### `[validate]`

| Key | Type | Default | Effect |
|---|---|---|---|
| `strict` | bool | `false` | Also report variables present in `.env` but absent from the example file |
| `validate_formats` | bool | `false` | Check URL, port and email values parse |
| `ignore` | list of strings | `[]` | Issue types to suppress |

Valid `ignore` entries: `missing_variable`, `extra_variable`, `placeholder_value`,
`boolean_trap`, `weak_secret`, `localhost_in_docker`, `invalid_url`, `invalid_port`,
`invalid_email`.

### `[sync]`

| Key | Type | Default | Effect |
|---|---|---|---|
| `naming_policy` | `"warn"` \| `"error"` \| `"ignore"` | `"warn"` | How `evnx sync` treats variable names outside `SCREAMING_SNAKE_CASE` |

### `[diff]`

| Key | Type | Default | Effect |
|---|---|---|---|
| `ignore_keys` | list of strings | `[]` | Keys not worth reporting — build IDs, timestamps, anything expected to differ |

### `[backup]`

| Key | Type | Default | Effect |
|---|---|---|---|
| `keep` | integer | `3` | Previous backups retained alongside the new one. Files beyond the limit are warned about, never deleted. `0` disables rotation |

### `[cloud]`

| Key | Type | Effect |
|---|---|---|
| `vault` | string | The vault this directory is bound to, as `name/environment` |

<Callout type="tip">
You do not write this one by hand. `evnx cloud link` writes it for you, preserving your
comments, key order, and any keys it does not recognise.
</Callout>

### `[vars]`

**v0.5.0+.** The project's variable contract — what each variable is, rather than how a
command behaves. Read by `validate`, `scan` and `sync`.

| Key | Type | Default | Effect |
|---|---|---|---|
| `required` | bool | `true` | Unstated means required. `false` marks a variable that may be absent |
| `secret` | bool | *unstated* | `true` reports a credential the heuristics cannot name; `false` retracts a guess made from the variable's name |
| `format` | string | none | `url`, `int`, `port`, `bool`, `email`, or a regular expression |
| `description` | string | none | Written into `.env.example` by `evnx sync` |
| `environments` | list of strings | all | Which environments the variable is required in |

```toml
[vars]
PORT = { format = "port", description = "HTTP listen port" }

[vars.STRIPE_KEY]
secret = true
environments = ["production"]
```

`evnx spec init` writes this section for you by inferring it from the files you already
have. Full behaviour, including what `secret = false` can and cannot retract:
**[evnx spec](/guides/commands/spec)**.

<Callout type="tip">
Section order does not matter. `[vars]` reads the same before or after
`[[scan.patterns]]` — verified both ways.

What *does* matter is that a plain key written **after** a `[[scan.patterns]]` block lands
inside that rule rather than in `[scan]`:

```toml
[scan]
severity = "high"

[[scan.patterns]]
name = "Acme API key"
regex = "ACME-[A-Z0-9]{32}"

exclude = ["fixtures"]     # ← belongs to the rule above, not to [scan]
```

That is ordinary TOML, not an evnx quirk — a header ends the table above it. evnx catches
it rather than silently ignoring it:

```
! /home/you/my-repo/.evnx.toml: unknown key `scan.patterns[0].exclude` (ignored)
```

Keep every `[[scan.patterns]]` block at the end of its section and the question does not
come up.
</Callout>

## evnx tells you when a config is in force

A run that loads a config says so, on **stderr**:

```bash
$ evnx scan .
  config    .evnx.toml (scan.severity=high, scan.exclude=1 patterns)
```

Run from a subdirectory, the path shows where the policy came from:

```bash
$ cd packages/api && evnx validate
  config    ../../.evnx.toml (scan.severity=high)
```

**This is not decoration.** `[scan] severity` and `[scan] exclude` can *weaken* what the
scanner reports, and the file is committed — so one commit could otherwise narrow scanning
for everyone who clones the repository, with nothing on the command line to show it.

Configurability is not the problem; silence is. A team genuinely needs to exclude its
fixtures. So the file is allowed to change the default and obliged to say so. Only the
settings that loosen a security default are listed in the parentheses; a config that sets
`[defaults] env_name` and nothing else announces itself plainly.

<Callout type="info">
The banner and all warnings go to stderr, never stdout, so
`evnx convert --to json > out.json` stays machine-readable. `--quiet` suppresses both.
</Callout>

## Unknown keys warn; they never fail

```bash
$ evnx validate
  config    .evnx.toml
! /home/you/my-repo/.evnx.toml: unknown key `scan.entropy_threshold` (ignored)
```

The file is committed and teams run mixed versions, so a config written for a later evnx
must keep working on an earlier one. That means unknown keys cannot be fatal — but a typo
must not be silent either, so the warning names the key and gives the full path to the file
to edit.

The schema is **additive only**: keys are added, never repurposed or removed.

A file that is not valid TOML *is* an error. Quietly ignoring a config someone wrote on
purpose would mean running with a policy they believe is in force.

## Worked examples

### A project whose real file is `.env.production`

```toml
[defaults]
env_name = "production"
```

`evnx validate`, `evnx diff`, `evnx convert` and `evnx backup` now all operate on
`.env.production` with no flags. `evnx validate --env .env` still reads `.env` — an explicit
flag always wins.

### A blocking CI gate

```toml
[scan]
severity = "high"
exclude  = ["fixtures", "testdata"]

[validate]
strict           = true
validate_formats = true
```

Then the CI step is just:

```bash
evnx scan .
evnx validate
```

Reporting only high-confidence detections is the usual choice for a gate that blocks a
merge. Both exclusions are substring patterns, so they cover those directories at any depth.

### A monorepo with one strict package

```toml
# my-repo/.evnx.toml — the baseline
[scan]
severity = "medium"
```

```toml
# my-repo/packages/payments/.evnx.toml — replaces the root config here
[scan]
severity = "high"

[validate]
strict = true
```

Remember that the nested file **replaces** the root one rather than merging with it, so
repeat anything you still want.

## What there is no config for

<Callout type="warning">
**There is no `EVNX_<SECTION>_<KEY>` environment-variable mechanism.** The variables evnx
reads are `EVNX_AUTO_FIX`, `EVNX_OUTPUT_JSON`, `EVNX_CONFIG_DIR`, `EVNX_PASSWORD`,
`EVNX_SERVER` and `EVNX_TOKEN` — nothing else. Pass flags directly instead:

```bash
evnx scan --severity high
evnx validate --strict
evnx scan --format sarif --exit-zero > results.sarif
```
</Callout>

There is also **no user-level config**. `~/.config/evnx/` holds credentials and cloud
settings, and those are deliberately separate: a policy file in your home directory would
apply to every project on the machine without being visible in any of them.

Entropy thresholds and per-command output defaults are **not configurable**. They were
described on this page for a long time and were never implemented — 4.8 for the generic
check and 4.5 for the gate on AWS secret keys are compiled in, and `--format` is a flag.

⚠️ Two things this paragraph used to list have since shipped, in v0.5.0: **custom secret
patterns** are `[[scan.patterns]]`, and **required-variable lists** are `[vars]`.
