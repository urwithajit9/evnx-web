# .env Syntax Reference

<Callout type="tip" title="Who this is for">
Anyone whose value contains a quote, a backslash, a newline, a `#` or a `$` — which is
most private keys, connection strings and JSON blobs. Everything on this page was
checked against the parser rather than transcribed from another tool's documentation,
because `.env` has no specification and implementations genuinely differ.
</Callout>

---

## The four forms

```bash
PLAIN=hello world
DOUBLE="hello world"
SINGLE='hello world'
BACKTICK=`hello world`
```

All four are accepted. They differ in **two** respects — whether backslash escapes are
resolved, and whether `$NAME` is expanded — and behave identically otherwise, including
multiline support.

| Form | Escapes resolved | Expands `$NAME` | Multiline |
|---|---|---|---|
| unquoted | ❌ literal | ✅ | — |
| `"double"` | ✅ **yes** | ✅ | ✅ |
| `'single'` | ❌ literal | ❌ **no** | ✅ |
| `` `backtick` `` | ❌ literal | ❌ **no** | ✅ |

**Single quotes are literal, fully.** That is the one rule worth remembering: whatever
is between them is the value. It is the answer to a backslash, a `$`, or both.

### Whitespace and `export`

```bash
SPACED   =   padded      # → "padded"; whitespace round = and at the ends is trimmed
export EXPORTED=value    # → the export prefix is accepted and dropped
EMPTY=                   # → "" (an empty value, not an error)
```

## Escapes resolve in double quotes, and only there

| Written | In `"…"` | In `'…'`, `` `…` `` or unquoted |
|---|---|---|
| `\t` | a tab | a backslash and a `t` |
| `\$` | `$`, never expanded | a backslash and a `$` |
| `\n` | a newline | a backslash and an `n` |
| `\"` | `"` | unchanged |
| `\\` | `\` | unchanged |

```bash
TABBED="col1\tcol2"      # → col1<tab>col2
LITERAL='col1\tcol2'     # → col1\tcol2
QUOTED="say \"hi\""      # → say "hi"
WINPATH='C:\Users\ajit'  # → C:\Users\ajit — single quotes are the escape hatch
```

<Callout type="warning" title="A Windows path or a regex belongs in single quotes">
`"C:\Users\ajit"` resolves `\U` and `\a` as escapes. Single quotes take the value
exactly as written, which is what you want for paths, regular expressions and anything
else where a backslash is data.
</Callout>

## Multiline values

Any of the three quote characters can span lines. The value ends at the matching
closing quote.

```bash
PRIVATE_KEY="-----BEGIN PRIVATE KEY-----
MIIEvQIBADANBgkqhkiG9w0BAQEFAASCBKcwggSjAgEAAoIBAQ...
-----END PRIVATE KEY-----"
```

<Callout type="warning" title="Escapes changed in v0.6.0 — and this affects multiline values">
Before v0.6.0, a **multiline** double-quoted value did not resolve escapes even though
a single-line one did. `\t` meant a tab on one line and a literal backslash-t across
two. That inconsistency is fixed: escapes now mean the same thing in a double-quoted
value regardless of how many lines it spans.

**PEM keys, certificates and base64 are unaffected** — they contain no backslashes, so
they are byte-identical before and after. What changes is a multiline value containing
`\n`, `\t` or `\"`: a JSON blob, for instance.

If a multiline value must be taken literally, use single quotes.
</Callout>

## Variable expansion

A value can reference another variable in the same file:

```bash
HOST=db.example.com
PORT=5432
DATABASE_URL=postgresql://user:pass@${HOST}:${PORT}/app
```

`$NAME` and `${NAME}` both work.

### Where it does and does not happen

**Single quotes and backticks do not expand.** They are literal in every respect —
escapes and variables alike:

```bash
B=world
A='hello $B'     # → hello $B
A=`hello $B`     # → hello $B
A="hello $B"     # → hello world
A=hello $B       # → hello world
```

<Callout type="warning" title="This changed in v0.7.0">
Before v0.7.0, expansion ran in **every** quoting form, so `'hello $B'` yielded
`hello world`. Single quotes were literal for backslashes and not for dollars, which
is not a rule anyone can hold in their head.

If a file of yours relied on expansion inside single quotes, it changes meaning
silently — the value stops being substituted, and nothing errors, because both forms
parse. Worth one `evnx validate` and a glance after upgrading.
</Callout>

**`\$` is a literal `$` in a double-quoted value**, so expansion can be kept for the
rest of the string:

```bash
B=world
A="\$B costs $B"    # → $B costs world
A="path\\$B"        # → path\world   (a real backslash, then the expansion)
```

A `$` that is not followed by an identifier is left alone in any form:

```bash
PRICE="costs $"      # → costs $
PRICE="costs $5"     # → costs $5
```

**An undefined reference still behaves differently depending on braces:**

```bash
A=hello $NOPE        # → hello $NOPE   (left as written)
A=hello ${NOPE}      # → Error: Undefined variable: ${NOPE} is not defined
```

<Callout type="tip" title="A secret containing a dollar sign — single-quote it">
This is the reliable answer, and the reason single quotes stopped expanding.

```bash
TOKEN='pa${SOMETHING}ss'      # → exactly that, no error
API_KEY='prefix$DB_PASS'      # → exactly that, even if DB_PASS is a key here
```

Before v0.7.0 neither was possible: the first made the **whole file fail to parse**,
and the second was **silently replaced** with the value of `DB_PASS` — substituting one
of your secrets into another, with no error and no way to prevent it.
</Callout>

### Expansion sees the file, not your shell

```bash
A=home is ${HOME}    # → Error: ${HOME} is not defined
```

Even though `HOME` is set in every shell. Expansion resolves **only** against the
`.env` file itself, which keeps the file self-contained — the same file produces the
same values on every machine.

Order does not matter. A variable may reference one defined further down.

## Comments

```bash
# A full-line comment.

KEY=value            # stripped — the value is "value"
KEY="value # here"   # kept — the value is "value # here"
```

An unquoted `#` starts a comment. Inside any quoted form it is part of the value.

## What does not work

### Triple-quoted heredocs

```bash
CONFIG="""
line one
line two
"""
```

```
Error: Invalid format at line 2: missing '=' separator
```

Not supported, and not planned — an ordinary double-quoted multiline value covers the
same ground. Use:

```bash
CONFIG="line one
line two"
```

### A quote that never closes

```bash
API_KEY="never closes
NEXT_KEY=value
```

```
Error: Unterminated quoted string at line 1
```

Worth knowing because the failure is reported at the line where the value **opened**,
not where the file ran out. If a file fails to parse near the end, look for an
unbalanced quote earlier.

<Callout type="info" title="`evnx doctor` reports this too, as of v0.6.0">
Before v0.6.0 `doctor` and the parser disagreed: `doctor` flagged the continuation
lines of a valid multiline value as invalid syntax, and could not represent an
unterminated value at all — so it called such a file clean while `validate` failed on
it. Both now use the same parser.
</Callout>

## Which form to use

| Your value contains | Use |
|---|---|
| nothing special | anything; unquoted is fine |
| spaces | any quoted form, or unquoted — spaces are preserved either way |
| a `#` | any quoted form |
| backslashes — a Windows path, a regex | `'single'` |
| a tab or newline you want resolved from `\t` / `\n` | `"double"` |
| real newlines — a PEM key, a certificate | any quoted form; `"double"` is conventional |
| a `$` followed by a word | `'single'` — or `\$` to keep expansion elsewhere in the value |
