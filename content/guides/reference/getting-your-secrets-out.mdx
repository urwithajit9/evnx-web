## ⚠️ This writes your secrets to disk in plain text

<Callout type="danger" title="Read this before the first example, not after">
`evnx cloud export` is the one evnx command whose **purpose** is to put
decrypted secrets on a filesystem. Everything else in evnx works to avoid
that: [`evnx cloud pull`](/guides/commands/cloud) writes a single file and asks
before overwriting, and `evnx cloud run` writes none at all.

Once those files exist they are ordinary files. Your backup software will copy
them. Your editor may index them. `git add .` will stage them. The encryption
that protected them stops at the moment this command succeeds.
</Callout>

That is not a flaw to be fixed. It is what an escape hatch is.

## Why it exists

The question is *what happens when we want to leave?*

It is the objection that blocks a **team** decision rather than an individual
one. One person can try a tool and stop using it. A team putting its production
credentials somewhere needs to know, before it starts, that it can get them back
out — into a format that is not ours, without our cooperation, and without
writing a script against an API.

An escape hatch nobody can demonstrate is not believed. So this command exists
to be run once, confirmed, and then mostly not used.

## The basics

Export the latest version of a vault:

```bash
evnx cloud export --vault api/production --output ~/evnx-export
```

Every version:

```bash
evnx cloud export --vault api/production --all-versions --output ~/evnx-export
```

### What lands on disk

```text
~/evnx-export/
  api-production/
    v1.env
    v2.env
    v3.env          ← the latest
    manifest.json
```

A subdirectory per vault, so exporting several into one place does not mix them
up. Files named by version number. And a manifest, because the first question
anyone asks of a directory of numbered files is *which one was current?*

<Callout type="info" title="Point `--output` outside your working tree">
The default is `./evnx-export`, which is convenient and wrong often enough to
be worth saying: an export inside a repository is one `git add .` away from
being committed. A path under your home directory, or a mounted volume you
control, is the better habit.
</Callout>

## You get the file back, not a reconstruction of it

With no `--to`, the exported files are the **exact bytes you pushed**.

This is a property of how evnx stores things rather than an effort export makes.
`evnx cloud push` encrypts the file verbatim — it does not parse it and
re-serialise it — so comments, blank lines, key order and quoting style all
survive the round trip. A multiline value written across five lines comes back
across the same five lines.

```bash
# These two files are byte-for-byte identical.
sha256sum .env
evnx cloud export --vault api/production --output /tmp/out
sha256sum /tmp/out/api-production/v3.env
```

<Callout type="tip" title="Which is why there is no `--to env`">
There is nothing to convert to. The `.env` you get is the `.env` you had.
</Callout>

## Converting instead

`--to` runs the export through the same formats [`evnx
convert`](/guides/commands/convert) offers — all fourteen of them:

```bash
evnx cloud export --vault api/production --to json --output ~/evnx-export
```

```text
json · yaml · shell · aws-secrets · gcp-secrets · azure-keyvault
github-actions · docker-compose · kubernetes · terraform
doppler · heroku · vercel · railway
```

The file extension follows the format, so `--to json` writes `v3.json` and
`--to terraform` writes `v3.tfvars`.

<Callout type="warning" title="A conversion keeps keys and values, and nothing else">
Comments, ordering and quoting do not survive a format change — there is
nowhere in JSON to put a `.env` comment. If the point of the export is to
*leave with your files*, take the default. If the point is to *load them
somewhere else*, take `--to`.
</Callout>

It is the same code path `evnx convert` uses, not a parallel one, so a value
that converts a particular way there converts the same way here. That is
enforced by a test rather than by intention.

## What it refuses, and when

Two refusals, both deliberately **early**:

<Callout type="success" title="A refusal never arrives after the work">
An unusable `--to`, and an output directory that already holds files, are both
refused **before** the master password is asked for and before a single blob is
downloaded.

A command that asks for your password, spends two minutes decrypting, and then
refuses teaches you to pass `--force` by reflex. This one costs nothing to get
wrong.
</Callout>

```bash
$ evnx cloud export --vault api/production --output ~/evnx-export
Error: /home/you/evnx-export/api-production already has files in it.
  Pass --force to overwrite them, or -o to export somewhere else.
  Refusing before anything was decrypted.
```

`--force` overwrites. Think once before using it: two exports of the same vault
taken at different times look identical on disk, and the older one may be the
one someone still needs.

## The manifest

`manifest.json` holds metadata only — no values.

```json
{
  "exported_at": "2026-10-01T23:23:17+09:00",
  "exported_by": "evnx 0.8.0",
  "vault": { "id": "…", "name": "api", "environment": "production" },
  "format": "env",
  "latest_version": 3,
  "versions_exported": 3,
  "versions": [
    {
      "version": 3,
      "file": "v3.env",
      "is_latest": true,
      "pushed_at": "2026-10-01T14:23:08Z",
      "key_count": 6,
      "key_names": ["DATABASE_URL", "API_KEY", "…"]
    }
  ]
}
```

`latest_version` is there for the question above. Every entry also carries
`is_latest`, so the answer survives someone reading one record out of context.

## File permissions

On Linux and macOS the directory is created `0700` and every file inside `0600`
— yours only.

<Callout type="warning" title="That protects them from other users on the machine, and nothing else">
It does not protect them from your backup tool, your cloud sync folder, your
editor's recent-files index, or a commit. Those are the realistic ways an
export leaks, and no file mode addresses any of them.
</Callout>

## ⚠️ An export is a photograph, not a mirror

<Callout type="danger" title="It does not stay in sync">
The moment you rotate a credential, the export is wrong — and it is wrong in
the most dangerous direction, because it still *looks* like a valid set of
secrets. Someone finding it in six months has no way to tell.

Delete an export when you are done with it. If you are keeping one as a
disaster-recovery copy, put a date on the directory and re-take it on a
schedule, the same way you would a database dump.
</Callout>

## This is not the command for CI

<Callout type="danger" title="Use `evnx cloud run` instead">
Writing secrets to a file in a pipeline is the thing evnx exists to avoid.
[`evnx cloud run`](/guides/commands/cloud) decrypts into a subprocess's
environment and never touches disk:

```bash
evnx cloud run --vault api/production -- ./deploy.sh
```

If you find yourself reaching for `cloud export` in a workflow file, that is
the command you actually wanted.
</Callout>

## Not the same as `evnx auth download-data`

These two commands sound alike and contain opposite things.

| | `evnx auth download-data` | `evnx cloud export` |
|---|---|---|
| Contains | account metadata | **your secrets, decrypted** |
| Secrets | none, and cannot have any | all of them |
| Comes from | the server's records | your vaults, decrypted here |
| Needs your master password | no | **yes** |
| Safe to email yourself | not ideal, but it holds no values | **no** |

They were deliberately given different names for this reason. See [exporting
your data](/guides/reference/exporting-your-data) for the metadata one.

## Shared vaults work the same way

A vault shared with you exports exactly like one you created. The wrapped key
arrives through the hybrid X25519 + ML-KEM-768 path instead of the symmetric
one, which is a difference in the cryptography and not in the command.

You need your own master password either way — the key is wrapped to *you*,
and the server cannot open it on your behalf.
