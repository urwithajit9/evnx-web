`evnx scan` ships about sixty rules in the binary, each written against the provider's
own documentation, each with fixtures. That core is small on purpose. For wider coverage
there is a catalogue, [evnx-rules](https://github.com/urwithajit9/evnx-rules), with packs
you add on request:

```bash
evnx scan rules add betterleaks
```

The second pack is a conversion of [Betterleaks](https://github.com/betterleaks/betterleaks),
the actively maintained fork of gitleaks by the same author. It's MIT-licensed, and its
rule file was updated the day before we pinned it. This post is about the conversion: Go
to Rust, CEL to plain fields, and what was deliberately left behind.

## Same format, a few new fields

Betterleaks still writes gitleaks' TOML, so evnx's existing gitleaks importer did most of
the work. A Betterleaks rule looks like this:

```toml
[[rules]]
id = "1password-service-account-token"
regex = '''ops_eyJ[a-zA-Z0-9+/]{250,}={0,3}'''
confidence = "high"
keywords = ["ops_eyj"]
validate = '''
let r = http.get("https://events.1password.com/api/v2/auth/introspect", …)
'''
filter = '''
entropy(finding["secret"]) <= 4.0
'''
```

The first conversion, with the gitleaks importer as it was, produced 469 rules. It looked
fine until we read the output: **not one rule had an entropy floor.** In gitleaks,
`entropy = 3.5` is a field. Betterleaks moved that check into `filter`, a CEL expression
that decides when to *drop* a finding. The importer ignored a field it didn't know, so
~400 rules would have reported every low-entropy placeholder upstream filters out.

## Reading just enough CEL

evnx has no CEL engine, and a scanner that evaluates arbitrary expressions from a
downloaded file isn't something we want. But the filters follow a pattern:

| Filter shape | Rules |
|---|---|
| `entropy(finding["secret"]) < N` alone | 159 |
| `entropy(finding["secret"]) <= N` alone | 136 |
| `entropy(…) < N \|\| tokenRatio(…) >= M` | 123 |
| other (`matchesAny` on paths or values, multi-line logic) | the rest |

So the importer (evnx 0.13.0, batch C13) reads only a **leading** entropy clause and
turns it into the rule's entropy floor: "drop if entropy < 4.0" means "report from 4.0
up". Anything after it can't be expressed, such as a `tokenRatio` heuristic or a path
match. That part is dropped, and the rule is **counted** in the pack's header, the same
way rules that lose a gitleaks allowlist are counted. Nothing is lost silently.

Three more fields carry over:

- **`confidence`** maps straight across: `low`, `medium` or `high`, and anything else
  becomes `medium`. In the converted pack, 370 rules are `high`.
- **`valueGroup`** is Betterleaks' name for gitleaks' `secretGroup`: which capture group
  is the secret.
- **`skipReport = true`** marks a rule that exists only as part of a *composite*, such as
  an Alibaba access key ID that only matters next to its secret. Reported alone, these
  are noise, so they're skipped and listed (44 of them).

## The result

```text
426 rules converted, 48 skipped.
384 rules have an entropy floor (none did before).
167 rules kept only the entropy floor of a filter, or were composites;
    the rest is not carried over, so they may report more than upstream.
```

Four of the skipped rules are Betterleaks' giant generic patterns (`generic-api-key`,
`generic-password`, …), whose compiled regex exceeds the size limit evnx scans with.
They're the noisiest rules in any scanner, and evnx has its own entropy fallback for that
job.

## What stayed behind on purpose: `validate`

238 Betterleaks rules can call the provider's API to check whether a key is live. That's
genuinely useful, and evnx doesn't do it, for one reason: **a scan never touches the
network.** That covers both the rules and the scan itself:

- Packs are downloaded only by `scan rules add`, pinned by sha256 in
  `.evnx/rules.lock`, and checked on every scan.
- A finding is never sent anywhere. Validation would mean sending your secret to a third
  party from a pre-commit hook, often without the person committing knowing it happened.

Live verification may come later as an explicit, opt-in flag (`--verify`, RM-73) with a
clear statement of what is sent where. It won't be on by default, and it won't arrive
inside a downloaded rule.

## gitleaks or Betterleaks?

Betterleaks is a superset: all but five gitleaks rules exist in it, plus 251 providers
gitleaks lacks (ClickUp, Figma, Gitea, ConfigCat, Cloudinary, …). The catalogue offers
both: `gitleaks` (221 rules, stable) and `betterleaks` (426, broad). **Add one or the
other.** With both installed, the same key is reported once per pack.

```bash
evnx scan rules add betterleaks
evnx scan rules list --category source-ci | head
```

## What's next for packs

Every imported rule should have fixtures: a positive and a near miss, as the core rules
do. Betterleaks' rules don't ship examples in the rule file, so for now `scan rules test`
only proves they compile. Measuring the pack's precision against a labelled corpus is
v0.14.0 work (RM-70). After that come Nosey Parker's archived rules, which do ship
examples.
