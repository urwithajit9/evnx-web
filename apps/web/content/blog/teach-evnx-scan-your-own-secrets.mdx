`evnx scan` knows 63 kinds of secret out of the box: AWS keys, GitHub tokens, Stripe keys,
OpenAI and Anthropic keys, and 50-odd more. Each built-in rule is a provider that **publishes
the shape of its tokens**, so evnx can recognise one without guessing.

Your company's internal API keys are not on that list, and never will be. Nobody outside your
team knows that `acme_live_` followed by 32 hex characters is a production credential. A key
like that still leaks the same way a Stripe key does: pasted into a config file, committed,
pushed.

Since v0.13.0, a team can teach `evnx scan` its own formats. This post walks through it with a
made-up company, Acme, from one rule in one repository up to a pack shared by many.

## Where a rule can live

| Scope | Where | Who gets it | Use it for |
|---|---|---|---|
| **Project** | `.evnx/rules/*.toml`, committed | Everyone who clones the repo, and CI, with no download | Your team's own token formats |
| **Personal** | `~/.config/evnx/rules/` | Only you, on every project | Formats only you deal with, such as a sandbox account |
| **One run** | `evnx scan --rules <file>` | That one scan | An incident: "did this leaked partner key end up anywhere?" |
| **Pack** | `evnx scan rules add <name, https URL or path>` | Every repo that adds it, pinned in `.evnx/rules.lock` | Formats several repositories share |

Every scope **adds** rules. None can switch off or weaken one of evnx's own (more on why below).

## Step 1: write the rule

```bash
evnx scan rules new acme-api-key
```

```text
✓ wrote /tmp/teach/.evnx/rules/acme-api-key.toml: set its regex and fixtures, then `evnx scan rules test`
```

The file is a template with every field explained:

```toml
# A rule file for `evnx scan` (C6). Its rules are added to evnx's own;
# an id evnx or another file already uses is refused, never replaced.
# Same fields as evnx's own rules; check it with `evnx scan rules test`.
version = 1

[[rules]]
id = "acme-api-key"
name = "Acme Api Key"
# The token's documented shape. Rust regex syntax, matched per line.
regex = 'REPLACE-ME-[A-Z0-9]{32}'
# How sure a match is (high, medium, low), and how bad if real
# (critical, high, medium, low).
confidence = "high"
severity = "high"
# url = "https://… where to revoke one"

# Values this rule must report, and close ones it must not.
positive = []
near_miss = []
```

Filled in for Acme's keys:

```toml
# Acme's internal API keys: "acme_live_" or "acme_test_", then 32 lowercase hex.
# Owner: platform team. Revoke at https://admin.acme.example/keys
version = 1

[[rules]]
id = "acme-api-key"
name = "Acme API Key"
provider = "Acme"
category = "generic"
regex = '\bacme_(?:live|test)_[0-9a-f]{32}\b'
confidence = "high"
severity = "critical"
url = "https://admin.acme.example/keys"

positive = ["acme_live_a4c123b1612dd272d1371c17149d4395"]
near_miss = ["acme_live_1234", "acme_prod_a4c123b1612dd272d1371c17149d4395"]
```

What each field is for:

- **`id`** is how everything else refers to the rule: allow markers, baselines, `[scan] disable`,
  SARIF. Pick it once; renaming it later makes it a new rule to every tool that tracked it.
- **`regex`** uses Rust's `regex` crate, which runs in linear time, so no rule can make a scan
  hang. Anchor it with `\b` and give exact lengths. A rule that matches ordinary text is noise
  in every repository it runs in.
- **`confidence`** is how sure a match is that it really is this kind of token. **`severity`** is
  how bad a leak would be. They are separate on purpose: a public browser key can be a certain
  match and still low risk. `evnx scan --severity high` filters on the second, `--confidence high`
  on the first.
- **`provider`** and **`category`** group the rule in `evnx scan rules list`. Both are
  optional, but `rules test` warns when they are missing. `category` must be one of the
  fixed list (`cloud`, `source-ci`, `ai`, `payments`, `databases-backends`, `auth`,
  `messaging-email`, `observability`, `infra-secrets`, `saas`, `keys-certificates`,
  `generic`).
- **`url`** is printed beside every finding, so whoever finds the leak knows where to revoke it.
- **`positive`** and **`near_miss`** are the rule's own tests. Use invented values: this file is
  committed, and a real key in it is a leak of its own.

## Step 2: test it

```bash
evnx scan rules test
```

```text
✓ 1 rule(s), 3 fixture value(s): all pass
```

The near misses are what earn the test its keep. If the regex were loosened to accept any
`acme_<word>_…`, the `acme_prod_` example would catch it. Here is the same command with a near
miss the rule wrongly matches:

```text
✗ acme-api-key: reports near miss "acme_prod_a4c123b1612dd272d1371c17149d4395"

  1 failure(s)
```

It exits 1, so it can run in CI on every change to `.evnx/rules/`.

## Step 3: watch it work

```bash
evnx scan rules list
```

```text
  generic
    acme-api-key                   Acme          critical  high    .evnx/rules/acme-api-key.toml

  64 rules
```

The rules are grouped by category (this is the end of the list). The last column says where
each rule comes from: `evnx` for the 63 built-in rules, a file path for yours. Then a key in source code:

```text
  evnx scan  Checking for exposed secrets

  scanning src/client.js

  ✗  Acme API Key                                critical
     src/client.js:1  acme…4395
     !  matches a live key format, not a placeholder
     →  revoke at https://admin.acme.example/keys

  1 finding  ·  1 critical
```

(The "Next steps" block that follows the summary is left out of this and the later outputs.)

The value is masked in the output. Commit `.evnx/rules/` and the rule now runs for everyone,
in CI, and in the commit hook, with nothing to install.

## Rules can add, never subtract

Suppose someone wants a quieter scan and writes a rule file reusing the id of a built-in rule:

```toml
version = 1

[[rules]]
id = "aws-access-key"
name = "Quieter AWS"
regex = 'NEVER'
confidence = "low"
severity = "low"
```

```text
Error: rule id 'aws-access-key' is in both evnx's own rules and .evnx/rules/override.toml: ids must be unique, and a rule file adds to evnx's rules, it cannot replace one

No verdict: evnx did not scan anything. This is not a clean result.
```

The scan does not run. This is deliberate: a rule file is easy to add in a large PR, and a scanner
that a rule file can weaken is a scanner a rule file can switch off. If a built-in rule really is
wrong for a project, `[scan] disable` in `.evnx.toml` does it, in one visible place a reviewer
will see.

## Personal rules and one-off runs

```bash
evnx scan rules new my-sandbox-token --personal
```

writes to `~/.config/evnx/rules/` instead, never committed. A scan says when personal rules are
in play, so a finding nobody else can reproduce is not a mystery:

```text
  + 1 personal rule(s) from /tmp/teach-home/.config/evnx/rules

  evnx scan  Checking for exposed secrets
```

For an incident, keep the rule out of the repo altogether:

```bash
evnx scan . --rules incident-2026-11.toml
```

```text
  ✗  Acme API Key                                critical
  ✗  Acme API Key                                critical
  ✗  Partner key from incident 2026-11           critical
```

(Two Acme findings: one in `src/client.js` and one in the rule file's own test value, which
is the next section's problem.)

## When a match is not a secret

Real repositories have test fixtures and documentation examples. Two ways to deal with them,
neither of which edits the rule:

**An allow marker**, on the line or the line above, names one rule and gives a reason:

```js
// evnx:allow acme-api-key - documented example key from the Acme SDK README
const example = "acme_test_…";
```

```text
  ✓  No new secrets

  1 file scanned
  ·  1 allowed inline — not counted; -v lists them
⋯ src/example.js:2  acme-api-key  allowed: documented example key from the Acme SDK README
```

The last line comes from `-v`. One trap: a scan of `.` also reads your rule files, and a
rule's `positive` values are, by definition, matches. The example above showed one. Put a
marker on the line above `positive` in the rule file (a `#` comment works in TOML), or
baseline it. The same goes for the fixtures in a pack.

**A baseline**, when you add a rule to a repository that already contains matches:

```bash
evnx scan --update-baseline
```

```text
✓ wrote /tmp/teach/.evnx/baseline.json with 1 finding(s); they are reported as known from now on
```

The baseline stores a fingerprint, the rule, the file and a date, **never the value**. Later
scans report those findings as "known" and only fail on new ones. A new key is still caught on
day one, and the backlog can be cleaned up and revoked at its own pace.

## Stop it at the commit

```bash
evnx scan hook install
```

```text
✓ /tmp/teach/.git/hooks/pre-commit runs `evnx scan --staged` before every commit
```

The hook uses the same rules, yours included. Staging a config file with an Acme key:

```text
  evnx scan  Checking what is staged for commit

  scanning src/new.cfg

  ✗  Acme API Key                                critical
     src/new.cfg:1  acme…6517
     !  matches a live key format, not a placeholder
     →  revoke at https://admin.acme.example/keys

  1 finding  ·  1 critical


Next steps:
  1. Unstage src/new.cfg: git restore --staged src/new.cfg (or git rm --cached src/new.cfg to stop tracking it)
  2. Move the values out of the file, into one git ignores such as .env, then stage it again
  3. If one was committed, pushed or shared before, revoke or rotate it
  Docs: https://docs.evnx.dev/cli/commands/scan
evnx scan: commit blocked, secrets are staged (see above).
  To commit anyway: git commit --no-verify. To turn the hook off: git config hooks.evnx-scan false
```

The commit did not happen. If evnx is not installed on a developer's machine, the hook **blocks**
rather than letting the commit through unchecked, and says how to install it.

## Many repositories: packs

Copying the same file into twenty repositories means twenty copies drifting apart. A **pack** is
the same rule file, added from one place and pinned:

```bash
evnx scan rules test packs/acme-internal.toml
evnx scan rules add packs/acme-internal.toml    # or an https:// URL
```

```text
✓ 2 rule(s), 4 fixture value(s): all pass
✓ added acme-internal: 2 rule(s) in .evnx/rules/acme-internal.toml, recorded in .evnx/rules.lock
· Commit .evnx/rules/ and .evnx/rules.lock so the team and CI use it too.
```

The lock file records where the pack came from and its sha256:

```toml
[[packs]]
name = "acme-internal"
kind = "path"
source = "packs/acme-internal.toml"
format = "evnx"
sha256 = "6335d8b12c2054650642692cf648ab5991e582aeeedd8d7e1437608361bf8125"
rules = 2
added = "2026-11-08"
```

and every scan checks it. Edit the pack in place, here by lowering a severity, and the scan
refuses to run on it:

```text
Error: .evnx/rules/acme-internal.toml changed since it was added; run `evnx scan rules update acme-internal` or remove it (`evnx scan rules remove acme-internal`)

No verdict: evnx did not scan anything. This is not a clean result.
```

It exits 2.

To take a new version, `evnx scan rules update` downloads it again, shows how the rule count
changed, and asks before replacing it (`--yes` for CI). The change then arrives as a reviewable
diff to `.evnx/rules/` and `rules.lock`, not as something a scanner fetched behind your back.
A scan itself **never touches the network**: only `rules add` and `rules update` download, and
only when you run them.

### By name, from a catalogue

Packs can also be added by name from a catalogue: an `index.toml` listing each pack's path and
sha256. evnx's public catalogue is [evnx-rules](https://github.com/urwithajit9/evnx-rules), whose
packs are gitleaks' rule set converted to evnx's format (`gitleaks`, 221 rules, MIT) and
Betterleaks' (`betterleaks`, 426 rules, MIT). Betterleaks' set is a superset of gitleaks',
so add one or the other, not both. The catalogue is public:

```bash
evnx scan rules add gitleaks
```

```text
✓ added gitleaks: 221 rule(s) in .evnx/rules/gitleaks.toml, recorded in .evnx/rules.lock
· Commit .evnx/rules/ and .evnx/rules.lock so the team and CI use it too.
```

The same command with `betterleaks` adds 426 rules. evnx refuses a download whose sha256 is not the one the catalogue lists, and records it in the
lock file like any other pack.

A company can run its own catalogue with the same layout (an `index.toml` and `packs/`) and point
evnx at it with `EVNX_RULES_CATALOGUE=https://rules.acme.example/index.toml`. Then
`evnx scan rules add acme-internal` works by name across every repository.

### Importing gitleaks rules you already have

If your team already maintains a gitleaks config, convert it rather than rewriting it. A pack is
named after its file, so copy `.gitleaks.toml` to a plain, distinct name first. `gitleaks.toml`
would clash with the catalogue's `gitleaks` pack (evnx refuses: "the pack 'gitleaks' is already added"):

```bash
cp .gitleaks.toml acme-gitleaks.toml
evnx scan rules add acme-gitleaks.toml --format gitleaks
```

```text
  1 gitleaks rule(s) not converted:
    p12-files: no regex: it matches file paths only
✓ added acme-gitleaks: 1 rule(s) in .evnx/rules/acme-gitleaks.toml, recorded in .evnx/rules.lock
· Commit .evnx/rules/ and .evnx/rules.lock so the team and CI use it too.
```

The converted copy is what gets stored and locked; evnx never reads gitleaks files at scan time.
Converted ids get the pack name as a prefix (`acme-gitleaks-acme-deploy-key`), and each rule comes in at medium severity and confidence.
Raise the ones that matter in your source file and convert again. A rule that matches only file
paths, which evnx's rules cannot express, is skipped and named, as above.

## Writing rules that hold up

- **Prefer a fixed prefix**: `acme_live_`, not "40 random characters". A prefix is what makes a
  match certain rather than a guess.
- **Give exact lengths and anchor with `\b`**, so a longer string that merely contains a key-like
  run does not match.
- **Write at least one near miss** for each way the rule could be too loose: wrong prefix, too
  short, wrong character set.
- **Set severity by what the key unlocks**: money, cloud accounts or signing keys are critical;
  account tokens high; anything designed to be public low.
- **Put an owner and a revoke URL in the file.** The person who finds the leak at 2 a.m. is
  rarely the person who wrote the rule.
- **Keep fixtures fake.** A rule file is committed and read by people and tools.
- Rule files are capped at 2 MB and 5,000 rules, and a file over the cap is refused by name.

## When a rule should be built in

If the format belongs to a public provider, not just your company, it may belong in evnx
itself. The bar is that **the provider documents a fixed prefix, or a fixed length and character
set** ordinary values do not share, and every built-in rule ships with fixtures and is checked
against real repositories for false positives. That is how the list went from 13 rules in
v0.12.0 to 63 in v0.13.0.
Formats without such documentation belong in a pack, where a team can choose to accept the
noise. Open an issue or a PR on [evnx](https://github.com/urwithajit9/evnx), or a pack on
[evnx-rules](https://github.com/urwithajit9/evnx-rules).

## The short version

```bash
evnx scan rules new acme-api-key     # 1. write it: .evnx/rules/acme-api-key.toml
evnx scan rules test                 # 2. it reports its positives, not its near misses
evnx scan rules list                 # 3. it is loaded, next to evnx's 63
git add .evnx/ && git commit         # 4. the team and CI have it, no download
evnx scan hook install               # 5. and it blocks a leak before the commit
```
