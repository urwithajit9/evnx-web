# Getting Started with @evnx/cli: Modern Environment Management for Next.js

<Callout type="info" title="Updated for v0.10.18">
Rewritten from real runs of evnx 0.10.18. The earlier version showed output from 0.2.1
and a Blueprint walkthrough that a Next.js project no longer reaches: in a folder with a
`package.json`, `evnx init` first asks whether to use what it detected, and answering no
writes nothing. This version names the blueprint instead.
</Callout>

Managing environment variables doesn't have to be a source of friction. With **@evnx/cli**
you get one tool for `.env` files across your Next.js projects: a template your team
commits, a local `.env` that stays out of git, and checks that catch placeholders and
leaked keys before they ship.

In this guide, we'll walk through:
- Installing `@evnx/cli` with npm or npx
- Verifying your installation
- Generating a Next.js + Supabase setup with `evnx init`
- Checking it with `evnx validate` and wiring it into `package.json`

---

## 📦 Installation: npm Ecosystem

### Option 1: Global Install (Recommended)

```bash
npm install -g @evnx/cli
```

### Option 2: Use with `npx` (No Install)

```bash
npx @evnx/cli init --help
```

### Option 3: Local Project Dependency

```bash
npm install --save-dev @evnx/cli
```

The npm package downloads the prebuilt binary for your platform, so every command —
cloud sync included — is there.

## ✅ Verify Installation

```bash
evnx --version
```

```text
evnx 0.10.18
```

If the version is older than you expect, another copy is earlier on your `PATH`:
`type -a evnx` lists them. [Managing your evnx install](/guides/reference/managing-your-evnx-install)
explains how to keep exactly one.

### Get Help

`evnx --help` lists twenty commands. The ones this guide uses:

```text
  init         Interactive project setup — the template, .env and the .evnx.toml contract
  add          Add environment variables to existing .env files
  validate     Check .env against .env.example, find issues
  scan         Detect secrets that look real (AWS keys, tokens, etc.)
```

## 🚀 Three Ways to Start with `evnx init`

Run with no flags in an empty folder, `init` shows a menu: **Blank**, **Blueprint** (a
pre-configured stack) or **Architect** (pick a language, framework, services and
infrastructure). In a project that already has a `package.json` or a
`docker-compose.yml`, it first proposes what it detected. Every mode has a
non-interactive form, which is what this guide uses:

```bash
evnx init --yes                                   # Blank: empty files
evnx init --blueprint supabase_fullstack --yes    # Blueprint: a named stack
evnx init --with nest,redis,gitlab_ci --yes       # Architect: the components you name
```

`evnx init --list-components` lists every name `--with` accepts (56 in 0.10.18), and a
mistyped blueprint id is refused with the list of all ten.

## 🧪 Hands-On: Next.js + Supabase Demo App

### Step 1: Create a Next.js App

```bash
npx create-next-app@latest evnx-supabase-demo --typescript --tailwind --app
cd evnx-supabase-demo
```

### Step 2: Generate the environment files

```bash
evnx init --blueprint supabase_fullstack --yes
```

```text
  evnx init  Set up environment variables for your project

✓ Created .env from template
✓ Created .gitignore with .env*, !.env.example, !.env.sample, !.env.template
✓ Created .env.example with 20 variables
  ✓ created .evnx.toml with 20 variable(s) in [vars]

Next steps:
  1. Edit .env and replace placeholder values
  2. Commit .env.example and .evnx.toml; never commit .env
  3. Run 'evnx validate' to check configuration
  4. Use 'evnx add' to add more variables later
```

Four files: `.env.example` (the template you commit), `.env` (your copy, mode `0600`,
gitignored), `.gitignore` entries, and `.evnx.toml`, the project's variable contract.

### Step 3: Review the template

An excerpt of `.env.example`:

```bash
# ── Backend-as-a-Service ──
# Client-side copy of SUPABASE_ANON_KEY (exposed to the browser by Next.js)
NEXT_PUBLIC_SUPABASE_ANON_KEY=your_supabase_anon_key_value
# Client-side copy of SUPABASE_URL (exposed to the browser by Next.js)
NEXT_PUBLIC_SUPABASE_URL=https://example.com
# Public anon key for client-side usage
SUPABASE_ANON_KEY=your_supabase_anon_key_value
SUPABASE_JWT_SECRET=your_supabase_jwt_secret_value
# Secret service key (server-side only!)
SUPABASE_SERVICE_ROLE_KEY=your_supabase_service_role_key_value
SUPABASE_URL=https://example.com

# ── Payments ──
# Client-side copy of STRIPE_PUBLIC_KEY (exposed to the browser by Next.js)
NEXT_PUBLIC_STRIPE_PUBLIC_KEY=your_stripe_public_key_value
# Publishable key (safe for client-side)
STRIPE_PUBLIC_KEY=your_stripe_public_key_value
# Secret key (server-side only)
STRIPE_SECRET_KEY=your_stripe_secret_key_value
```

The `NEXT_PUBLIC_` lines are browser copies of values that are meant to be public. A
secret such as `SUPABASE_SERVICE_ROLE_KEY` never gets one. The blueprint also brings
NextAuth, Resend and Vercel variables.

### Step 4: Fill in `.env`

`init` already created `.env` from the template. Open it and replace the placeholders with
the values from your Supabase, Stripe and Resend dashboards. Never commit it; the
`.gitignore` lines `init` wrote keep it out.

### Step 5: Check it

```bash
evnx validate
```

Right after `init` it fails on purpose, listing every placeholder still in `.env`
(`Validation failed: 17 errors` on this blueprint). Use it as a checklist; it exits `0`
once every value is real.

### Step 6: Use in Your Next.js Code

```typescript
// lib/supabase/client.ts
import { createBrowserClient } from '@supabase/ssr'

export const createClient = () =>
  createBrowserClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!
  )
```

### Step 7: Add to Your Workflow (Optional)

```json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "env:setup": "evnx init --yes",
    "env:check": "evnx validate",
    "env:scan": "evnx scan"
  }
}
```

`env:setup` is what a teammate runs after cloning: with the committed template present,
`evnx init --yes` keeps it and creates their `.env` from it.

## 🎯 Why This Matters

| Before @evnx/cli | After @evnx/cli |
|-----------------|-----------------|
| Manual `.env.example` maintenance | Generated from stack-aware components, then `evnx add` for new names |
| Guessing which vars your stack needs | Ten blueprints and 56 components |
| Risk of committing secrets | `.gitignore` written for you, and `evnx scan` before you push |
| Onboarding friction for new devs | `evnx init --yes` on a fresh clone |

## 🔜 What's Next?

1. **Add variables**: `evnx add service redis --yes` or `evnx add custom NAME=value --yes`.
2. **Validate before commit**: `evnx validate` in CI or a pre-commit hook.
3. **Scan for leaks**: `evnx scan`.
4. **Keep the template honest**: `evnx sync` adds names your `.env` has and the template lacks.
