base64 is not encryption. Everyone knows that, and still a lot of credentials sit in repositories
as base64, because that is the shape some tool wanted them in. The `data:` of a Kubernetes Secret
is base64 by definition. CI systems ask for multi-line values as base64. A connection string that
travels in a URL is percent-encoded.

To a scanner that reads text, those values are a run of letters. A password inside
`cG9zdGdyZXM6Ly9...` does not match the rule for connection strings, because the rule is looking for
`postgres://`. Before 0.16.0 the best evnx could say about such a value was "high-entropy string,
low confidence", and only when the variable name or the randomness gave it a reason.

From 0.16.0, `evnx scan` decodes such values once and looks at what is inside.

## What it finds

A throwaway env file, with one fake database URL written three ways. The values are built at run
time, so the file holds nothing that was ever real:

```bash
U='postgres://app:Wq8pZr4tLm2vXy7k@db.internal:5432/app'
B=$(printf %s "$U" | base64 -w0)
H=$(python3 -c 'import sys; print(sys.argv[1].encode().hex())' "$U")
P=$(python3 -c 'import sys, urllib.parse; print(urllib.parse.quote(sys.argv[1], safe=""))' "$U")
printf 'DB_B64=%s\nDB_HEX=%s\nDB_PCT=%s\n' "$B" "$H" "$P" > app.env
```

```text
DB_B64=cG9zdGdyZXM6Ly9hcHA6V3E4cFpyNHRMbTJ2WHk3a0BkYi5pbnRlcm5hbDo1NDMyL2FwcA==
DB_HEX=706f7374677265733a2f2f6170703a577138705a7234744c6d32765879376b4064622e696e7465726e616c3a353433322f617070
DB_PCT=postgres%3A%2F%2Fapp%3AWq8pZr4tLm2vXy7k%40db.internal%3A5432%2Fapp
```

```console
$ evnx scan app.env

  evnx scan  Checking for exposed secrets

  scanning app.env

  ✗  Credentials in a connection string          high
     app.env:1 (DB_B64)  <48 chars>
     !  a password in a postgres:// URL, not a placeholder
     ·  found inside a base64-encoded value, decoded once

  ✗  Credentials in a connection string          high
     app.env:2 (DB_HEX)  <48 chars>
     !  a password in a postgres:// URL, not a placeholder
     ·  found inside a hex-encoded value, decoded once

  ✗  Credentials in a connection string          high
     app.env:3 (DB_PCT)  <48 chars>
     !  a password in a postgres:// URL, not a placeholder
     ·  found inside a url-encoded value, decoded once

  3 findings  ·  3 high
…
```

Each finding sits on the line of the encoded value and says how it was encoded. `<48 chars>` is
the length of the decoded URL; the value itself is never printed.

The same goes for a Kubernetes Secret. Nothing in the scanner knows about Kubernetes here: a
`data:` value is just another value in a YAML file, and it gets decoded like any other.

```yaml filename="secret.yaml"
apiVersion: v1
kind: Secret
metadata:
  name: app
type: Opaque
data:
  DATABASE_URL: cG9zdGdyZXM6Ly9hcHA6V3E4cFpyNHRMbTJ2WHk3a0BkYi5pbnRlcm5hbDo1NDMyL2FwcA==
  LOG_LEVEL: aW5mbw==
  REGION: ZXUtd2VzdC0xLXByaW1hcnk=
```

```console
$ evnx scan secret.yaml

  evnx scan  Checking for exposed secrets

  scanning secret.yaml

  ✗  Credentials in a connection string          high
     secret.yaml:7 (data.DATABASE_URL)  <48 chars>
     !  a password in a postgres:// URL, not a placeholder
     ·  found inside a base64-encoded value, decoded once

  1 finding  ·  1 high


Next steps:
  1. Move the values out of secret.yaml before you commit — into a file git ignores, such as .env, read at run time
  2. If one was pushed or shared before, revoke or rotate it
```

`LOG_LEVEL` is `info`, four bytes, and its base64 is too short to be a candidate. `REGION` decodes
to `eu-west-1-primary`, which is text but matches no key format, so nothing is said about it.
The finding names the line and the key: `secret.yaml:7 (data.DATABASE_URL)`. A finding from
decoded text in a YAML, JSON, TOML or notebook file carries `key_path` like any other, so in
JSON it has `"key_path": "data.DATABASE_URL"` beside `"encoded": "base64"`.

## Deciding what to decode

Decoding every word in every file would be slow and would find things that are not there. So a
value has to pass four gates before any rule sees it.

**It must look like an encoding.** The scanner splits each line into runs of the characters
base64, hex and percent-encoding use: letters, digits and `+ / _ % . ~ -`, with up to two `=` of
padding at the end. A run of 16 to 4096 characters is a candidate. Shorter runs hold too little to
be a key; longer ones are usually embedded images or bundles.

**It must decode cleanly in one encoding.** A candidate with a `%` in it is tried only as
percent-encoding, and needs at least one valid `%XX`. Otherwise it is tried as hex (an even number
of hex digits) and as base64 (a length that is a multiple of four, in the standard or the URL-safe
alphabet, not a mix).

**The result must be text.** It must be valid UTF-8, at least 8 characters, with no control
characters but tab, CR and LF. This is the gate that does most of the work. An image, a hash, a
git object id, ciphertext or random base64 decodes to bytes that are not text, and is dropped here.
A SHA-256 written in hex, for example, decodes to 32 bytes of noise.

**There is a budget.** One file offers at most 10,000 candidates. A minified bundle full of tokens
costs a bounded amount of time, and the rest of the file is still scanned as written.

And it is **one level**. What comes out of a decode is never decoded again. A value encoded twice
stays a run of letters:

```console
$ evnx scan twice.env

  evnx scan  Checking for exposed secrets

  scanning twice.env

  !  High-entropy string (possible secret)       medium, low confidence
     twice.env:1 (TWICE)  <96 chars>

  1 finding  ·  1 medium
```

That is a choice, not an oversight. Each extra level multiplies the candidates, and almost nobody
encodes a credential twice except to hide it on purpose. A scanner that chases that case pays for it
on every file of every project.

## Only key formats look at decoded text

Here is the rule that keeps this from turning into noise: **decoded text is checked against the
format rules only.** Those are the rules that recognise a value by its shape: a known prefix
(`sk_live_`, `ghp_`, `glpat-`, `AKIA`), a private-key header, a connection string with a password
in it. Two kinds of check never look at decoded text:

- **Entropy.** The usual reason to flag an unknown string is that it looks random. Decoded bytes
  of anything that was random to begin with still look random, and decoded bytes of anything else
  look like text. Neither tells you whether it is a secret. An entropy check on decoded text would
  only produce a second, vaguer finding about a value that already has one.
- **Names.** `API_SECRET=…` is suspicious because of the name. But decoded text has no reliable
  "name": a string like `password=…` inside a blob is a guess at structure, and a scanner that
  guessed would report every config fragment that mentions a password field.

You can see the second point in a run. This value is a base64 of `password=` followed by a fake
password:

```console
$ cat named.env
APP_CONFIG=cGFzc3dvcmQ9V3E4cFpyNHRMbTJ2WHk3aw==
$ evnx scan named.env

  evnx scan  Checking for exposed secrets

  scanning named.env

  !  High-entropy string (possible secret)       medium, low confidence
     named.env:1 (APP_CONFIG)  <36 chars>

  1 finding  ·  1 medium
```

The decoded text is not reported: it holds a password-like word and nothing with a known shape.
The finding you see is about the encoded value **as written**, from the entropy check that runs on
every value. That check is unchanged, and the same thing happens to a plain base64 greeting or a
random logo:

```console
$ cat other.env
GREETING=aGVsbG8gZnJvbSB0aGUgc3RhZ2luZyB0ZWFt
LOGO=l1kjJQG2BdHTYbcw6UXGpnhYgSZ+8kB6iMADx0qu/C59EKLTgoJ+da2osYtuoyqm
$ evnx scan other.env
…
  !  High-entropy string (possible secret)       medium, low confidence
     other.env:1 (GREETING)  <36 chars>

  !  High-entropy string (possible secret)       medium, low confidence
     other.env:2 (LOGO)  <64 chars>

  2 findings  ·  2 medium
```

So decoding adds findings and never removes one, with one exception that keeps the output honest.
When a decoded value matches a format rule, that finding **replaces** whatever else was said about
the same value on that line, the entropy or name finding for the encoded text. One value stays one
finding, and it is the one with the better reason. That is why `DB_B64` above shows a single high
finding and not an extra "high-entropy string" beside it.

If the low-confidence findings on encoded values are noise for your project, the usual tools apply:
`--confidence medium` to set the floor, `evnx:allow <rule-id> reason=…` on the line, or the
baseline.

## In JSON and CI

A finding from decoded text carries `encoded`: `base64`, `hex` or `url`. Findings from the value as
written leave the field out.

```console
$ evnx scan app.env --format json
```

```json
{"rule_id": "connection-string-credentials", "location": "app.env:1 (DB_B64)", "file": "app.env", "line": 1, "variable": "DB_B64", "encoded": "base64", "confidence": "high", "value_preview": "<48 chars>"}
{"rule_id": "connection-string-credentials", "location": "app.env:2 (DB_HEX)", "file": "app.env", "line": 2, "variable": "DB_HEX", "encoded": "hex", "confidence": "high", "value_preview": "<48 chars>"}
{"rule_id": "connection-string-credentials", "location": "app.env:3 (DB_PCT)", "file": "app.env", "line": 3, "variable": "DB_PCT", "encoded": "url", "confidence": "high", "value_preview": "<48 chars>"}
```

Those are a few fields of each finding, one per line, picked out of the full document with a small
script; the document itself is scan JSON `schema_version` 3, with the usual `run` header.

`--format github` turns them into annotations on the lines, so a pull request shows them where the
encoded value is:

```text
::error file=app.env,line=1,title=Secret detected (high)::DB_B64 matches Credentials in a connection string. Rotate this credential at its source
::error file=app.env,line=2,title=Secret detected (high)::DB_HEX matches Credentials in a connection string. Rotate this credential at its source
::error file=app.env,line=3,title=Secret detected (high)::DB_PCT matches Credentials in a connection string. Rotate this credential at its source
```

This is one of the changes that can turn a passing pipeline red after the upgrade: a secret that
was always in an encoded value is now found. That is the point, but check each one. A real key
gets rotated. A test value gets `evnx:allow` with a reason, or goes into the baseline with
`evnx scan --update-baseline`.

## What it does not do

- It does not decrypt anything. A sealed or encrypted value decodes to bytes that are not text and
  is dropped at the third gate. That is correct: if it is properly encrypted, it is not the leak.
- It decodes once. Nested encodings are not followed.
- It ignores values shorter than 16 or longer than 4096 characters.
- It only reports what a format rule recognises. A plain password in base64, with no prefix or URL
  around it, is not found by decoding. The entropy and name checks on the value as written are what
  stand between you and that one.

The rules themselves, and how to add your own formats so that decoded text is checked against them
too, are in [Scan rules and packs](/guides/reference/scan-rules-and-packs) and
[How evnx scan works](/guides/reference/how-evnx-scan-works).
