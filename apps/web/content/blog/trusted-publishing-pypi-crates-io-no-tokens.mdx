A release pipeline that holds a registry token holds a credential that can publish your
package from anywhere, until someone remembers to rotate it. A manual `cargo publish`
after each tag has the opposite problem: it depends on someone remembering, and for
evnx's sister crate that step was skipped twice.

From v0.11.0, evnx publishes to PyPI and crates.io with **trusted publishing**. This post
covers how it works on each registry, the settings each one offers, and how to check a
published version yourself.

---

## How it works

The registry is told, once, which GitHub repository and workflow may publish the
package. When that workflow runs, GitHub gives the job an OIDC token that says, signed,
*I am workflow X in repository Y, running for ref Z*. The job hands that to the registry,
which checks it against the configuration and returns a token valid for minutes, for that
package only.

Nothing long-lived is stored. A leaked repository secret cannot publish, because there is
none to leak.

---

## PyPI

On pypi.org, a project's **Publishing** settings take a *trusted publisher*:

| Field | What it pins |
|---|---|
| Owner and repository | which GitHub repository may publish |
| Workflow file | which workflow in it, by file name |
| Environment (optional) | which GitHub Actions environment the job must run in |

The publish job asks for `id-token: write` and stops passing a password:

```yaml
publish:
  permissions:
    contents: read
    id-token: write
  # environment: pypi        # only if the trusted publisher names one
  steps:
    - uses: pypa/gh-action-pypi-publish@<pinned commit> # release/v1
```

Without `password:`, the action authenticates with OIDC. It also uploads **PEP 740
attestations**, so PyPI can show where each file was built.

An environment is worth naming when you want more than "this workflow": GitHub
environments can require a reviewer's approval, or limit deployment to certain branches
or tags, before the job is given its OIDC token.

## crates.io

crates.io's trusted publishing takes the same three fields. The job exchanges its OIDC
token through `rust-lang/crates-io-auth-action`:

```yaml
publish-crate:
  needs: release
  permissions:
    contents: read
    id-token: write
  steps:
    - uses: rust-lang/crates-io-auth-action@<pinned commit>
      id: auth
    - run: cargo publish
      env:
        CARGO_REGISTRY_TOKEN: ${{ steps.auth.outputs.token }}
```

The action returns a token valid for minutes and **revokes it when the job ends**. Two
guards are worth adding around it:

- **Check that the tag equals `Cargo.toml`'s version** before publishing, so a mistagged
  commit publishes nothing.
- **Skip a version that is already on crates.io** instead of failing, so re-running a
  release after a partial failure is safe.

## Hardening options

Trusted publishing removes the need for a stored token; it does not by itself forbid
one. Each registry offers more, and which to use depends on how you release:

| Option | Where | Effect | Cost |
|---|---|---|---|
| *Require trusted publishing for all new versions* | crates.io, crate settings | a plain API token can no longer publish the crate | a manual `cargo publish` stops working until you turn it off |
| Remove old API tokens | registry account, CI secrets | nothing long-lived is left to leak | the fallback path goes with it |
| A GitHub environment with protection rules | repository settings, then named in the trusted publisher | approval, or a branch or tag rule, before the job gets its token | a person in the loop for every release |
| Pin actions by commit | the workflow | an action's tag cannot be moved under you | updates become deliberate, by PR |

A cautious default for a new action version in a job that holds a publishing credential:
let it age a little before pinning it, so the job is not its first user.

## Checking a published version

Both registries record how a version was published, and anyone can read it.

**PyPI** serves each file's attestation, which names the publisher it trusted:

```bash
curl -s -H 'Accept: application/vnd.pypi.integrity.v1+json' \
  "https://pypi.org/integrity/<project>/<version>/<file>/provenance" \
  | jq -c '.attestation_bundles[0].publisher'
```

The answer names the repository and workflow (and the environment, if one is set).

**crates.io** records the run and commit instead of a user:

```bash
curl -s -A 'your-name (contact)' "https://crates.io/api/v1/crates/<crate>/<version>" \
  | jq -c '.version | {num, published_by, trustpub_data}'
```

A version published this way has `published_by: null` and a `trustpub_data` with the
repository, the workflow run id and the commit, which you can open on GitHub and read.

For evnx, v0.11.0 was the first release published this way, and both registries took it
on the first attempt.

## Tokens versus trusted publishing

| | API token | Trusted publishing |
|---|---|---|
| What CI stores | a long-lived secret | nothing |
| Who can publish | anyone holding the token, from anywhere | the configured workflow, from GitHub Actions |
| Lifetime | until rotated or revoked | minutes, revoked when the job ends (crates.io) |
| What the registry records | the account | the repository, workflow run and commit |
| Release archives | — | pair it with [SLSA build provenance](/blog/signing-every-evnx-release-slsa-provenance) for the binaries |
